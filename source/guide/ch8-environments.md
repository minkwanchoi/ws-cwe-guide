# 제8장 개발환경별 고려사항

이 장은 같은 목적의 보안 활동이 개발환경에 따라 어떤 수단으로 바뀌는지 보인다. 8.1은 일반 완화책(mitigation)을 특성 조건으로 다시 적고 조건이 맞지 않을 때의 대체 활동을 지침 ID로 연결한다. 8.2~8.6은 개발 언어 축(2.6과 제5장)을 뺀 5축 20종 환경을 축별 표로 요약한다. 8.7은 목록에 없는 환경을 추가하는 절차를 실제 계산 결과로 보인다. 지침 전문은 부록 C에, 사례 전체는 부록 E에 있다.

## 8.1 일반 완화책의 특성별 적용성과 대체 활동

일반 완화책은 특성이 맞을 때만 쓸 수 있다. CWE 완화책은 대개 MMU(메모리 관리 장치)가 있는 범용 OS와 완전한 호스트 컴파일러를 전제한다. 예를 들어 CWE-119·120의 Environment Hardening 완화책은 컴파일러의 자동 버퍼 오버플로 검출, 실행 파일·라이브러리 위치의 무작위화, 하드웨어 NX 비트를 쓰는 데이터 실행 방지를 든다([CWE] CWE-119·120 완화책, Phase Operation·Build and Compilation).

MMU가 없는 MCU·베어메탈(bare-metal)이나 보호 기능이 없는 벤더 컴파일러에서는 이 수단을 그대로 쓸 수 없다. 그래서 아래 표는 완화책마다 "쓸 수 있는 특성 조건"과 "조건이 안 맞을 때의 대체 활동"을 적는다. 환경 이름 대신 특성으로 썼으므로 새 환경에도 그대로 적용된다. 스택 보호·`_FORTIFY_SOURCE`·제어 흐름 보호 행의 근거는 표 아래에 적었다.

웹 응용 방화벽·서버 설정 같은 웹 서비스 완화책은 특성으로 가르지 않고 사용 기술로 판정한다. 웹 서비스를 탑재하지 않으면 사용 기술 체크리스트(G-4)에서 비해당으로 판정한다.

**컴파일러 보호 기능의 근거.** 위 표의 스택 보호·`_FORTIFY_SOURCE`·제어 흐름 보호 행은 근거 목록의 다음 사실에 따른다.

- **스택 보호와 TI 컴파일러.** TI는 컴파일러 계열에 따라 다르다. tiarmclang은 `-fstack-protector`·`-fstack-protector-strong`·`-fstack-protector-all`을 제공하고 사용자가 `__stack_chk_fail()`과 `__stack_chk_guard`를 정의해야 한다(TI Arm Clang 5.1.0.LTS 사용자 가이드 15.2절). 전통 컴파일러 cl2000·cl430·cl6x는 세 사용자 가이드(SPRU514AA·SLAU132Y·SPRUI04G)의 전체 옵션 요약표에 스택 카나리(stack canary)·새니타이저(sanitizer) 옵션이 없다. 가이드는 컴파일러가 스택 오버플로를 검사하는 수단을 제공하지 않는다고 적고, 대신 `--entry_hook`으로 점검 코드를 넣을 수 있다고 안내한다(CCS-05, 참고문헌 49). 다른 판을 쓰면 그 판의 사용자 가이드로 다시 확인한다. IAR·Keil은 근거를 확보하지 못해 표에 넣지 않았다.
- **avr-gcc.** GCC 14.2.0 `configure.ac`는 avr 타깃에서 스택 보호 런타임 라이브러리(libssp)를 빌드하지 않는다. 그래서 표에서 avr-gcc를 L2 = 없음으로 둔다(AVR-05).
- **arm-none-eabi.** 플래그만 켜서는 동작을 보장하지 못한다. `__stack_chk_guard`·`__stack_chk_fail`이 어디서 오는지 링크 맵으로 확인해 툴체인이 제공하지 않으면 직접 구현하고, 제공하더라도 가드 값 초기화와 실패 시 동작을 확인한다. libasan은 없다(GCC-05, [libsanitizer `configure.tgt`](https://gcc.gnu.org/git/?p=gcc.git;a=blob_plain;f=libsanitizer/configure.tgt;hb=refs/tags/releases/gcc-14.2.0)).
- **`_FORTIFY_SOURCE`.** glibc에 한정되지 않고 C 라이브러리가 이 검사를 구현하면 쓸 수 있다. Zephyr v4.2.0은 Picolibc·Newlib 사용 시 이 검사를 지원하고 최소 libc에서는 기본값이 '검사 없음'이다(GCC-01).
- **`/CETCOMPAT`.** x64 대상에만 적용되고 Visual Studio 2019부터 제공되므로 링크 옵션에 일괄로 넣지 않는다(MSVC-03).

**8.2~8.6의 읽는 법.** 각 절의 표는 환경마다 기본 특성, 제약과 대체 수단, 대표 지침, 사례 확인 현황, 검증 공백을 한 행으로 요약한다. 대표 지침의 괄호는 보정 유형과 대상 기준선이다. '사례 확인 n/m'은 그 환경 지침 m건 중 오픈소스 근거가 '확인' 상태로 붙은 n건이다(부록 E). '(부분 k)'는 그중 지침의 일부만 원문으로 확인한 건수다. [근거] 원천 데이터의 환경별 특성 기본값(부록 G-2), 환경 지침(부록 C), 근거 목록(부록 E)

| 서드파티·오픈소스 라이브러리(OSS) | 같음 | CVE가 그대로 상속되고 폐쇄망 반입·오프라인 DB·라이선스가 쟁점 → SBOM, 서명·해시 검증 뒤 사내 미러, MISRA를 제외해도 CWE 점검 유지 | OSS-01(→D-03), OSS-05(→M-07), OSS-08(강화→T-01) | 10/10 | — |

## 8.6 개발·시험 망 환경

망 환경 축은 개발·시험 망(N1)을 정한다. 2종 20건 중 사례 확인은 20건이고, 그중 7건은 지침의 일부만 확인했다. 지침은 모두 '일반'이고 조건은 대부분 N1으로 갈리고 4건은 항상 적용한다(NET-IN-04·06·09, NET-CL-09). 지침 선택 도구에서는 환경 축 대신 '개발 환경' 질문의 개발·시험 망(인터넷 연결·내부망·폐쇄망)으로 묻는다(부록 C의 NET-IN·NET-CL 묶음은 그대로다).

| 환경(코드) | 기본 특성 | 제약 / 대체 수단 | 대표 지침 | 사례 확인 | 검증 공백(사례 미확보 등) |
|---|---|---|---|---|---|
| 내부망(NET-IN) | N1 내부망 | 클라우드 SAST·온라인 라이선스·공개 저장소 직접 접근 불가 → 사내 미러, 오프라인 규칙 집합, 내부 라이선스 서버 | NET-IN-04(→D-05), NET-IN-05(강화→M-07), NET-IN-01(추가, 6.5) | 10/10(부분 2) | NET-IN-02·08은 일부만 확인 |
| 폐쇄망(NET-CL) | N1 폐쇄망 | 매체 반입만 가능하고 데이터가 늦음 → 오프라인 번들, 데이터 기준일 표기, 반입 검사 | NET-CL-01(추가), NET-CL-03(대체→M-05), NET-CL-04(강화→M-07) | 10/10(부분 5) | NET-CL-03·05·06·07·10은 일부만 확인(운영 절차라 [보완] 성격) |

망 지침의 조건은 `N1 ∈ {내부망, 폐쇄망}`이거나 '항상'인 것이 많아, 폐쇄망 과제에는 내부망 지침(NET-IN-02~10)도 들어온다(8.7).

## 8.7 새 환경 추가 절차 예시: Cortex-M33 위의 Zephyr RTOS

이 절은 절차 예시다. 결과 목록을 고정 조합으로 쓰지 않는다. 가정한 과제는 Cortex-M33 MCU 위에서 Zephyr RTOS를 쓰고, arm-none-eabi GCC로 C 코드를 빌드하며, 폐쇄망에서 개발한다. 운영체제/런타임 축에 Zephyr가 없으므로 G-1 특성 시트로 추가하고, 가장 비슷한 FreeRTOS를 최근접 환경으로 지정한다. 아래 수치는 원천 데이터(적용 조건, 최종 갱신 2026. 11. 2.)에 2.5의 선택 규칙을 실제로 실행해 얻었다[^calc77].

**②~④ 환경 선택·추가와 특성값 확정.** 탑재 환경은 기존 MCU를 고르고 후보값이 둘인 특성을 덮어쓴다(사유는 G-3): H3 = 보안 부팅·보안 키 저장(TrustZone-M 기반 보안 부팅(secure boot)을 쓴다고 가정, 칩 문서로 확인), H5 = 표준(32비트 Arm 코어). M2는 MCU 기본값 '있음'을 그대로 쓴다(출고 전 디버그 포트 잠금).

운영체제는 새 환경 "Zephyr RTOS"의 G-1 시트를 쓴다: S1 = RTOS(필수 입력), S2 = 태스크 보호(칩에 MPU(메모리 보호 장치)가 있고 과제에서 씀), S3 = 없음, S4 = 직렬·버스 링크만, M3 = 지원 중(사용 버전의 지원 기한은 벤더 문서로 확인), 최근접 환경 = FreeRTOS. 이 예시의 Zephyr 근거는 v4.2.0 기준이다.

IDE/컴파일러는 GCC를 고르고 L2를 '부분'으로 정한다(arm-none-eabi). 언어는 C, 망은 폐쇄망이며, 과제 결정 특성은 S5 = 금지다. 지침 선택 도구의 '사용하는 기능' 질문에는 외부 파일·메시지 입력 해석(직렬 링크 명령 해석)과 현장·원격 업데이트(현장 매체·정비 포트)만 고른다.

확정값은 H1 없음, H3 보안 부팅·보안 키 저장, H4 단일, H5 표준, S1 RTOS, S2 태스크 보호, S3 없음, S4 직렬·버스 링크만, S5 금지, L1 네이티브-비안전, L2 부분, L3 가능, M2 있음, M3 지원 중, N1 폐쇄망이다.

**⑤ 결과: 106건.**

| 포함 사유 | 건수 | 내용 |
|---|---:|---|
| [기준선] | 32 | 33개 중 M-03만 빠진다(S3 = 없음). |
| [특성 일치] | 56 | 범위가 '일반'이고 조건이 참인 지침(선택한 환경의 일반 지침 포함). MCU 8, BM 7, SBC 7, SOC 3, VXW 1, PSOS 1, AVR 1, LC 9, NET-IN 9, NET-CL 10 |
| [선택 환경] | 10 | GCC-01·02·04~10, LC-08 |
| [상속: 최근접 FreeRTOS — 검토] | 8 | FRT-01~05, FRT-07~09 |
| 확인 필요 | 0 | 모든 특성값을 하나로 정하고 '사용하는 기능'에 답했다. |
| **합계** | **106** | 단계별 요구사항 분석 1, 설계 25, 구현 41, 통합 및 시험 23, 유지보수 16 |

도구 화면은 상속 8건을 확인 필요로 접어 '지침 98건, 확인 필요 8건'으로 보인다.

**눈여겨볼 포함·제외.** 지침이 출처 환경이 아니라 특성 조건으로 선택되므로(2.3), 베어메탈 지침 BM-04~10과 PSOS-05(S1 = RTOS), VXW-07도 들어온다. H3을 덮어쓴 효과로 SBC-01·SOC-02·SOC-04가 확인 필요에서 특성 일치로 바뀌고, 양산 보호 설정 시험 AVR-09는 H3 값(읽기보호·퓨즈, 보안 부팅·보안 키 저장)에 따라 들어온다. M2(있음)로 SBC-09·SOC-07이 들어오고, 폐쇄망을 고르면 NET-IN-02~10도 들어온다. 대체 관계는 I-08 → GCC-05, M-05 → NET-CL-03이며, 각 기준선 수단은 "대체됨(→ 지침 ID)"으로 남긴다.

빠지는 주요 지침과 사유(과제 값)는 다음과 같다: M-03(S3 = 없음), GCC-03 hosted 하드닝(hardening)(S1 = RTOS, 대신 GCC-05), FRT-06 상속 제외(S4 = 직렬·버스 링크만), AVR-01(조건은 S2 = 단일 주소공간인데 과제는 S2 = 태스크 보호, 같은 목적은 MCU-01), MCU-04·DSP-05(H5 = 표준), BM-01~03(S1 = RTOS), SBC-02(H1 = 없음), PC-06(S1 = RTOS), PSOS-06~09(M3 = 지원 중), SBC-08(S5 = 금지).

**⑤의 상속 판정.** 상속 지침 8건은 사용자가 하나씩 유지·수정·제외를 판정해 G-3에 적는다. FreeRTOS 고유 API·설정 이름은 그대로 쓸 수 없으므로 6건이 '수정'이다.

FRT-01(→D-04, `xTaskCreateRestricted`), FRT-02(→D-07, `configSUPPORT_STATIC_ALLOCATION`·heap_n), FRT-03(훅·설정 이름, Zephyr 커널이 `__stack_chk_guard`를 정의하므로 컴파일러 스택 보호와 함께 검토, 사례 상자 8-2), FRT-04(FromISR 계열 API), FRT-05(→I-07, `xSemaphoreCreateMutex`), FRT-07(→T-07, 측정 API)은 원칙을 유지하고 대응 기능을 벤더 문서로 확인해 [보완]으로 적는다. FRT-02·07은 원칙이 MCU-01·BM-01·MCU-07과 겹친다.

FRT-08(MPU 위반 시 fault와 안전 상태 전이 확인)과 FRT-09(→M-05·M-07, 버전·지원 종료일 기록과 종료 전 이전)는 원칙이 같아 '유지'다.

**고유 공백.** Zephyr 고유의 설정·API 지침은 이 가이드에 없다. 상속 '수정' 판정에서 확인한 대응 기능과 Zephyr 고유 위험은 사용자 지침(`U-` 접두어)으로 사용자 파일에 적고 [보완]으로 표시한다(2.5). 근거 목록(부록 E)에서 확인된 Zephyr 사실은 세 가지뿐이다. FORTIFY 검사는 Picolibc·Newlib에서 지원된다(GCC-01). 커널이 `__stack_chk_guard`를 정의한다(GCC-05). `west spdx`로 SPDX SBOM(소프트웨어 구성명세서)을 만든다(OSS-01). 이 범위를 넘는 Zephyr 진술은 벤더 문서로 확인한 뒤 쓴다.

**'모름'으로 시작하면.** 같은 조합에서 S3·S4·S5를 '모름'으로 두고 '사용하는 기능'에도 답하지 않으면 결과는 110건이다(기준선 29, 특성 일치 52, 선택 환경 10, 상속 9, 확인 필요 10). 확인 필요 10건은 특성을 몰라 들어온 M-03, PC-03, SBC-03, SBC-05, SBC-08, MCU-01, LC-01과 기능에 답하지 않아 들어온 I-04·T-04·T-06이고, FRT-06도 S4를 모르므로 상속에 들어온다. 값을 확정하고 기능에 답하면 4건이 빠져 106건이 된다. 선택 규칙은 모르는 값을 지침을 더 주는 쪽으로 처리한다(2.5).

**지침 선택 도구와의 관계.** [지침 선택 도구](selection-tool.md)는 같은 원천 데이터로 선택 규칙(⑤)을 계산한다. 대체 기록과 고유 공백 판단은 G-3에 사람이 적는다. 도구는 선택한 환경들의 후보값을 합쳐 값이 둘 이상이면 '혼합'으로 표시하고, 그 특성을 조건으로 쓰는 지침을 '확인 필요'로 접어 넣는다.

첫 화면의 ATmega 예시 조합은 환경 코드로 MCU(탑재 환경) → BM(운영체제/런타임) → AVR(IDE/컴파일러) → BSP(기반 소프트웨어) → LC(언어) → NET-CL(망)을 고르고, 특성을 덮어쓰지 않고 '사용하는 기능'에도 답하지 않은 상태다.

같은 규칙으로 계산하면 115건(기준선 31, 특성 일치 54, 선택 환경 19, 확인 필요 11)이고, 화면에는 지침 104건과 확인 필요 11건으로 보인다. 확인 필요 11건 가운데 I-04는 기능에 답하지 않아 들어왔다. 여기에 과제 결정값(H3 읽기보호·퓨즈, H5 비표준, S4 직렬·버스 링크만, S5 금지)을 넣고 '사용하는 기능'에 외부 파일·메시지 입력 해석과 현장·원격 업데이트를 고르면 확인 필요가 0이 되고 111건(기준선 32, 특성 일치 60, 선택 환경 19)이 된다.

[^calc77]: **8.7 계산 방법.** 지침 선택 도구의 선택 로직(환경 기본값 합집합, 직접 지정값 덮어쓰기, '모름'·'혼합' 시 확인 필요, 최근접 환경 고유 지침 상속)을 Python으로 옮겨 원천 데이터(적용 조건과 환경 지침)에 실행했고(2026. 10. 15.), 지침 선택 도구 화면에서 같은 조합을 세어 본문 수치를 확인했다(2026. 10. 22.). 특성 목록을 15개로 줄인 뒤 다시 세었다(2026. 11. 2.).
