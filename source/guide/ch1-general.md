# 제1장 개요

이 장은 목적, 범위, 관련 기준, 용어, 사용법을 적는다. 어디부터 읽을지는 1.5의 독자별 읽는 경로를 본다.

## 1.1 목적

이 가이드는 무기체계 임베디드 소프트웨어 개발자가 소프트웨어 수명주기 단계마다 수행할 보안약점 예방 활동을 정리한다. 대상은 매뉴얼의 「보안약점 점검 목록(44개)」과 CWE-658(C)·CWE-659(C++)·CWE-660(Java) 뷰를 이루는 보안약점이다. 가이드는 다음 활동을 단계별로 안내한다.

| 활동 | 단계 | 내용 |
|---|---|---|
| 예방 | 요구사항 분석·설계·구현 | 보안약점이 코드에 들어가지 않게 요구사항·구조·코딩규칙·빌드 설정을 정하고, 단위시험으로 먼저 거른다. |
| 확인 | 통합 및 시험 | 남은 보안약점을 정적시험·동적시험과 보조 시험으로 찾아낸다. |
| 유지 | 유지보수 | 변경·배포·구성요소 취약점 때문에 보안약점이 다시 생기지 않게 관리한다. |

**매뉴얼 시험과의 관계.** 매뉴얼의 소프트웨어 신뢰성시험은 만들어진 코드에서 결함을 찾는 **결과 점검**이다. 이 가이드는 그 앞에서 결함이 생기지 않게 하는 **예방 활동**을 다룬다. 신뢰성시험은 정적시험과 동적시험으로 나누어 수행하며([표준] 방위사업청 매뉴얼 제2024-6호 부록 7, 인쇄 7-4쪽), 항목과 합격 기준은 6.2·6.3에 정리했다.

매뉴얼은 정적시험을 소프트웨어 개발 초기부터 수행하고 통합시험 단계에서 종합적으로 실시하도록 한다([표준] 매뉴얼 부록 7, 인쇄 7-5쪽). 설계·구현 단계에서 보안약점을 막아 두면 통합 및 시험 단계에서 한꺼번에 드러나는 결함이 줄어든다. 시험을 통합 시점에 한 번만 하면 사업 후반부에 결함이 몰려 수정이 어렵다는 지적은 2019년 연구에도 있다(최민관 외, 2019)[^hist].

이 가이드는 매뉴얼을 대신하지 않는다. 시험 방법, 합격 기준, 테일러링(tailoring)과 예외 결정은 매뉴얼과 사업관리회의 결정을 따른다. 가이드는 그 결정에 쓸 **활동·산출물·판정 기록**을 개발자 관점에서 정리한다.

[^hist]: **연혁.** 매뉴얼은 2014년 제정(제2014-1호, 2014. 2. 19.) 이후 2016·2017·2018·2020·2022·2024년에 개정되었다([표준] 매뉴얼 제2024-6호 표지). 논문(최민관 외, 2019)은 2016년 개정의 요지로 시험 대상 언어에 C#·Java 추가, 자체 코딩규칙 65개에서 MISRA-C(143개)·MISRA-C++(228개) 등 국제 표준으로 강화, CWE 항목의 선별 적용에서 전체 적용으로 전환, 소스코드 메트릭 6종의 제한값 적용(예: 함수 파라미터 8개 이하)을 든다. 이 내용은 2016년판 원문으로 확인하지 못했으며 현행 요구가 아니다. 현행 제2024-6호에서는 다음이 다르다. 제한값은 이전 판에 있었고 현행 제2024-6호에서는 사업별로 정한다(부록 7, 인쇄 7-12쪽). 취약점 점검은 자동화 도구가 지원하는 항목은 모두 적용하고, 도구가 지원하지 않는 항목은 대안과 사유를 제출해 사업관리부서·기술지원기관과 협의하는 조건부 문구다(부록 7, 인쇄 7-10쪽). 「보안약점 점검 목록」 44개는 이후 개정에서 추가되었다. 매뉴얼 제2024-6호 본문·부록에서는 MISRA 규칙 개수(143·228)에 대한 서술을 찾지 못했다.

## 1.2 적용 범위

| 구분 | 범위 |
|---|---|
| 대상 소프트웨어 | 무기체계에 탑재되는 임베디드 소프트웨어와, 이를 지원하는 지상 장비·시험 도구 소프트웨어. 과제에서 새로 개발하거나 고친 코드를 대상으로 하며, 공개 소프트웨어를 가져와 고친 코드와 자동 생성 코드도 포함한다. 매뉴얼도 개발·공개·자동 생성 코드는 시험 대상으로, 기개발 소프트웨어와 상용(COTS) 소프트웨어는 비대상으로 구분한다. 다만 기개발·상용 소프트웨어를 수정하면 영향 범위를 시험하고, 자동 생성 코드는 타당한 사유가 있으면 제외할 수 있다([표준] 매뉴얼 부록 7, 인쇄 7-2·7-3쪽). 이 가이드는 기개발·상용 소프트웨어를 구성요소 선정(D-03)과 취약점 추적(M-05)의 대상으로 다룬다. |
| 개발 언어 | **C·C++·Java**: CWE 언어 뷰(658·659·660)가 있다. **C#·Python**: CWE 언어 뷰가 없어 **보조 언어**로 다룬다. C#은 매뉴얼 정적시험 적용 언어(C·C++·Java·C#)에 들어 있다. 다만 이 네 언어도 자동화 도구가 지원하지 않으면 제외하며([표준] 매뉴얼 부록 7, 인쇄 7-2쪽), 도구가 지원하지 않는 언어는 개발도구 등의 기능으로 시험하고 그 방식은 소프트웨어 검토회의나 사업관리회의에서 정한다([표준] 매뉴얼 부록 7, 인쇄 7-5쪽). 따라서 C#은 뷰만 없을 뿐 매뉴얼 시험 대상이다. 매뉴얼에서 Python은 신뢰성시험의 적용 언어가 아니며, 신뢰성시험 범위에 넣을지는 과제의 선택 사항이다. 신뢰성시험 외 다른 시험 제도에 포함되는지는 검토가 필요하다. 이와 별개로 Python 코드에도 보안약점이 생기므로 보안 점검을 권고한다(5.7). |
| 수명주기 단계 | 요구사항 분석·설계·구현·통합 및 시험·유지보수 5단계. 매뉴얼 단계와의 대응은 2.2에 있다. |
| 대상 보안약점 | 197개. 「보안약점 점검 목록」 44개와 CWE-658/659/660 구성 보안약점 중 이 목록에 없는 153개를 합한 수다(2.1). 보조 항목 4개도 다룬다(2.1, 부록 A-3). |
| 개발환경 | 6축 25종을 기본 목록으로 둔다(탑재 환경, 운영체제/런타임, IDE/컴파일러, 기반 소프트웨어, 개발 언어, 개발·시험 망). 이 목록은 닫혀 있지 않다. 사용자가 특성 시트로 새 환경을 추가할 수 있다(2.4·2.5, 부록 G). |
| 다루지 않는 것 | ① 운용 중 침해 대응과 보안 관제 ② 매뉴얼의 **보안성시험**(전장관리정보체계 대상 별도 시험, 6.4) ③ 매뉴얼의 시험 절차·서식 자체. 유지보수는 소프트웨어 변경·배포·취약점 추적까지만 다룬다. |

## 1.4 용어와 표기

**핵심 용어.** 용어는 국립국어원 → TTA 정보통신용어사전 → 행정안전부·KISA 가이드(보안약점 이름) → SPRi → 매뉴얼(신뢰성시험 항목 이름) 순서로 정하고, 굳은 외래어는 개발자가 쓰는 말을 따른다. 전체 대조표는 부록 F에 둔다.

| 용어 | 이 가이드에서의 뜻 |
|---|---|
| 보안약점 / 취약점 | CWE 항목처럼 결함을 낳을 수 있는 잠재적 약점은 '보안약점', CVE처럼 공개된 개별 결함은 '취약점'이라 쓴다. |
| 「보안약점 점검 목록(44개)」 | 매뉴얼 부록 7의 `<보안약점 점검 목록>` 표에 실린 CWE 44개. 매뉴얼은 이 목록을 CWE-658/659/660과 나란히 두며 '공통 보안약점'이라 부르지 않는다. |
| 언어 뷰 | CWE-658(C), CWE-659(C++), CWE-660(Java). MITRE CWE의 뷰(view)로, 그 언어로 작성된 소프트웨어에서 나타나면서 모든 언어에 공통되지는 않는 보안약점을 모은다([CWE] CWE-658 Objective). |
| 추상화 수준 | MITRE CWE가 보안약점을 얼마나 구체적으로 기술했는지에 따라 나눈 수준. Pillar(기둥)·Class(분류)·Base(기본)·Variant(변형) 네 가지이고, 둘 이상의 약점을 묶은 Compound(복합: Chain(연쇄)·Composite(합성))가 따로 있다. 상위·하위는 전체 약점 계층 뷰(CWE-1000)의 ChildOf 관계로 정한다(2.8). |
| MITRE 매핑 권고 | MITRE가 CWE 항목마다 붙인 취약점 매핑용 표지(Mapping Notes의 Usage). 허용(Allowed)·검토 후 허용(Allowed-with-Review)·권장하지 않음(Discouraged)·금지(Prohibited) 네 가지다(2.8). |
| 정적시험 / 동적시험 | 매뉴얼의 신뢰성시험 항목 이름. 일반 기법을 말할 때는 '정적 분석(static analysis)', '동적 분석(dynamic analysis)'이라 쓴다. |
| 코드 실행률(Coverage) | 매뉴얼 용어. 문장·분기·MC/DC 실행률을 포함한다. |
| 기준선 활동 | 모든 과제에 기본으로 적용하는 단계별 공통 활동 33개(R-01~M-07, 일부는 적용 조건이 있음, 2.3). |
| 특성 | 지침이 필요한지 가능한지를 가르는 개발환경의 속성(예: MMU 유무, OS 유형). 코드로 쓴다(H1 등, 2.4). |
| 지침 | 특정 특성이나 환경에서 기준선 활동을 추가·대체·강화하거나 비해당으로 판정하는 개별 행동 단위. 기본 245건이다. |
| 규칙별 해설 | CWE 항목마다 만든 해설 페이지. 여기서 '규칙'은 CWE 항목을 가리키며, 분석 도구의 보안 규칙(부록 D)과 다르다. |
| 적용성 판정 | 과제에서 각 보안약점이 '해당', '조건부', '비해당' 중 무엇인지 근거와 함께 기록하는 일(2.5 ⑥). |
| 참조 오픈소스 프로젝트(참조 프로젝트) | 실제 무기체계 과제가 비공개이므로 근거로 삼는 공개 오픈소스 프로젝트(PX4, ArduPilot, NASA cFS·F´, FreeRTOS 등). |

**표기 규칙.**

- **영어 병기**: 지침 단위로 처음 나올 때 '퍼징(fuzzing)'처럼 병기하고 두 번째부터는 한글만 쓴다. MMU·MPU·RTOS·SBOM 같은 약어는 약어를 쓰고 첫 등장에 한글 풀이를 붙인다. 코드·옵션·API·도구 이름(`-fstack-protector-strong`, ASan, `BinaryFormatter`)은 영문 그대로 쓴다.
- **상태 표시**: 사례 근거의 검증 상태(확인·부분·검토 중·미확보)와 적용성 판정 값(해당·조건부·비해당)은 기호가 아닌 한글 낱말로 쓴다. 흑백 인쇄에서도 구분되게 하기 위해서다.

**식별자 규칙.** 본문·부록·지침 선택 도구·Excel은 같은 식별자를 쓴다. 하이픈 유무와 마디 수로 종류를 가린다.

**기준선 활동 ID 부여 규칙.** 기준선 활동 ID는 접두어 한 글자와 두 자리 일련번호로 이루어진다. 접두어는 활동이 속한 수명주기 단계다. R은 요구사항 분석(Requirements), D는 설계(Design), I는 구현(Implementation), T는 통합 및 시험(Test), M은 유지보수(Maintenance)이고, 번호는 접두어마다 01부터 매긴다. 2026. 10. 20. 접두어와 단계가 달랐던 두 활동의 ID를 바꿨고, 옛 번호 D-01·T-03은 다른 활동에 다시 쓰지 않고 비워 둔다. 그 전에 작성한 과제 문서에 적힌 옛 ID는 다음 대응으로 읽는다.

| 옛 ID | 새 ID | 기준선 활동 | 수명주기 단계 |
|---|---|---|---|
| D-01 | R-01 | 보안 요구사항 정의 | 요구사항 분석 |
| T-03 | I-10 | 호스트(타깃 외) 동적 분석 | 구현 |

단계별 기준선 활동은 다음과 같다. 설계 단계가 D-02부터, 통합 및 시험 단계에 T-03이 없는 것은 위 대응 때문이다.

| 수명주기 단계 | 기준선 활동 ID | 개수 |
|---|---|---:|
| 요구사항 분석 | R-01 | 1 |
| 설계 | D-02~D-09 | 8 |
| 구현 | I-01~I-10 | 10 |
| 통합 및 시험 | T-01·T-02·T-04~T-08 | 7 |
| 유지보수 | M-01~M-07 | 7 |
| **합계** | | **33** |

**환경 지침 ID 부여 규칙.** 환경 지침 ID는 환경 코드와 두 자리 일련번호로 이루어진다(예: MCU-03은 마이크로컨트롤러 환경의 3번째 지침). 번호는 그 환경 안에서 지침을 만든 순서다. 처음 만든 지침은 대체로 단계 순이지만, 나중에 보강한 지침은 뒤 번호를 받는다. 예를 들어 C#의 LCS-10은 유지보수 지침이지만, 그 뒤 번호인 LCS-11·12는 나중에 보강한 통합 및 시험 지침이다. 지침의 단계는 각 지침에 적힌 단계 칸을 본다. 기준선 활동과 환경 지침 모두 폐기한 ID의 번호는 다시 쓰지 않는다.

**내 환경으로 찾기.** 기준 절차는 2.5의 ①~⑦이다. ⑤ 지침 목록은 지침 선택 도구로 받는다. Excel(guide-data.xlsx)에서는 환경별 지침 시트의 적용 조건 열로 걸러 찾고, 종이로만 쓸 때는 부록 C 서두의 **특성 → 지침 역색인**으로 직접 찾는다.

**부속 도구와의 관계.** 부속 도구는 Excel [guide-data.xlsx](downloads.md)와 [cwe-phase-matrix.xlsx](downloads.md), [지침 선택 도구](selection-tool.md)이다. 이 가이드와 부속 도구는 같은 원천 데이터(문서 정보 참고)에서 만들므로 ID·기준일·용어가 같고, 문구가 서로 다르면 이 가이드가 우선한다. 가이드를 개정할 때는 원천 데이터를 고친 뒤 모든 산출물을 다시 만든다. 사용자가 추가한 환경은 사용자 쪽 파일(내보낸 특성 시트)로만 남기며, 원천에 넣으려면 개정을 거친다.

**근거의 역할 한정.** 이 가이드가 인용하는 오픈소스 사례로 확인되는 것은 지침이 실제 임베디드 코드에서 실행 가능하다는 것(구현 사례)과 지침을 지키지 않으면 실제 결함이 난다는 것(CVE 사례)뿐이다. 오픈소스 프로젝트는 무기체계가 아니므로 사례가 무기체계 적합성을 입증하지는 않는다.
