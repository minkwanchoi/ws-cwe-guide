# 실무 요약본

개발 실무자용으로 본문의 핵심을 2쪽 분량으로 정리했다. 수치·용어는 본문과 같고, 자세한 근거는 괄호의 절 번호에 있다.

!!! abstract "핵심"
    - 보안약점 예방은 요구사항 분석·설계·구현 단계에서 한다. 보안약점 점검 목록 44개의 CWE 원문 완화책에 붙은 단계 표기는 약 78%가 이 세 단계다(2.2). 매뉴얼의 정적시험·동적시험은 결과 점검이고, 이 가이드는 그 앞의 예방 활동을 중심으로 시험·유지보수 단계의 확인·유지 활동까지 안내한다(1.1).
    - 모든 과제는 기준선 활동 33개 가운데 적용 조건이 맞는 활동을 수행하고, 개발환경의 특성에 따라 고른 환경 지침을 더한다. 환경 지침은 [지침 선택 도구](selection-tool.md)로 받는다.
    - 정적 분석 도구가 보안약점 점검 목록 항목을 지원하지 않으면 하위 CWE 지원 여부를 먼저 확인하고, 대안과 사유를 대안·사유서로 정리해 사업관리부서·기술지원기관과 협의한다(6.2).
    - CWE별 완화책·탐지 방법·나쁜 예·좋은 예는 [규칙별 해설](cwe/index.md)에서 CWE 번호로 찾는다.

## 범위와 구성

| 항목 | 내용 |
|---|---|
| 대상 보안약점 | 197개: 매뉴얼 제2024-6호 「보안약점 점검 목록(44개)」 + MITRE CWE 5.0 언어 뷰 CWE-658(C)·659(C++)·660(Java) 구성원 가운데 보안약점 점검 목록에 없는 153개. 197개와 따로 세는 보조 항목 4개(CWE-611·295·299·916)도 다룬다. CWE는 MITRE가 관리하는 소프트웨어 보안약점 목록이다. C#·Python은 CWE 언어 뷰가 없어 보조 언어로 다룬다. |
| 단계 | 소프트웨어 수명주기 5단계: 요구사항 분석·설계·구현·통합 및 시험·유지보수(제3~7장) |
| 지침 | 기준선 활동 33개(모든 과제, 일부 조건부) + 환경 지침 245건(개발환경 6축 25종, 특성 15개에 따라 선택) |

## 쓰는 순서

기준 절차는 2.5의 ①~⑦이다.

1. **내 환경 정하기(①~④).** 실행 단위마다 탑재 환경·운영체제/런타임·개발 언어 등 축별 환경을 고르고, 과제가 정하는 특성(동적 메모리 정책)을 하나로 정한다(부록 G-1~G-3).
2. **지침 받기·판정(⑤~⑥).** 지침 선택 도구로 지침 목록을 받고, 사용 기술 체크리스트로 197개 보안약점의 적용성(해당·조건부·비해당)을 기록한다(부록 G-4).
3. **단계마다 적용·점검(⑦).** 제3~7장의 기준선 활동과 받은 지침을 적용하고, 단계 검토 때 자가점검표로 확인한다(부록 G-5). 쓸 수 없는 수단은 지우지 않고 "대체됨(→ 지침 ID)"으로 남긴다.

## 정적 분석 도구가 지원하지 않을 때

매뉴얼은 취약점 점검에서 자동화 도구가 지원하는 항목은 모두 적용하고, 지원하지 않는 항목은 대안과 사유를 제출해 협의하도록 한다(매뉴얼 제2024-6호 부록 7, 인쇄 7-10쪽). 이 가이드는 다음 순서로 대안을 고른다(6.2).

- **⓪ 하위 CWE 지원 확인.** 보안약점 점검 목록 44개 가운데 Class(분류) 9개(CWE-99·119·285·327·330·400·404·732·755)는 도구가 이 번호 대신 하위 CWE로 보고할 수 있다. 예를 들어 CWE-119 대신 CWE-787·125로 보고할 수 있다. MITRE는 이 가운데 CWE-119·285·330·400·755를 취약점 매핑에 '권장하지 않음'으로 둔다(MITRE CWE 5.0 Mapping Notes, 2.8). 하위 CWE를 지원하면 미지원이 아니다.
- **①~④ 대안.** CWE 원문 탐지 방법 가운데 자동 정적 분석을 뺀 나머지(코드 리뷰 I-09, 동적 분석 T-02·I-10, 퍼징 T-04 등)를 쓴다. 원문에 그런 탐지 방법이 없으면 가장 가까운 상위 CWE의 탐지 방법을 상속한다. SEI CERT 대응 규칙이 있으면 그 규칙을 코드 리뷰 체크리스트나 다른 도구의 규칙으로 점검한다. 모두 부족하면 코드 리뷰 체크리스트와 경계값·오류 주입 시험(T-05)을 쓴다.
- 대안과 사유는 항목 번호·쓴 대안·수행 기록을 담은 대안·사유서에 담아 제출하고 협의한다(매뉴얼 제2024-6호 부록 7, 인쇄 7-10쪽). 하위 CWE로 지원됨을 보일 때는 점검 결과·FA 사유서(부록 7 별첨 1-7·1-8, 인쇄 7-22쪽)에 근거를 적는다.

## 개발환경에 따라 바꿀 것

CWE 완화책은 대개 MMU(메모리 관리 장치)가 있는 범용 OS와 완전한 호스트 컴파일러를 전제한다(8.1). 대표 특성과 바뀌는 수단은 다음과 같다.

| 특성 | 바뀌는 수단(대표 지침) |
|---|---|
| H1(MMU 유무) = 없음 | ASLR·프로세스 격리·타깃 새니타이저 대신 MPU(메모리 보호 장치) 영역 보호, 정적 할당, 호스트 단위시험(BSP-03, MCU-08) |
| S1(OS 유형) = RTOS·베어메탈 | ISR(인터럽트 서비스 루틴) 공유변수 보호, 고장 안전 상태 정의, 코드 실행률은 디버거·트레이스로 실보드에서 측정(MCU-02·05, BM-08) |
| L2(컴파일러 보호 기능 지원) = 부분·없음 | L2 = 부분이면 하드닝 플래그 대신 guard 심볼 구현 확인(없으면 직접 구현)과 컴파일러가 지원하는 trap 모드 UBSan, L2 = 없음이면 스택 페인팅과 정적 분석(GCC-05, CCS-05, AVR-05) |
| 사용 기술: 현장·원격 업데이트 없음(공장 재프로그래밍만) | 서명된 업데이트(M-04)는 적용성 판정에 비해당으로 기록. 생산 단계 이미지 해시 확인과 읽기 보호로 바꾼다 |
| N1(개발·시험 망) = 내부망·폐쇄망 | 자동 업데이트와 온라인 조회 대신 반입 번들, 사내 미러, 데이터 기준일 표기(NET-CL-03·04, NET-IN-05·08) |

## 나쁜 예·좋은 예

보안약점 점검 목록 44개와 보조 항목 4개 CWE마다 C·C++·C#·Java·Python의 나쁜 예와 좋은 예를 규칙별 해설에 싣는다. 언어마다 분석기(Python은 Bandit)·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 도구로 잡기 어려운 CWE-615(주석문 안에 포함된 시스템 주요정보)와 C·C++·C#·Java의 CWE-259(하드코드된 비밀번호)는 생성형 AI를 쓴 별도 검토로 판정했다. 그 언어에서 생길 수 없는 약점은 '예시 없음'과 사유를 적었다. 코드는 이 가이드가 새로 작성했다.
