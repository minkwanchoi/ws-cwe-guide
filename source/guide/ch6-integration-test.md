# 제6장 통합 및 시험 단계 지침

## 6.1 단계 목표·입력·산출물

통합 및 시험 단계는 구현한 소프트웨어를 통합해 매뉴얼의 신뢰성시험(정적시험·동적시험)으로 보안약점이 남았는지 확인하고, 매뉴얼 시험이 잘 잡지 못하는 결함을 보조 시험으로 찾는 단계다.

**입력.** 요구사항 분석 단계의 SRS 보안 요구사항·중요 기능 목록과 소프트웨어개발계획서의 신뢰성·보안성 시험계획, 언어별 점검 기준표와 보안약점 적용성 판정(부록 G-4, 제3장), 설계 단계의 ICD 필드 범위표·권한 매트릭스·자원 예산표(제4장), 구현 단계의 사업 코딩 표준·편차 대장, 빌드 설정 기준, 상시 정적 분석 결과, 소프트웨어단위시험결과와 호스트·타깃 빌드 차이 목록(제5장), 환경 프로파일과 지침 선택 결과(부록 G-3)를 입력으로 쓴다.

**산출물.** 활동마다 '산출물' 항목에 적었다(6.2~6.4).

**시험 활동 도출.** 통합 및 시험 단계 지침은 CWE의 탐지 방법(Detection Methods)에서 끌어낸다. Testing 단계 완화책(mitigation)이 197개 중 7개 항목(보안약점 점검 목록 44개 중 2개, 2.2)에만 있기 때문이다. 아래 표는 탐지 방법을 계열로 묶고 계열마다 대응하는 이 장의 시험 활동을 적는다[^cnt51].

| 탐지 방법 계열 | 보안약점 점검 목록 44개 | 197개 전체 | 이 가이드의 시험 활동 |
|---|---:|---:|---|
| 정적 분석(자동·수동, 소스·바이너리) | 43 | 169 | T-01 정적시험, T-08 운용 빌드 산출물 검사(바이너리) |
| 　그중 바이너리·바이트코드 대상 | 14 | 18 | T-08 |
| 동적 분석(자동·수동 결과 해석, 블랙박스·퍼징 포함) | 28 | 65 | T-02 타깃 동적시험, T-05 경계값·오류 주입, T-07 자원·장시간, I-10 호스트 동적 분석(구현 단계, 제5장) |
| 　그중 퍼징(fuzzing) | 8 | 20 | T-04 퍼징 |
| 　그중 블랙박스 | 7 | 13 | T-06 보안 기능 부정 시험 |
| 설계 검토 | 15 | 19 | D-09 설계 보안성 검토(제4장) |
| 탐지 방법 없음 | 0 | 15 | 2.7 근거 규칙 적용 |

[^cnt51]: **6.1 집계 기준.** CWE 5.0 원문(197개 항목)의 탐지 방법 이름으로 항목 단위로 셌다(한 항목에 같은 계열 방법이 여럿 있어도 1). '정적 분석'은 이름에 Static이 들어간 방법이고, '동적 분석'은 이름에 Dynamic이 들어간 방법과 Fuzzing·Black Box다. 보안약점 점검 목록 44개 중 정적 분석 계열이 없는 항목은 CWE-628 하나다. 퍼징 8개는 CWE-369·400·415·416·457·469·562·732, 블랙박스 7개는 CWE-134·190·259·319·330·494·732다.

**탐지 방법이 없는 15개.** 모두 언어 뷰 항목이고, 4개가 Java 뷰에만 있는 항목이다. 2.7의 규칙에 따라 상위 CWE의 탐지 방법을 상속한다. 바로 위 상위가 197개 안에 있고 탐지 방법이 있는 경우는 2개(CWE-600 ← 248, CWE-689 ← 362)다.

나머지 13개는 CWE 5.0 전체 목록에서 상위 계통(ChildOf, View 1000)을 따라 올라가 확인했다(2.7). 13개 모두 가장 가까운 상위에 탐지 방법이 있었다. 13개 중 2개는 두 단계 위의 197개 안 상위(CWE-536·537 ← 209)에서, 11개는 197개 밖의 상위에서 찾았다. 다만 197개 밖 상위는 CWE-1325가 상속하는 CWE-770(4건)을 빼면 탐지 방법이 1건뿐이고, 7개 항목은 기둥(Pillar) 항목(CWE-664·707)에서 상속하므로 일반 원칙 수준이다. 그래서 이 항목들은 T-01 정적시험과 코드 리뷰를 주 수단으로 삼는다. 상속한 상위 항목은 각 CWE의 규칙별 해설 페이지에 표시한다.

**기준선 시험 활동과 매뉴얼 시험의 관계.** 매뉴얼의 신뢰성시험은 정적시험과 동적시험으로 이루어진다([표준] 매뉴얼 부록 7, 인쇄 7-4쪽). T-01과 T-02가 이 두 시험에 대응하고, 나머지 활동은 매뉴얼 시험을 대신하지 않는 **보조 시험**이다. 보조 시험은 매뉴얼 시험 전에 결함을 미리 줄이고, 매뉴얼 시험이 잘 잡지 못하는 결함(해제된 자원 사용(use-after-free), 경쟁조건(race condition), 자원 고갈, 인증 우회)을 찾는 데 쓴다.

**기준선 활동.** 이 단계의 기준선 활동은 7개(T-01·T-02·T-04~T-08)이고, T-03이 비는 까닭은 1.4에 있다. 활동은 시험 종류별 절(6.2~6.4)에 두고, 아래 표로 모아 보인다. '강화·대체 지침' 항목의 뜻은 2.3에 있다.

| 기준선 활동 | 다루는 절 | 매뉴얼 시험과의 관계 |
|---|---|---|
| T-01 정적시험(소스·바이너리)과 오탐·편차 판정 | 6.2 | 정적시험 |
| T-08 운용 빌드 산출물 검사 | 6.2 | 보조 시험 |
| T-02 타깃 동적시험 | 6.3 | 동적시험 |
| T-04 퍼징 | 6.3 | 보조 시험(외부 통신 스택이나 외부 파일·명령 입력이 있을 때) |
| T-05 경계값·오류 주입 시험 | 6.3 | 보조 시험(동적시험 케이스로 흡수 가능) |
| T-07 타깃 자원·장시간 시험 | 6.3 | 보조 시험 |
| T-06 보안 기능 부정 시험 | 6.4 | 보조 시험(인증·암호·업데이트를 쓰거나 외부 통신이 있을 때) |

## 6.2 정적시험과 도구 미지원 대안

매뉴얼의 정적시험은 소프트웨어를 실행하지 않고 잠재 결함을 찾는 시험으로, 코딩규칙 검증·취약점 점검·소스코드 메트릭 점검으로 이루어진다([표준] 매뉴얼 본문, 인쇄 11쪽). 개발자가 각 항목에서 할 일은 다음과 같다.

| 시험 항목 | 매뉴얼이 정한 것(부록 7) | 개발자가 할 일 |
|---|---|---|
| 코딩규칙 검증 | 부록 6 코딩규칙(관련 표준은 1.3)의 준수 여부(인쇄 7-10쪽) | I-01의 사업 코딩 표준과 같은 규칙 집합을 도구에 설정하고, 시험확인서에 적을 규칙 수와 도구·버전을 기록한다(7-27쪽). |
| 취약점 점검 | 소프트웨어 취약점 점검(CWE-658/659/660)과 보안약점 점검 목록. 도구가 지원하는 항목은 모두 적용하고 미지원 CWE 항목은 대안·사유를 내고 협의한다. 보안약점을 추가로 식별하면 규칙을 추가한다(7-10쪽). | 도구의 CWE 지원표를 197개 목록과 대조해 미지원 항목마다 대안(6.2의 대안 ⓪~④, 규칙별 해설의 '탐지 방법' 절)과 사유를 적는다. 적용성 판정(G-4)의 비해당 항목과 미지원 항목을 섞지 않는다. 시험확인서에는 실제 쓴 CWE 판을 적는다(서식 예시는 V4.10). |
| 소스코드 메트릭 | 종류 6가지를 예시로 들고 제한값 칸은 비워 둔다. 종류·제한값은 연구개발주관기관이 제시해 소프트웨어 검토회의 등에서 정하고, 넘으면 미달성 분석결과보고서를 낸다(7-12쪽). | 사업에서 정한 제한값을 빌드 경고 기준으로 걸어 구현 중에 넘지 않게 한다. 다른 사업이나 이전 판 매뉴얼의 수치를 그대로 가져오지 않는다[^metric]. |
| 합격 기준 | 결함이 검출되지 않아야 하며, 거짓경보와 시험 대상이 아닌 것은 결함에 넣지 않는다(7-10쪽). | 오탐(매뉴얼의 거짓경보) 판정마다 근거(코드 위치, 판정 사유, 판정자)를 남긴다. |
| 시기·도구 | 개발 초기부터 하고 통합시험 단계에서 종합한다. 도구는 관련 표준 인증 제품이 원칙이고, 없으면 소프트웨어 검토회의에서 정한다(7-5쪽). | 같은 도구·규칙 설정을 CI(지속적 통합)에서 커밋마다 돌린다(I-09). |

[^metric]: 논문이 소개한 고정 제한값은 이전 판 매뉴얼의 것이고, 현행 제2024-6호에서는 제한값을 사업별로 정한다.

**도구가 지원하지 않는 항목의 대안.** 매뉴얼 규정은 위 표의 취약점 점검 행과 같다(부록 7, 인쇄 7-10쪽). 행정안전부·KISA 「소프트웨어 개발보안 가이드」도 구현 단계에서 코드 리뷰 또는 소스코드 진단으로 소스코드 수준의 안전성을 보장하라고 한다([표준] 인쇄 22쪽). 이 가이드는 대안을 다음 순서로 고르고, 항목마다 고른 결과를 규칙별 해설 페이지의 '탐지 방법' 절과 내려받기 Excel에 실었다. ⓪ 하위 CWE와 매핑 권고는 부록 A-2에도 한 표로 모았다(원천: CWE 5.0 원문의 탐지 방법, 상위 CWE 상속 표, 언어 뷰의 SEI CERT 대응).

**⓪ 하위 CWE 지원 확인(대안을 고르기 전).** 보안약점 점검 목록 항목이 Class(분류)이거나 MITRE 매핑 권고(Mapping Notes의 Usage)가 '권장하지 않음(Discouraged)'·'검토 후 허용(Allowed-with-Review)'이면, 도구가 이 CWE 번호 대신 하위 CWE로 보고하는지 먼저 확인한다. 하위 CWE를 지원하면 미지원이 아니며, 지원하는 하위 CWE 목록을 점검 결과·FA 사유서(코딩규칙점검·취약점점검, 매뉴얼 제2024-6호 부록 7 별첨 1-7·1-8, 인쇄 7-22쪽)에 근거로 적는다. 추상화 수준과 매핑 권고의 뜻은 [2.8 CWE 계층과 이 가이드](ch2-framework.md#cwe-hierarchy)를 본다.

| 순서 | 대안의 출처 | 이 가이드의 활동 | 근거 |
|---|---|---|---|
| ① | CWE 원문 탐지 방법(Detection Methods) 가운데 자동 정적 분석을 뺀 나머지. SOAR 효과성(높음·보통·부분 적용)을 함께 적는다. SOAR는 CWE 탐지 방법이 인용하는 보고서(MITRE 참고문헌 REF-1479, 부록 F)이고, '부분 적용'은 근거 표시 '부분'(2.7)과 다른 말이다. | 수동 정적 분석·수동 분석 → I-09 코드 리뷰 / 바이너리·바이트코드 정적 분석(다른 도구 또는 수동) → T-08 / 자동 동적 분석·결과 해석 동적 분석 → T-02·I-10 / 수동 동적 분석 → T-02·T-05 / 퍼징 → T-04 / 블랙박스 → T-06 / 화이트박스 → I-10·T-05 / 아키텍처·설계 검토 → D-09 / 정형 검증·시뮬레이션·에뮬레이션 → 과제에서 정함 | [CWE] 각 항목 Detection Methods, SOAR [REF-1479] |
| ② | 원문에 탐지 방법이 아예 없으면(197개 중 15개, 6.1) 가장 가까운 상위 CWE(ChildOf, View 1000)의 탐지 방법을 상속한다. | 상위 항목의 ①과 같다 | [CWE] 2.7 규칙 1 |
| ③ | SEI CERT 대응 규칙이 있으면 그 규칙을 코드 리뷰 체크리스트 항목이나 다른 도구의 규칙으로 점검한다. | I-09, 또는 두 번째 정적 분석 도구·컴파일러 경고 | [표준] SEI CERT(2.7 규칙 2) |
| ④ | 위가 모두 없거나 부족하면 [보완]으로 코드 리뷰 체크리스트와 경계값·오류 주입 단위시험을 쓴다. | I-09, T-05 | [보완] |

**공통안과 고유안.** 위 표에서 ①의 탐지 방법별 활동 대응, ③의 점검 방법, ④는 모든 항목에 같은 공통안이다. 규칙별 해설 페이지와 부록 A-2에는 항목마다 달라지는 고유안만 싣는다. 고유안은 점검 착안점(그 보안약점을 도구 없이 찾는 방법과 활동), ⓪의 하위 CWE, ①의 원문 탐지 방법과 SOAR 효과성, ②의 상속 대상, ③의 SEI CERT 규칙 번호다. 점검 착안점은 「보안약점 점검 목록(44개)」에 둔다. 착안점은 언어 중립으로 쓰고, 특정 언어에서만 성립하면 언어를 밝힌다. 착안점의 근거는 이 가이드가 검증한 나쁜 예·좋은 예의 판정 방법[예시], CWE 원문의 탐지 방법·완화책[CWE], SEI CERT 규칙[표준], 실무 보완[보완]이다.

대안을 쓸 때는 다음을 지킨다. 첫째, 다른 정적 분석 도구·컴파일러 경고(`-Wall -Wextra -Wformat=2` 등)·새니타이저가 그 항목을 잡는지 먼저 확인한다. 도구 하나가 지원하지 않는다고 바로 수동 수단으로 가지 않는다. 반대로 도구에 그 CWE에 대응하는 규칙이 있어도 규칙의 대상 조건이 과제와 맞지 않으면 미지원과 같다. 예를 들어 .NET 분석기의 오염 추적 규칙은 HTTP 요청 입력만 추적하므로 콘솔·파일 입력의 삽입을 경고하지 않는다(5.6). 이런 항목은 규칙 이름만 보고 '지원'으로 적지 않고 ①~④의 대안을 함께 적는다.

## 6.3 동적시험과 보조 시험

**매뉴얼의 동적시험.** 동적시험은 소프트웨어를 실제 하드웨어(Target)에 탑재한 상태에서 소프트웨어통합시험서의 절차에 따라 요구사항 기반으로 실행하고 코드 실행률(Coverage)을 점검하는 시험이다([표준] 매뉴얼 본문, 인쇄 11쪽). 시험종류(문장·분기·MC/DC)는 결함의 영향도·발생빈도·제어가능성을 평가해 정하며, MIL-STD-882E·DO-178 같은 국제 표준을 적용해 개발하면 그 표준을 따를 수 있다(부록 7, 인쇄 7-13~7-14쪽).

합격 기준은 설정한 시험종류의 코드 실행률 100%이고(7-15쪽), 방어 코드처럼 도구 한계로 목표를 달성할 수 없으면 해당 소스를 분석해 설명 자료를 붙인다(7-16쪽). 실제 하드웨어 시험이 제한되면 호스트 환경에서 할 수 있으나, 시험 환경과 타깃 환경의 차이를 분석해 소프트웨어통합시험서(STD)에 반영하고, 하드웨어 제약으로 타깃 동적시험이 제한되면 타당한 사유를 제시해 사업관리회의에서 방안을 정한다(7-5쪽). 시험은 연구개발주관기관이 자체로 하거나 제3자가 검증하고, 기술지원기관이 결과를 검토한다(7-5·7-15쪽).

## 6.5 시험 환경 고려(내부망·폐쇄망)

이 절은 정적시험·동적시험을 실행하는 시험 환경을 다룬다. 개발 전반의 망 환경 지침(반입·반출, 패키지 저장소, 계정·비밀 관리)은 8.6과 부록 C에, 재현 가능한 빌드(reproducible build)는 M-07(7.2)에 있다.

**통합 시험 환경의 보안 이슈(배경).** 2019년 연구는 망분리 환경에서 신뢰성시험 도구를 효율적으로 쓰려고, 한 서버가 폐쇄망과 내부망 사용자에게 동시에 서비스하는 통합 시험 환경을 제안했고, 이에 따른 보안 이슈에 대응하려면 보안 취약점 관련 추가 시험과 사용자별 접근 권한의 엄격한 관리가 필요하다고 판단했다(최민관 외, 2019, 4.3절). 이 가이드는 이 판단을 NET-IN-01(내부망)과 NET-CL-02(폐쇄망)로 옮겼다.

통합 구성이면 취약점 관련 추가 시험과 사용자별 접근 권한 관리를 적용하고, 서버를 망별로 나눌지는 연구가 다루지 않은 문제이므로 망분리 정책과 위험평가로 정한다([보완]). 폐쇄망은 반입 경로를 통한 단방향 데이터 이동을 기본으로 한다([보완]).

**시험 결과를 믿을 수 있게 하는 환경 지침.** 폐쇄망·내부망에서는 도구의 규칙 데이터가 늦게 들어오고 라이선스가 부족해 시험이 빠지기 쉽다. 다음 지침으로 시험 결과의 완전성과 추적성을 지킨다.

| 지침 | 내용 | 근거 |
|---|---|---|
| NET-IN-08 / NET-CL-08 (→ T-01 강화) | 반입한 SAST 규칙 집합(rule pack)과 CWE/CVE 데이터는 서명·해시를 확인하고, 결함 샘플 세트로 검출 회귀시험을 통과한 뒤 쓴다. 보고서에 규칙 집합·데이터 기준일을 적고, 기준일이 오래되면 경고한다. | [보완] 오프라인 환경의 정보 지연 대응 |
| NET-IN-09 / NET-CL-09 | 커밋 ID, 빌드 번호, 도구·규칙 집합 버전, 타깃 하드웨어 식별자, 정적시험·동적시험 결과를 하나의 ID로 묶어 보관한다. 독립된 두 환경에서 같은 소스를 빌드해 산출물 해시가 같은지 확인한다. | [사례] Reproducible Builds 정의 문서(조회 2026. 10. 15.) · [보완] |
| NET-IN-07 / NET-CL-05 | 도구 라이선스를 확보하지 못해 시험이 빠지면 '통과'가 아니라 '미수행'으로 기록하고 빌드를 실패시킨다. 오프라인 라이선스는 만료일보다 앞서 갱신 파일을 반입한다. | [보완] 시험 완전성 |

시험 장비가 부족하면, 소프트웨어기술지원기관이 연구개발주관기관의 요청에 따라 자체 보유 장비를 라이선스 범위 안에서 지원할 수 있다는 규정도 확인한다([표준] 「무기체계 소프트웨어 개발 지원에 관한 규정」(방위사업청 훈령 제948호) 제9조 제7항).

## 6.7 언어별 시험 고려

언어별 시험 고려 사항은 2.6 활동표의 통합 및 시험 열(LC-08, LCPP-08, LJ-09, LCS-09·11·12, LPY-09·11·12)을 따른다. 그 표에 더해 다음을 지킨다.

- **Java**: 타깃 JVM에서 코드 실행률 계측이 어려우면 협의 절차(2.5)에 따라 대체 근거를 확정한다(LJ-09).
- **C#**: 상용 도구 결과는 협의 절차(2.5)로 확정한 C# 점검 기준표(LCS-01)에 맞춰 보고한다(LCS-09). C#은 매뉴얼 신뢰성시험의 적용 언어이므로 동적시험의 시험종류(문장·분기·MC/DC, 매뉴얼 제2024-6호 부록 7, 인쇄 7-13쪽)를 .NET 코드 실행률 도구가 잴 수 있는지 착수 때 확인한다. 예로 coverlet README가 밝힌 지원 범위는 라인·분기·메서드 실행률이다([표준] coverlet v10.1.0 README). 인증된 도구가 없어 coverlet 같은 도구를 쓰거나 잴 수 없는 시험종류의 대안이 필요하면 소프트웨어 검토회의(신뢰성시험계획)에서 정하고, 실제 타깃 시험이 제한되어 호스트에서 쟀다면 타깃 환경과의 차이를 STD에 적는다(매뉴얼 부록 7, 인쇄 7-5쪽, LCS-11). 외부 입력을 해석하는 코드가 있으면 SharpFuzz로 퍼징한다. SharpFuzz로 계측하려면 계측 도구를 돌리는 장비에 .NET 8.0 이상이 설치되어 있어야 하고 AFL 엔진은 Linux·macOS에서 돌므로(Windows는 libFuzzer 엔진), .NET Framework 대상 코드는 시범 적용으로 계측 가능 여부를 먼저 확인한다([표준] SharpFuzz v2.2.0 README). 대상 예는 MissionPlanner의 MAVLink 패킷 해석 메서드다([사례] MissionPlanner1.3.83, `ExtLibs/Mavlink/MavlinkParse.cs:128`)(LCS-12).
- **Python**: 매뉴얼과의 관계는 1.2와 5.7에 있다. Bandit·Ruff·mypy·pip-audit 결과와 coverage.py 코드 실행률은 과제의 보안·품질 기록으로 남기고, 찾은 보안약점은 조치하고 기록한다(LPY-09). 메시지 파서 같은 입력 해석 코드는 Atheris로 퍼징한다. Atheris 현행 판(3.0.0)은 Linux·macOS와 Python 3.11~3.13만 지원하므로 Windows에서 도는 Python 코드는 OS에 의존하지 않는 해석기 모듈을 Linux 호스트(가상 머신 등)에서 시험한다([표준] Atheris 3.0.0 README; 대상 예: [사례] pymavlink v2.4.50, `mavutil.py:484`)(LPY-11). 배포·반입 전에는 디버그 코드와 남은 비밀을 찾아 지운다. KISA 「Python 시큐어코딩 가이드」는 배포 전 디버그 코드를 반드시 확인·삭제하라고 하고(인쇄 147쪽), Ruff T100은 `breakpoint()`·`pdb` 같은 디버거 호출을 찾는다. PyInstaller로 묶은 배포본에도 디컴파일될 수 있는 .pyc 파일이 들어가므로 같은 기준으로 검사한다([표준] PyInstaller v6.22.3 문서)(LPY-12).
