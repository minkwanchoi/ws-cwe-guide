    3.1 단계 목표·입력·산출물¶

    요구사항 분석 단계는 무엇을 보호해야 하는지와 어떤 보안약점을 점검 대상으로 삼을지를 요구사항으로 정하는 단계다. 매뉴얼은 연구개발주관기관이 소프트웨어요구사항명세서(SRS)의 소프트웨어 품질특성 요구사항에 신뢰성·보안성 요구사항을 작성하도록 하고([표준] 매뉴얼 제2024-6호 제4장 Ⅱ.3, 인쇄 111쪽), 기술지원기관은 SRS에 신뢰성시험·보안성시험(전장관리정보체계) 등 품질요소 요구사항이 들어 있는지 검토한다(제2장 Ⅵ, 인쇄 37쪽).

    행정안전부·KISA 「소프트웨어 개발보안 가이드」도 분석 단계에서 처리 대상 정보와 기능에 적용할 보안항목을 식별하고, 이를 요구사항 정의서에 넣어 설계·구현·시험 단계에 적용하도록 한다([표준] 인쇄 32·35쪽). 이 단계에서 정한 요구사항은 뒤 단계 지침의 기준이 된다.

    입력. 체계요구사항명세서와 운용 개념, 외부 인터페이스 목록, 착수 때 만든 환경 프로파일과 지침 선택 결과(부록 G-3), 보안약점 적용성 판정 초안(부록 G-4)을 입력으로 쓴다.

    산출물에 넣을 보안 항목. 문서 이름은 매뉴얼의 산출물 이름을 따른다. 과제가 다른 문서 체계를 쓰면 해당 문서에 넣는다.

    산출물 넣을 보안 항목 관련 기준선 활동
    소프트웨어요구사항명세서(SRS)의 보안 요구사항 외부 입력의 범위·길이·자료형·단위, 인증·인가가 필요한 중요 기능과 기능별 보호 요구, 전송·저장 구간별 암호 요구, 오류가 났을 때의 안전 상태, 자원 상한 R-01(자원 상한은 D-07, 안전 상태는 D-08로 설계)
    SRS의 소프트웨어 품질요소(품질특성) 신뢰성·보안성 요구사항(보안성시험 요구사항 포함, 매뉴얼 인쇄 40·111쪽) R-01
    SRS의 보안 관련 확인 항목 기밀정보의 손실과 보호 관련 요구사항(매뉴얼 인쇄 40쪽) R-01
    보안약점 적용성 판정 기록지(부록 G-4) 197개 보안약점별 해당·조건부·비해당과 사유(판정 방법은 3.3) —
    언어별 점검 기준표 C#의 CWE 매핑, Java 웹·J2EE 항목 판정, Python 신뢰성시험 범위 포함 여부·보안 점검 범위(3.5) — (언어 지침 LCS-01, LJ-01, LPY-01)

    3.2 기준선 활동 R-01¶

    요구사항 분석 단계의 기준선 활동은 R-01 하나다. '강화·대체 지침' 항목의 뜻은 2.3에 있다.

    R-01 보안 요구사항 정의¶

    요구사항 분석 · 기준선

    • 적용 조건: 항상
    • 대상 약점: CWE-119, CWE-190, CWE-285, CWE-306, CWE-319, CWE-307, CWE-521
    • 지침: 외부에서 들어오는 모든 데이터의 범위·길이·자료형·단위를 요구사항으로 적는다. 인증·인가가 필요한 중요 기능(업데이트, 설정 변경, 키 주입, 운용 모드 전환 명령 등)을 식별해 기능마다 보호 요구를 적는다. 전송·저장 구간별 암호 요구와 오류가 났을 때의 안전 상태도 요구사항으로 정한다.
    • 산출물: SRS 보안 요구사항 절(외부 인터페이스 요구사항의 필드 범위 포함). 설계 단계에서 ICD 필드 범위표로 구체화한다(제4장).
    • 근거: [CWE] CWE-119·190 완화책(Requirements) · [표준] 매뉴얼 제2024-6호 제4장 Ⅱ.3(SRS 품질특성의 신뢰성·보안성 요구사항, 인쇄 111쪽), 행정안전부·KISA 「소프트웨어 개발보안 가이드」(분석단계 보안항목 식별, 인쇄 32·35쪽), SSDF PW.1(PW.1.2)·PO.1.2 · [사례] 사례 상자 3-1
    • 강화·대체 지침: 없음

    사례 상자 3-1 — 요구사항에 폭주 대응을 적은 사례 이 사례는 지침이 실제 임베디드 코드에 쓰인 예다. 무기체계 적합성을 입증하지 않는다.

    • [사례·확인] (R-01) NASA F´ v4.4.1, Svc/CmdDispatcher/docs/sdd.md:17 — 명령 분배 컴포넌트 설계서의 요구사항 표가 큐 넘침(DoS 공격)을 피하려고 들어오는 명령을 버린다는 요구 CD-005를 검증 방법(단위시험)과 함께 적었다. (확인 2026. 10. 15.)

    3.3 적용 보안약점과 점검 기준 정하기¶

    적용성 판정은 요구사항 분석 단계에서 한다. 197개 보안약점 가운데 과제가 쓰지 않는 기술에서만 생기는 것은 사용 기술 체크리스트로 '비해당'을 판정하고 사유를 부록 G-4에 남긴다(2.5 ⑥, 부록 B). 예를 들어 CWE-259·307·521·759는 비밀번호 인증(사용자 계정 또는 장비 간 연결)을 쓸 때만 생긴다. 판정 결과는 SRS의 보안 요구사항과 함께 검토받는다.

    점검 기준을 일찍 정하는 이유. 매뉴얼은 취약점 점검에서 도구 미지원 항목의 대안과 사유를 내고 협의하게 하고(6.2), 개발 준비 단계의 소프트웨어개발계획서에 신뢰성·보안성 시험계획을 넣도록 한다(제4장 Ⅱ.3, 인쇄 111쪽). 그래서 점검 대상 목록과 미지원 항목의 대안은 통합 및 시험 단계가 아니라 이 단계에서 정해 두어야 시험계획과 도구 선정에 반영된다.

    보안항목을 찾을 때 참고할 목록. 행정안전부·KISA 「소프트웨어 개발보안 가이드」의 분석·설계단계 보안설계 기준 20개(SR1-1~SR4-1)는 전자정부 정보시스템을 대상으로 만든 것이다([표준] 인쇄 13·35~36·342~347쪽, 판권면). 그중 시스템 자원 접근·명령어 수행 입력값 검증(SR1-4), 허용된 범위 내 메모리 접근(SR1-8), 보안기능 입력값 검증(SR1-9), 업로드·다운로드 파일 검증(SR1-10), 보안기능 8개(SR2-1~SR2-8), 예외처리(SR3-1)는 임베디드 과제에서도 보안 요구사항을 찾는 점검표로 쓸 수 있다([보완] 항목 선택은 이 가이드의 판단).

    3.4 특성에 따른 요구사항 보정¶

    이 단계는 특성에 따른 보정이 따로 없다(R-01의 강화·대체 지침 없음). 뒤 단계 활동의 보정은 활동마다 '강화·대체 지침'과 8.1을 본다.

    3.5 언어별 요구사항 고려¶

    CWE 언어 뷰가 없거나 웹 전제 항목이 많은 언어는 이 단계에서 점검 기준을 따로 정한다.

    • Java: 프로젝트가 쓰는 프레임워크·API와 CWE-660 항목을 대조해 J2EE·웹 전용 항목은 비해당 사유를 적고, 나머지는 점검 대상으로 확정한다(LJ-01).
    • C#: C# 전용 CWE 뷰가 없으므로 「보안약점 점검 목록(44개)」과 CWE-658/660 가운데 C#에서도 생길 수 있는 항목을 골라 C# 점검 기준표를 만들고, 해당·비해당 사유를 협의 절차(2.5)에 따라 확정해 점검 기준으로 삼는다(LCS-01). 웹 UI(ASP.NET)를 두는 과제는 Microsoft .NET 보안 규칙 가운데 웹 전용으로 비해당 판정한 규칙(부록 D)을 다시 판정해 C# 점검 기준표에 적는다.
    • Python: 매뉴얼과의 관계는 1.2와 5.7에 있다. 이 단계에서 신뢰성시험 범위 포함 여부, 다른 시험 제도 검토 결과, 보안 점검 범위(Bandit 규칙·의존성 취약점 점검·퍼징 대상)를 정해 기록하고, 시험 합부 판정에 영향을 주는 스크립트는 입력·출력 사양을 문서화한다(LPY-01).

    3.6 단계 자가점검표¶

    요구사항 분석 단계 자가점검표(3-1~3-7)는 부록 G-5 요구사항 분석 단계에 있다. SRS를 내거나 소프트웨어요구사항검토회의(SSR)를 준비할 때 그 표로 스스로 확인한다.
