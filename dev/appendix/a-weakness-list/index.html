    부록 A. 보안약점 점검 목록(44개) 조견표¶

    이 쪽의 목차
    • A-1. 단계별 지침
    • A-2. 도구 지원 확인
    • A-3. 보조 항목(197개 밖) 4개

    이 부록의 역할. 항목 하나의 자세한 설명·완화책·탐지 방법·예시는 규칙별 해설에 있다. 이 부록은 44개를 한 표로 가로질러 보는 조견표다(예: 설계 검토 때 설계 열만 훑기).

    읽는 법. 「무기체계 소프트웨어 개발 및 관리 매뉴얼」(방위사업청 매뉴얼 제2024-6호) 부록 7의 「보안약점 점검 목록」 44개를 싣는다. 행은 매뉴얼 표 순서이고, 범주는 규칙별 해설과 같은 MITRE CWE-1400이다(색인의 범주). 약점 이름은 행정안전부·KISA 「소프트웨어 개발보안 가이드」 구현단계 보안약점 항목명을 따르고(구현단계 항목에 따로 없는 CWE-259·312·319·497은 같은 가이드 분석·설계단계 사례 제목, 가이드에 없는 항목은 CWE 원제목 번역. 항목명과 다르게 적은 곳은 부록 F의 '약점 이름 표기 주석'), CWE 번호는 규칙별 해설(없으면 MITRE 원문)로 연결된다.

    • A-1 단계별 지침: 항목마다 수명주기 5단계(요구사항 분석·설계·구현·통합 및 시험·유지보수)와 임베디드 고려를 한 행에 싣는다. 본문 제3~7장의 기준선 활동과 함께 쓴다. '통합 및 시험' 열의 호스트 새니타이저·단위시험 내용은 구현 단계의 I-10으로 한다(2.2). 추상화는 MITRE CWE의 추상화 수준(분류(Class)·기본(Base)·변형(Variant)·복합(Compound))이고, 적용성은 부록 B와 같은 규칙이다.
    • A-2 도구 지원 확인: 정적 분석 도구의 CWE 지원표와 대조할 때 먼저 볼 두 가지(MITRE 매핑 권고, ⓪ 도구가 이 번호 대신 보고할 수 있는 하위 CWE)를 44개 한 표로 싣는다. 도구가 지원하지 않을 때의 항목별 대안(점검 착안점, ① CWE 원문 탐지 방법, ② 상위 CWE 상속, ③ SEI CERT 규칙)은 각 항목 해설의 '탐지 방법' 절에, 모든 항목에 같은 공통안은 6.2에 있다. MITRE 매핑 권고는 MITRE가 그 CWE를 취약점 매핑에 쓰는 것을 '권장하지 않음'(Discouraged)·'검토 후 허용'(Allowed-with-Review)으로 둔 경우만 적는다('—'은 허용).
    • A-3 보조 항목(197개 밖) 4개: 보안약점 점검 목록과 언어 뷰 밖이지만 무기체계 소프트웨어에 해당해 따로 세는 약점(CWE-611·295·299·916)의 추가 근거, 단계별 지침, 도구 미지원 시 대안을 싣는다.

    A-1. 단계별 지침¶

    CWE·이름·범주·추상화·적용성 요구사항 분석1 설계 구현 통합 및 시험 유지보수 임베디드 고려
    CWE-22 경로 조작(path traversal)
    언어 무관
    파일 처리
    기본(Base)
    조건부: 파일시스템 사용(파일시스템(S3)이 '없음' 외의 값)    		 — 외부 입력으로 파일 경로를 구성하지 않도록 설계하고, 불가피하면 허용 파일 목록(ID→경로 매핑)과 고정 기준 디렉터리를 정의한다. 구현(C·C++) realpath()로 정규화한 뒤 기준 디렉터리를 경로 요소 단위로 검증하고(문자열 비교라면 접두어 뒤가 구분자인지까지 확인한다) '..', '/', '\', NUL 문자를 거부한다. open() 시 O_NOFOLLOW를 사용한다.
    구현(Java) Path.toRealPath()로 링크까지 풀어 정규화한 뒤 startsWith(baseDir)로 검증하고, 파일명은 [A-Za-z0-9._-] 허용목록(allowlist) 정규식으로 제한한다.    		 '../', 인코딩된 '%2e%2e%2f', 절대 경로, 긴 경로를 포함한 경로 퍼징(fuzzing)과 정적 분석(오염 추적)으로 입력→파일 API 흐름을 점검한다. 파일 저장 위치·디렉터리 구조 변경 시 기준 디렉터리 검증 로직을 재점검하고, 운용 중 최소 권한 계정으로 실행한다. RTOS(실시간 운영체제) 파일시스템(FatFs, VxWorks dosFs)은 권한 개념이 약하므로 외부 명령(정비 단말·직렬 명령)으로 파일명을 받지 말고 고정 인덱스로 접근한다.
    CWE-59 링크 따라가기(Link Following)
    언어 무관
    파일 처리
    기본(Base)
    조건부: 파일시스템 사용(파일시스템(S3)이 '없음' 외의 값)    		 — 민감 파일은 일반 사용자가 쓸 수 없는 전용 디렉터리에 두고, 공용 임시 디렉터리(/tmp) 사용을 설계 단계에서 배제한다. 구현(C·C++) open(path, O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW, 0600) 후 fstat()으로 소유자·파일 유형을 확인하고, lstat()→open() 순서의 검사 방식을 쓰지 않는다. mkstemp()를 사용한다.
    구현(Java) Files.newByteChannel(path, LinkOption.NOFOLLOW_LINKS 등)을 사용하고, Files.createTempFile()로 임시 파일을 만든다.    		 심볼릭/하드 링크를 미리 생성해 둔 상태에서 파일 생성·쓰기 기능을 실행하는 시나리오 시험을 수행한다. 디렉터리 권한(sticky bit, 소유자) 구성을 형상관리(configuration management) 대상에 포함하고 배포 시 점검한다. 임베디드 Linux SBC에서 /tmp가 tmpfs일 때도 동일하게 적용하며, 읽기 전용 루트 파일시스템(squashfs)으로 쓰기 가능한 경로를 줄이고, 남는 쓰기 경로(tmpfs·기록 파티션)에는 위 규칙을 적용한다.
    CWE-78 운영체제 명령어 삽입(OS command injection)
    언어 무관
    삽입
    기본(Base)
    조건부: OS 명령 실행 사용    		 — 외부 프로세스 호출 대신 라이브러리 API로 기능을 구현하도록 설계하고, 불가피한 경우 실행 가능한 명령을 고정 목록으로 정의한다. 구현(C·C++) system()/popen() 사용을 금지하고 execve()에 고정 경로와 인자 배열을 전달한다. 환경변수(PATH, IFS)를 초기화한다.
    구현(Java) Runtime.exec(String) 대신 ProcessBuilder(List<String>)로 명령과 인자를 분리하고, 명령은 허용목록(allowlist)에서만 선택한다.    		 ';', '|', '&&', '$()', 백틱, 개행 문자를 포함한 운영체제 명령어 삽입(OS command injection) 퍼징(fuzzing)과 정적 분석으로 입력→system/exec 흐름을 점검한다. 외부 스크립트·유틸리티 변경 시 호출부를 재검토하고, 실행 계정 권한을 최소화한다. BusyBox 기반 SBC의 웹/정비 인터페이스에서 셸 호출이 흔하므로 특히 금지하며, MCU 직렬 명령 해석기는 고정 명령 테이블로 구현한다.
    CWE-89 SQL 삽입(SQL injection)
    언어 무관
    삽입
    기본(Base)
    조건부: DB 사용    		 — DB 접근 계층을 매개변수화 질의(Prepared Statement) 또는 검증된 ORM으로 일원화하고, DB 계정 권한을 최소화한다. 구현(C·C++) SQLite 등 사용 시 sqlite3_prepare_v2()+sqlite3_bind_*()로 바인딩하고, sprintf로 질의문을 조합하지 않는다.
    구현(Java) PreparedStatement의 ? 바인딩을 사용하고, 정렬 열·테이블 이름 등 바인딩 불가 요소는 허용목록(allowlist)으로 매핑한다.    		 SQL 메타문자(' " -- ; /* */) 기반 퍼징(fuzzing), sqlmap 등 동적 점검, 정적 분석(오염 추적)을 수행한다. 스키마·질의 변경 시 동적 질의 신규 발생 여부를 코드 리뷰 체크리스트로 확인한다. SBC 내장 SQLite(운용기록·임무데이터 DB)에 적용한다. MCU에는 대개 해당하지 않는다.
    CWE-99 자원 삽입
    언어 무관
    삽입
    분류(Class)
    해당    		 — 포트 번호, 장치명, 소켓·파이프 이름 등 자원 식별자를 외부 입력으로 직접 지정하지 못하도록 고정값 또는 매핑 테이블로 설계한다. 구현(C·C++) 외부 입력을 자원 식별자로 사용할 때 허용 범위·허용목록(allowlist) 검증 후 사용한다(예: 포트 1024~65535 및 허용목록).
    구현(Java) Socket/ServerSocket 포트, 파일·클래스 이름에 외부 입력을 사용할 때 허용목록 검증을 적용한다.    		 경계값·허용 외 식별자를 입력하는 부정 시험과 정적 분석(오염 추적)으로 검증한다. 자원 매핑 테이블을 형상관리(configuration management) 항목으로 관리한다. CAN ID, UART 채널, GPIO/주변장치 번호를 외부 메시지로 지정하는 구조를 피하고, 인덱스 범위 검증 후 상수 테이블로 매핑한다.
    CWE-119 메모리 버퍼 오버플로우
    C·C++
    메모리 안전
    분류(Class)
    해당    		 R-01 · 원문 완화책(요구사항) 1건 버퍼 크기 상한을 인터페이스통제문서(ICD)에 정의하고, 안전한 문자열/버퍼 라이브러리와 길이 포함 API 사용을 설계 표준으로 지정한다. 구현(C·C++) strcpy/strcat/sprintf/gets를 금지하고 strncpy+종단 처리, snprintf, memcpy 전 길이 검증을 수행한다. 배열 인덱스는 사용 전 범위를 확인하고 C++은 std::array/std::vector::at(), std::string을 사용한다.
    구현(Java) 언어 차원에서 경계 검사가 수행되나 JNI·ByteBuffer 사용 시 인덱스/길이 검증을 하고 ArrayIndexOutOfBoundsException을 정상 흐름으로 쓰지 않는다.    		 정적 분석(경계 분석), 호스트 빌드에서 -fsanitize=address 동적 분석, 프로토콜·파일 입력 퍼징(fuzzing, AFL++/libFuzzer)을 수행한다. ICD·메시지 길이 변경 시 관련 버퍼 정의와 길이 검증을 영향분석하여 회귀 퍼징을 재수행한다. MMU가 없는 MCU·DSP는 ASLR이 없고 하드웨어 실행 금지도 MPU가 있고 설정했을 때만 쓸 수 있어, 오버플로가 제어 흐름 탈취나 오동작으로 이어지기 쉽다. 버퍼 오버플로는 경계 검사로 막고 경계 바이트나 -fstack-protector-strong 빌드로 확인한다. MPU(메모리 보호 장치) 스택 가드 영역, 스택 페인팅(stack painting), 링커 맵 기반 스택 사용량 분석은 스택 고갈을 잡는 수단으로 따로 적용한다.
    CWE-134 포맷 스트링(format string) 삽입
    C·C++
    메모리 안전
    기본(Base)
    해당    		 원문 완화책(요구사항) 1건 로그·출력 함수는 고정 포맷 스트링만 받는 래퍼 API로 설계한다. 구현(C·C++) printf(buf) 형태를 금지하고 printf("%s", buf)를 사용한다. 가변인자 래퍼에는 attribute((format(printf,n,m)))를 지정한다.
    구현(Java) String.format()/MessageFormat의 포맷 인자로 외부 입력을 사용하지 않는다.    		 -Wformat=2 -Wformat-security 경고를 오류로 처리하고, %n·%x 등을 포함한 입력 퍼징(fuzzing)을 수행한다. 로그 메시지 추가·변경 시 포맷 스트링 고정 여부를 코드 리뷰로 확인한다. 경량 printf 구현(newlib-nano, 벤더 printf)도 %n을 지원할 수 있으므로 동일 규칙을 적용하고, 디버그 UART 출력 함수에 특히 주의한다.
    CWE-190 정수형 오버플로우
    C
    잘못된 계산

    A-3. 보조 항목(197개 밖) 4개¶

    「보안약점 점검 목록(44개)」과 언어 뷰 153개를 합한 197개 밖이지만 무기체계 소프트웨어에 해당하는 약점 4개를 보조 항목으로 싣는다. 197개 집계에는 넣지 않고 따로 세며, 정의와 근거는 2.1에 있다. 적용성은 A-1·부록 B와 같은 규칙이며 네 항목 모두 그 기술을 쓸 때만 생기는 '조건부'다(부록 G-4-1 사용 기술 체크리스트). 단계별 지침은 그 CWE를 대상 CWE 목록에 둔 기준선 활동과 환경 지침이다. 도구 미지원 시 고유 대안은 규칙별 해설 '탐지 방법' 절과 같은 규칙(6.2)이다. 예시(나쁜 예·좋은 예)는 보안약점 점검 목록 44개와 같이 규칙별 해설 페이지에 싣는다. 이 판은 보조 항목에 점검 착안점을 싣지 않는다.
