    Out-of-bounds Read

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), Go, C, C++ · 기술: 산업제어시스템·운영기술(ICS/OT)
    원문 MITRE CWE-125 (CWE 5.0)

    한 줄 요약

    의도한 버퍼의 끝을 지나거나 시작보다 앞에서 데이터를 읽는 약점이다.

    설명(Description)¶

    제품이 의도한 버퍼의 끝을 지나서, 또는 버퍼의 시작보다 앞에서 데이터를 읽는 약점이다.

    원문(Description · Dimensions)

    The product reads data past the end, or before the beginning, of the intended buffer.

    Dimensions: Behavior-Type = Read; Resource-Type = Memory Buffer; Resource-Property = Out-of-bounds

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 메모리 읽기 공격자가 암호 키, 개인식별정보(PII), 메모리 주소 등 추가 공격에 쓰일 수 있는 비밀 값을 얻을 수 있다.
    기밀성 보호 메커니즘 우회 범위 밖 메모리에는 ASLR 등 보호 기법을 우회하는 데 쓸 수 있는 메모리 주소 같은 정보가 있을 수 있어, 별도 약점을 이용한 코드 실행 공격의 신뢰도를 높이는 데 쓰일 수 있다.
    가용성 서비스 거부: 비정상 종료·재시작 공격자가 버퍼 범위 밖 메모리를 읽게 만들어 세그멘테이션 오류나 비정상 종료를 일으킬 수 있으며, 이는 코드가 가변 길이 데이터를 읽으면서 문자열의 NUL 같은 센티널이 있어 읽기가 멈출 것이라 가정할 때 특히 일어나기 쉽다.
    기타 상황에 따라 다름 읽기 작업이 그 밖의 정의되지 않았거나 예상하지 못한 결과를 낼 수 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) 입력값 검증 모든 입력을 악의적이라고 가정하고, 명세에 엄격히 맞는 입력만 받는 허용목록('accept known good') 방식으로 검증해 맞지 않는 입력은 거부하거나 맞게 변환한다. 검증할 때는 길이·유형·허용 값 전체 범위·누락/추가 입력·구문·관련 필드 간 일관성·업무 규칙을 모두 고려한다(예: 'boat'는 영숫자만 있어 구문상 유효하지만 'red'·'blue' 같은 색상만 받는 필드라면 유효하지 않다). 악의적이거나 잘못된 입력을 찾는 방식(거부목록)에만 의존하지 않는다. 이 방식은 특히 코드 환경이 바뀔 때 원치 않는 입력을 하나 이상 놓치기 쉬워 검증이 우회될 수 있다. 다만 거부목록은 공격 탐지나 즉시 거부할 정도로 잘못된 입력을 가려내는 데는 쓸모가 있을 수 있다. 범위를 벗어난 읽기가 생길 가능성을 줄이려면 모든 길이 인자·버퍼 크기 계산·오프셋을 검증하고 올바르게 계산되는지 확인한다. 신뢰할 수 없는 입력에서 NUL 같은 센티널(sentinel) 문자에 의존하는 것을 특히 조심한다.
    원문

    Assume all input is malicious. Use an "accept known good" input validation strategy, i.e., use a list of acceptable inputs that strictly conform to specifications. Reject any input that does not strictly conform to specifications, or transform it into something that does.

    When performing input validation, consider all potentially relevant properties, including length, type of input, the full range of acceptable values, missing or extra inputs, syntax, consistency across related fields, and conformance to business rules. As an example of business rule logic, "boat" may be syntactically valid because it only contains alphanumeric characters, but it is not valid if the input is only expected to contain colors such as "red" or "blue."

    Do not rely exclusively on looking for malicious or malformed inputs. This is likely to miss at least one undesirable input, especially if the code's environment changes. This can give attackers enough room to bypass the intended validation. However, denylists can be useful for detecting potential attacks or determining which inputs are so malformed that they should be rejected outright.

    To reduce the likelihood of introducing an out-of-bounds read, ensure that you validate and ensure correct calculations for any length argument, buffer size calculation, or offset. Be especially careful of relying on a sentinel (i.e. special character such as NUL) in untrusted inputs.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. In the following code, the method retrieves a value from an array at a specific array index location that is given as an input parameter to the method

    Bad / C

    int getValueFromArray(int *array, int len, int index) {

  int value;

                             // check that the array index is less than the maximum

                             // length of the array

  if (index < len) {

                                     // get the value at the specified index of the array

    value = array[index];

  }

                             // if array index is invalid then output error message

                             // and return value indicating error

  else {
    printf("Value is: %d\n", array[index]);
    value = -1;
  }

  return value;

}

    However, this method only verifies that the given array index is less than the maximum length of the array but does not check for the minimum value (CWE-839). This will allow a negative value to be accepted as the input array index, which will result in reading data before the beginning of the buffer (CWE-127) and may allow access to sensitive memory. The input array index should be checked to verify that is within the maximum and minimum range required for the array (CWE-129). In this example the if statement should be modified to include a minimum range check, as shown below.

    Good / C

    ...

                     // check that the array index is within the correct

                     // range of values for the array

if (index >= 0 && index < len) {

...

    Example 2. In the following C/C++ example, the method processMessageFromSocket() will get a message from a socket, save the message into a buffer, and place the contents of the buffer into a structure that contains the message length and the message body. Then a for loop is used to copy the message body into a local character string, which will be passed to another method for processing.

    Bad / C

                     int processMessageFromSocket(int socket) {

           // initialize variable to represent the failure case by default

           int success = -1;

                     char buffer[BUFFER_SIZE];

           char message[MESSAGE_SIZE];

                     // get message from socket and store into buffer

                     // for clarity of this example, ignore the possibility that buffer > BUFFER_SIZE

           if (getMessage(socket, buffer, BUFFER_SIZE) > 0) {

                         // place contents of the buffer into message structure

                 ExMessage *msg = recastBuffer(buffer);

                         // copy message body into string for processing

                         int index;

                 for (index = 0; index < msg->msgLength; index++) {

                   message[index] = msg->msgBody[index];

                 }

                 message[index] = '\0';

                         // process message

                 success = processMessage(message);

           }

           return success;

         }

    However, the message length variable (msgLength) from the structure is used as the condition for ending the for loop without validating that msgLength accurately reflects the actual length of the message body (CWE-606). If msgLength indicates a length that is longer than the size of a message body (CWE-130), then this can result in a buffer over-read by reading past the end of the buffer (CWE-126).

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법(원문 효과성별): 높음: 퍼징(Fuzzing) / 보통: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: ARR30-C, ARR38-C, EXP39-C, STR31-C, STR32-C

    언어 뷰 항목의 단계별 지침 (적용성 판정 기준은 부록 B, 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 입력 데이터의 길이·형식을 사양에 정의하고, 경계 정보를 포인터와 함께 전달(포인터+길이)하는 인터페이스로 설계한다.
    구현 배열·버퍼 읽기 전 인덱스와 길이를 검증하고 NUL 종단되지 않은 데이터에 strlen을 사용하지 않으며 길이 지정 함수(memcmp, strnlen)를 사용한다.
    통합 및 시험 AddressSanitizer·Valgrind로 범위 밖 읽기를 탐지하고 libFuzzer/AFL++ 퍼징과 정적 분석 도구(예: Coverity, Polyspace)로 분석을 병행한다.
    유지보수 파서·프로토콜 처리 코드 변경 시 길이 필드 검증을 재점검하고, 정보 노출 사고 이력을 취약점 DB에 반영한다.
    임베디드 고려 MCU에서 범위 밖 읽기는 폴트 없이 인접 SFR·키 저장 영역 값을 읽어 정보 노출·오동작을 일으킬 수 있으므로 MPU 읽기 보호 영역 설정과 수신 프레임 길이 검증을 적용한다.

    기반 소프트웨어 (3건) BSP-05 DMA·캐시·인터럽트 안전, OSS-03 불필요 기능 제거와 격리, OSS-09 취약점 스캔과 퍼징
    개발 언어 (4건) LC-04 금지 문자열 함수 대체, LC-09 호스트 동적 분석과 타깃 코드 실행률, LCPP-04 배열·포인터 연산 대체, LCS-02 unsafe·P/Invoke 경계 최소화

    참조 요지
    CVE-2026-7320 널리 쓰이는 웹 브라우저의 오디오 처리기에서 범위를 벗어난 읽기가 일어나 전역 데이터 영역을 읽을 수 있다.
    원문

    Out-of-bounds read in audio processor used in a common web browser, allowing a read of the global data section
    CVE-2023-1018 Trusted Platform Module의 참조 구현 코드가 데이터 길이를 검사하지 않아 공격자가 버퍼 끝을 넘어 2바이트를 읽을 수 있다.
    원문

    The reference implementation code for a Trusted Platform Module does not implement length checks on data, allowing for an attacker to read 2 bytes past the end of a buffer.
    CVE-2020-11899 임베디드 시스템에 쓰이는 IP 스택에서 범위 밖 읽기가 일어난다(CISA KEV에 따르면 실제 악용됨).
    원문

    Out-of-bounds read in IP stack used in embedded systems, as exploited in the wild per CISA KEV.
    CVE-2014-0160 연쇄: "Heartbleed" 버그는 일관되지 않은 길이 매개변수(CWE-130)를 받아 범위 밖 읽기(CWE-126)를 일으키며, 반환된 메모리에 개인 키 같은 암호 키와 그 밖의 민감한 데이터가 들어 있을 수 있다.
    원문

    Chain: "Heartbleed" bug receives an inconsistent length parameter (CWE-130) enabling an out-of-bounds read (CWE-126), returning memory that could include private cryptographic keys and other sensitive data.
    CVE-2021-40985 HTML 변환 패키지에 버퍼 언더리드가 있어 비정상 종료를 일으킬 수 있다.
    원문

    HTML conversion package has a buffer under-read, allowing a crash
    CVE-2018-10887 연쇄: 예기치 않은 부호 확장(CWE-194)이 정수 오버플로(CWE-190)로 이어져 범위 밖 읽기(CWE-125)가 일어난다.
    원문

    Chain: unexpected sign extension (CWE-194) leads to integer overflow (CWE-190), causing an out-of-bounds read (CWE-125)
    CVE-2009-2523 연쇄: 제품이 입력 문자열이 NULL로 끝나지 않는 경우를 처리하지 않아(CWE-170) 버퍼 오버리드(CWE-125)나 힙 기반 버퍼 오버플로(CWE-122)가 일어난다.
    원문

    Chain: product does not handle when an input string is not NULL terminated (CWE-170), leading to buffer over-read (CWE-125) or heap-based buffer overflow (CWE-122).
    CVE-2018-16069 연쇄: 웹 브라우저 렌더링 엔진의 연속된 부동소수점 정밀도 오류(CWE-1339)가 범위 밖 읽기(CWE-125)를 일으켜 교차 출처 데이터에 접근하게 된다.
    원문

    Chain: series of floating-point precision errors (CWE-1339) in a web browser rendering engine causes out-of-bounds read (CWE-125), giving access to cross-origin data
