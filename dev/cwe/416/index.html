    Use After Free

    항목 내용
    추상화 수준 변형(Variant)
    상태 안정(Stable)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++
    원문 MITRE CWE-416 (CWE 5.0)

    한 줄 요약

    해제된 메모리를 다시 사용하거나 참조해, 재할당된 영역을 원래 포인터로 다루게 될 수 있는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 해제된 메모리를 다시 사용하거나 참조하는 약점이다. 이후 어느 시점에 그 메모리가 다시 할당되어 다른 포인터에 저장될 수 있고, 이때 원래 포인터는 새로 할당된 영역 내부의 어딘가를 가리키게 된다. 그 메모리는 새 포인터로 동작하는 코드의 '소유'이므로, 원래 포인터를 사용하는 모든 연산은 더 이상 유효하지 않다.

    원문(Description)

    The product reuses or references memory after it has been freed. At some point afterward, the memory may be allocated again and saved in another pointer, while the original pointer references a location somewhere within the new allocation. Any operations using the original pointer are no longer valid because the memory "belongs" to the code that operates on the new pointer.

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 메모리 수정 해당 메모리 영역이 다른 곳에서 할당되어 정상적으로 쓰이고 있으면, 이미 해제된 메모리를 사용할 때 유효한 데이터가 손상될 수 있다.
    가용성 서비스 거부: 비정상 종료·재시작 해제된 데이터를 사용한 뒤 청크 병합(chunk consolidation)이 일어나면, 잘못된 데이터가 청크 정보로 쓰여 프로세스가 비정상 종료될 수 있다.
    기밀성 메모리 읽기 해제된 메모리에 대한 읽기 연산은 때로 비정상 종료 대신 민감한 정보를 유출할 수 있다.
    무결성 / 기밀성 / 가용성 허가되지 않은 코드·명령 실행 청크 병합 전에 악의적인 데이터가 입력되면 임의 위치 쓰기(write-what-where) 프리미티브를 이용해 임의 코드를 실행할 수 있다. 예를 들어 C++에서 새로 할당된 데이터가 클래스를 담고 있으면 힙 데이터 곳곳에 여러 함수 포인터가 흩어져 있을 수 있고, 그중 하나를 유효한 셸코드의 주소로 덮어쓰면 임의 코드 실행이 가능하다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) 공격 표면 축소 포인터를 해제한 뒤에는 NULL로 설정하도록 한다. 단, 자료구조가 여러 개이거나 복잡하면 이 전략의 효용이 낮아질 수 있다.
    원문

    When freeing pointers, be sure to set them to NULL once they are freed. However, the utilization of multiple or complex data structures may lower the usefulness of this strategy.

    		 심층 방어(Defense in Depth) — 버그로 이 포인터에 접근하려 하면 NULL 역참조로 여전히 비정상 종료나 예상치 못한 동작이 생길 수 있지만, 코드 실행 위험은 줄이거나 없앤다.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 운용자 콘솔이 보낸 명령을 큐에서 꺼내 실행하고 확인 응답(ack)을 돌려준다(C). 센서 목록을 갱신하면서 선두 센서 정보를 화면에 띄운다(C++). 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct OpCommand {
    uint16_t seq;              /* 운용자 콘솔이 붙인 명령 순번 */
    char verb[12];
    struct OpCommand *next;
} OpCommand;

static OpCommand *queue_head, *queue_tail;

static int enqueue(uint16_t seq, const char *verb)
{
    OpCommand *c = calloc(1, sizeof *c);
    if (c == NULL) {
        return -1;
    }
    c->seq = seq;
    strncpy(c->verb, verb, sizeof c->verb - 1);
    if (queue_tail != NULL) {
        queue_tail->next = c;
    } else {
        queue_head = c;
    }
    queue_tail = c;
    return 0;
}

/* 맨 앞 명령을 실행하고 큐에서 꺼내 해제한 뒤 콘솔에 확인 응답을 보낸다 */
static void run_next(void)
{
    OpCommand *cmd = queue_head;
    if (cmd == NULL) {
        return;
    }
    queue_head = cmd->next;
    if (queue_head == NULL) {
        queue_tail = NULL;
    }
    printf("exec %s\n", cmd->verb);
    free(cmd);
    printf("ack seq=%u\n", (unsigned)cmd->seq);   /* 이미 해제한 메모리를 읽는다 */
}

int main(void)
{
    if (enqueue(41, "MODE-SAFE") != 0) {
        return 1;
    }
    run_next();
    return 0;
}

    명령 구조체를 해제한 뒤에 그 안의 순번(seq)을 읽어 확인 응답을 만든다. 해제된 메모리는 다른 할당에 다시 쓰일 수 있어 엉뚱한 순번을 보내거나 공격자가 넣은 값을 읽을 수 있다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct OpCommand {
    uint16_t seq;              /* 운용자 콘솔이 붙인 명령 순번 */
    char verb[12];
    struct OpCommand *next;
} OpCommand;

static OpCommand *queue_head, *queue_tail;

static int enqueue(uint16_t seq, const char *verb)
{
    OpCommand *c = calloc(1, sizeof *c);
    if (c == NULL) {
        return -1;
    }
    c->seq = seq;
    strncpy(c->verb, verb, sizeof c->verb - 1);
    if (queue_tail != NULL) {
        queue_tail->next = c;
    } else {
        queue_head = c;
    }
    queue_tail = c;
    return 0;
}

/* 맨 앞 명령을 실행하고 큐에서 꺼내 해제한 뒤 콘솔에 확인 응답을 보낸다 */
static void run_next(void)
{
    OpCommand *cmd = queue_head;
    if (cmd == NULL) {
        return;
    }
    queue_head = cmd->next;
    if (queue_head == NULL) {
        queue_tail = NULL;
    }
    printf("exec %s\n", cmd->verb);
    uint16_t done_seq = cmd->seq;      /* 해제 뒤에 쓸 값은 미리 꺼내 둔다 */
    free(cmd);
    cmd = NULL;                        /* 같은 변수를 실수로 다시 쓰지 않게 한다 */
    printf("ack seq=%u\n", (unsigned)done_seq);
}

int main(void)
{
    if (enqueue(41, "MODE-SAFE") != 0) {
        return 1;
    }
    run_next();
    return 0;
}

    해제 뒤에 필요한 값은 해제 전에 지역 변수로 꺼내 두고, 해제한 포인터는 바로 NULL로 바꿔 같은 변수를 실수로 다시 쓰는 일을 줄인다(LC-07). 같은 메모리를 가리키는 다른 포인터까지 막지는 못한다.

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: heap-use-after-free 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-416 Demonstrative Example 2(오류 처리에서 해제한 포인터를 다시 사용) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdio>
#include <vector>

struct Sensor {
    int id;
    double range_km;
};

// 센서 목록을 갱신하면서 선두 센서 정보를 화면에 띄운다
int main() {
    std::vector<Sensor> sensors;
    sensors.reserve(2);
    sensors.push_back({101, 12.5});
    const Sensor &lead = sensors.front();   // 첫 센서를 참조로 붙잡아 둔다

    sensors.push_back({102, 30.0});
    sensors.push_back({103, 41.2});        // 용량을 넘어 재할당: 예전 저장 공간은 해제된다

    std::printf("lead %d at %.1f km\n", lead.id, lead.range_km);  // 해제된 공간을 읽는다
    return 0;
}

    std::vector 원소에 대한 참조를 붙잡아 둔 채 push_back을 하면, 용량을 넘을 때 저장 공간이 재할당되면서 예전 공간이 해제된다. 그 뒤 참조로 읽으면 해제된 메모리를 읽는다.

    좋은 예

    #include <cstdio>
#include <vector>

struct Sensor {
    int id;
    double range_km;
};

// 센서 목록을 갱신하면서 선두 센서 정보를 화면에 띄운다
int main() {
    std::vector<Sensor> sensors;
    sensors.reserve(2);
    sensors.push_back({101, 12.5});
    const std::size_t lead_index = 0;     // 참조 대신 위치(또는 센서 번호)를 보관한다

    sensors.push_back({102, 30.0});
    sensors.push_back({103, 41.2});        // 재할당이 일어나도 위치 값은 그대로 유효하다

    const Sensor &lead = sensors[lead_index];  // 쓰기 직전에 다시 찾는다
    std::printf("lead %d at %.1f km\n", lead.id, lead.range_km);
    return 0;
}

    컨테이너를 고치는 동안에는 참조·포인터·반복자 대신 위치(또는 센서 번호)를 보관하고, 쓰기 직전에 다시 찾는다(LCPP-06).

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: heap-use-after-free 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-416 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(언어상 생기지 않음): C#의 관리 객체는 참조가 있는 동안 해제되지 않고, Dispose한 객체를 다시 쓰면 대개 ObjectDisposedException이 나지만 런타임이 보장하지는 않는다. unsafe 포인터, fixed 블록 밖으로 가져간 포인터, P/Invoke로 받은 비관리 메모리에서는 같은 문제가 생기므로 그 범위에는 C 예시와 C 지침을 적용한다(LCS-02).

    Java — 예시 없음(언어상 생기지 않음): Java는 참조가 남아 있는 객체를 가비지 수집기가 해제하지 않으므로 해제된 메모리를 읽는 일이 없다. 닫은 자원을 다시 쓰는 논리 오류는 예외로 드러나며, JNI로 부르는 네이티브 코드에는 C 예시를 적용한다(LJ-08).

    Python — 예시 없음(언어상 생기지 않음): Python은 참조가 남아 있는 객체를 해제하지 않으므로 해제된 메모리를 읽는 일이 없다. 닫은 파일·소켓을 다시 쓰는 논리 오류는 ValueError·OSError로 드러난다. ctypes 포인터가 가리키던 버퍼 객체가 먼저 사라지는 경우(Python 쪽 참조를 남기지 않은 경우)와 C 확장 모듈에서는 같은 문제가 생기므로 그 범위에는 C 예시와 C 지침을 적용한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. The following example demonstrates the weakness.

    Bad / C

    #include <stdio.h>
#include <unistd.h>
#define BUFSIZER1 512
#define BUFSIZER2 ((BUFSIZER1/2) - 8)
int main(int argc, char **argv) {
  char *buf1R1;
  char *buf2R1;
  char *buf2R2;
  char *buf3R2;
  buf1R1 = (char *) malloc(BUFSIZER1);
  buf2R1 = (char *) malloc(BUFSIZER1);
  free(buf2R1);
  buf2R2 = (char *) malloc(BUFSIZER2);
  buf3R2 = (char *) malloc(BUFSIZER2);
  strncpy(buf2R1, argv[1], BUFSIZER1-1);
  free(buf1R1);
  free(buf2R2);
  free(buf3R2);
}

    Example 2. The following code illustrates a use after free error:

    Bad / C

    char* ptr = (char*)malloc (SIZE);
if (err) {
  abrt = 1;
  free(ptr);
}
...
if (abrt) {
  logError("operation aborted before commit", ptr);
}

    When an error occurs, the pointer is immediately freed. However, this pointer is later incorrectly used in the logError function.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    (C·C++) DMA 버퍼를 전송 완료 인터럽트 전에 해제하거나 재사용하는 경로가 있는지 소유권 플래그와 완료 처리 순서를 확인한다. I-09·I-07 [보완]
    • ① 원문 탐지 방법(원문 효과성별): 높음: 퍼징(Fuzzing) / 보통: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: MEM00-C, MEM01-C, MEM30-C
