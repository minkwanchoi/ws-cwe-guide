    Incorrect Calculation of Buffer Size

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++
    원문 MITRE CWE-131 (CWE 5.0)

    한 줄 요약

    버퍼를 할당할 때 쓸 크기를 올바르게 계산하지 않는 약점이다.

    설명(Description)¶

    제품이 버퍼를 할당할 때 사용할 크기를 올바르게 계산하지 않는 약점이다.

    원문(Description)

    The product does not correctly calculate the size to be used when allocating a buffer.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 가용성 / 기밀성 서비스 거부: 비정상 종료·재시작 / 허가되지 않은 코드·명령 실행 / 메모리 읽기 / 메모리 수정 잘못된 계산이 메모리 할당에 쓰이면 예상보다 작거나 큰 버퍼가 만들어질 수 있고, 예상보다 작으면 범위 밖 읽기·쓰기(CWE-119)로 이어져 비정상 종료, 임의 코드 실행, 민감한 데이터 노출을 일으킬 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 16건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해야 한다(CWE-602 방지). 공격자는 검사 뒤에 값을 바꾸거나 클라이언트에서 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있기 때문이다.
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.

    		 —
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 피하기 쉽게 하는 구조를 제공하는 검증된 라이브러리나 프레임워크를 사용한다 [REF-1482]. 예상치 못한 결과 없이 숫자를 다루기 쉽게 하는 라이브러리나 버퍼 크기를 자동으로 추적하는 버퍼 할당 루틴을 쓰며, 예로 SafeInt(C++)나 IntegerLib(C 또는 C++) 같은 안전한 정수 처리 패키지가 있다 [REF-106].
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid [REF-1482].

    Use libraries or frameworks that make it easier to handle numbers without unexpected consequences, or buffer allocation routines that automatically track buffer size.

    Examples include safe integer handling packages such as SafeInt (C++) or IntegerLib (C or C++). [REF-106]

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 실행 환경 강화 작업에 필요한 최소 권한으로 코드를 실행하고 [REF-76], 가능하면 한 작업에만 쓰는 제한된 권한의 격리된 계정을 만들어 공격이 성공해도 나머지 소프트웨어나 환경에 바로 접근하지 못하게 한다(예: 데이터베이스 애플리케이션은 특히 일상 운영에서 데이터베이스 관리자 권한으로 실행할 필요가 거의 없다). (유지보수 단계에도 해당)
    원문

    Run your code using the lowest privileges that are required to accomplish the necessary tasks [REF-76]. If possible, create isolated accounts with limited privileges that are only used for a single task. That way, a successful attack will not immediately give the attacker access to the rest of the software or its environment. For example, database applications rarely need to run as the database administrator, especially in day-to-day operations.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 입력을 변환·인코딩하기 위해 버퍼를 할당할 때는 가능한 가장 큰 인코딩을 처리할 만큼 메모리를 할당한다. 예를 들어 HTML 엔터티 인코딩에서 "&" 문자를 "&amp;"로 바꾸는 루틴이라면 출력 버퍼는 입력 버퍼의 최소 5배 크기여야 한다.
    원문

    When allocating a buffer for the purpose of transforming, converting, or encoding an input, allocate enough memory to handle the largest possible encoding. For example, in a routine that converts "&" characters to "&amp;" for HTML entity encoding, the output buffer needs to be at least 5 times as large as the input buffer.

    		 —
    구현(Implementation) — 프로그래밍 언어의 내부 표현과 수치 계산의 상호작용을 이해한다(CWE-681). 바이트 크기 차이, 정밀도, 부호 있음/없음 구분, 절단, 형 변환과 캐스팅, 'not-a-number' 계산, 표현 범위보다 너무 크거나 작은 수의 처리 방식에 주의하고 [REF-7], 32비트·64비트 등 수 표현에 영향을 줄 수 있는 차이도 고려한다.
    원문

    Understand the programming language's underlying representation and how it interacts with numeric calculation (CWE-681). Pay close attention to byte size discrepancies, precision, signed/unsigned distinctions, truncation, conversion and casting between types, "not-a-number" calculations, and how the language handles numbers that are too large or too small for its underlying representation. [REF-7]

    Also be careful to account for 32-bit, 64-bit, and other potential differences that may affect the numeric representation.

    		 —
    구현(Implementation) 입력값 검증 모든 숫자 입력이 예상 범위 안에 있는지 확인하는 입력값 검증을 수행하고, 입력이 예상 범위의 최솟값과 최댓값 요구 조건을 모두 충족하도록 강제한다.
    원문

    Perform input validation on any numeric input by ensuring that it is within the expected range. Enforce that the input meets both the minimum and maximum requirements for the expected range.

    		 —
    구현(Implementation) — 크기 필드 뒤에 원시 데이터가 오는 구조화된 입력 데이터를 처리할 때 크기 필드와 실제 데이터 크기 사이의 불일치를 찾아 해소한다(CWE-130).
    원문

    When processing structured incoming data containing a size field followed by raw data, identify and resolve any inconsistencies between the size field and the actual size of the data (CWE-130).

    		 —
    구현(Implementation) — 문자열의 NUL 바이트처럼 데이터 구조의 끝을 표시하는 센티널(sentinel)을 쓰는 메모리를 할당할 때는, 할당해야 할 전체 메모리 양을 계산할 때 센티널도 포함한다.
    원문

    When allocating memory that uses sentinels to mark the end of a data structure - such as NUL bytes in strings - make sure you also include the sentinel in your calculation of the total amount of memory that must be allocated.

    		 —
    구현(Implementation) — strcpy를 strncpy로 바꾸는 것처럼, 길이 제한 없는 복사 함수를 길이 인자를 받는 대응 함수로 바꾼다. 그런 함수가 없으면 만든다.
    원문

    Replace unbounded copy functions with analogous functions that support length arguments, such as strcpy with strncpy. Create these if they are not available.

    		 보통(Moderate) — 이 방법도 경계값 오류(off-by-one, CWE-193)나 버퍼 길이 계산 오류(CWE-131) 같은 계산 오류에 여전히 취약하고, 잠재적 오버플로 문제만 다루므로 자원 소모·고갈 문제는 여전히 생길 수 있다.
    구현(Implementation) — CWE-467을 피하려면 적절한 데이터 형식에 sizeof()를 사용한다.
    원문

    Use sizeof() on the appropriate data type to avoid CWE-467.

    		 —
    구현(Implementation) — 원하는 동작에 맞는 형식을 사용한다. 예를 들어 C/C++에서는 높이·너비 등 수량 관련 값처럼 절대 음수가 될 수 없는 값에만 부호 없는(unsigned) 형식을 쓰며, 이렇게 하면 검증이 단순해지고 예상하지 못한 형 변환에 따른 의외의 결과가 줄어든다.
    원문

    Use the appropriate type for the desired action. For example, in C/C++, only use unsigned types for values that could never be negative, such as height, width, or other numbers related to quantity. This will simplify validation and will reduce surprises related to unexpected casting.

    		 —
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 일부 컴파일러나 컴파일러 확장이 제공하는 자동 버퍼 오버플로 탐지 기능을 쓴다. 예로 Microsoft Visual Studio의 /GS 플래그, Fedora/Red Hat의 FORTIFY_SOURCE GCC 플래그, StackGuard, ProPolice가 있으며 카나리 기반 탐지와 범위·인덱스 검사 등을 제공한다(카나리 기반 탐지는 D3FEND D3-SFCV [REF-1334] 참고). (유지보수 단계에도 해당)
    원문

    Use automatic buffer overflow detection mechanisms that are offered by certain compilers or compiler extensions. Examples include: the Microsoft Visual Studio /GS flag, Fedora/Red Hat FORTIFY_SOURCE GCC flag, StackGuard, and ProPolice, which provide various mechanisms including canary-based detection and range/index checking.

    D3-SFCV (Stack Frame Canary Validation) from D3FEND [REF-1334] discusses canary-based detection in detail.

    		 심층 방어(Defense in Depth) — 이 기능들은 일부 유형의 오버플로만 탐지하므로 반드시 완전한 해결책은 아니다. 또한 대개 애플리케이션을 종료하는 방식으로 대응하므로 결과는 여전히 서비스 거부다.
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 프로그램의 실행 파일과 라이브러리를 메모리에 무작위로 배치하는 기능이나 확장을 써서 실행·컴파일한다. 주소를 예측할 수 없게 되어 공격자가 악용할 코드로 안정적으로 점프하는 것을 막을 수 있다. 예로 ASLR(Address Space Layout Randomization) [REF-58] [REF-60]과 PIE(Position-Independent Executables) [REF-64]가 있다. 가져온 모듈도 기본 메모리 주소가 다른 모듈과 겹치면 무작위로 만든 주소로 재배치될 수 있다(Windows의 rebasing, Linux의 prelinking [REF-1332]). 단, 라이브러리용 ASLR은 실행 시 라이브러리를 재배치해야 해서 prelink의 목적을 없애므로 prelink와 함께 쓸 수 없다. 자세한 내용은 D3FEND의 D3-SAOR(Segment Address Offset Randomization) [REF-1335]에 있다. (유지보수 단계에도 해당)
    원문

    Run or compile the software using features or extensions that randomly arrange the positions of a program's executable and libraries in memory. Because this makes the addresses unpredictable, it can prevent an attacker from reliably jumping to exploitable code.

    Examples include Address Space Layout Randomization (ASLR) [REF-58] [REF-60] and Position-Independent Executables (PIE) [REF-64]. Imported modules may be similarly realigned if their default memory addresses conflict with other modules, in a process known as "rebasing" (for Windows) and "prelinking" (for Linux) [REF-1332] using randomly generated addresses. ASLR for libraries cannot be used in conjunction with prelink since it would require relocating the libraries at run-time, defeating the whole purpose of prelinking.

    For more information on these techniques see D3-SAOR (Segment Address Offset Randomization) from D3FEND [REF-1335].

    		 심층 방어(Defense in Depth) — 이 기법들은 완전한 해결책이 아니다. 예를 들어 익스플로잇은 코드 실행의 신뢰성을 높이려고 메모리 주소를 노출하는 버그를 흔히 이용하며 [REF-1337], 부채널 공격으로 ASLR을 우회할 수 있음도 밝혀졌다 [REF-1333].
    구현(Implementation) 컴파일·빌드 강화 컴파일러 경고를 꼼꼼히 살펴 메모리 연산의 부호 있음/없음 불일치나 초기화되지 않은 변수 사용처럼 보안 영향이 있을 수 있는 문제를 없앤다. 약점이 악용되는 일이 드물더라도 한 번의 실패가 시스템 전체의 침해로 이어질 수 있다.
    원문

    Examine compiler warnings closely and eliminate problems with potential security implications, such as signed / unsigned mismatch in memory operations, or use of uninitialized variables. Even if the weakness is rarely exploitable, a single failure may lead to the compromise of the entire system.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 5건)

    Example 1. The following code allocates memory for a maximum number of widgets. It then gets a user-specified number of widgets, making sure that the user does not request too many. It then initializes the elements of the array using InitializeWidget(). Because the number of widgets can vary for each request, the code inserts a NULL pointer to signify the location of the last widget.

    Bad / C

    int i;
unsigned int numWidgets;
Widget **WidgetList;

numWidgets = GetUntrustedSizeValue();
if ((numWidgets == 0) || (numWidgets > MAX_NUM_WIDGETS)) {
  ExitError("Incorrect number of widgets requested!");
}
WidgetList = (Widget **)malloc(numWidgets * sizeof(Widget *));
printf("WidgetList ptr=%p\n", WidgetList);
for(i=0; i<numWidgets; i++) {
  WidgetList[i] = InitializeWidget();
}
WidgetList[numWidgets] = NULL;
showWidgets(WidgetList);

    However, this code contains an off-by-one calculation error (CWE-193). It allocates exactly enough space to contain the specified number of widgets, but it does not include the space for the NULL pointer. As a result, the allocated buffer is smaller than it is supposed to be (CWE-131). So if the user ever requests MAX_NUM_WIDGETS, there is an out-of-bounds write (CWE-787) when the NULL is assigned. Depending on the environment and compilation settings, this could cause memory corruption.

    Example 2. The following image processing code allocates a table for images.

    Bad / C

    img_t table_ptr; /*struct containing img data, 10kB each*/
int num_imgs;
...
num_imgs = get_num_imgs();
table_ptr = (img_t*)malloc(sizeof(img_t)*num_imgs);
...

    This code intends to allocate a table of size num_imgs, however as num_imgs grows large, the calculation determining the size of the list will eventually overflow (CWE-190). This will result in a very small list to be allocated instead. If the subsequent code operates on the list as if it were num_imgs long, it may result in many types of out-of-bounds problems (CWE-119).

    Example 3. This example applies an encoding procedure to an input string and stores it into a buffer.

    Bad / C

    char * copy_input(char *user_supplied_string){

  int i, dst_index;
  char *dst_buf = (char*)malloc(4*sizeof(char) * MAX_SIZE);
  if ( MAX_SIZE <= strlen(user_supplied_string) ){
    die("user string too long, die evil hacker!");
  }
  dst_index = 0;
  for ( i = 0; i < strlen(user_supplied_string); i++ ){

    if( '&' == user_supplied_string[i] ){
      dst_buf[dst_index++] = '&';
      dst_buf[dst_index++] = 'a';
      dst_buf[dst_index++] = 'm';
      dst_buf[dst_index++] = 'p';
      dst_buf[dst_index++] = ';';
    }
    else if ('<' == user_supplied_string[i] ){

                                             /* encode to &lt; */

    }
    else dst_buf[dst_index++] = user_supplied_string[i];

  }
  return dst_buf;

}

    The programmer attempts to encode the ampersand character in the user-controlled string, however the length of the string is validated before the encoding procedure is applied. Furthermore, the programmer assumes encoding expansion will only expand a given character by a factor of 4, while the encoding of the ampersand expands by 5. As a result, when the encoding procedure expands the string it is possible to overflow the destination buffer if the attacker provides a string of many ampersands.

    Example 4. The following code is intended to read an incoming packet from a socket and extract one or more headers.

    Bad / C

    DataPacket *packet;
int numHeaders;
PacketHeader *headers;

sock=AcceptSocketConnection();
ReadPacket(packet, sock);
numHeaders =packet->headers;

if (numHeaders > 100) {
  ExitError("too many headers!");
}
headers = malloc(numHeaders * sizeof(PacketHeader);
ParsePacketHeaders(packet, headers);

    The code performs a check to make sure that the packet does not contain too many headers. However, numHeaders is defined as a signed int, so it could be negative. If the incoming packet specifies a value such as -3, then the malloc calculation will generate a negative number (say, -300 if each header can be a maximum of 100 bytes). When this result is provided to malloc(), it is first converted to a size_t type. This conversion then produces a large value such as 4294966996, which may cause malloc() to fail or to allocate an extremely large amount of memory (CWE-195). With the appropriate negative numbers, an attacker could trick malloc() into using a very small positive number, which then allocates a buffer that is much smaller than expected, potentially leading to a buffer overflow.

    Example 5. The following code attempts to save three different identification numbers into an array. The array is allocated from memory using a call to malloc().

    Bad / C

    int *id_sequence;

                     /* Allocate space for an array of three ids. */

id_sequence = (int*) malloc(3);
if (id_sequence == NULL) exit(1);

                     /* Populate the id array. */

id_sequence[0] = 13579;
id_sequence[1] = 24680;
id_sequence[2] = 97531;

    The problem with the code above is the value of the size parameter used during the malloc() call. It uses a value of '3' which by definition results in a buffer of three bytes to be created. However the intention was to create a buffer that holds three ints, and in C, each int requires 4 bytes worth of memory, so an array of 12 bytes is needed, 4 bytes for each int. Executing the above code could result in a buffer overflow as 12 bytes of data is being saved into 3 bytes worth of allocated space. The overflow would occur during the assignment of id_sequence[0] and would continue with the assignment of id_sequence[1] and id_sequence[2].

    The malloc() call could have used '3*sizeof(int)' as the value for the size parameter in order to allocate the correct amount of space required to store the three ints.

    관찰 사례(원문 Observed Examples 17건 중 앞의 8건, 요지는 한글 요약이고 원문은 접은 상자)

    참조 요지
    CVE-2025-46687 연쇄: Javascript 엔진 코드가 길이를 검사하지 않아(CWE-1284) 정수 오버플로(CWE-190)가 일어나고, 이 때문에 예상보다 작은 버퍼가 할당되어(CWE-131) 힙 기반 버퍼 오버플로(CWE-122)가 발생한다.
    원문

    Chain: Javascript engine code does not perform a length check (CWE-1284) leading to integer overflow (CWE-190) causing allocation of smaller buffer than expected (CWE-131) resulting in a heap-based buffer overflow (CWE-122)
    CVE-2025-27363 글꼴 렌더링 라이브러리가 signed short 값을 unsigned long에 대입하는 경우를 제대로 처리하지 않아(CWE-195) 정수 랩어라운드(CWE-190)가 일어나고, 버퍼가 너무 작아져(CWE-131) 범위 밖 쓰기(CWE-787)로 이어진다.
    원문

    Font rendering library does not properly handle assigning a signed short value to an unsigned long (CWE-195), leading to an integer wraparound (CWE-190), causing too small of a buffer (CWE-131), leading to an out-of-bounds write (CWE-787).
    CVE-2020-17087 연쇄: 정수 절단(CWE-197)으로 버퍼가 작게 할당되어(CWE-131) 커널 풀에서 범위 밖 쓰기(CWE-787)가 일어난다(CISA KEV에 따르면 실제 악용됨).
    원문

    Chain: integer truncation (CWE-197) causes small buffer allocation (CWE-131) leading to out-of-bounds write (CWE-787) in kernel pool, as exploited in the wild per CISA KEV.
    CVE-2004-1363 치환 오버플로: 길이 검사를 한 뒤에 확장되는 환경 변수를 이용한 버퍼 오버플로다.
    원문

    substitution overflow: buffer overflow using environment variables that are expanded after the length check is performed
    CVE-2004-0747 치환 오버플로: 환경 변수 확장을 이용한 버퍼 오버플로다.
    원문

    substitution overflow: buffer overflow using expansion of environment variables
    CVE-2005-2103 치환 오버플로: 많은 수의 치환 문자열을 이용한 버퍼 오버플로다.
    원문

    substitution overflow: buffer overflow using a large number of substitution strings
    CVE-2005-3120 변환 오버플로: 제품이 들어오는 데이터에 이스케이프 문자를 덧붙이지만 버퍼 길이에 이를 반영하지 않는다.
    원문

    transformation overflow: product adds extra escape characters to incoming data, but does not account for them in the buffer length
    CVE-2003-0899 변환 오버플로: ">"를 "&gt;" 등으로 확장할 때 버퍼 오버플로가 일어난다.
    원문

    transformation overflow: buffer overflow when expanding ">" to "&gt;", etc.
