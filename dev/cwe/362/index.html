    Concurrent Execution using Shared Resource with Improper Synchronization

    항목 내용

    적용 플랫폼 언어: C, C++, Java, Python · 기술: 모바일(Mobile), 산업제어시스템·운영기술(ICS/OT)
    원문 MITRE CWE-362 (CWE 5.0)

    한 줄 요약

    공유 자원에 일시적 배타 접근이 필요한 동시 실행 코드에서, 다른 코드가 그 자원을 바꿀 수 있는 시간 틈이 있는 약점이다.

    설명(Description)¶

    제품에 공유 자원에 대한 일시적·배타적 접근이 필요한 동시 실행 코드 시퀀스가 있지만, 동시에 실행되는 다른 코드 시퀀스가 그 공유 자원을 바꿀 수 있는 시간 틈(timing window)이 있는 약점이다.

    기술 해설(Technical Nuance)

    경쟁조건은 서로 밀접한 다음 속성을 위반한다.

    • 배타성(exclusivity): 코드 시퀀스에 공유 자원에 대한 배타적 접근 권한이 주어진다. 곧 원래 시퀀스의 실행이 끝나기 전에는 다른 코드 시퀀스가 공유 자원의 속성을 바꿀 수 없다.

    • 원자성(atomicity): 코드 시퀀스가 동작상 원자적이다. 곧 다른 스레드나 프로세스가 같은 자원에 대해 같은 명령어 시퀀스(또는 그 일부)를 동시에 실행할 수 없다.

    '간섭 코드 시퀀스'가 여전히 공유 자원에 접근할 수 있어 배타성을 위반하면 경쟁조건이 존재한다.

    간섭 코드 시퀀스는 '신뢰된' 것일 수도 '신뢰되지 않은' 것일 수도 있다. 신뢰된 간섭 코드 시퀀스는 제품 안에 있어 공격자가 수정할 수 없고 간접적으로만 호출될 수 있다. 신뢰되지 않은 간섭 코드 시퀀스는 공격자가 직접 작성할 수 있고 대개 취약한 제품 밖에 있다.

    배경(Background Details)

    경쟁조건은 동시 실행 환경에서 생기며 사실상 코드 시퀀스의 속성이다. 상황에 따라 코드 시퀀스는 함수 호출, 소수의 명령어, 일련의 프로그램 호출 등의 형태일 수 있다.

    원문(Description · Technical Nuance · Background Details)

    The product contains a concurrent code sequence that requires temporary, exclusive access to a shared resource, but a timing window exists in which the shared resource can be modified by another code sequence operating concurrently.

    A race condition violates these properties, which are closely related:

    - Exclusivity: the code sequence is given exclusive access to the shared resource, i.e., no other code sequence can modify properties of the shared resource before the original sequence has completed execution.

    - Atomicity: the code sequence is behaviorally atomic, i.e., no other thread or process can concurrently execute the same sequence of instructions (or a subset) against the same resource.

    A race condition exists when an "interfering code sequence" can still access the shared resource, violating exclusivity.

    The interfering code sequence could be "trusted" or "untrusted." A trusted interfering code sequence occurs within the product; it cannot be modified by the attacker, and it can only be invoked indirectly. An untrusted interfering code sequence can be authored directly by the attacker, and typically it is external to the vulnerable product.

    A race condition occurs within concurrent environments, and it is effectively a property of a code sequence. Depending on the context, a code sequence may be in the form of a function call, a small number of instructions, a series of program invocations, etc.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 —
    구현(Implementation) 구현 프로그래머는 일부 코드 시퀀스가 너무 빨리 실행되어 간섭 코드 시퀀스의 영향을 받지 않는다고 가정할 수 있다. 실제로 그렇지 않으면 원자성이 깨진다. 예를 들어 단일 "x++" 문은 코드 수준에서는 원자적으로 보여도 명령어 수준에서는 읽기(x의 원래 값), 계산(x+1), 쓰기(결과를 x에 저장)로 이루어져 원자적이지 않다.

    영향(Common Consequences)¶

    영역 영향 설명
    가용성 서비스 거부: 자원 소모(CPU) / 서비스 거부: 자원 소모(메모리) / 서비스 거부: 자원 소모(기타) 경쟁조건으로 자원 정리 루틴을 우회하거나 초기화 루틴을 여러 번 유발할 수 있으면 자원 고갈로 이어질 수 있다.
    가용성 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 불안정 경쟁조건으로 여러 제어 흐름이 한 자원에 동시에 접근할 수 있으면 제품이 예상하지 못한 상태가 되어 비정상 종료될 수도 있다.
    기밀성 / 무결성 파일·디렉터리 읽기 / 애플리케이션 데이터 읽기 경쟁조건이 예측 가능한 자원 이름, 느슨한 권한과 결합되면 공격자가 기밀 데이터를 덮어쓰거나 접근할 수 있다(CWE-59).
    접근 통제 허가되지 않은 코드·명령 실행 / 권한 획득 또는 신원 도용 / 보호 메커니즘 우회 사용자 인증 여부 기록이나 외부인이 영향을 주어서는 안 되는 중요한 상태 정보 수정처럼, 기대한 동기화가 보안에 중요한 코드에 있으면 보안상 영향이 생길 수 있다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 지원하는 언어에서는 동기화 기본 요소(synchronization primitive)를 사용하되, 성능 영향을 줄이도록 임계 코드에만 적용한다.
    원문

    In languages that support it, use synchronization primitives. Only wrap these around critical code to minimize the impact on performance.
    아키텍처·설계(Architecture and Design) — Spring의 데이터 접근 추상화 같은 스레드 안전 기능을 사용한다.
    원문

    Use thread-safe capabilities such as the data access abstraction in Spring.
    아키텍처·설계(Architecture and Design) — 공유 자원 사용을 최소화해 제어 흐름의 복잡성을 가능한 한 없애고 예상하지 못한 상황이 생길 가능성을 줄인다. 이렇게 하면 필요한 동기화의 양도 줄고, 공격자가 임계구역을 반복 유발할 수 있는 서비스 거부(CWE-400)의 가능성을 줄이는 데 도움이 될 수도 있다.
    원문

    Minimize the usage of shared resources in order to remove as much complexity as possible from the control flow and to reduce the likelihood of unexpected conditions occurring.

    Additionally, this will minimize the amount of synchronization necessary and may even help to reduce the likelihood of a denial of service where an attacker may be able to repeatedly trigger a critical section (CWE-400).
    아키텍처·설계(Architecture and Design) / 운용(Operation) 실행 환경 강화 작업에 필요한 최소 권한으로 코드를 실행하고 [REF-76], 가능하면 한 작업에만 쓰는 제한된 권한의 격리된 계정을 만들어 공격이 성공해도 나머지 소프트웨어나 환경에 바로 접근하지 못하게 한다(예: 데이터베이스 애플리케이션은 특히 일상 운영에서 데이터베이스 관리자 권한으로 실행할 필요가 거의 없다). (유지보수 단계에도 해당)
    원문

    Run your code using the lowest privileges that are required to accomplish the necessary tasks [REF-76]. If possible, create isolated accounts with limited privileges that are only used for a single task. That way, a successful attack will not immediately give the attacker access to the rest of the software or its environment. For example, database applications rarely need to run as the database administrator, especially in day-to-day operations.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 멀티스레딩에서 공유 변수를 다룰 때는 스레드 안전 함수만 사용한다.
    원문

    When using multithreading and operating on shared variables, only use thread-safe functions.
    구현(Implementation) — 공유 변수에는 원자적 연산을 사용한다. "x++"처럼 무해해 보이는 구문에 주의한다. 이런 구문은 코드 수준에서는 원자적으로 보일 수 있지만 명령어 수준에서는 읽기·계산·쓰기로 이루어져 원자적이지 않다.
    원문

    Use atomic operations on shared variables. Be wary of innocent-looking constructs such as "x++". This may appear atomic at the code layer, but it is actually non-atomic at the instruction layer, since it involves a read, followed by a computation, followed by a write.
    구현(Implementation) — 가능하면 뮤텍스(mutex)를 사용하되, CWE-412 같은 관련 약점을 피하도록 주의한다.
    원문

    Use a mutex if available, but be sure to avoid related weaknesses such as CWE-412.
    구현(Implementation) — 동기화 부담을 피하려다 생기는 이중 검사 잠금(double-checked locking, CWE-609) 등의 구현 오류를 피한다.
    원문

    Avoid double-checked locking (CWE-609) and other implementation errors that arise when trying to avoid the overhead of synchronization.
    구현(Implementation) — 코드의 임계 부분에서는 인터럽트나 시그널을 비활성화하되, 그 코드가 긴 루프나 무한 루프에 빠지지 않게 한다.
    원문

    Disable interrupts or signals over critical parts of the code, but also make sure that the code does not go into a large or infinite loop.
    구현(Implementation) — 예상하지 못한 컴파일러 최적화나 재배치를 피하도록 중요한 변수에 volatile 형 한정자를 사용한다. 이것이 동기화 문제를 꼭 해결하지는 않지만 도움이 될 수 있다.
    원문

    Use the volatile type modifier for critical variables to avoid unexpected compiler optimization or reordering. This does not necessarily solve the synchronization problem, but it can help.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 3건)

    Example 1. This code could be used in an e-commerce application that supports transfers between accounts. It takes the total amount of the transfer, sends it to the new account, and deducts the amount from the original account.

    Bad / Perl

    $transfer_amount = GetTransferAmount();
$balance = GetBalanceFromDatabase();

if ($transfer_amount < 0) {
  FatalError("Bad Transfer Amount");
}
$newbalance = $balance - $transfer_amount;
if (($balance - $transfer_amount) < 0) {
  FatalError("Insufficient Funds");
}
SendNewBalanceToDatabase($newbalance);
NotifyUser("Transfer of $transfer_amount succeeded.");
NotifyUser("New balance: $newbalance");

    A race condition could occur between the calls to GetBalanceFromDatabase() and SendNewBalanceToDatabase().

    Suppose the balance is initially 100.00. An attack could be constructed as follows:

    Attack / Pseudocode

    In the following pseudocode, the attacker makes two simultaneous calls of the program, CALLER-1 and CALLER-2. Both callers are for the same user account.
CALLER-1 (the attacker) is associated with PROGRAM-1 (the instance that handles CALLER-1). CALLER-2 is associated with PROGRAM-2.
CALLER-1 makes a transfer request of 80.00.
PROGRAM-1 calls GetBalanceFromDatabase and sets $balance to 100.00
PROGRAM-1 calculates $newbalance as 20.00, then calls SendNewBalanceToDatabase().
Due to high server load, the PROGRAM-1 call to SendNewBalanceToDatabase() encounters a delay.
CALLER-2 makes a transfer request of 1.00.
PROGRAM-2 calls GetBalanceFromDatabase() and sets $balance to 100.00. This happens because the previous PROGRAM-1 request was not processed yet.
PROGRAM-2 determines the new balance as 99.00.
After the initial delay, PROGRAM-1 commits its balance to the database, setting it to 20.00.
PROGRAM-2 sends a request to update the database, setting the balance to 99.00

    At this stage, the attacker should have a balance of 19.00 (due to 81.00 worth of transfers), but the balance is 99.00, as recorded in the database.

    To prevent this weakness, the programmer has several options, including using a lock to prevent multiple simultaneous requests to the web application, or using a synchronization mechanism that includes all the code between GetBalanceFromDatabase() and SendNewBalanceToDatabase().

    Example 2. The following function attempts to acquire a lock in order to perform operations on a shared resource.

    Bad / C

    void f(pthread_mutex_t *mutex) {

  pthread_mutex_lock(mutex);

                             /* access shared resource */

  pthread_mutex_unlock(mutex);

}

    However, the code does not check the value returned by pthread_mutex_lock() for errors. If pthread_mutex_lock() cannot acquire the mutex for any reason, the function may introduce a race condition into the program and result in undefined behavior.

    In order to avoid data races, correctly written programs must check the result of thread synchronization functions and appropriately handle all errors, either by attempting to recover from them or reporting them to higher levels.

    Good / C

    int f(pthread_mutex_t *mutex) {

  int result;

  result = pthread_mutex_lock(mutex);
  if (0 != result)
    return result;

                             /* access shared resource */

  return pthread_mutex_unlock(mutex);

}

    Example 3. Suppose a processor's Memory Management Unit (MMU) has 5 other shadow MMUs to distribute its workload for its various cores. Each MMU has the start address and end address of "accessible" memory. Any time this accessible range changes (as per the processor's boot status), the main MMU sends an update message to all the shadow MMUs.

    Suppose the interconnect fabric does not prioritize such "update" packets over other general traffic packets. This introduces a race condition. If an attacker can flood the target with enough messages so that some of those attack packets reach the target before the new access ranges gets updated, then the attacker can leverage this scenario.
