    Improper Restriction of Operations within the Bounds of a Memory Buffer

    항목 내용
    추상화 수준 분류(Class)
    상태 안정(Stable)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    MITRE 매핑 권고 권장하지 않음(Discouraged) — 결과를 기록할 때는 더 구체적인 CWE를 쓴다(MITRE 권고 CWE: CWE-787·CWE-125·CWE-825)
    원문(Mapping Notes)

    Rationale: CWE-119 is commonly misused in low-information vulnerability reports when lower-level CWEs could be used instead, or when more details about the vulnerability are available.

    Comments: Look at CWE-119's children and its descendants, which should generally be a better fit. Since this issue is resultant from other weaknesses, conduct root cause analysis to determine the error(s) that led to operations outside of intended buffer boundaries.
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++, Assembly · 기술 무관
    원문 MITRE CWE-119 (CWE 5.0)

    한 줄 요약

    메모리 버퍼를 다루면서 버퍼의 의도된 경계 밖 메모리 위치를 읽거나 쓰는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 메모리 버퍼에 대해 연산을 수행하면서 버퍼의 의도된 경계 밖에 있는 메모리 위치를 읽거나 쓰는 약점이다.

    배경(Background Details)

    일부 언어는 메모리 위치를 직접 주소 지정할 수 있게 허용하면서, 그 위치가 참조 중인 메모리 버퍼에 유효한지 자동으로 확인하지 않는다.

    원문(Description · Background Details · Dimensions)

    The product performs operations on a memory buffer, but it reads from or writes to a memory location outside the buffer's intended boundary.

    Certain languages allow direct addressing of memory locations and do not automatically ensure that these locations are valid for the memory buffer that is being referenced.

    Dimensions: Behavior-Type = Restriction of Operations; Behavior-Property = Improper; Resource-Type = Memory Buffer; Resource-Property = within the Bounds

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 허가되지 않은 코드·명령 실행 / 메모리 수정 그 결과 다른 변수, 자료 구조, 프로그램 내부 데이터와 연결되어 있을 수 있는 예상치 못한 메모리 위치에 읽기·쓰기가 일어날 수 있다. 공격자가 접근 가능한 메모리를 효과적으로 제어할 수 있으면 일반 버퍼 오버플로처럼 임의 코드 실행이 가능할 수 있다. 포인터 크기(대개 32 또는 64비트)만큼 덮어쓰면 함수 포인터를 자신의 악성 코드로 돌려 제어 흐름을 바꿀 수 있고, 단 1바이트만 바꿀 수 있어도 임의 코드 실행이 가능할 수 있다. 같은 문제를 되풀이해 악용할 수 있기 때문일 때도 있고, 관리자 여부 플래그 같은 보안상 중요한 애플리케이션 고유 데이터를 덮어쓸 수 있기 때문일 때도 있다.
    가용성 / 기밀성 메모리 읽기 / 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 자원 소모(CPU) / 서비스 거부: 자원 소모(메모리) 범위 밖 메모리 접근은 관련 메모리(경우에 따라 명령어까지)를 손상시킬 가능성이 매우 높고 비정상 종료로 이어질 수 있으며, 프로그램을 무한 루프에 빠뜨리는 등 가용성을 해치는 다른 공격도 가능하다.
    기밀성 메모리 읽기 범위 밖 읽기의 경우 공격자가 민감한 정보에 접근할 수 있고, 그 정보에 현재 버퍼의 메모리 위치 같은 시스템 세부 정보가 있으면 더 심각할 수 있는 후속 공격을 만드는 데 쓰일 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 7건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    CWE 단계(Phase) 전략 요지 효과성
    요구사항(Requirements) 언어 선택 이 약점이 생기지 않거나 피하기 쉬운 구조를 제공하는 언어를 쓴다. 예를 들어 Java, Perl처럼 자체 메모리 관리를 하는 많은 언어는 버퍼 오버플로가 생기지 않고 Ada, C#은 대개 오버플로 보호를 제공하지만 프로그래머가 끌 수 있으며, 언어 자체가 이론상 안전해도 네이티브 코드와의 인터페이스에서는 여전히 오버플로가 생길 수 있음에 유의한다.
    원문

    Use a language that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, many languages that perform their own memory management, such as Java and Perl, are not subject to buffer overflows. Other languages, such as Ada and C#, typically provide overflow protection, but the protection can be disabled by the programmer.

    Be wary that a language's interface to native code may still be subject to overflows, even if the language itself is theoretically safe.

    		 —

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리나 프레임워크를 쓴다. 예로 Messier와 Viega의 Safe C String Library(SafeStr) [REF-57], Microsoft의 Strsafe.h [REF-56]가 있으며, 오버플로가 생기기 쉬운 문자열 처리 함수의 더 안전한 버전을 제공한다.
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    Examples include the Safe C String Library (SafeStr) by Messier and Viega [REF-57], and the Strsafe.h library from Microsoft [REF-56]. These libraries provide safer versions of overflow-prone string-handling functions.

    		 많은 버퍼 오버플로는 문자열과 관련이 없으므로 완전한 해결책이 아니다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 일부 컴파일러나 컴파일러 확장이 제공하는 자동 버퍼 오버플로 탐지 기능을 쓴다. 예로 Microsoft Visual Studio의 /GS 플래그, Fedora/Red Hat의 FORTIFY_SOURCE GCC 플래그, StackGuard, ProPolice가 있으며 카나리 기반 탐지와 범위·인덱스 검사 등을 제공한다(카나리 기반 탐지는 D3FEND D3-SFCV [REF-1334] 참고). (유지보수 단계에도 해당)
    원문

    Use automatic buffer overflow detection mechanisms that are offered by certain compilers or compiler extensions. Examples include: the Microsoft Visual Studio /GS flag, Fedora/Red Hat FORTIFY_SOURCE GCC flag, StackGuard, and ProPolice, which provide various mechanisms including canary-based detection and range/index checking.

    D3-SFCV (Stack Frame Canary Validation) from D3FEND [REF-1334] discusses canary-based detection in detail.

    		 심층 방어(Defense in Depth) — 이 기능들은 일부 유형의 오버플로만 탐지하므로 반드시 완전한 해결책은 아니다. 또한 대개 애플리케이션을 종료하는 방식으로 대응하므로 결과는 여전히 서비스 거부다.
    구현(Implementation) — 애플리케이션의 메모리를 할당·관리할 때 다음 규칙을 지키는 것을 고려한다: 버퍼가 지정한 만큼 큰지 다시 확인하고, strncpy()처럼 복사할 바이트 수를 받는 함수는 대상 버퍼 크기가 소스 버퍼 크기와 같으면 문자열을 NUL로 종단하지 않을 수 있음에 유의하며, 반복문에서 버퍼에 접근하면 경계를 검사해 할당된 공간을 넘어 쓸 위험이 없게 하고, 필요하면 복사·연결 함수에 넘기기 전에 모든 입력 문자열을 적당한 길이로 자른다.
    원문

    Consider adhering to the following rules when allocating and managing an application's memory:

    - Double check that the buffer is as large as specified.

    - When using functions that accept a number of bytes to copy, such as strncpy(), be aware that if the destination buffer size is equal to the source buffer size, it may not NULL-terminate the string.

    - Check buffer boundaries if accessing the buffer in a loop and make sure there is no danger of writing past the allocated space.

    - If necessary, truncate all input strings to a reasonable length before passing them to the copy and concatenation functions.

    		 —
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 프로그램의 실행 파일과 라이브러리를 메모리에 무작위로 배치하는 기능이나 확장을 써서 실행·컴파일한다. 주소를 예측할 수 없게 되어 공격자가 악용할 코드로 안정적으로 점프하는 것을 막을 수 있다. 예로 ASLR(Address Space Layout Randomization) [REF-58] [REF-60]과 PIE(Position-Independent Executables) [REF-64]가 있다. 가져온 모듈도 기본 메모리 주소가 다른 모듈과 겹치면 무작위로 만든 주소로 재배치될 수 있다(Windows의 rebasing, Linux의 prelinking [REF-1332]). 단, 라이브러리용 ASLR은 실행 시 라이브러리를 재배치해야 해서 prelink의 목적을 없애므로 prelink와 함께 쓸 수 없다. 자세한 내용은 D3FEND의 D3-SAOR(Segment Address Offset Randomization) [REF-1335]에 있다. (유지보수 단계에도 해당)
    원문

    Run or compile the software using features or extensions that randomly arrange the positions of a program's executable and libraries in memory. Because this makes the addresses unpredictable, it can prevent an attacker from reliably jumping to exploitable code.

    Examples include Address Space Layout Randomization (ASLR) [REF-58] [REF-60] and Position-Independent Executables (PIE) [REF-64]. Imported modules may be similarly realigned if their default memory addresses conflict with other modules, in a process known as "rebasing" (for Windows) and "prelinking" (for Linux) [REF-1332] using randomly generated addresses. ASLR for libraries cannot be used in conjunction with prelink since it would require relocating the libraries at run-time, defeating the whole purpose of prelinking.

    For more information on these techniques see D3-SAOR (Segment Address Offset Randomization) from D3FEND [REF-1335].

    		 심층 방어(Defense in Depth) — 이 기법들은 완전한 해결책이 아니다. 예를 들어 익스플로잇은 코드 실행의 신뢰성을 높이려고 메모리 주소를 노출하는 버그를 흔히 이용하며 [REF-1337], 부채널 공격으로 ASLR을 우회할 수 있음도 밝혀졌다 [REF-1333].
    구현(Implementation) — strcpy를 strncpy로 바꾸는 것처럼, 길이 제한 없는 복사 함수를 길이 인자를 받는 대응 함수로 바꾼다. 그런 함수가 없으면 만든다.
    원문

    Replace unbounded copy functions with analogous functions that support length arguments, such as strcpy with strncpy. Create these if they are not available.

    		 보통(Moderate) — 이 방법도 경계값 오류(off-by-one, CWE-193), 버퍼 길이 계산 오류(CWE-131) 같은 계산 실수에는 여전히 취약하다.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-04 퍼징

    유지보수 (본문 제7장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) 실행 환경 강화 하드웨어 NX·XD 비트를 이용한 데이터 실행 방지(Data Execution Protection)를 제공하는 CPU와 운영체제, 또는 PaX [REF-60] [REF-61]처럼 이를 소프트웨어로 흉내 내는 기법을 쓴다. 이 기법들은 실행되는 모든 명령이 코드 세그먼트에 속한 메모리 주소에만 있도록 보장한다(자세한 내용은 D3FEND의 D3-PSEP(Process Segment Execution Prevention) [REF-1336]).
    원문

    Use a CPU and operating system that offers Data Execution Protection (using hardware NX or XD bits) or the equivalent techniques that simulate this feature in software, such as PaX [REF-60] [REF-61]. These techniques ensure that any instruction executed is exclusively at a memory address that is part of the code segment.

    For more information on these techniques see D3-PSEP (Process Segment Execution Prevention) from D3FEND [REF-1336].

    		 심층 방어(Defense in Depth) — 버퍼 오버플로로 인접 변수를 덮어써 소프트웨어 상태를 위험하게 바꿀 수 있으므로 완전한 해결책이 아니다. 또한 자기 수정 코드가 필요한 경우에는 쓸 수 없고, 대개 애플리케이션 종료로 대응하므로 공격은 여전히 서비스 거부를 일으킬 수 있다.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 데이터링크로 받은 센서 상태 메시지에서 센서 이름 필드를 꺼내 고정 크기 구조체에 옮긴다. 이름 길이는 메시지 헤더의 길이 바이트가 알려 준다. C++ 예시는 정비 명령으로 받은 채널 번호를 센서 표본 버퍼의 슬롯 번호로 쓴다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <stdint.h>

#define SENSOR_NAME_MAX 12

typedef struct {
    uint16_t sensor_id;
    char name[SENSOR_NAME_MAX];
} SensorRecord;

/* msg[0..1]: 센서 번호, msg[2]: 이름 길이, msg[3..]: 이름 */
static void decode_sensor(const uint8_t *msg, SensorRecord *out)
{
    uint8_t name_len = msg[2];
    out->sensor_id = (uint16_t)(msg[0] << 8 | msg[1]);
    memcpy(out->name, &msg[3], name_len);   /* 길이 바이트를 그대로 믿는다 */
}

int main(void)
{
    uint8_t link_msg[64] = {0x00, 0x2A, 40};
    memset(&link_msg[3], 'K', 40);
    SensorRecord rec;
    decode_sensor(link_msg, &rec);
    printf("sensor %u\n", rec.sensor_id);
    return 0;
}

    메시지 안의 길이 바이트(40)를 그대로 복사 길이로 써서 12바이트짜리 name 필드 뒤의 스택 메모리를 덮어쓴다. 길이 필드는 송신 측이 정하는 값이므로 신뢰 경계 밖의 입력이다.

    좋은 예

    #include <stdio.h>
#include <string.h>
#include <stdint.h>

#define SENSOR_NAME_MAX 12

typedef struct {
    uint16_t sensor_id;
    char name[SENSOR_NAME_MAX];
} SensorRecord;

/* 성공 0, 형식 오류 -1. msg_len은 실제로 받은 바이트 수 */
static int decode_sensor(const uint8_t *msg, size_t msg_len, SensorRecord *out)
{
    if (msg_len < 3) {
        return -1;
    }
    size_t name_len = msg[2];
    if (name_len >= sizeof out->name || 3 + name_len > msg_len) {
        return -1;                           /* 필드 상한과 받은 길이를 모두 검사 */
    }
    out->sensor_id = (uint16_t)(msg[0] << 8 | msg[1]);
    memcpy(out->name, &msg[3], name_len);
    out->name[name_len] = '\0';
    return 0;
}

int main(void)
{
    uint8_t link_msg[64] = {0x00, 0x2A, 40};
    memset(&link_msg[3], 'K', 40);
    SensorRecord rec;
    if (decode_sensor(link_msg, sizeof link_msg, &rec) != 0) {
        puts("rejected: bad name length");
        return 0;
    }
    printf("sensor %u %s\n", rec.sensor_id, rec.name);
    return 0;
}

    복사하기 전에 길이를 대상 필드 크기(종단 문자 자리 포함)와 실제로 받은 메시지 길이 두 가지로 검사하고, 어긋나면 메시지를 버린다. 검증 지점은 메시지 해석 함수 한 곳에 둔다(D-02·I-03).

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: stack-buffer-overflow 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-119 Demonstrative Example 1(호스트 이름을 고정 버퍼에 복사) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 입력데이터 검증 및 표현 1-9 '스택에 할당된 버퍼 오버플로우'(인쇄 40쪽) 참고 — 이 항목의 표 1 대응 CWE는 CWE-121(CWE-119의 하위)

    C++

    나쁜 예

    #include <array>
#include <cstdint>
#include <cstdio>
#include <memory>
#include <vector>

class SensorRing {
public:
    void store(std::size_t slot, std::uint16_t sample) {
        samples_[slot] = sample;            // slot 범위를 검사하지 않는다
    }
    std::uint16_t at(std::size_t slot) const { return samples_[slot]; }
private:
    std::array<std::uint16_t, 8> samples_{};
};

int main() {
    // 정비 명령으로 받은 채널 번호를 그대로 슬롯 번호로 쓴다
    std::vector<std::size_t> cmd_slots{2, 5, 11};
    auto ring = std::make_unique<SensorRing>();
    for (auto s : cmd_slots) {
        ring->store(s, 0x1234);
    }
    std::printf("%u\n", static_cast<unsigned>(ring->at(2)));
    return 0;
}

    std::array의 operator[]는 범위를 검사하지 않으므로, 외부 명령에서 온 슬롯 번호 11이 8칸짜리 배열 밖의 힙 메모리를 덮어쓴다.

    좋은 예

    #include <array>
#include <cstdint>
#include <cstdio>
#include <memory>
#include <optional>
#include <vector>

class SensorRing {
public:
    bool store(std::size_t slot, std::uint16_t sample) {
        if (slot >= samples_.size()) {
            return false;                    // 범위 밖이면 거부하고 호출자가 처리
        }
        samples_[slot] = sample;
        return true;
    }
    std::optional<std::uint16_t> at(std::size_t slot) const {
        if (slot >= samples_.size()) {
            return std::nullopt;             // 읽기도 같은 방식으로 검사
        }
        return samples_[slot];
    }
private:
    std::array<std::uint16_t, 8> samples_{};
};

int main() {
    std::vector<std::size_t> cmd_slots{2, 5, 11};
    auto ring = std::make_unique<SensorRing>();
    for (auto s : cmd_slots) {
        if (!ring->store(s, 0x1234)) {
            std::printf("rejected slot %zu\n", s);
        }
    }
    if (auto v = ring->at(2)) {
        std::printf("%u\n", static_cast<unsigned>(*v));
    }
    return 0;
}

    쓰기와 읽기 모두 크기와 먼저 비교하고, 실패를 반환값(bool·std::optional)으로 호출자에게 알린다. 예외를 쓰지 않기로 정한 임베디드 C++ 과제에서는 at()의 예외 대신 이처럼 명시적 검사를 쓴다. 객체는 std::make_unique로 만들어 해제를 스마트 포인터에 맡긴다.

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: heap-buffer-overflow 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-119 Demonstrative Example 3·4(입력으로 받은 배열 첨자의 범위 검사 누락) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(언어상 생기지 않음): C#의 관리 코드는 경계를 검사한다. unsafe 블록·stackalloc·P/Invoke 경계에서는 C 예시와 같은 문제가 생기므로 그 범위에 C 지침을 적용한다(LCS-02).

    Java — 예시 없음(언어상 생기지 않음): Java는 배열 접근마다 경계를 검사해 ArrayIndexOutOfBoundsException을 던지므로 메모리 덮어쓰기로 이어지지 않는다. JNI로 부르는 네이티브 코드에는 C 예시를 적용한다.

    Python — 예시 없음(언어상 생기지 않음): Python은 리스트·bytes·bytearray 색인마다 경계를 검사해 IndexError를 던지고 슬라이스는 범위 밖을 잘라 내므로 메모리 덮어쓰기로 이어지지 않는다. ctypes(create_string_buffer·memmove·from_buffer)와 C 확장 모듈, numpy의 메모리 보기(as_strided 등)에서는 C와 같은 문제가 생기므로 그 범위에는 C 예시와 C 지침을 적용한다.

    아키텍처·설계 검토 SOAR [REF-1479]에 따르면 다음 탐지 기법이 유용할 수 있다 — 비용 효과 매우 높음: 정형 기법 / 구성에 의한 정확성(Correct-By-Construction). 부분 적용에 비용 효과적: 인스펙션(IEEE 1028 표준, 요구사항·설계·소스코드 등에 적용 가능).

    점검 착안점 활동 근거
    (C·C++) 외부 메시지의 길이·개수·색인 필드가 memcpy의 길이, 배열 색인, 루프 상한으로 쓰이기 전에 대상 버퍼 크기와 비교되는지 데이터 흐름을 따라 확인한다. I-09·I-03 [예시] CWE-119 C 예시(길이 바이트를 복사 길이로 사용) · [표준] SEI CERT ARR30-C·ARR38-C
    (C·C++) 호스트 빌드를 AddressSanitizer로 계측하고 길이 필드를 최댓값이나 버퍼 크기+1로 바꾼 메시지를 넣어 stack-buffer-overflow·heap-buffer-overflow 보고가 나오는지 확인한다. 타깃에서는 대상 버퍼 바로 뒤에 알려진 패턴의 경계 바이트를 둔 시험 빌드나 -fstack-protector-strong 빌드에 같은 메시지를 넣어, 경계 바이트가 바뀌거나 __stack_chk_fail이 불리는지 본다. MPU 가드 영역과 스택 페인팅은 스택 고갈을 잡는 수단이라 버퍼 오버플로 확인으로 대신하지 않는다. I-10·T-04·T-07 [예시] CWE-119 예시 검증(AddressSanitizer 보고) · [CWE] CWE-119 탐지 방법(자동 동적 분석: ASan)
    (C++) std::array·std::vector의 operator[]처럼 범위를 검사하지 않는 접근에 외부 값이 색인으로 들어가는 곳을 찾는다. I-09 [예시] CWE-119 C++ 예시(std::array operator[]에 외부 슬롯 번호 사용)
    (Java·C#) JNI·P/Invoke·unsafe 코드로 네이티브 함수에 버퍼를 넘기는 곳에서 길이 인자가 실제 배열 길이와 맞는지, 네이티브 쪽이 그 길이를 지키는지 확인한다. I-09 [보완]

    단계 지침
    요구사항 분석 R-01 보안 요구사항 정의, 원문 완화책(요구사항) 1건 → 완화책
    설계 버퍼 크기 상한을 인터페이스통제문서(ICD)에 정의하고, 안전한 문자열/버퍼 라이브러리와 길이 포함 API 사용을 설계 표준으로 지정한다.
    구현(C·C++) strcpy/strcat/sprintf/gets를 금지하고 strncpy+종단 처리, snprintf, memcpy 전 길이 검증을 수행한다. 배열 인덱스는 사용 전 범위를 확인하고 C++은 std::array/std::vector::at(), std::string을 사용한다.
    구현(Java) 언어 차원에서 경계 검사가 수행되나 JNI·ByteBuffer 사용 시 인덱스/길이 검증을 하고 ArrayIndexOutOfBoundsException을 정상 흐름으로 쓰지 않는다.
    통합 및 시험 정적 분석(경계 분석), 호스트 빌드에서 -fsanitize=address 동적 분석, 프로토콜·파일 입력 퍼징(fuzzing, AFL++/libFuzzer)을 수행한다.
    유지보수 ICD·메시지 길이 변경 시 관련 버퍼 정의와 길이 검증을 영향분석하여 회귀 퍼징을 재수행한다.
    임베디드 고려 MMU가 없는 MCU·DSP는 ASLR이 없고 하드웨어 실행 금지도 MPU가 있고 설정했을 때만 쓸 수 있어, 오버플로가 제어 흐름 탈취나 오동작으로 이어지기 쉽다. 버퍼 오버플로는 경계 검사로 막고 경계 바이트나 -fstack-protector-strong 빌드로 확인한다. MPU(메모리 보호 장치) 스택 가드 영역, 스택 페인팅(stack painting), 링커 맵 기반 스택 사용량 분석은 스택 고갈을 잡는 수단으로 따로 적용한다.
