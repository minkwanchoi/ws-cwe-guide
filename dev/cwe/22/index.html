    Improper Limitation of a Pathname to a Restricted Directory

    항목 내용
    추상화 수준 기본(Base)
    상태 안정(Stable)

    Rationale: This CWE entry might have children that would be more appropriate.

    적용 플랫폼 언어: 언어 무관, Go, Python · 기술: 인공지능·기계학습(AI/ML)
    원문 MITRE CWE-22 (CWE 5.0)

    한 줄 요약

    외부 입력으로 만든 경로명의 특수 요소를 제대로 무력화하지 않아 제한된 디렉터리 밖을 가리키게 될 수 있는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 외부 입력으로 제한된 상위 디렉터리 아래의 파일이나 디렉터리를 가리키려는 경로명을 만들면서, 경로명이 제한된 디렉터리 밖의 위치로 해석되게 할 수 있는 특수 요소를 제대로 무력화하지 않는 약점이다. 많은 파일 작업은 제한된 디렉터리 안에서 이루어지도록 의도되지만, 공격자는 '..'과 '/' 구분자 같은 특수 요소로 제한된 위치를 벗어나 시스템의 다른 곳에 있는 파일이나 디렉터리에 접근할 수 있다. 가장 흔한 특수 요소 중 하나는 '../' 시퀀스로, 대부분의 현대 운영체제에서 현재 위치의 상위 디렉터리로 해석되며 이를 상대 경로 조작(relative path traversal)이라 한다. 경로 조작에는 '/usr/local/bin' 같은 절대 경로명으로 예상하지 못한 파일에 접근하는 경우도 포함되며, 이를 절대 경로 조작(absolute path traversal)이라 한다.

    원문(Description · Extended Description)

    The product uses external input to construct a pathname that is intended to identify a file or directory that is located underneath a restricted parent directory, but the product does not properly neutralize special elements within the pathname that can cause the pathname to resolve to a location that is outside of the restricted directory.

    Many file operations are intended to take place within a restricted directory. By using special elements such as ".." and "/" separators, attackers can escape outside of the restricted location to access files or directories that are elsewhere on the system. One of the most common special elements is the "../" sequence, which in most modern operating systems is interpreted as the parent directory of the current location. This is referred to as relative path traversal. Path traversal also covers the use of absolute pathnames such as "/usr/local/bin" to access unexpected files. This is referred to as absolute path traversal.

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 허가되지 않은 코드·명령 실행 공격자가 프로그램이나 라이브러리처럼 코드 실행에 쓰이는 중요 파일을 생성하거나 덮어쓸 수 있다.
    무결성 파일·디렉터리 수정 공격자가 프로그램·라이브러리·중요 데이터 같은 중요 파일을 덮어쓰거나 생성할 수 있고, 그 파일이 보안 메커니즘에 쓰이면 그 메커니즘을 우회할 수 있다(예: 비밀번호 파일 끝에 새 계정을 추가해 인증을 우회할 수 있다).
    기밀성 파일·디렉터리 읽기 공격자가 예상하지 못한 파일의 내용을 읽어 민감한 데이터를 노출시킬 수 있고, 그 파일이 보안 메커니즘에 쓰이면 그 메커니즘을 우회할 수 있다(예: 비밀번호 파일을 읽어 무차별 대입으로 비밀번호를 추측해 시스템 계정에 침입할 수 있다).
    가용성 서비스 거부: 비정상 종료·재시작 공격자가 프로그램·라이브러리·중요 데이터 같은 예상하지 못한 중요 파일을 덮어쓰거나 삭제·손상시킬 수 있으며, 이로 인해 제품이 아예 동작하지 않거나, 인증 같은 보호 메커니즘의 경우 사용자가 잠겨 접근하지 못하게 될 수 있다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해야 한다(CWE-602 방지). 공격자는 검사 뒤에 값을 바꾸거나 클라이언트에서 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있기 때문이다.
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.

    		 —
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 이 약점을 피하기 쉬운 구조를 제공하는 검증된 라이브러리나 프레임워크를 쓴다 [REF-1482].
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid [REF-1482].

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 실행 환경 강화 작업에 필요한 최소 권한으로 코드를 실행하고 [REF-76], 가능하면 한 작업에만 쓰는 제한된 권한의 격리된 계정을 만들어 공격이 성공해도 나머지 소프트웨어나 환경에 바로 접근하지 못하게 한다(예: 데이터베이스 애플리케이션은 특히 일상 운영에서 데이터베이스 관리자 권한으로 실행할 필요가 거의 없다). (유지보수 단계에도 해당)
    원문

    Run your code using the lowest privileges that are required to accomplish the necessary tasks [REF-76]. If possible, create isolated accounts with limited privileges that are only used for a single task. That way, a successful attack will not immediately give the attacker access to the rest of the software or its environment. For example, database applications rarely need to run as the database administrator, especially in day-to-day operations.

    		 —
    아키텍처·설계(Architecture and Design) 변환을 통한 강제 파일 이름이나 URL처럼 허용 대상이 한정되거나 알려져 있으면, 숫자 ID 같은 고정 입력값을 실제 파일 이름·URL에 대응시키는 매핑을 만들고 그 밖의 입력은 모두 거부한다. 예를 들어 ID 1을 'inbox.txt', ID 2를 'profile.txt'에 대응시킬 수 있으며, ESAPI AccessReferenceMap [REF-185] 같은 기능이 이를 제공한다.
    원문

    When the set of acceptable objects, such as filenames or URLs, is limited or known, create a mapping from a set of fixed input values (such as numeric IDs) to the actual filenames or URLs, and reject all other inputs.

    For example, ID 1 could map to "inbox.txt" and ID 2 could map to "profile.txt". Features such as the ESAPI AccessReferenceMap [REF-185] provide this capability.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.
    아키텍처·설계(Architecture and Design) / 운용(Operation) 공격 표면 축소 가능하면 라이브러리·include·유틸리티 파일을 웹 문서 루트 밖에 둔다. 그럴 수 없으면 별도 디렉터리에 두고 웹 서버의 접근 통제로 공격자가 직접 요청하지 못하게 한다. 흔한 방법은 호출하는 프로그램마다 고정 상수를 정의하고 라이브러리·include 파일에서 그 상수가 있는지 확인해, 없으면 직접 요청된 것으로 보고 즉시 끝내는 것이다. 이렇게 하면 기본 프로그램에는 있지만 include 파일에는 없는 보호 장치를 공격자가 우회할 가능성을 크게 줄이고, 공격 표면(attack surface)도 줄일 수 있다. (유지보수 단계에도 해당)
    원문

    Store library, include, and utility files outside of the web document root, if possible. Otherwise, store them in a separate directory and use the web server's access control capabilities to prevent attackers from directly requesting them. One common practice is to define a fixed constant in each calling program, then check for the existence of the constant in the library/include file; if the constant does not exist, then the file was directly requested, and it can exit immediately.

    This significantly reduces the chance of an attacker being able to bypass any protection mechanisms that are in the base program but not in the include files. It will also reduce the attack surface.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) 입력값 검증 모든 입력을 악의적이라고 가정하고, 명세에 엄격히 맞는 입력만 받는 허용목록('accept known good') 방식으로 검증해 맞지 않는 입력은 거부하거나 맞게 변환한다. 검증할 때는 길이·유형·허용 값 전체 범위·누락/추가 입력·구문·관련 필드 간 일관성·업무 규칙을 모두 고려한다(예: 'boat'는 영숫자만 있어 구문상 유효하지만 'red'·'blue' 같은 색상만 받는 필드라면 유효하지 않다). 악의적이거나 잘못된 입력을 찾는 방식(거부목록)에만 의존하지 않는다. 이 방식은 특히 코드 환경이 바뀔 때 원치 않는 입력을 하나 이상 놓치기 쉬워 검증이 우회될 수 있다. 다만 거부목록은 공격 탐지나 즉시 거부할 정도로 잘못된 입력을 가려내는 데는 쓸모가 있을 수 있다. 파일 이름은 쓸 수 있는 문자 집합을 엄격히 제한한 허용목록으로 검증한다. 가능하면 '.'은 하나만 허용하고(CWE-23 방지) '/' 같은 디렉터리 구분자는 빼며(CWE-36 방지) 허용 확장자 목록을 쓴다(CWE-434 방지). 위험한 문자를 지우는 필터링에만 의존하지 않는다. 필터링은 불완전할 수 있는 거부목록과 같아(CWE-184) '\'도 디렉터리 구분자로 쓰는 파일 시스템에서는 '/'만 걸러서는 부족하고, 적용 방식에 따라 지운 결과가 다시 위험한 데이터가 될 수 있다(CWE-182, 예: '.../...//'에서 '../'를 차례로 지우면 남은 문자가 다시 '../'가 된다).
    원문

    Assume all input is malicious. Use an "accept known good" input validation strategy, i.e., use a list of acceptable inputs that strictly conform to specifications. Reject any input that does not strictly conform to specifications, or transform it into something that does.

    When performing input validation, consider all potentially relevant properties, including length, type of input, the full range of acceptable values, missing or extra inputs, syntax, consistency across related fields, and conformance to business rules. As an example of business rule logic, "boat" may be syntactically valid because it only contains alphanumeric characters, but it is not valid if the input is only expected to contain colors such as "red" or "blue."

    Do not rely exclusively on looking for malicious or malformed inputs. This is likely to miss at least one undesirable input, especially if the code's environment changes. This can give attackers enough room to bypass the intended validation. However, denylists can be useful for detecting potential attacks or determining which inputs are so malformed that they should be rejected outright.

    When validating filenames, use stringent allowlists that limit the character set to be used. If feasible, only allow a single "." character in the filename to avoid weaknesses such as CWE-23, and exclude directory separators such as "/" to avoid CWE-36. Use a list of allowable file extensions, which will help to avoid CWE-434.

    Do not rely exclusively on a filtering mechanism that removes potentially dangerous characters. This is equivalent to a denylist, which may be incomplete (CWE-184). For example, filtering "/" is insufficient protection if the filesystem also supports the use of "\" as a directory separator. Another possible error could occur when the filtering is applied in a way that still produces dangerous data (CWE-182). For example, if "../" sequences are removed from the ".../...//" string in a sequential fashion, two instances of "../" would be removed from the original string, but the remaining characters would still form the "../" string.

    Ensure that error messages only contain minimal details that are useful to the intended audience and no one else. The messages need to strike the balance between being too cryptic (which can confuse users) or being too detailed (which may reveal more than intended).     Avoid inconsistent messaging that might accidentally tip off an attacker about internal state, such as whether a user account exists or not.

    In the context of path traversal, error messages which disclose path information can help attackers craft the appropriate attack strings to move through the file system hierarchy.

    요구사항 분석 —
    설계 외부 입력으로 파일 경로를 구성하지 않도록 설계하고, 불가피하면 허용 파일 목록(ID→경로 매핑)과 고정 기준 디렉터리를 정의한다.

    구현(Java) Path.toRealPath()로 링크까지 풀어 정규화한 뒤 startsWith(baseDir)로 검증하고, 파일명은 [A-Za-z0-9._-] 허용목록(allowlist) 정규식으로 제한한다.
    통합 및 시험 '../', 인코딩된 '%2e%2e%2f', 절대 경로, 긴 경로를 포함한 경로 퍼징(fuzzing)과 정적 분석(오염 추적)으로 입력→파일 API 흐름을 점검한다.
    유지보수 파일 저장 위치·디렉터리 구조 변경 시 기준 디렉터리 검증 로직을 재점검하고, 운용 중 최소 권한 계정으로 실행한다.
    임베디드 고려 RTOS(실시간 운영체제) 파일시스템(FatFs, VxWorks dosFs)은 권한 개념이 약하므로 외부 명령(정비 단말·직렬 명령)으로 파일명을 받지 말고 고정 인덱스로 접근한다.
