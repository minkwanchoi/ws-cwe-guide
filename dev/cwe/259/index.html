    Use of Hard-coded Password

    항목 내용
    추상화 수준 변형(Variant)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 조건부 — 사용자 계정·비밀번호 사용
    적용 플랫폼 언어 무관 · 기술: 산업제어시스템·운영기술(ICS/OT)
    원문 MITRE CWE-259 (CWE 5.0)

    이름 표기

    「소프트웨어 개발보안 가이드」(2021. 11.)의 구현단계 기준은 CWE-259·321을 '하드코드된 중요정보'(인쇄 237쪽) 하나로 묶는다. 이 가이드는 둘을 따로 다루므로 같은 가이드 분석·설계단계 사례의 그림 제목 '하드코드된 비밀번호'(그림 3-21, 인쇄 95쪽)를 이름으로 쓴다.

    한 줄 요약

    자체 인바운드 인증이나 외부 구성요소로의 아웃바운드 인증에 하드코드된 비밀번호를 쓰는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 하드코드된 비밀번호를 포함하고, 이를 자체 인바운드 인증이나 외부 구성요소로의 아웃바운드 인증에 사용하는 약점이다.

    기술 해설(Technical Nuance)

    하드코드된 비밀번호에는 크게 두 가지 유형이 있다.

    • 인바운드(inbound): 제품의 인증 메커니즘이 하드코드된 비밀번호를 검사한다.

    • 아웃바운드(outbound): 제품이 다른 시스템이나 구성요소에 접속하며, 그 접속에 쓰는 하드코드된 비밀번호를 포함한다.

    원문(Description · Technical Nuance)

    The product contains a hard-coded password, which it uses for its own inbound authentication or for outbound authentication to external components.

    There are two main variations of a hard-coded password:

    Inbound: the product contains an authentication mechanism that checks for a hard-coded password.
    Outbound: the product connects to another system or component, and it contains a hard-coded password for connecting to that component.

    구현(Implementation) 구현 실현(REALIZATION): 이 약점은 아키텍처 보안 전술을 구현하는 과정에서 생긴다.

    영향(Common Consequences)¶

    영역 영향 설명
    접근 통제 권한 획득 또는 신원 도용 하드코드된 비밀번호를 쓰면 악의적인 사용자가 해당 계정으로 접근할 수 있는 것이 거의 확실하다.
    접근 통제 권한 획득 또는 신원 도용 / 행위 은닉 / 유지보수성 저하 하드코드된 비밀번호는 대개 시스템 관리자가 탐지하기 어려운 심각한 인증 실패로 이어지고, 탐지하더라도 고치기 어려워 관리자가 제품을 아예 비활성화해야 할 수도 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 아웃바운드 인증에서는 비밀번호를 코드 밖의 강하게 보호·암호화된 설정 파일이나 데이터베이스에 저장해 같은 시스템의 다른 로컬 사용자를 포함한 모든 외부자의 접근을 막고, 그 키도 적절히 보호한다(CWE-320). 암호화로 파일을 보호할 수 없다면 파일 권한을 최대한 제한한다.
    원문

    For outbound authentication: store passwords outside of the code in a strongly-protected, encrypted configuration file or database that is protected from access by all outsiders, including other local users on the same system. Properly protect the key (CWE-320). If you cannot use encryption to protect the file, then make sure that the permissions are as restrictive as possible.
    아키텍처·설계(Architecture and Design) — 인바운드 인증에서는 첫 로그인용 기본 사용자 이름과 비밀번호를 하드코드하지 말고, 사용자가 고유하고 강한 비밀번호를 입력하도록 요구하는 '첫 로그인' 모드를 쓴다.
    원문

    For inbound authentication: Rather than hard-code a default username and password for first time logins, utilize a "first login" mode that requires the user to enter a unique strong password.
    아키텍처·설계(Architecture and Design) — 접근 통제 검사를 수행해 하드코드된 비밀번호가 필요한 기능에 접근할 수 있는 주체를 제한한다. 예를 들어 그 기능을 네트워크 연결이 아닌 시스템 콘솔을 통해서만 켤 수 있게 할 수 있다.
    원문

    Perform access control checks and limit which entities can access the feature that requires the hard-coded password. For example, a feature might only be enabled through the system console instead of through a network connection.
    아키텍처·설계(Architecture and Design) — 인바운드 인증에서는 비밀번호에 강한 단방향 해시를 적용해 적절한 접근 통제가 있는 설정 파일이나 데이터베이스에 저장하고, 인증 시 받은 비밀번호의 해시를 저장된 해시와 비교한다. 그러면 파일·데이터베이스가 도난당해도 공격자는 비밀번호를 크래킹해야 하며, 해시마다 무작위로 할당한 솔트를 쓰면 무차별 대입 공격에 필요한 계산량이 늘어 레인보 테이블(rainbow table) 방법의 효과를 제한할 수 있다.
    원문

    For inbound authentication: apply strong one-way hashes to your passwords and store those hashes in a configuration file or database with appropriate access control. That way, theft of the file/database still requires the attacker to try to crack the password. When receiving an incoming password during authentication, take the hash of the password and compare it to the hash that you have saved.

    Use randomly assigned salts for each separate hash that you generate. This increases the amount of computation that an attacker needs to conduct a brute-force attack, possibly limiting the effectiveness of the rainbow table method.
    아키텍처·설계(Architecture and Design) — 프런트엔드와 백엔드 간 연결에는 세 가지 방안이 있으나 어느 것도 완전하지 않다. 자동으로 바뀌고 정해진 시간 간격마다 시스템 관리자가 입력해야 하는 생성 비밀번호를 메모리에만 두어 그 기간에만 유효하게 하는 방안, 백엔드에서 그 비밀번호로 전체 접근이 아닌 프런트엔드에 유효한 동작만 수행하게 제한하는 방안, 재전송(replay) 공격을 막도록 메시지에 시간에 민감한 값으로 태그와 체크섬을 붙이는 방안이다.
    원문

    For front-end to back-end connections: Three solutions are possible, although none are complete.

    The first suggestion involves the use of generated passwords which are changed automatically and must be entered at given time intervals by a system administrator. These passwords will be held in memory and only be valid for the time intervals.
    Next, the passwords used should be limited at the back end to only performing actions valid for the front end, as opposed to having full access.
    Finally, the messages sent should be tagged and checksummed with time sensitive values so as to prevent replay style attacks.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 정비 콘솔·시험 장비·임무 계획 도구가 다른 장치나 서버에 로그인할 때 비밀번호가 필요하다. 이 비밀번호를 소스코드에 상수로 둘지, 장비마다 주입한 보호 저장소(보안요소·키 저장 영역·비밀 저장소)에서 실행 중에 받아 올지를 비교한다. 예시의 비밀번호 값은 모두 가짜(EXAMPLE-ONLY)다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다(도구로 잡기 어려운 약점은 생성형 AI를 쓴 별도 검토로 판정했다). 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <stddef.h>

typedef struct {
    const char *account;
    const char *password;
} Credential;

/* 정비 콘솔 계정표: 비밀번호가 펌웨어 이미지에 그대로 들어간다 */
static const Credential BUILTIN_ACCOUNTS[] = {
    { "maint", "EXAMPLE-ONLY" },
    { "depot", "EXAMPLE-ONLY-2" },
};

static int console_login(const char *account, const char *typed)
{
    for (size_t i = 0; i < sizeof BUILTIN_ACCOUNTS / sizeof BUILTIN_ACCOUNTS[0]; ++i) {
        if (strcmp(BUILTIN_ACCOUNTS[i].account, account) == 0) {
            return strcmp(BUILTIN_ACCOUNTS[i].password, typed) == 0;
        }
    }
    return 0;
}

int main(void)
{
    printf("login maint: %s\n", console_login("maint", "guess") ? "granted" : "denied");
    return 0;
}

    정비 계정 비밀번호를 소스코드 상수로 두어 같은 펌웨어를 쓰는 모든 장비가 같은 비밀번호를 갖고, 외부 플래시 덤프나 바이너리 문자열 검사로 바로 꺼낼 수 있다. 바꾸려면 펌웨어를 다시 빌드·배포해야 한다. 코드 리뷰에서는 password·passwd·secret 같은 이름의 문자열 상수와 strcmp 비교 대상이 리터럴인 곳을 찾고, 운용 빌드 산출물에는 문자열 검사를 함께 한다(T-08).

    좋은 예

    #include <stdio.h>
#include <stddef.h>

#define SALT_LEN 16
#define HASH_LEN 32

/* 플랫폼이 제공하는 보호 저장소(보안요소·키 저장 영역)에서 계정의 솔트와 비밀번호 해시를 읽는다.
   실제 장비에서는 드라이버로 구현하고, 값은 출고·정비 절차에서 장비마다 주입한다.
   이 예시는 아직 주입되지 않은 상태를 흉내 낸다. */
static int secure_store_read(const char *account, unsigned char salt[SALT_LEN], unsigned char hash[HASH_LEN])
{
    (void)account; (void)salt; (void)hash;
    return -1;
}

/* 자리표시: 실제로는 검증된 암호 라이브러리의 비밀번호 해시 함수(PBKDF2·Argon2 등)를 부른다.
   그럴듯한 대역이 제품에 남지 않게, 구현 전에는 실패를 돌려준다 */
static int hash_password(const char *typed, const unsigned char salt[SALT_LEN], unsigned char out[HASH_LEN])
{
    (void)typed; (void)salt; (void)out;
    return -1;
}

static int equal_const_time(const unsigned char *a, const unsigned char *b, size_t n)
{
    unsigned char diff = 0;
    for (size_t i = 0; i < n; ++i) diff |= (unsigned char)(a[i] ^ b[i]);
    return diff == 0;
}

/* 이후 쓰이지 않는 버퍼의 memset은 최적화로 제거될 수 있어 volatile로 지운다(CWE-14).
   플랫폼에 explicit_bzero·memset_s·SecureZeroMemory가 있으면 그것을 쓴다 */
static void wipe(void *p, size_t n)
{
    volatile unsigned char *v = p;
    while (n-- > 0) *v++ = 0;
}

static int console_login(const char *account, const char *typed)
{
    unsigned char salt[SALT_LEN], stored[HASH_LEN], computed[HASH_LEN];
    int ok = 0;
    if (secure_store_read(account, salt, stored) != 0) {
        return 0;             /* 주입 전이면 기본 비밀번호 없이 거부(fail closed) */
    }
    if (hash_password(typed, salt, computed) == 0) {
        /* 평문이 아니라 같은 길이(32바이트)의 해시끼리 끝까지 비교한다 */
        ok = equal_const_time(stored, computed, HASH_LEN);
    }
    wipe(computed, sizeof computed);
    wipe(stored, sizeof stored);
    return ok;
}

int main(void)
{
    printf("login maint: %s\n", console_login("maint", "guess") ? "granted" : "denied");
    return 0;
}

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    수동 분석 침투 시험(penetration test), 위협 모델링, 활성 세션을 기록·수정하는 대화형 도구처럼 사람이 직접 분석하는 도구·기법으로 이 약점을 탐지할 수 있다.
    원문

    This weakness can be detected using tools and techniques that require manual (human) analysis, such as penetration testing, threat modeling, and interactive tools that allow the tester to record and modify an active session.

    		 이런 수동 방법은 완전 자동화 기법보다 더 효과적일 수 있으며, 특히 설계·업무 규칙과 관련된 약점에서 그렇다.
    블랙박스 시험 운영체제·네트워크와 상호작용하는 소프트웨어 프로세스를 살피는 모니터링 도구를 쓴다. 소스코드가 없거나, 직접 개발하지 않은 소프트웨어이거나, 빌드 단계에서 새 약점이 들어오지 않았는지 확인하려 할 때 유용하다. 도구로는 실행 중인 프로세스에 붙는 디버거, truss(Solaris)·strace(Linux) 같은 시스템 호출 추적 도구, FileMon·RegMon·Process Monitor 등 Sysinternals 유틸리티(Windows), 네트워크 트래픽을 보는 스니퍼·프로토콜 분석기가 있다. 모니터를 프로세스에 붙이고 로그인을 수행한 뒤, 디스어셈블된 코드에서 입력을 고정 문자열이나 값과 비교하는 것으로 보이는 명령어가 있는지 살핀다.
    원문

    Use monitoring tools that examine the software's process as it interacts with the operating system and the network. This technique is useful in cases when source code is unavailable, if the software was not developed by you, or if you want to verify that the build phase did not introduce any new weaknesses. Examples include debuggers that directly attach to the running process; system-call tracing utilities such as truss (Solaris) and strace (Linux); system activity monitors such as FileMon, RegMon, Process Monitor, and other Sysinternals utilities (Windows); and sniffers and protocol analyzers that monitor network traffic.

    Attach the monitor to the process and perform a login. Using disassembled code, look at the associated instructions and see if any of them appear to be comparing the input to a fixed string or value.

    		 —
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    password·passwd·pw·secret·credential 같은 이름의 상수와, 인증·접속 함수(strcmp, equals, 접속 문자열 생성)에 리터럴이 그대로 넘어가는 곳을 찾는다. I-09 [예시] CWE-259 예시(코드 리뷰 판정) · [표준] SEI CERT MSC03-J
    운용 빌드 실행 파일·펌웨어 이미지·클래스 파일·어셈블리에서 문자열을 추출해(strings, javap, 디컴파일러) 계정·비밀번호처럼 보이는 문자열을 찾는다. 역어셈블러로 인증 함수가 입력을 고정 문자열·상수와 비교하는지도 본다. T-08 [예시] CWE-259 예시 설명(실행 파일·상수 풀·#US 힙에 평문으로 남음) · [CWE] CWE-259 탐지 방법(Black Box: 역어셈블 코드에서 고정 문자열 비교 확인)
    형상저장소 이력 전체에서 비밀값을 검색해 과거 커밋에 남은 비밀번호도 찾고, 찾으면 소스에서 지우는 것과 별도로 그 비밀번호를 바꾼다. M-02 [보완]
    설치 직후 상태에서 기본 비밀번호를 바꾸기 전에 중요 기능이 막히는지, 최초 접속 때 새 비밀번호를 정하게 하는지 시험한다. T-06·M-03 [CWE] CWE-259 완화책(Architecture and Design: 최초 로그인 모드)
    • ① 원문 탐지 방법(원문 효과성별): 효과 등급 없음: 수동 분석, 블랙박스 시험. 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: MSC03-J

    이 가이드에서 다루는 곳¶

    부록 A의 이 항목 행에 있는 단계별 지침 (요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 인증정보는 코드와 분리된 보호 저장소(암호화 설정파일, 보안요소/TPM, 키 관리 체계)에 저장하도록 설계하고, 최초 접속 시 변경을 강제한다.
    구현(C·C++) 소스·헤더·바이너리 상수에 비밀번호를 기록하지 않는다. 장비가 상대에게 내는 비밀번호(외부 접속 인증, outbound)는 보호 저장소에서 런타임에 로드하고 사용 후 소거한다. 장비가 검증하는 비밀번호(수신 인증, inbound)는 솔트와 반복 기반 해시(CWE-759·916)만 저장해 상수 시간으로 비교한다.
    구현(Java) 비밀번호를 String 리터럴로 두지 않는다. 외부 접속 인증(outbound) 비밀번호는 KeyStore/암호화된 외부 설정에서 char[]로 로드하고 사용 후 Arrays.fill()로 소거한다. 수신 인증(inbound) 비밀번호는 솔트와 반복 기반 해시(CWE-759·916)만 저장해 상수 시간으로 비교한다.
    통합 및 시험 정적 분석의 하드코드된 자격증명 탐지, 바이너리 strings/엔트로피 분석, 형상저장소 이력 스캔(gitleaks 등)을 수행한다.
    유지보수 자격증명 교체 절차를 운용 매뉴얼에 정의하고, 노출 시 즉시 폐기·재발급한다.
    임베디드 고려 펌웨어 이미지 덤프(JTAG/SWD, 외부 플래시)로 상수가 추출되므로 읽기 보호 퓨즈(AVR Lock bit, RDP)와 보안요소(ATECC 등)를 활용한다.

    기준선 활동 3건

    • D-05 암호·키·비밀 관리 설계 (설계)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 8건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
