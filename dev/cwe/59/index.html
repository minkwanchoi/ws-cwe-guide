    Improper Link Resolution Before File Access

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 조건부 — 파일시스템 사용(파일시스템(S3)이 '없음' 외의 값)
    적용 플랫폼 언어 무관 · 운영체제: Windows, Unix · 기술 무관
    원문 MITRE CWE-59 (CWE 5.0)

    한 줄 요약

    파일 이름으로 파일에 접근할 때 그 이름이 의도하지 않은 자원으로 연결되는 링크·바로가기를 가리키는 것을 막지 못해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 파일 이름을 기준으로 파일에 접근하려 하지만, 그 파일 이름이 의도하지 않은 자원으로 연결되는 링크(link)나 바로가기(shortcut)를 가리키는 것을 제대로 막지 못하는 약점이다.

    배경(Background Details)

    소프트 링크(soft link)는 UNIX 용어로, Windows 기반 플랫폼의 단순 바로가기와 같은 뜻이다.

    원문(Description · Background Details)

    The product attempts to access a file based on the filename, but it does not properly prevent that filename from identifying a link or shortcut that resolves to an unintended resource.

    Soft links are a UNIX term that is synonymous with simple shortcuts on Windows-based platforms.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 실현(REALIZATION): 이 약점은 아키텍처 보안 전술을 구현하는 과정에서 생긴다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 / 무결성 / 접근 통제 파일·디렉터리 읽기 / 파일·디렉터리 수정 / 보호 메커니즘 우회 공격자가 파일 시스템의 의도하지 않은 위치로 이동해 예상치 못한 파일의 내용을 읽거나 덮어쓸 수 있고, 그 파일이 보안 메커니즘에 쓰이면 해당 메커니즘을 우회할 수 있다.
    기타 허가되지 않은 코드·명령 실행 소프트 링크라고도 불리는 Windows 단순 바로가기는 '.LNK' 파일이 일반 파일처럼 업로드될 수 있어 원격으로 악용될 수 있으며, 원격 실행을 가능하게 할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 1건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) 권한 분리 소프트웨어 시스템의 각 주체에 접근 권한을 부여할 때 최소 권한 원칙을 따른다. 파일 접근을 거부하면 공격자가 그 파일을 중요 파일로 연결되는 링크로 바꿔치기하는 것을 막을 수 있다. 또한 시스템을 잘 구획해 신뢰할 수 있는 보호 영역을 마련한다.
    원문

    Follow the principle of least privilege when assigning access rights to entities in a software system.

    Denying access to a file can prevent an attacker from replacing that file with a link to a sensitive file. Ensure good compartmentalization in the system to provide protected areas that can be trusted.

    구현 (본문 제5장)¶

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 자체 점검 결과·장비 위치 기록·고장 보고서·동기화 기록을 여러 계정이 함께 쓰는 공용 폴더에 고정 이름으로 쓴다. 다른 계정이 그 이름으로 보호 파일(항법 설정·임무 자료·키 묶음·운용자 명부)을 가리키는 심볼릭 링크나 하드 링크(운영체제 설정에 따라 원본 파일의 소유자이거나 쓰기 권한이 있어야 만들 수 있다)를 미리 만들어 두면, 기록하는 쪽 권한으로 보호 파일이 덮어써진다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>

static void show(const char *path)
{
    char buf[64] = "";
    FILE *f = fopen(path, "r");
    if (f != NULL) { if (fgets(buf, sizeof buf, f) == NULL) buf[0] = '\0'; fclose(f); }
    printf("%s = %s\n", path, buf);
}

int main(void)
{
    mkdir("spool", 0777);                       /* 여러 계정이 함께 쓰는 스풀 */
    FILE *c = fopen("nav.cfg", "w");             /* 보호해야 할 항법 설정 */
    if (c != NULL) { fputs("NAV-CFG v3", c); fclose(c); }
    symlink("../nav.cfg", "spool/bit.txt");     /* 다른 계정이 미리 심은 링크 */

    /* 자체 점검(BIT) 결과를 고정 이름으로 기록: 링크를 그대로 따라감 */
    FILE *f = fopen("spool/bit.txt", "w");
    if (f != NULL) { fputs("BIT PASS 0412", f); fclose(f); }
    show("nav.cfg");
    return 0;
}

    fopen("w")는 마지막 경로 요소가 심볼릭 링크여도 따라가 대상 파일을 비우고 쓴다. 미리 심어 둔 링크 때문에 항법 설정 파일이 점검 결과로 덮어써진다.

    좋은 예

    #include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void show(const char *path)
{
    char buf[64] = "";
    FILE *f = fopen(path, "r");
    if (f != NULL) { if (fgets(buf, sizeof buf, f) == NULL) buf[0] = '\0'; fclose(f); }
    printf("%s = %s\n", path, buf);
}

int main(void)
{
    mkdir("spool", 0777);
    FILE *c = fopen("nav.cfg", "w");
    if (c != NULL) { fputs("NAV-CFG v3", c); fclose(c); }
    symlink("../nav.cfg", "spool/bit.txt");

    /* 새 파일만 만든다(O_EXCL), 마지막 요소가 링크면 실패(O_NOFOLLOW) */
    int fd = open("spool/bit.txt", O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW, 0600);
    if (fd < 0) {
        printf("refused to write report: %s\n", strerror(errno));
    } else {
        const char msg[] = "BIT PASS 0412";
        if (write(fd, msg, sizeof msg - 1) < 0) perror("write");
        close(fd);
    }
    show("nav.cfg");
    return 0;
}

    open()에 O_CREAT|O_EXCL|O_NOFOLLOW를 주어 새 파일만 만들고, 그 이름에 링크나 파일이 이미 있으면 실패하게 한다(I-04). 실제 과제에서는 공용 폴더 대신 전용 디렉터리나 mkstemp()를 쓴다.

    검증: 실행 결과 · Linux(gcc)에서 빌드 — 나쁜 예에서 nav.cfg = BIT PASS 검출, 좋은 예에서 미검출·refused to write report 출력 확인 · 참고: MITRE CWE-59 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <filesystem>
#include <fstream>
#include <iostream>
#include <string>

namespace fs = std::filesystem;

std::string firstLine(const fs::path &p) {
    std::ifstream in(p);
    std::string s;
    std::getline(in, s);
    return s;
}

int main() {
    fs::create_directories("export");                 // 공용 내보내기 폴더
    std::ofstream("mission.db") << "MISSION-DB r7";   // 보호해야 할 임무 자료
    fs::remove("export/log.csv");
    fs::create_hard_link("mission.db", "export/log.csv");  // 미리 심어 둔 하드 링크

    // 장비 위치 기록을 고정 이름으로 내보냄: 링크된 원본 파일을 덮어쓴다
    std::ofstream out("export/log.csv", std::ios::trunc);
    out << "T001,00.00,000.00\n";
    out.close();
    std::cout << "mission.db = " << firstLine("mission.db") << '\n';
}

    std::ofstream으로 고정 이름을 열어 덮어쓰면 그 이름이 하드 링크일 때 링크된 원본(임무 자료)의 내용이 바뀐다. Windows에서 심볼릭 링크는 기본으로 관리자 권한(또는 개발자 모드)이 있어야 만들지만 하드 링크는 그런 권한 없이 만들 수 있다. 다만 Windows 11에서는 쓰기 권한이 없는 파일에 하드 링크를 만들 수 없었으므로(이 가이드 실험, 판·API에 따라 다를 수 있음), 이 예시는 링크를 심는 계정이 원본에 쓰기 권한을 가진 경우를 보인다.

    좋은 예

    #include <windows.h>

#include <filesystem>
#include <fstream>
#include <iostream>
#include <random>
#include <string>

namespace fs = std::filesystem;

std::string firstLine(const fs::path &p) {
    std::ifstream in(p);
    std::string s;
    std::getline(in, s);
    return s;
}

// CREATE_NEW: 그 이름에 파일이나 링크가 이미 있으면 열지 않고 실패한다
bool writeFreshFile(const fs::path &p, const std::string &data) {
    HANDLE h = CreateFileW(p.c_str(), GENERIC_WRITE, 0, nullptr, CREATE_NEW, FILE_ATTRIBUTE_NORMAL, nullptr);
    if (h == INVALID_HANDLE_VALUE) return false;
    DWORD written = 0;
    const BOOL ok = WriteFile(h, data.data(), static_cast<DWORD>(data.size()), &written, nullptr);
    CloseHandle(h);
    return ok && written == data.size();
}

int main() {
    fs::create_directories("export");
    std::ofstream("mission.db") << "MISSION-DB r7";
    fs::remove("export/log.csv");
    fs::create_hard_link("mission.db", "export/log.csv");

    // 다른 계정이 쓸 수 없는 전용 폴더나 예측할 수 없는 이름으로, 이미 있으면 실패하게 만든
    // 임시 파일에 쓴 뒤 교체한다. rename은 그 자리의 디렉터리 항목만 바꾸고 링크가 가리키던 원본은 건드리지 않는다.
    std::random_device rd;
    const fs::path tmp = "export/log." + std::to_string(rd()) + std::to_string(rd()) + ".part";
    if (!writeFreshFile(tmp, "T001,00.00,000.00\n")) {
        std::cout << "temp name already exists, export aborted\n";
        return 1;
    }
    fs::rename(tmp, "export/log.csv");
    std::cout << "mission.db = " << firstLine("mission.db") << '\n';
    std::cout << "export = " << firstLine("export/log.csv") << '\n';
}

    같은 폴더에 예측할 수 없는 이름의 임시 파일을 CreateFileW(CREATE_NEW)로 새로 만들어 쓰고(그 이름에 파일이나 링크가 이미 있으면 실패), fs::rename으로 교체한다. rename은 그 이름의 디렉터리 항목만 바꾸므로 링크가 가리키던 원본은 그대로 남는다(I-04). 임시 파일은 다른 계정이 쓸 수 없는 전용 폴더나 예측할 수 없는 이름으로, 이미 있으면 실패하게 만들어야 한다. 고정 이름 임시 파일을 지우고 다시 만들면 그 틈에 링크를 심을 수 있다.

    검증: 실행 결과 — 나쁜 예에서 mission.db = T001 검출, 좋은 예에서 미검출·mission.db = MISSION-DB r7…export = T001 출력 확인 · 참고: MITRE CWE-59 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    using System.Runtime.InteropServices;

Directory.CreateDirectory("dropbox");                     // 공용 자료 교환 폴더
File.WriteAllText("ops.roster", "ROSTER-ALPHA");           // 보호해야 할 운용자 명부
string target = Path.Combine("dropbox", "sync.log");
File.Delete(target);
CreateHardLink(target, "ops.roster", IntPtr.Zero);         // 다른 계정이 심어 둔 하드 링크

// 동기화 기록을 고정 이름으로 덮어씀: 링크가 가리키는 명부 파일이 바뀐다
File.WriteAllText(target, "SYNC OK 0412");
Console.WriteLine("ops.roster = " + File.ReadAllText("ops.roster"));

[DllImport("kernel32.dll", CharSet = CharSet.Unicode, SetLastError = true)]
static extern bool CreateHardLink(string newName, string existingName, IntPtr security);

    File.WriteAllText는 이미 있는 이름을 열어 내용을 바꾸므로, 그 이름이 하드 링크면 링크된 운용자 명부 파일이 덮어써진다. 예시는 링크를 만들기 위해서만 Win32 CreateHardLink를 P/Invoke로 부른다.

    좋은 예

    using System.Runtime.InteropServices;

Directory.CreateDirectory("dropbox");

    f.write("RADIO-KEYS=0x5A1F\n")

def write_bit_result(text):
    # O_NOFOLLOW: 마지막 경로 요소가 심볼릭 링크면 열지 않는다. O_EXCL: 이미 있는 파일도 열지 않는다

        fd = os.open("shared/bit-result.txt", flags, 0o600)
    except OSError as e:
        print("refused to write BIT result:", e.strerror)
        return
    with os.fdopen(fd, "w") as f:
        f.write(text)

    os.open에 O_NOFOLLOW와 O_EXCL을 함께 줘 링크이거나 이미 있는 파일이면 열지 않는다(I-04, LPY-06). 더 나은 방법은 공용 폴더에 고정 이름으로 쓰지 않는 것이다. 프로그램 전용 폴더(소유자만 쓰기)나 tempfile.mkstemp()·mkdtemp()로 만든 이름을 쓴다. O_NOFOLLOW는 마지막 경로 요소만 확인하므로 중간 디렉터리도 다른 계정이 바꿀 수 없게 둔다.
