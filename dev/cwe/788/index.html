    Access of Memory Location After End of Buffer

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    MITRE 매핑 권고 권장하지 않음(Discouraged) — 결과를 기록할 때는 더 구체적인 CWE를 쓴다(하위 CWE: CWE-121·CWE-122·CWE-126)
    원문(Mapping Notes)

    Rationale: The CWE entry might be misused when lower-level CWE entries might be available. It also overlaps existing CWE entries and might be deprecated in the future.

    Comments: If the "Access" operation is known to be a read or a write, then investigate children of entries such as CWE-787: Out-of-bounds Write and CWE-125: Out-of-bounds Read.
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++
    원문 MITRE CWE-788 (CWE 5.0)

    한 줄 요약

    버퍼 끝 이후의 메모리 위치를 참조하는 인덱스나 포인터로 버퍼를 읽거나 쓰는 약점이다.

    설명(Description)¶

    제품이 버퍼 끝 이후의 메모리 위치를 참조하는 인덱스나 포인터로 버퍼를 읽거나 쓰는 약점이다.

    원문(Description · Dimensions)

    The product reads or writes to a buffer using an index or pointer that references a memory location after the end of the buffer.

    Dimensions: Behavior-Type = Access; Resource-Type = Memory Location; Resource-Property = After End; Resource-Type = Buffer

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 대개 포인터나 그 인덱스가 버퍼 이후 위치까지 증가할 때, 또는 포인터 연산 결과가 버퍼 이후 위치가 될 때 생긴다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 메모리 읽기 범위를 벗어난 읽기의 경우 공격자가 민감한 정보에 접근할 수 있으며, 그 정보에 현재 버퍼의 메모리 위치 같은 시스템 세부 정보가 있으면 더 심각한 결과를 낼 수 있는 후속 공격을 만드는 데 쓰일 수 있다.
    무결성 / 가용성 메모리 수정 / 서비스 거부: 비정상 종료·재시작 범위 밖 메모리 접근은 관련 메모리(경우에 따라 명령어까지)를 손상시킬 가능성이 매우 높고 비정상 종료로 이어질 수 있으며, 프로그램을 무한 루프에 빠뜨리는 등 가용성을 해치는 다른 공격도 가능하다.
    무결성 메모리 수정 / 허가되지 않은 코드·명령 실행 공격자가 접근할 수 있는 메모리를 효과적으로 제어할 수 있으면 일반 버퍼 오버플로처럼 임의 코드를 실행할 수 있다. 포인터 크기만큼(대개 32 또는 64비트) 메모리를 덮어쓸 수 있으면 함수 포인터를 자신의 악성 코드로 돌릴 수 있다. 1바이트만 바꿀 수 있어도 임의 코드 실행이 가능할 수 있다. 같은 문제를 반복해 악용해 같은 효과를 낼 수 있거나, 사용자가 관리자인지 나타내는 플래그처럼 보안상 중요한 애플리케이션 고유 데이터를 덮어쓸 수 있기 때문이다.

    완화책(Potential Mitigations)¶

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 4건)

    Example 1. This example takes an IP address from a user, verifies that it is well formed and then looks up the hostname and copies it into a buffer.

    Bad / C

    void host_lookup(char *user_supplied_addr){

  struct hostent *hp;
  in_addr_t *addr;
  char hostname[64];
  in_addr_t inet_addr(const char *cp);

                             /*routine that ensures user_supplied_addr is in the right format for conversion */

  validate_addr_form(user_supplied_addr);
  addr = inet_addr(user_supplied_addr);
  hp = gethostbyaddr( addr, sizeof(struct in_addr), AF_INET);
  strcpy(hostname, hp->h_name);

}

    This function allocates a buffer of 64 bytes to store the hostname, however there is no guarantee that the hostname will not be larger than 64 bytes. If an attacker specifies an address which resolves to a very large hostname, then the function may overwrite sensitive data or even relinquish control flow to the attacker.

    Note that this example also contains an unchecked return value (CWE-252) that can lead to a NULL pointer dereference (CWE-476).

    Example 2. In the following example, it is possible to request that memcpy move a much larger segment of memory than assumed:

    Bad / C

    int returnChunkSize(void *) {

                             /* if chunk info is valid, return the size of usable memory,

                             * else, return -1 to indicate an error

                             */

  ...

}
int main() {
  ...
  memcpy(destBuf, srcBuf, (returnChunkSize(destBuf)-1));
  ...
}

    If returnChunkSize() happens to encounter an error it will return -1. Notice that the return value is not checked before the memcpy operation (CWE-252), so -1 can be passed as the size argument to memcpy() (CWE-805). Because memcpy() assumes that the value is unsigned, it will be interpreted as MAXINT-1 (CWE-195), and therefore will copy far more memory than is likely available to the destination buffer (CWE-787, CWE-788).

    Example 3. This example applies an encoding procedure to an input string and stores it into a buffer.

    Bad / C

    char * copy_input(char *user_supplied_string){

  int i, dst_index;
  char *dst_buf = (char*)malloc(4*sizeof(char) * MAX_SIZE);
  if ( MAX_SIZE <= strlen(user_supplied_string) ){
    die("user string too long, die evil hacker!");
  }
  dst_index = 0;
  for ( i = 0; i < strlen(user_supplied_string); i++ ){

    if( '&' == user_supplied_string[i] ){
      dst_buf[dst_index++] = '&';
      dst_buf[dst_index++] = 'a';
      dst_buf[dst_index++] = 'm';
      dst_buf[dst_index++] = 'p';
      dst_buf[dst_index++] = ';';
    }
    else if ('<' == user_supplied_string[i] ){

                                             /* encode to &lt; */

    }
    else dst_buf[dst_index++] = user_supplied_string[i];

  }
  return dst_buf;

}

    The programmer attempts to encode the ampersand character in the user-controlled string, however the length of the string is validated before the encoding procedure is applied. Furthermore, the programmer assumes encoding expansion will only expand a given character by a factor of 4, while the encoding of the ampersand expands by 5. As a result, when the encoding procedure expands the string it is possible to overflow the destination buffer if the attacker provides a string of many ampersands.

    Example 4. In the following C/C++ example, the method processMessageFromSocket() will get a message from a socket, save the message into a buffer, and place the contents of the buffer into a structure that contains the message length and the message body. Then a for loop is used to copy the message body into a local character string, which will be passed to another method for processing.

    Bad / C

                     int processMessageFromSocket(int socket) {

           // initialize variable to represent the failure case by default

           int success = -1;

                     char buffer[BUFFER_SIZE];

           char message[MESSAGE_SIZE];

                     // get message from socket and store into buffer

                     // for clarity of this example, ignore the possibility that buffer > BUFFER_SIZE

           if (getMessage(socket, buffer, BUFFER_SIZE) > 0) {

                         // place contents of the buffer into message structure

                 ExMessage *msg = recastBuffer(buffer);

                         // copy message body into string for processing

                         int index;

                 for (index = 0; index < msg->msgLength; index++) {

                   message[index] = msg->msgBody[index];

                 }

                 message[index] = '\0';

                         // process message

                 success = processMessage(message);

           }

           return success;

         }

    However, the message length variable (msgLength) from the structure is used as the condition for ending the for loop without validating that msgLength accurately reflects the actual length of the message body (CWE-606). If msgLength indicates a length that is longer than the size of a message body (CWE-130), then this can result in a buffer over-read by reading past the end of the buffer (CWE-126).

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ⓪ 하위 CWE 지원 확인: 도구가 이 번호 대신 하위 CWE(CWE-121·CWE-122·CWE-126)로 보고하는지 먼저 확인한다. 지원하면 '미지원'이 아니며, 지원하는 CWE 목록을 점검 결과·FA 사유서에 근거로 적는다.
    • ① 원문 탐지 방법(원문 효과성별): 높음: 퍼징(Fuzzing) / 보통: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.

    이 가이드에서 다루는 곳¶

    언어 뷰 항목의 단계별 지침 (적용성 판정 기준은 부록 B, 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 버퍼 크기와 루프 경계를 명세하고 경계 검사 책임을 인터페이스에 포함한다.
    구현 루프 조건은 < 길이로 작성하여 off-by-one을 방지하고 널 종료 문자 공간을 확보하며 길이 지정 함수를 사용한다.
    통합 및 시험 -fsanitize=address, 경계값 시험, 퍼징, 정적 분석 도구(예: Polyspace, Coverity)로 검출한다.
    유지보수 버퍼 크기 상수 변경 시 이를 사용하는 모든 코드의 경계를 재점검한다.
    임베디드 고려 MCU에서는 인접 메모리가 다른 변수·주변장치 레지스터일 수 있으므로 링커 맵으로 배치를 확인하고 MPU로 영역을 분리한다.

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.
