    Improper Null Termination

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: C, C++
    원문 MITRE CWE-170 (CWE 5.0)

    한 줄 요약

    문자열이나 배열을 널 문자 등 종단 문자로 끝내지 않거나 잘못 끝내는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 문자열이나 배열을 널 문자 또는 그에 준하는 종단 문자로 끝내지 않거나 잘못 끝내는 약점이다.

    원문(Description · Dimensions)

    The product does not terminate or incorrectly terminates a string or array with a null character or equivalent terminator.

    Dimensions: Code-Type = Null Termination; Code-Property = Improper

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 널 종단 오류는 흔히 두 가지 방식으로 생긴다. off-by-one 오류로 널이 경계 밖에 쓰여 오버플로로 이어질 수 있고, 프로그램이 strncpy() 함수를 잘못 호출해 널 종단 문자가 아예 추가되지 않을 수 있다. 다른 상황도 가능하다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 / 무결성 / 가용성 메모리 읽기 / 허가되지 않은 코드·명령 실행 널 문자가 빠진 경우가 가장 위험하며, 거의 확실히 정보 노출로 이어지고 임의 코드 실행에 악용될 수 있는 버퍼 오버플로 상황을 낳을 수도 있다.
    기밀성 / 무결성 / 가용성 서비스 거부: 비정상 종료·재시작 / 메모리 읽기 / 서비스 거부: 자원 소모(CPU) / 서비스 거부: 자원 소모(메모리) 문자열에 널 문자가 빠지면 대부분의 문자열 복사 함수는 문자열의 의도된 경계 밖까지 널 문자를 찾을 때까지 데이터를 읽으며, 이로 인해 세그멘테이션 오류로 인한 비정상 종료, 인접한 민감 메모리의 복사·외부 전송, 고정 크기 버퍼에 쓸 때의 버퍼 오버플로가 생길 수 있다.
    무결성 / 가용성 메모리 수정 / 서비스 거부: 비정상 종료·재시작 잘못 놓인 널 문자는 여러 보안 문제를 낳을 수 있으며, 가장 큰 문제는 버퍼 오버플로의 일종과 임의 위치 쓰기 조건(write-what-where)으로 유효한 데이터나 명령어 위에 널 문자가 쓰여 데이터가 손상되는 것이다. 무작위 위치의 널 문자는 시스템을 정의되지 않은 상태로 만들어 비정상 종료가 나기 쉽게 하고, 메모리의 다른 데이터를 손상시킬 수 있다.
    무결성 / 기밀성 / 가용성 / 접근 통제 / 기타 실행 논리 변경 / 허가되지 않은 코드·명령 실행 널 문자가 프로세스 흐름을 손상시키거나 접근 통제 플래그에 영향을 주면 임의 코드 실행을 허용하는 논리 오류로 이어질 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    CWE 단계(Phase) 전략 요지
    요구사항(Requirements) — 이런 문제에 취약하지 않은 언어를 쓴다. 단, 취약한 언어로 작성되었을 수 있는 하위 수준 구성요소와의 널 바이트 상호작용 오류(CWE-626)에 주의한다.
    원문

    Use a language that is not susceptible to these issues. However, be careful of null byte interaction errors (CWE-626) with lower-level constructs that may be written in a language that is susceptible.

    설계 (본문 제4장)¶

    원문 완화책 없음

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 사용하는 모든 문자열 함수가 널 문자를 어떻게 덧붙이는지 완전히 이해하고, 문자열 끝에 널을 덧붙일 때 off-by-one 오류에 주의한다.
    원문

    Ensure that all string functions used are understood fully as to how they append null characters. Also, be wary of off-by-one errors when appending nulls to the end of strings.
    구현(Implementation) — 성능 제약이 허용하면 문자열 버퍼의 널 종단을 검증하는 별도 코드를 추가할 수 있으나, 이는 다소 단순하고 오류가 생기기 쉬운 해결책이다.
    원문

    If performance constraints permit, special code can be added that validates null-termination of string buffers, this is a rather naive and error-prone solution.
    구현(Implementation) — 길이 제한이 있는 문자열 처리 함수로 바꾸고, 결함과 함께 보고된 버퍼 오버런 추적 경로에 관련된 버퍼 길이를 점검한다.
    원문

    Switch to bounded string manipulation functions. Inspect buffer lengths involved in the buffer overrun trace reported with the defect.
    구현(Implementation) — 버퍼를 널로 채우는 코드를 추가한다. 단, 널로 끝나지 않은 문자열이 버퍼의 물리적 끝에 쓰이지 않도록 버퍼 길이는 여전히 점검해야 한다.
    원문

    Add code that fills buffers with nulls (however, the length of buffers still needs to be inspected, to ensure that the non null-terminated string is not written at the physical end of the buffer).

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 외부에서 받은 고정 길이 문자열 필드(상태 보고 메시지의 장치 식별자, 임무 계획 파일의 경로점 이름)는 글자를 꽉 채우면 끝에 종단 문자('\0')가 없다. 이 필드를 운용 로그·지도 화면에 표시할 문자열로 바꾼다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>

#define UNIT_ID_LEN 8   /* ICD: 장치 식별자 필드 8바이트, 남는 칸만 '\0' */

typedef struct {
    unsigned char kind;
    char unit_id[UNIT_ID_LEN];
    unsigned char status;
} HealthReport;

/* 상태 보고 메시지의 장치 식별자를 운용 로그에 남긴다 */
static size_t log_unit(const HealthReport *rep)
{
    char label[UNIT_ID_LEN];
    strncpy(label, rep->unit_id, sizeof label);  /* 8글자를 꽉 채우면 '\0'이 붙지 않는다 */
    size_t n = strlen(label);                    /* 종단 문자를 찾아 label 밖까지 읽는다 */
    printf("unit %.*s status %u\n", (int)n, label, rep->status);
    return n;
}

int main(void)
{
    HealthReport rep = {0x11, {'R', 'A', 'D', 'A', 'R', '-', '0', '7'}, 3};
    log_unit(&rep);
    return 0;
}

    strncpy는 원본이 대상 크기만큼 차 있으면 종단 문자를 붙이지 않는다. 그 결과를 strlen으로 재면 label 배열 밖의 스택 메모리까지 읽어 길이와 출력 내용이 틀어진다.

    좋은 예

    #include <stdio.h>
#include <string.h>

#define UNIT_ID_LEN 8   /* ICD: 장치 식별자 필드 8바이트, 남는 칸만 '\0' */

typedef struct {
    unsigned char kind;
    char unit_id[UNIT_ID_LEN];
    unsigned char status;
} HealthReport;

/* 상태 보고 메시지의 장치 식별자를 운용 로그에 남긴다 */
static size_t log_unit(const HealthReport *rep)
{
    char label[UNIT_ID_LEN + 1];                 /* 종단 문자 자리를 따로 둔다 */
    const char *nul = memchr(rep->unit_id, '\0', UNIT_ID_LEN);
    size_t n = nul ? (size_t)(nul - rep->unit_id) : UNIT_ID_LEN;  /* 필드 안에서만 길이를 잰다 */
    memcpy(label, rep->unit_id, n);
    label[n] = '\0';                             /* 복사한 뒤 직접 종단한다 */
    printf("unit %s status %u\n", label, rep->status);
    return n;
}

int main(void)
{
    HealthReport rep = {0x11, {'R', 'A', 'D', 'A', 'R', '-', '0', '7'}, 3};
    log_unit(&rep);
    return 0;
}

    종단 문자 자리를 한 칸 더 잡고, 길이는 memchr로 필드 범위 안에서만 잰 뒤 복사하고 직접 종단한다. 고정 길이 필드는 '종단 문자가 없을 수 있다'를 기본 가정으로 둔다(LC-04).

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: stack-buffer-overflow 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-170 Demonstrative Example 3(strncpy가 종단 문자를 붙이지 않는 경우) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 입력데이터 검증 및 표현 1-17 '널 종료 문제'(인쇄 65쪽) 참고

    C++

    나쁜 예

    #include <cstdio>
#include <cstring>
#include <string>
#include <vector>

constexpr std::size_t kNameField = 6;  // 임무 계획 파일: 경로점 이름 6바이트, 남는 칸만 '\0'

// 파일에서 읽은 이름 필드로 지도 화면에 표시할 이름표를 만든다
std::string waypoint_label(const std::vector<char> &field) {
    return std::string(field.data());   // '\0'이 반드시 있다고 가정하고 끝까지 읽는다
}

int main() {
    std::vector<char> field(kNameField);
    std::memcpy(field.data(), "ALPHA7", kNameField);  // 6글자를 꽉 채운 이름
    std::string label = waypoint_label(field);
    std::printf("waypoint %s\n", label.c_str());
    return 0;
}

    std::string(const char*) 생성자는 '\0'이 나올 때까지 읽는다. 6바이트를 꽉 채운 이름 필드에는 종단 문자가 없어 벡터 버퍼 밖의 힙 메모리까지 읽는다.

    좋은 예

    #include <algorithm>
#include <cstdio>
#include <cstring>
#include <string>
#include <vector>

constexpr std::size_t kNameField = 6;  // 임무 계획 파일: 경로점 이름 6바이트, 남는 칸만 '\0'

// 파일에서 읽은 이름 필드로 지도 화면에 표시할 이름표를 만든다
std::string waypoint_label(const std::vector<char> &field) {
    auto stop = std::find(field.begin(), field.end(), '\0');  // 필드 범위 안에서만 끝을 찾는다
    return std::string(field.begin(), stop);                  // 길이를 정해 복사, 종단은 string이 붙인다
}

int main() {
    std::vector<char> field(kNameField);
    std::memcpy(field.data(), "ALPHA7", kNameField);  // 6글자를 꽉 채운 이름
    std::string label = waypoint_label(field);
    std::printf("waypoint %s\n", label.c_str());
    return 0;
}

    std::find로 필드 범위 안에서 끝을 찾고 반복자 구간 생성자로 길이를 정해 복사한다. 종단 문자는 std::string이 스스로 붙인다.

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: heap-buffer-overflow 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-170 Demonstrative Example 1(읽은 데이터에 종단 문자가 있다고 가정) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(언어상 생기지 않음): C#의 string과 배열은 길이를 따로 가지므로 종단 누락으로 넘쳐 읽지 않는다. unsafe 코드와 P/Invoke 경계(예: Marshal.PtrToStringAnsi는 '\0'까지 읽는다)에서는 같은 문제가 생기므로 그 범위에는 C 예시와 C 지침을 적용한다(LCS-02).

    Java — 예시 없음(언어상 생기지 않음): Java의 String과 배열은 길이를 따로 가지고 종단 문자에 기대지 않으므로 종단 누락 때문에 경계 밖을 읽는 일이 없다. 다만 고정 길이 바이트 필드를 문자열로 바꿀 때 남는 '\0'이 섞이지 않게 길이를 정해 변환하고, JNI로 부르는 네이티브 코드에는 C 예시를 적용한다(LJ-08).

    Python — 예시 없음(언어상 생기지 않음): Python의 str·bytes는 길이를 따로 가지고 종단 문자에 기대지 않으므로 종단 누락 때문에 경계 밖을 읽는 일이 없다. 다만 고정 길이 바이트 필드(struct·ctypes c_char 배열)를 문자열로 바꿀 때 남는 '\0'이 섞이지 않게 길이를 정해 변환하고(bytes.split(b'\0', 1)[0] 등), ctypes의 c_char_p·string_at처럼 '\0'까지 읽는 함수에 넘기는 버퍼에는 C 예시를 적용한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 3건)

    Example 1. The following code reads from cfgfile and copies the input into inputbuf using strcpy(). The code mistakenly assumes that inputbuf will always contain a NULL terminator.

    Bad / C

    #define MAXLEN 1024
...
char *pathbuf[MAXLEN];
...
read(cfgfile,inputbuf,MAXLEN); //does not null terminate
strcpy(pathbuf,inputbuf); //requires null terminated input
...

    The code above will behave correctly if the data read from cfgfile is null terminated on disk as expected. But if an attacker is able to modify this input so that it does not contain the expected NULL character, the call to strcpy() will continue copying from memory until it encounters an arbitrary NULL character. This will likely overflow the destination buffer and, if the attacker can control the contents of memory immediately following inputbuf, can leave the application susceptible to a buffer overflow attack.

    Example 2. In the following code, readlink() expands the name of a symbolic link stored in pathname and puts the absolute path into buf. The length of the resulting value is then calculated using strlen().

    Bad / C

    char buf[MAXPATH];
...
readlink(pathname, buf, MAXPATH);
int length = strlen(buf);
...

    The code above will not always behave correctly as readlink() does not append a NULL byte to buf. Readlink() will stop copying characters once the maximum size of buf has been reached to avoid overflowing the buffer, this will leave the value buf not NULL terminated. In this situation, strlen() will continue traversing memory until it encounters an arbitrary NULL character further on down the stack, resulting in a length value that is much larger than the size of string. Readlink() does return the number of bytes copied, but when this return value is the same as stated buf size (in this case MAXPATH), it is impossible to know whether the pathname is precisely that many bytes long, or whether readlink() has truncated the name to avoid overrunning the buffer. In testing, vulnerabilities like this one might not be caught because the unused contents of buf and the memory immediately following it may be NULL, thereby causing strlen() to appear as if it is behaving correctly.

    Example 3. While the following example is not exploitable, it provides a good example of how nulls can be omitted or misplaced, even when "safe" functions are used:

    Bad / C

    #include <stdio.h>
#include <string.h>

int main() {

  char longString[] = "String signifying nothing";
  char shortString[16];

  strncpy(shortString, longString, 16);
  printf("The last character in shortString is: %c (%1$x)\n", shortString[15]);
  return (0);

}

    The above code gives the following output: "The last character in shortString is: n (6e)". So, the shortString array does not end in a NULL character, even though the "safe" string function strncpy() was used. The reason is that strncpy() does not implicitly add a NULL character at the end of the string when the source is equal in length or longer than the provided size.

    방법 요지 효과성
