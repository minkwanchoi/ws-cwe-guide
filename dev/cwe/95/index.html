    Improper Neutralization of Directives in Dynamically Evaluated Code

    항목 내용
    추상화 수준 변형(Variant)
    상태 미완성(Incomplete)
    소속 언어 뷰 Java(CWE-660)
    가이드 적용성 조건부 — 동적 코드 평가(eval 등) 사용
    적용 플랫폼 언어: Java, JavaScript, Python, Perl, PHP, Ruby, 인터프리터 언어(Interpreted) · 기술: 인공지능·기계학습(AI/ML)
    원문 MITRE CWE-95 (CWE 5.0)

    한 줄 요약

    상위 구성요소에서 받은 입력의 코드 구문을 무력화하지 않거나 잘못 무력화한 채 eval 같은 동적 평가 호출에 쓰는 약점이다.

    설명(Description)¶

    제품이 상위 구성요소에서 입력을 받으면서, 그 입력을 동적 평가 호출(예: "eval")에 쓰기 전에 코드 구문을 무력화(neutralize)하지 않거나 잘못 무력화하는 약점이다.

    원문(Description)

    The product receives input from an upstream component, but it does not neutralize or incorrectly neutralizes code syntax before using the input in a dynamic evaluation call (e.g. "eval").

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 실현(REALIZATION): 이 약점은 아키텍처 보안 전술을 구현하는 과정에서 생긴다.
    구현(Implementation) 구현 이 약점은 많은 수의 함수를 호출하거나 많은 변수를 설정하려 할 수 있는 핸들러/디스패치 절차에서 흔히 나타난다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 파일·디렉터리 읽기 / 애플리케이션 데이터 읽기 삽입된 코드가 제한된 데이터나 파일에 접근할 수 있다.
    접근 통제 보호 메커니즘 우회 일부 경우 삽입 가능한 코드가 인증을 제어해 원격 취약점으로 이어질 수 있다.
    접근 통제 권한 획득 또는 신원 도용 삽입된 코드는 공격자가 직접 접근하지 못하도록 되어 있는 자원에 접근할 수 있다.
    무결성 / 기밀성 / 가용성 / 기타 허가되지 않은 코드·명령 실행 삽입되는 제어 평면 데이터는 언제나 데이터 조회나 쓰기에 부수적으로 따라오므로 코드 삽입 공격은 거의 모든 경우 데이터 무결성 손실로 이어질 수 있으며, 흔히 임의 코드 실행을 일으키거나 적어도 실행될 수 있는 코드를 바꿀 수 있다.
    부인 방지 행위 은닉 삽입된 제어 코드가 수행하는 동작은 흔히 로그에 남지 않는다.

    완화책(Potential Mitigations)¶

    원문 완화책 4건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) / 구현(Implementation) 리팩터링 가능하면 eval()을 전혀 쓰지 않아도 되도록 코드를 리팩터링한다. (구현 단계에도 해당)
    원문

    If possible, refactor your code so that it does not need to use eval() at all.

    		 —

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) 입력값 검증 모든 입력을 악의적이라고 가정하고, 명세에 엄격히 맞는 입력만 받는 허용목록('accept known good') 방식으로 검증해 맞지 않는 입력은 거부하거나 맞게 변환한다. 검증할 때는 길이·유형·허용 값 전체 범위·누락/추가 입력·구문·관련 필드 간 일관성·업무 규칙을 모두 고려한다(예: 'boat'는 영숫자만 있어 구문상 유효하지만 'red'·'blue' 같은 색상만 받는 필드라면 유효하지 않다). 악의적이거나 잘못된 입력을 찾는 방식(거부목록)에만 의존하지 않는다. 이 방식은 특히 코드 환경이 바뀔 때 원치 않는 입력을 하나 이상 놓치기 쉬워 검증이 우회될 수 있다. 다만 거부목록은 공격 탐지나 즉시 거부할 정도로 잘못된 입력을 가려내는 데는 쓸모가 있을 수 있다.
    원문

    Assume all input is malicious. Use an "accept known good" input validation strategy, i.e., use a list of acceptable inputs that strictly conform to specifications. Reject any input that does not strictly conform to specifications, or transform it into something that does.

    When performing input validation, consider all potentially relevant properties, including length, type of input, the full range of acceptable values, missing or extra inputs, syntax, consistency across related fields, and conformance to business rules. As an example of business rule logic, "boat" may be syntactically valid because it only contains alphanumeric characters, but it is not valid if the input is only expected to contain colors such as "red" or "blue."

    Do not rely exclusively on looking for malicious or malformed inputs. This is likely to miss at least one undesirable input, especially if the code's environment changes. This can give attackers enough room to bypass the intended validation. However, denylists can be useful for detecting potential attacks or determining which inputs are so malformed that they should be rejected outright.

    		 —
    구현(Implementation) — 입력은 검증하기 전에 애플리케이션의 현재 내부 표현으로 디코딩·정규화하고(CWE-180, CWE-181), 같은 입력을 실수로 두 번 디코딩하지 않게 한다(CWE-174). 이런 오류가 있으면 검사를 통과한 뒤에 위험한 입력이 들어와 허용목록 방식이 우회될 수 있다. OWASP ESAPI Canonicalization 컨트롤 같은 라이브러리를 쓴다. 입력이 더 이상 바뀌지 않을 때까지 정규화를 반복하는 것을 고려한다. 이중 디코딩 같은 상황은 피할 수 있지만, 제대로 인코딩된 위험 내용을 담아도 되는 입력이 의도치 않게 바뀔 수 있다.
    원문

    Inputs should be decoded and canonicalized to the application's current internal representation before being validated (CWE-180, CWE-181). Make sure that your application does not inadvertently decode the same input twice (CWE-174). Such errors could be used to bypass allowlist schemes by introducing dangerous inputs after they have been checked. Use libraries such as the OWASP ESAPI Canonicalization control.

    Consider performing repeated canonicalization until your input does not change any more. This will avoid double-decoding and similar scenarios, but it might inadvertently modify inputs that are allowed to contain properly-encoded dangerous content.

    		 —
    구현(Implementation) — Python 프로그램에서는 코드를 실행하지 않도록 의도적으로 설계된 ast.literal_eval() 함수를 eval 대신 쓰도록 흔히 권장한다. 그러나 공격자가 깊게 중첩된 구조로 메모리나 스택을 과도하게 소비시킬 수 있으므로 [REF-1372], Python 문서는 신뢰할 수 없는 데이터에 ast.literal_eval()을 쓰지 말라고 권한다 [REF-1373].
    원문

    For Python programs, it is frequently encouraged to use the ast.literal_eval() function instead of eval, since it is intentionally designed to avoid executing code. However, an adversary could still cause excessive memory or stack consumption via deeply nested structures [REF-1372], so the python documentation discourages use of ast.literal_eval() on untrusted data [REF-1373].

    		 권장하지 않는 관행(Discouraged Common Practice)

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. edit-config.pl: This CGI script is used to modify settings in a configuration file.

    Bad / Perl

    use CGI qw(:standard);

sub config_file_add_key {

  my ($fname, $key, $arg) = @_;

                             # code to add a field/key to a file goes here

}

sub config_file_set_key {

  my ($fname, $key, $arg) = @_;

                             # code to set key to a particular file goes here

}

sub config_file_delete_key {

  my ($fname, $key, $arg) = @_;

                             # code to delete key from a particular file goes here

}

sub handleConfigAction {

  my ($fname, $action) = @_;
  my $key = param('key');
  my $val = param('val');

                             # this is super-efficient code, especially if you have to invoke

                             # any one of dozens of different functions!

  my $code = "config_file_$action_key(\$fname, \$key, \$val);";
  eval($code);

}

$configfile = "/home/cwe/config.txt";
print header;
if (defined(param('action'))) {
  handleConfigAction($configfile, param('action'));
}
else {
  print "No action specified!\n";
}

    The script intends to take the 'action' parameter and invoke one of a variety of functions based on the value of that parameter - config_file_add_key(), config_file_set_key(), or config_file_delete_key(). It could set up a conditional to invoke each function separately, but eval() is a powerful way of doing the same thing in fewer lines of code, especially when a large number of functions or variables are involved. Unfortunately, in this case, the attacker can provide other values in the action parameter, such as:

    Attack

    add_key(",","); system("/bin/ls");

    This would produce the following string in handleConfigAction():

    Result

    config_file_add_key(",","); system("/bin/ls");

    Any arbitrary Perl code could be added after the attacker has "closed off" the construction of the original function call, in order to prevent parsing errors from causing the malicious eval() to fail before the attacker's payload is activated. This particular manipulation would fail after the system() call, because the "_key(\$fname, \$key, \$val)" portion of the string would cause an error, but this is irrelevant to the attack because the payload has already been activated.

    Example 2. This simple python3 script asks a user to supply a comma-separated list of numbers as input and adds them together.

    Bad / Python

                      def main():

                      sum = 0

            try:

                          numbers = eval(input("Enter a comma-separated list of numbers: "))

            except SyntaxError:

                  print("Error: invalid input")

                  return

                      for num in numbers:

                          sum = sum + num

                      print(f"Sum of {numbers} = {sum}")

                  main()

    The eval() function can take the user-supplied list and convert it into a Python list object, therefore allowing the programmer to use list comprehension methods to work with the data. However, if code is supplied to the eval() function, it will execute that code. For example, a malicious user could supply the following string:

    Attack

    __import__('subprocess').getoutput('rm -r *')

    This would delete all the files in the current directory. For this reason, it is not recommended to use eval() with untrusted input.

    A way to accomplish this without the use of eval() is to apply an integer conversion on the input within a try/except block. If the user-supplied input is not numeric, this will raise a ValueError. By avoiding eval(), there is no opportunity for the input string to be executed as code.

    Good / Python

                      def main():

                      sum = 0

                      numbers = input("Enter a comma-separated list of numbers: ").split(",")

                      try:

                          for num in numbers:

                              sum = sum + int(num)

                          print(f"Sum of {numbers} = {sum}")

                      except ValueError:

                          print("Error: invalid input")

                  main()

    An alternative, commonly-cited mitigation for this kind of weakness is to use the ast.literal_eval() function, since it is intentionally designed to avoid executing code. However, an adversary could still cause excessive memory or stack consumption via deeply nested structures [REF-1372], so the python documentation discourages use of ast.literal_eval() on untrusted data [REF-1373].

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법은 자동 정적 분석뿐이다. 다른 정적 분석 도구·컴파일러 경고로 점검한다.

    언어 뷰 항목의 단계별 지침 (적용성 판정 기준은 부록 B, 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 동적 코드 평가(eval, ScriptEngine) 사용을 설계 단계에서 배제하고 필요 시 허용 기능을 허용목록으로 정의한다.
    구현 ScriptEngine.eval, Nashorn/Groovy 평가에 외부 입력 전달을 금지하고 허용 값 목록 기반 검증 후 정해진 로직으로 분기한다.
    통합 및 시험 정적 분석 도구(예: SpotBugs(find-sec-bugs), Fortify)로 동적 평가 호출 경로를 추적하고 코드 삽입 페이로드로 시험한다.
    유지보수 동적 평가 사용처를 목록화하여 변경 시 보안 검토를 거치고, 스크립트 엔진은 OS 수준 격리(프로세스 분리·최소 권한)로 제한한다(SecurityManager는 Java 17에서 제거 예정으로 표시, Java 24에서 비활성화).
    임베디드 고려 JVM이 올라가는 SBC에서 스크립트 엔진 탑재를 최소화하고 원격 입력으로 스크립트가 실행되지 않게 한다.

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 2건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.

    축 지침
    개발 언어 (2건) LPY-04 동적 코드 실행 금지, LPY-09 Bandit·린터·취약점 점검
