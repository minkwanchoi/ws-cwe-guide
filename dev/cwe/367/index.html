    Time-of-check Time-of-use (TOCTOU) Race Condition

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    적용 플랫폼 언어 무관
    원문 MITRE CWE-367 (CWE 5.0)

    한 줄 요약

    자원 상태를 검사한 뒤 사용하기 전에 상태가 바뀌어 검사 결과가 무효가 될 수 있는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 자원을 사용하기 전에 그 상태를 검사하지만, 검사와 사용 사이에 자원 상태가 바뀌어 검사 결과를 무효로 만들 수 있다.

    원문(Description)

    The product checks the state of a resource before using that resource, but the resource's state can change between the check and the use in a way that invalidates the results of the check.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 공격자가 검사와 사용 사이에 자원 상태에 영향을 줄 수 있으면 이 약점은 보안과 관련될 수 있으며, 이는 파일, 메모리, 멀티스레드 프로그램의 변수 같은 공유 자원에서 일어날 수 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기타 실행 논리 변경 / 예상하지 못한 상태 공격자는 원래 권한이 없는 자원에 접근할 수 있다.
    무결성 / 기타 애플리케이션 데이터 수정 / 파일·디렉터리 수정 / 메모리 수정 / 기타 이런 경쟁조건을 이용해 해당 사용자가 보통 읽거나 쓸 수 없는 자원에 대한 읽기·쓰기 접근을 얻을 수 있다.
    무결성 / 기타 기타 악의적 사용자가 해당 자원이나 (손상된 자원을 통해) 다른 자원을 원치 않는 방식으로 바꿀 수 있다.
    부인 방지 행위 은닉 파일 등 자원을 정당한 방식이 아니라 이 방법으로 쓰면 그 활동이 로그에 남지 않을 수 있다.
    부인 방지 / 기타 기타 일부 경우 악의적 사용자가 원래 접근할 수 없는 파일(예: 로그 파일)을 삭제할 수 있다.
    기타 예상하지 못한 상태 자원이 예상하지 못한 상태일 때 제품이 잘못된 동작을 할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 7건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 여러 프로세스의 파일 작업이 서로 끼어드는 것을 제한한다.
    원문

    Limit the interleaving of operations on files from multiple processes.
    구현(Implementation) / 아키텍처·설계(Architecture and Design) — 작업을 원자적으로 수행할 수 없고 여러 프로세스·스레드가 자원을 공유해야 한다면, 자원 검사와 사용 사이의 시간(CPU 사이클)을 줄이도록 한다. 단, 이는 문제를 고치지 못하며 공격 성공을 더 어렵게 만들 수 있을 뿐이다. (구현 단계에도 해당)
    원문

    If you cannot perform operations atomically and you must share access to the resource between multiple processes or threads, then try to limit the amount of time (CPU cycles) between the check and use of the resource. This will not fix the problem, but it could make it more difficult for an attack to succeed.
    아키텍처·설계(Architecture and Design) — 자원을 효과적으로 보호하는 데 쓸 수 있는 환경 차원의 잠금 메커니즘이 있는지 확인한다.
    원문

    Ensure that some environmental locking mechanism can be used to protect resources effectively.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — TOCTOU 취약점에 대한 가장 기본적인 조언은 사용 전에 검사를 하지 않는 것이다. 이는 상태와 동일성(identity)을 보장할 수 없는 자원에 함수를 실행한다는 근본 문제를 해결하지는 못하지만, 검사가 주는 잘못된 안도감을 줄이는 데는 도움이 된다.
    원문

    The most basic advice for TOCTOU vulnerabilities is to not perform a check before the use. This does not resolve the underlying issue of the execution of a function on a resource whose state and identity cannot be assured, but it does help to limit the false sense of security given by the check.
    구현(Implementation) — 변경 대상 파일을 현재 사용자·그룹이 소유한 경우, 해당 문장을 실행할 때 유효 gid와 uid를 현재 사용자·그룹의 것으로 설정한다.
    원문

    When the file being altered is owned by the current user and group, set the effective gid and uid to that of the current user and group when executing this statement.
    구현(Implementation) — 사용 호출 뒤에 자원을 다시 검사해 동작이 올바르게 수행되었는지 확인한다.
    원문

    Recheck the resource after the use call to verify that the action was taken appropriately.
    구현(Implementation) — 잠금을 검사 뒤가 아니라 검사 전에 걸어, 검사한 자원이 사용 시점에도 같은 상태이도록 한다.
    원문

    Ensure that locking occurs before the check, as opposed to afterwards, such that the resource, as checked, is the same as it is when in use.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 두 태스크(또는 프로세스)가 같은 자원을 다룬다. 정비 기록 파일을 쓰기 전에 '일반 파일인지' 확인하거나, 빈 정비 베이·전원 팩·링크 슬롯이 있는지 확인한 뒤 차감한다. 검사와 사용 사이의 틈에 다른 쪽이 끼어들면 검사 결과가 낡은 채로 사용된다. 예시는 그 틈을 시험용 장치(바꿔치기 함수·동기화 장치)로 일부러 열어 결과가 매번 같게 재현한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

/* 시험 재현: 검사와 사용 사이에 다른 프로세스가 기록 파일을 키 파일 링크로 바꾼다 */
static void race_window(const char *path)
{
    unlink(path);
    if (symlink("crypto_keys.dat", path) != 0) perror("symlink");
}

static int save_maint_record(const char *path, const char *record)
{
    struct stat info;
    if (lstat(path, &info) != 0 || !S_ISREG(info.st_mode)) {  /* 검사: 이름으로 확인 */
        return -1;
    }
    race_window(path);
    FILE *log = fopen(path, "w");              /* 사용: 같은 이름을 다시 연다 */
    if (log == NULL) return -1;
    fputs(record, log);
    return fclose(log);
}

static void put_text(const char *name, const char *text)
{
    FILE *f = fopen(name, "w");
    if (f) { fputs(text, f); fclose(f); }
}

int main(void)
{
    put_text("crypto_keys.dat", "KEYSET-A");
    unlink("maint.log");                        /* 이전 실행이 남긴 링크를 따라가지 않게 지운다 */
    put_text("maint.log", "");
    printf("save result %d\n", save_maint_record("maint.log", "PBIT OK"));

    char now[32] = "";
    FILE *k = fopen("crypto_keys.dat", "r");
    if (k) { if (!fgets(now, sizeof now, k)) now[0] = '\0'; fclose(k); }
    printf("key file '%s': %s\n", now, strcmp(now, "KEYSET-A") ? "PROTECTED FILE OVERWRITTEN" : "intact");
    return 0;
}

    lstat()으로 경로 이름을 검사한 뒤 fopen()으로 같은 이름을 다시 연다. 그 사이에 다른 프로세스가 기록 파일을 키 파일로 가는 심볼릭 링크로 바꾸면, 높은 권한의 정비 프로그램이 보호된 키 파일을 덮어쓴다.

    좋은 예

    #include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

/* 시험 재현: 여는 순간 직전에 다른 프로세스가 기록 파일을 키 파일 링크로 바꾼다 */
static void race_window(const char *path)
{
    unlink(path);
    if (symlink("crypto_keys.dat", path) != 0) perror("symlink");
}

static int save_maint_record(const char *path, const char *record)
{
    race_window(path);
    int fd = open(path, O_WRONLY | O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK);  /* 먼저 열고 링크는 거부, FIFO에 막히지 않는다 */
    if (fd < 0) {
        printf("open refused: %s\n", strerror(errno));
        return -1;
    }
    struct stat info;                           /* 검사: 연 핸들 기준, 하드 링크(st_nlink != 1)도 거부 */
    if (fstat(fd, &info) != 0 || !S_ISREG(info.st_mode) || info.st_nlink != 1 || ftruncate(fd, 0) != 0) {
        close(fd);
        return -1;
    }
    ssize_t n = write(fd, record, strlen(record));
    close(fd);
    return n == (ssize_t)strlen(record) ? 0 : -1;   /* 부분 쓰기도 실패로 돌려준다 */
}

static void put_text(const char *name, const char *text)
{
    FILE *f = fopen(name, "w");
    if (f) { fputs(text, f); fclose(f); }
}

int main(void)
{
    put_text("crypto_keys.dat", "KEYSET-A");
    unlink("maint.log");                        /* 이전 실행이 남긴 링크를 따라가지 않게 지운다 */
    put_text("maint.log", "");
    printf("save result %d\n", save_maint_record("maint.log", "PBIT OK"));

    char now[32] = "";
    FILE *k = fopen("crypto_keys.dat", "r");
    if (k) { if (!fgets(now, sizeof now, k)) now[0] = '\0'; fclose(k); }
    printf("key file '%s': %s\n", now, strcmp(now, "KEYSET-A") ? "PROTECTED FILE OVERWRITTEN" : "intact");
    return 0;
}

    먼저 O_NOFOLLOW로 열어 심볼릭 링크를 거부하고, O_NONBLOCK으로 경로가 FIFO로 바뀌어도 open이 멈추지 않게 하며, 검사는 연 핸들에 fstat()으로 해 일반 파일이 아니거나 다른 이름(하드 링크)이 함께 있으면(st_nlink != 1) 거부한다. 검사와 사용이 같은 파일 객체를 가리키므로 이름 바꿔치기가 통하지 않는다. 일부만 쓴 경우도 실패로 돌려준다. 기록 폴더 자체를 다른 계정이 쓸 수 없게 두는 것도 함께 한다.

    검증: 실행 결과 · Linux(gcc)에서 빌드 — 나쁜 예에서 PROTECTED FILE OVERWRITTEN 검출, 좋은 예에서 미검출·open refused:…key file 'KEYSET-A': intact 출력 확인 · 참고: MITRE CWE-367 Demonstrative Example 2(access() 검사 뒤 fopen()) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 시간 및 상태 3-1 '경쟁 조건: 검사시점과 사용시점(TOCTOU)'(인쇄 140쪽) 참고

    C++

    나쁜 예

    #include <condition_variable>
#include <cstdio>
#include <mutex>
#include <thread>

// 시험 재현: 두 태스크가 모두 '검사'를 마친 뒤에야 '사용'으로 넘어가게 순서를 고정
class Rendezvous {
    std::mutex m_;
    std::condition_variable cv_;
    int arrived_ = 0;
public:
    void meet() {
        std::unique_lock<std::mutex> lk(m_);
        if (++arrived_ == 2) cv_.notify_all();
        else cv_.wait(lk, [this] { return arrived_ >= 2; });
    }
};

int bays_left = 1;   // 비어 있는 정비 베이 수
Rendezvous window;

void assign_request(const char *console) {
    if (bays_left > 0) {          // 검사
        window.meet();                    // 검사와 사용 사이에 다른 태스크가 끼어든다
        --bays_left;              // 사용: 검사 결과가 이미 낡았다
        std::printf("%s: assignment command issued\n", console);
    }
}

int main() {
    std::thread a(assign_request, "console-1");
    std::thread b(assign_request, "console-2");
    a.join();
    b.join();
    std::printf("bays_left=%d\n", bays_left);
    return 0;
}

    빈 정비 베이 수를 검사한 뒤 차감하기까지가 보호되지 않아, 두 콘솔 태스크가 모두 '1개 남음'을 보고 둘 다 할당 명령을 낸다. 실제 장비에서는 스케줄러 선점이나 다중 코어가 이 틈을 만든다.

    #include <condition_variable>
#include <cstdio>

// 시험 재현: 두 태스크가 같은 순간에 할당을 요청하도록 출발을 맞춘다
class Rendezvous {
    std::mutex m_;
    std::condition_variable cv_;
    int arrived_ = 0;
public:
    void meet() {
        std::unique_lock<std::mutex> lk(m_);
        if (++arrived_ == 2) cv_.notify_all();
        else cv_.wait(lk, [this] { return arrived_ >= 2; });
    }
};

int bays_left = 1;
std::mutex bay_lock;   // 남은 수 검사와 차감을 한 구간으로 묶는다
Rendezvous window;

void assign_request(const char *console) {
    window.meet();
    std::lock_guard<std::mutex> guard(bay_lock);
    if (bays_left > 0) {
        --bays_left;
        std::printf("%s: assignment command issued\n", console);
    } else {
        std::printf("%s: denied, no bay left\n", console);
    }
}

int main() {
    std::thread a(assign_request, "console-1");
    std::thread b(assign_request, "console-2");
    a.join();
    b.join();
    std::printf("bays_left=%d\n", bays_left);
    return 0;
}

internal sealed class UplinkPool(int freeSlots)
{
    // 검사와 차감을 한 임계구역으로 묶는다. System.Threading.Lock은 .NET 9 이상
    // (이전 판은 private readonly object _gate = new();)
    private readonly Lock _gate = new();
    private int _free = freeSlots;

    public int FreeSlots { get { lock (_gate) { return _free; } } }

    public void Reserve(string console)
    {
        lock (_gate)
        {
            if (_free == 0)
            {
                Console.WriteLine($"{console}: denied, no slot");
                return;
            }
            _free--;
        }
        Console.WriteLine($"{console}: slot reserved");
    }
}

    import java.util.concurrent.CountDownLatch;

public class Example {

    import java.util.concurrent.CountDownLatch;

public class Example {
    static final AtomicInteger FUEL_CELLS = new AtomicInteger(1);
    static final CountDownLatch START = new CountDownLatch(2);

        START.countDown();                          // 시험 재현: 두 정비조가 동시에 요청

            START.await();
        } catch (InterruptedException e) {

        }
    }

    The call to access() behaves as expected, and returns 0 if the user running the program has the necessary permissions to write to the file, and -1 otherwise. By tricking the program into performing an operation that would otherwise be impermissible, the attacker has gained elevated privileges. This type of vulnerability is not limited to programs with root privileges.     요구사항 분석 —
    설계 공유 자원 접근은 원자적 연산이나 잠금으로 보호하도록 설계하고, 검사와 사용을 분리하지 않는 인터페이스를 정의한다.
    구현(C·C++) access()→open() 대신 open() 후 fstat()으로 확인한다. 공유 데이터는 뮤텍스(mutex)로 검사·사용 구간 전체를 보호한다.
    구현(Java) Files.exists() 후 생성 대신 Files.createFile()의 원자적 생성과 예외 처리를 사용하고, synchronized/Lock으로 임계구역(critical section)을 보호한다.
    통합 및 시험 스트레스·병행성 시험, 공유 메모리 경쟁을 잡는 ThreadSanitizer(-fsanitize=thread) 동적 분석(dynamic analysis), 정적 분석의 경쟁조건(race condition) 탐지를 수행한다. 파일 TOCTOU는 코드 리뷰와 바꿔치기 시험으로 확인한다.
    유지보수 태스크 우선순위·스케줄 변경 시 임계구역 영향을 재분석한다.
    임베디드 고려 ISR(인터럽트 서비스 루틴)과 태스크가 공유하는 변수는 volatile 및 인터럽트 차단 또는 원자 명령으로 보호하고, 다중 바이트 변수(8비트 AVR의 16비트 변수)를 비원자적으로 읽지 않는다.

    기준선 활동 1건

    • I-07 동시성·공유자원 보호 (구현)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 8건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.

    축 지침
