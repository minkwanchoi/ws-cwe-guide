    Signal Handler with Functionality that is not Asynchronous-Safe

    항목 내용
    추상화 수준 변형(Variant)
    상태 미완성(Incomplete)
    소속 언어 뷰 C(CWE-658)
    가이드 적용성 조건부 — 시그널(POSIX signal) 사용
    적용 플랫폼 언어: 언어 무관, C
    원문 MITRE CWE-828 (CWE 5.0)

    한 줄 요약

    재진입이 불가능하거나 중단될 수 있는, 비동기 안전하지 않은 코드를 담은 시그널 핸들러를 정의하는 약점이다.

    설명(Description)¶

    제품이 비동기 안전(asynchronous-safe)하지 않은 코드, 즉 재진입(reentrant)이 불가능하거나 중단될 수 있는 코드를 담은 시그널 핸들러를 정의하는 약점이며, 상황에 따라 서비스 거부와 코드 실행을 포함한 다양한 결과를 낳는 예상하지 못한 시스템 상태로 이어질 수 있다. 시그널 핸들러는 대개 프로세스에 사건을 알리려고 프로그램의 정상 기능이나 다른 시그널까지 중단시키도록 의도되는데, 핸들러가 전역·정적 변수를 쓰거나 그런 상태나 관련 메타데이터에 의존하는 함수를 호출하면 정상 기능이 쓰는 시스템 상태를 손상시킬 수 있고, 이로 인해 프로그램이 경쟁조건 등의 약점에 노출되어 공격자가 프로그램 상태를 손상시킬 수 있다. 서비스 거부가 흔한 결과이지만 일부 경우 이 약점은 코드 실행에 악용될 수 있다. 이 문제를 일으키는 상황에는 핸들러 안에서 재진입 불가 함수를 호출하는 경우(예: 메모리를 관리하며 내부 전역 변수를 수정하는 malloc(); 실제로 재진입 가능한 함수는 매우 적다), 다른 시그널 핸들러를 포함한 프로그램의 다른 기능이 접근할 수 있는 전역 변수나 관련 메타데이터·구조를 비원자적으로 쓰는 코드 시퀀스(함수 호출일 필요는 없으며, 같은 함수가 여러 시그널의 핸들러로 등록되는 경우가 흔하다), 한 번만 실행되도록 의도한 핸들러가 같은 시그널의 반복 전달이나 같은 핸들러를 쓰는 다른 시그널의 전달로 여러 번 호출되는 경우(CWE-831)가 있다. 일부 환경이나 맥락에서는 시그널 핸들러 자체가 중단될 수도 있다. 시그널 핸들러와 제품의 정상 동작이 같은 상태 변수 집합을 다뤄야 하는데 정상 실행이 그 변수를 수정하는 도중에 시그널이 오면, 핸들러 실행 중에 변수가 잘못되거나 손상된 상태일 수 있고 핸들러에서 돌아온 뒤에도 그럴 수 있다.

    원문(Description · Extended Description)

    The product defines a signal handler that contains code sequences that are not asynchronous-safe, i.e., the functionality is not reentrant, or it can be interrupted.

    This can lead to an unexpected system state with a variety of potential consequences depending on context, including denial of service and code execution.

    Signal handlers are typically intended to interrupt normal functionality of a program, or even other signals, in order to notify the process of an event. When a signal handler uses global or static variables, or invokes functions that ultimately depend on such state or its associated metadata, then it could corrupt system state that is being used by normal functionality. This could subject the program to race conditions or other weaknesses that allow an attacker to cause the program state to be corrupted. While denial of service is frequently the consequence, in some cases this weakness could be leveraged for code execution.

    There are several different scenarios that introduce this issue:

    - Invocation of non-reentrant functions from within the handler. One example is malloc(), which modifies internal global variables as it manages memory. Very few functions are actually reentrant.

    - Code sequences (not necessarily function calls) contain non-atomic use of global variables, or associated metadata or structures, that can be accessed by other functionality of the program, including other signal handlers. Frequently, the same function is registered to handle multiple signals.

    - The signal handler function is intended to run at most one time, but instead it can be invoked multiple times. This could happen by repeated delivery of the same signal, or by delivery of different signals that have the same handler function (CWE-831).

    Note that in some environments or contexts, it might be possible for the signal handler to be interrupted itself.

    If both a signal handler and the normal behavior of the product have to operate on the same set of state variables, and a signal is received in the middle of the normal execution's modifications of those variables, the variables may be in an incorrect or corrupt state during signal handler execution, and possibly still incorrect or corrupt upon return.

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 서비스 거부: 비정상 종료·재시작 / 허가되지 않은 코드·명령 실행 가장 흔한 결과는 제품 상태 손상이며, 이는 비정상 종료나 종료로 이어질 수 있으나, 시그널 핸들러가 보안 관련 라이브러리나 보호 메커니즘의 상태 변수를 다루면 보호 메커니즘 우회, 권한 상승, 정보 노출처럼 훨씬 심각한 결과가 생길 수 있다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) / 아키텍처·설계(Architecture and Design) — 시그널 핸들러 안에서 재진입 불가 기능을 쓰지 않게 하며, 여기에는 재진입 불가 라이브러리 호출을 모두 재진입 가능한 호출로 바꾸는 것도 포함된다. 단, 이는 항상 가능하지는 않으며 제품의 많은 부분을 다시 작성하거나 재설계해야 할 수 있고, 재진입 안전한 라이브러리 대안이 없거나 설계상 시스템 상태와 시그널 핸들러 사이의 재진입 불가 상호작용이 필요한 경우도 있다. (구현 단계에도 해당)
    원문

    Eliminate the usage of non-reentrant functionality inside of signal handlers. This includes replacing all non-reentrant library calls with reentrant calls.

    Note: This will not always be possible and may require large portions of the product to be rewritten or even redesigned. Sometimes reentrant-safe library alternatives will not be available. Sometimes non-reentrant interaction between the state of the system and the signal handler will be required by design.

    		 높음(High)

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 시그널 핸들러 안에서 재진입 불가 기능을 꼭 써야 한다면 시그널을 적절히 차단(block)하거나 마스킹해야 하며, 여기에는 같은 기능을 쓸 수 있는 다른 시그널을 핸들러 안에서 차단하는 것과, 제품의 정상 동작이 그 기능에 접근하거나 그 기능을 수정하는 동안 그 기능에 의존하는 모든 시그널을 차단하는 것이 포함된다.
    원문

    Where non-reentrant functionality must be leveraged within a signal handler, be sure to block or mask signals appropriately. This includes blocking other signals within the signal handler itself that may also leverage the functionality. It also includes blocking all signals reliant upon the functionality when it is being accessed or modified by the normal behaviors of the product.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. This code registers the same signal handler function with two different signals (CWE-831). If those signals are sent to the process, the handler creates a log message (specified in the first argument to the program) and exits.

    Bad / C

    char *logMessage;

void handler (int sigNum) {

  syslog(LOG_NOTICE, "%s\n", logMessage);
  free(logMessage);

                             /* artificially increase the size of the timing window to make demonstration of this weakness easier. */

  sleep(10);
  exit(0);

}

int main (int argc, char* argv[]) {

  logMessage = strdup(argv[1]);

                             /* Register signal handlers. */

  signal(SIGHUP, handler);
  signal(SIGTERM, handler);

                             /* artificially increase the size of the timing window to make demonstration of this weakness easier. */

  sleep(10);

}

    The handler function uses global state (globalVar and logMessage), and it can be called by both the SIGHUP and SIGTERM signals. An attack scenario might follow these lines:

    The program begins execution, initializes logMessage, and registers the signal handlers for SIGHUP and SIGTERM. The program begins its "normal" functionality, which is simplified as sleep(), but could be any functionality that consumes some time. The attacker sends SIGHUP, which invokes handler (call this "SIGHUP-handler"). SIGHUP-handler begins to execute, calling syslog(). syslog() calls malloc(), which is non-reentrant. malloc() begins to modify metadata to manage the heap. The attacker then sends SIGTERM. SIGHUP-handler is interrupted, but syslog's malloc call is still executing and has not finished modifying its metadata. The SIGTERM handler is invoked. SIGTERM-handler records the log message using syslog(), then frees the logMessage variable.

    At this point, the state of the heap is uncertain, because malloc is still modifying the metadata for the heap; the metadata might be in an inconsistent state. The SIGTERM-handler call to free() is assuming that the metadata is inconsistent, possibly causing it to write data to the wrong location while managing the heap. The result is memory corruption, which could lead to a crash or even code execution, depending on the circumstances under which the code is running.

    Note that this is an adaptation of a classic example as originally presented by Michal Zalewski [REF-360]; the original example was shown to be exploitable for code execution.

    Also note that the strdup(argv[1]) call contains a potential buffer over-read (CWE-126) if the program is called without any arguments, because argc would be 0, and argv[1] would point outside the bounds of the array.

    Example 2. The following code registers a signal handler with multiple signals in order to log when a specific event occurs and to free associated memory before exiting.

    Bad / C

    #include <signal.h>
#include <syslog.h>
#include <string.h>
#include <stdlib.h>

void *global1, *global2;
char *what;
void sh (int dummy) {

  syslog(LOG_NOTICE,"%s\n",what);
  free(global2);
  free(global1);

                             /* Sleep statements added to expand timing window for race condition */

  sleep(10);
  exit(0);

}

int main (int argc,char* argv[]) {

  what=argv[1];
  global1=strdup(argv[2]);
  global2=malloc(340);
  signal(SIGHUP,sh);
  signal(SIGTERM,sh);

                             /* Sleep statements added to expand timing window for race condition */

  sleep(10);
  exit(0);

}

    However, the following sequence of events may result in a double-free (CWE-415):

    a SIGHUP is delivered to the process sh() is invoked to process the SIGHUP This first invocation of sh() reaches the point where global1 is freed At this point, a SIGTERM is sent to the process the second invocation of sh() might do another free of global1 this results in a double-free (CWE-415)

    This is just one possible exploitation of the above code. As another example, the syslog call may use malloc calls which are not async-signal safe. This could cause corruption of the heap management structures. For more details, consult the example within "Delivering Signals for Fun and Profit" [REF-360].

    탐지 방법(Detection Methods)¶

    방법 요지
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법은 자동 정적 분석뿐이다. 다른 정적 분석 도구·컴파일러 경고로 점검한다.
    • ③ SEI CERT 대응 규칙: SIG31-C

    단계 지침
    요구사항 분석 —
    설계 시그널 핸들러는 플래그 설정만 수행하고 실제 처리는 메인 루프에서 하도록 설계한다.
    구현 핸들러에서는 volatile sig_atomic_t 변수 설정과 async-signal-safe 함수(_exit, write 등)만 호출하고 malloc, printf 등 비재진입 함수 사용을 금지한다.
    통합 및 시험 정적 분석 도구(예: Coverity, clang-tidy bugprone-signal-handler)와 시그널 동시 발생 스트레스 시험을 수행한다.
    유지보수 핸들러 변경 시 호출 함수의 비동기 안전성을 재확인하고 시그널 마스크 설정을 점검한다.
    임베디드 고려 MCU의 ISR에도 동일 원칙을 적용하여 ISR은 짧게 유지하고 volatile 플래그·큐로 태스크에 위임하며 비재진입 라이브러리 호출을 금지한다.

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    관련 규칙·사례¶

    • SEI CERT 규칙: SIG31-C
    • 상위 항목(전체 약점 계층 View 1000): CWE-364 시그널 핸들러 경쟁조건
    • 하위 항목(이 가이드 범위 197개 안): CWE-479 시그널 핸들러의 비재진입 함수 사용

    관찰 사례(원문 Observed Examples 6건, 요지는 한글 요약이고 원문은 접은 상자)

    참조 요지
    CVE-2008-4109 시그널 핸들러가 결국 안전하지 않은 syslog/malloc/sprintf를 호출하는 함수를 사용해 여러 번의 로그인 시도로 서비스 거부가 일어난다.
    원문

    Signal handler uses functions that ultimately call the unsafe syslog/malloc/sprintf, leading to denial of service via multiple login attempts
    CVE-2006-5051 연쇄: 시그널 핸들러에 기능이 너무 많아(CWE-828) 경쟁조건(CWE-362)이 생기고, 이것이 이중 해제(CWE-415)로 이어진다.
    원문

    Chain: Signal handler contains too much functionality (CWE-828), introducing a race condition (CWE-362) that leads to a double free (CWE-415).
    CVE-2001-1349 시그널 핸들러에서 라이브러리 함수를 안전하지 않게 호출한다.
    원문

    unsafe calls to library functions from signal handler
    CVE-2004-0794 SIGURG로 시그널 핸들러를 원격에서 중단시킬 수 있으며, 다른 변형도 있다.
    원문

    SIGURG can be used to remotely interrupt signal handler; other variants exist.
    CVE-2004-2259 부하가 높을 때 FTP 서버가 malloc/free 같은 비재진입 함수를 실행하는 중 SIGCHLD 시그널을 받으면 비정상 종료될 수 있다.
    원문

    SIGCHLD signal to FTP server can cause crash under heavy load while executing non-reentrant functions like malloc/free.
    CVE-2002-1563 데몬 루프에서 카운터를 수정하는 동안 SIGCHLD를 막지 않아 카운터 값이 어긋난다.
    원문

    SIGCHLD not blocked in a daemon loop while counter is modified, causing counter to get out of sync.
