    Missing Authentication for Critical Functionality

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, Go · 기술: 클라우드 컴퓨팅(Cloud Computing), 산업제어시스템·운영기술(ICS/OT), 인공지능·기계학습(AI/ML)
    원문 MITRE CWE-306 (CWE 5.0)

    한 줄 요약

    증명 가능한 사용자 신원이 필요하거나 자원을 많이 쓰는 기능에 인증을 전혀 하지 않는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 증명 가능한 사용자 신원을 요구하거나 상당한 양의 자원을 소비하는 기능에 대해 어떤 인증도 수행하지 않는다.

    원문(Description)

    The product does not perform any authentication for functionality that requires a provable user identity or consumes a significant amount of resources.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 누락(OMISSION): 아키텍처·설계 단계에서 보안 전술을 빠뜨려 생기는 약점이다.
    아키텍처·설계(Architecture and Design) 설계 개발자는 때로 주 채널에서만 인증하고 비공개라고 가정한 보조 채널을 여는데, 예를 들어 로그인 메커니즘이 인증 성공 후 두 번째 포트를 열고 인증된 측만 접속한다고 가정해 그 포트에서는 인증을 생략할 수 있다.
    운용(Operation) 유지보수 데이터를 클라우드(S3 버킷, Azure blob, Google Cloud Storage 등)로 옮길 때 내부망 호스팅이 주던 보호를 잃을 위험이 있으며, 접근에 인증이 필요 없으면 공격자가 인터넷 어디서든 데이터에 접근하기 쉬워질 수 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    접근 통제 / 기타 권한 획득 또는 신원 도용 / 상황에 따라 다름 중요 기능을 노출하면 사실상 공격자에게 그 기능의 권한 수준을 준다. 결과는 기능에 따라 다르지만 민감한 데이터 읽기·수정, 관리자 등 특권 기능 접근, 나아가 임의 코드 실행까지 이를 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: R-01 보안 요구사항 정의

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 소프트웨어를 익명·일반·특권·관리 영역으로 나누고, 신원 증명이 필요한 영역을 식별해 중앙집중식 인증 기능을 쓴다. 인가된 측만 접근한다고 가정한 채널을 포함해 모든 통신 채널과 상호작용 수단을 식별하고 모두 적절히 보호한다. 개발자는 때로 주 채널에서만 인증하고 비공개라고 가정한 보조 채널을 열어 둔다(예: 한 네트워크 포트에서 대기하는 로그인 기능이 인증에 성공한 뒤 두 번째 포트를 열어 접속을 기다리면서, 인증된 측만 접속한다고 가정해 그 포트에서는 인증하지 않을 수 있다). 일반적으로 소프트웨어나 프로토콜이 하나의 세션이나 사용자 상태를 여러 연결·채널에 걸쳐 유지하도록 허용하면 그 전체에 인증과 적절한 자격 증명 관리를 적용해야 한다.
    원문

    Divide the software into anonymous, normal, privileged, and administrative areas. Identify which of these areas require a proven user identity, and use a centralized authentication capability.

    Identify all potential communication channels, or other means of interaction with the software, to ensure that all channels are appropriately protected, including those channels that are assumed to be accessible only by authorized parties. Developers sometimes perform authentication at the primary channel, but open up a secondary channel that is assumed to be private. For example, a login mechanism may be listening on one network port, but after successful authentication, it may open up a second port where it waits for the connection, but avoids authentication because it assumes that only the authenticated party will connect to the port.

    In general, if the software or protocol allows a single session or user state to persist across multiple connections or channels, authentication and appropriate credential management need to be used throughout.
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해야 한다(CWE-602 방지). 공격자는 검사 뒤에 값을 바꾸거나 클라이언트에서 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있기 때문이다.
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.
    아키텍처·설계(Architecture and Design) — 가능하면 직접 만든 인증 루틴을 피하고 프레임워크·운영체제·환경이 제공하는 인증 기능을 쓰는 것을 고려한다. 이런 기능은 인증 고유의 흔한 약점을 피하고 자동 감사·추적을 지원하며 인증과 인가(authorization)를 분리하기 쉽게 할 수 있다. 웹처럼 둘의 경계가 때로 흐린 환경에서 서버 제공 기능 대신 자체 인증 루틴이 필요하면 페이지가 직접 요청될 수 있으므로 그 루틴을 모든 페이지에 적용해야 한다.
    원문

    Where possible, avoid implementing custom, "grow-your-own" authentication routines and consider using authentication capabilities as provided by the surrounding framework, operating system, or environment. These capabilities may avoid common weaknesses that are unique to authentication; support automatic auditing and tracking; and make it easier to provide a clear separation between authentication tasks and authorization tasks.

    In environments such as the World Wide Web, the line between authentication and authorization is sometimes blurred. If custom authentication routines are required instead of those provided by the server, then these routines must be applied to every single page, since these pages could be requested directly.
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리나 프레임워크를 쓴다. 예를 들어 OpenSSL이나 ESAPI Authenticator [REF-45]처럼 인증 기능이 있는 라이브러리 사용을 고려한다.
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, consider using libraries with authentication capabilities such as OpenSSL or the ESAPI Authenticator [REF-45].

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) / 시스템 구성(System Configuration) / 운용(Operation) — 클라우드(S3 버킷, Azure blob, Google Cloud Storage 등)에 데이터를 저장할 때는 제공자의 통제 기능으로, 데이터 접근이 허용되어야 하는 사용자에게 강한 인증을 요구한다 [REF-1297] [REF-1298] [REF-1302]. (유지보수 단계에도 해당)
    원문

    When storing data in the cloud (e.g., S3 buckets, Azure blobs, Google Cloud Storage, etc.), use the provider's controls to require strong authentication for users who should be allowed to access the data [REF-1297] [REF-1298] [REF-1302].

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-06 보안 기능 부정 시험

    유지보수 (본문 제7장)¶

    이 단계를 함께 가리키는 원문 완화책은 구현 단계에 1건 실었다('유지보수 단계에도 해당' 표시). 이 단계의 기준선 활동: M-03 배포·설치 구성 기준선, M-06 운용 보호.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 정비 포트·원격 명령 채널·데이터링크로 들어온 명령 가운데 펌웨어 업데이트 시작, 암호 키 갱신, 공장 초기화, 임무 중단 같은 것은 중요 기능이다. 예시에서는 로그인하지 않았거나 발신자를 확인할 수 없는 연결에서 이런 명령이 들어온다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <stddef.h>

typedef struct {
    int authenticated;          /* 정비 포트 세션의 인증 상태 */
} PortSession;

typedef const char *(*Handler)(void);

static const char *get_status(void)      { return "STATUS ok"; }
static const char *begin_fw_update(void) { return "EXECUTED (flash bank erased)"; }
static const char *erase_mission(void)   { return "EXECUTED (mission data erased)"; }

static const struct { const char *name; Handler fn; } COMMANDS[] = {
    { "GET_STATUS", get_status },
    { "BEGIN_FW_UPDATE", begin_fw_update },
    { "ERASE_MISSION", erase_mission },
};

/* 정비 포트로 받은 명령을 찾아 그대로 실행한다: 세션 인증 상태를 보지 않는다 */
static const char *dispatch(const PortSession *s, const char *name)
{
    (void)s;
    for (size_t i = 0; i < sizeof COMMANDS / sizeof COMMANDS[0]; ++i) {
        if (strcmp(COMMANDS[i].name, name) == 0) {
            return COMMANDS[i].fn();
        }
    }
    return "UNKNOWN";
}

int main(void)
{
    const PortSession anonymous = { 0 };        /* 로그인하지 않은 연결 */
    const char *frames[] = { "GET_STATUS", "BEGIN_FW_UPDATE" };
    for (size_t i = 0; i < 2; ++i) {
        printf("auth=%s cmd=%s -> %s\n", anonymous.authenticated ? "yes" : "no",
               frames[i], dispatch(&anonymous, frames[i]));
    }
    return 0;
}

    명령 표에서 이름만 찾아 실행하고 세션 인증 상태를 보지 않아, 로그인하지 않은 연결에서도 펌웨어 업데이트 시작 같은 중요 기능이 실행된다.

    좋은 예

    #include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <stddef.h>

typedef struct {
    int authenticated;          /* 정비 포트 세션의 인증 상태 */
    uint32_t expires_tick;      /* 세션 만료 시각(틱) */
} PortSession;

typedef const char *(*Handler)(void);

static const char *get_status(void)      { return "STATUS ok"; }
static const char *begin_fw_update(void) { return "EXECUTED (flash bank erased)"; }
static const char *erase_mission(void)   { return "EXECUTED (mission data erased)"; }

/* 설계 단계에서 '인증 없이 허용'으로 정한 명령만 표시한다. 표시를 빠뜨리면 인증을 요구한다(기본 거부) */
static const struct { const char *name; Handler fn; int public_ok; } COMMANDS[] = {
    { "GET_STATUS", get_status, 1 },
    { "BEGIN_FW_UPDATE", begin_fw_update, 0 },
    { "ERASE_MISSION", erase_mission, 0 },
};

/* 틱 카운터가 한 바퀴 돌아도 판정이 뒤집히지 않게 차이로 비교한다(세션 수명은 카운터 주기의 절반 미만) */
static int session_valid(const PortSession *s, uint32_t now)
{
    return s->authenticated && (int32_t)(s->expires_tick - now) > 0;
}

static const char *dispatch(const PortSession *s, const char *name, uint32_t now)
{
    for (size_t i = 0; i < sizeof COMMANDS / sizeof COMMANDS[0]; ++i) {
        if (strcmp(COMMANDS[i].name, name) == 0) {
            if (!COMMANDS[i].public_ok && !session_valid(s, now)) {
                return "REJECTED (authentication required)";
            }
            return COMMANDS[i].fn();
        }
    }
    return "UNKNOWN";
}

int main(void)
{
    const PortSession anonymous = { 0, 0 };
    const char *frames[] = { "GET_STATUS", "BEGIN_FW_UPDATE" };
    for (size_t i = 0; i < 2; ++i) {
        printf("auth=%s cmd=%s -> %s\n", anonymous.authenticated ? "yes" : "no",
               frames[i], dispatch(&anonymous, frames[i], 100u));
    }
    return 0;
}

    설계 단계에서 인증 없이 허용하기로 정한 명령만 표시하고 나머지는 모두 인증을 요구하므로, 표시를 빠뜨려도 거부된다(기본 거부). 디스패처 한 곳에서 인증 상태와 세션 만료를 확인해 새 명령을 추가해도 같은 관문을 지나게 된다. 만료는 틱 카운터가 한 바퀴 돌아도 뒤집히지 않게 차이로 비교한다.

sealed record Frame(string Command, byte[]? Tag);

sealed class UplinkHandler(byte[] key)
{
    // 중요 명령은 HMAC-SHA256 태그가 맞을 때만 처리한다(실제로는 재전송 방지 카운터도 함께 검사한다)
    bool Authentic(Frame f)
    {
        if (f.Tag is null)
        {
            return false;
        }
        byte[] expected = HMACSHA256.HashData(key, Encoding.ASCII.GetBytes(f.Command));
        return CryptographicOperations.FixedTimeEquals(expected, f.Tag);
    }

    public string Process(Frame f)
    {
        if (!Authentic(f))
        {
            return "REJECTED (authentication required)";
        }
        return f.Command switch
        {
            "SET_HOME" => "EXECUTED (home point changed)",
            "ABORT_MISSION" => "EXECUTED (mission aborted)",
            _ => "UNKNOWN",
        };
    }
}

    import hashlib
import hmac
import json
import os

DEVICE_KEY = os.urandom(32)          # 실제로는 키 적재 장비가 넣은 장비별 키
CRITICAL = {"FACTORY_RESET", "FW_UPDATE_START", "KEY_ROLLOVER"}
seen_counters = set()                # 실제로는 비휘발성 저장소에 두어 재시작 뒤의 재전송도 막는다


def sign(body):                      # 인가된 정비 단말이 하는 일(시험용)
    return hmac.new(DEVICE_KEY, body.encode(), hashlib.sha256).hexdigest()


def parse_frame(frame):
    msg = json.loads(frame)
    body = msg["body"]
    cmd, mac = body["cmd"], msg.get("mac", "")
    if not isinstance(cmd, str) or not isinstance(mac, str):
        raise TypeError("field type")
    return body, cmd, mac.encode(), json.dumps(body, sort_keys=True)


def on_maint_command(frame):
    try:
        body, cmd, mac, canonical = parse_frame(frame)
    except (ValueError, KeyError, TypeError, RecursionError):
        return "REJECTED (malformed frame)"        # 인증 전 입력의 형식 오류로 처리기가 멈추지 않게 한다
    if cmd in CRITICAL:
        # 중요 명령은 장비 키로 만든 인증값과 재사용 방지 카운터가 맞을 때만 실행
        if not hmac.compare_digest(sign(canonical).encode(), mac):
            return f"{cmd} -> REJECTED (not authenticated)"
        counter = body.get("counter")
        if not isinstance(counter, int) or counter in seen_counters:
            return f"{cmd} -> REJECTED (replay)"
        seen_counters.add(counter)
        return f"{cmd} -> EXECUTED (authenticated)"
    return "status: nominal" if cmd == "STATUS" else "unknown command"

print(on_maint_command(json.dumps({"body": {"cmd": ["x"]}})))                            # 잘못된 필드 형식
print(on_maint_command(json.dumps({"body": signed, "mac": sign(json.dumps(signed, sort_keys=True))})))

    수동 분석 침투 시험(penetration test), 위협 모델링, 활성 세션을 기록·수정하는 대화형 도구처럼 사람의 수동 분석이 필요한 도구·기법으로 탐지할 수 있으며, 특히 수동 정적 분석은 자체 인증 메커니즘의 정확성을 평가하는 데 유용하다.
    원문

    This weakness can be detected using tools and techniques that require manual (human) analysis, such as penetration testing, threat modeling, and interactive tools that allow the tester to record and modify an active session.

    Specifically, manual static analysis is useful for evaluating the correctness of custom authentication mechanisms.

    		 이런 수동 방법은 완전 자동화 기법보다 더 효과적일 수 있으며, 특히 설계·업무 규칙과 관련된 약점에서 그렇다.

    점검 착안점 활동 근거
    설계 산출물에서 펌웨어 업데이트·키 갱신·공장 초기화·임무 중단 같은 중요 기능을 목록으로 만들고, 기능마다 모든 진입 경로(데이터링크, 정비 포트, 버스 명령)에 인증 검사가 있는지 확인한다. D-09·D-02 [CWE] CWE-306 완화책(Architecture and Design: 인증이 필요한 영역 구분) · [CWE] CWE-306 탐지 방법(설계 검토: 공격 모델링)
    로그인하지 않은 연결, 토큰이 없는 요청, 서명·MAC이 없는 프레임으로 중요 명령을 보내 실행되는지 시험한다. T-06 [예시] CWE-306 예시 검증(인증 없는 중요 명령 실행 확인)
    명령 표에서 이름만 찾아 실행하는 공통 분기 지점에 인증 상태 확인이 있는지, 새 명령을 추가할 때 이 확인을 건너뛸 수 있는 구조인지 본다. I-09 [예시] CWE-306 C 예시(명령 표 실행 경로에 인증 확인 없음)
    CAN·1553B처럼 프로토콜에 인증이 없는 버스로 중요 기능에 들어가는 경로를 따로 목록으로 만들어 메시지 인증 적용 여부를 확인한다. D-02·D-09 [보완]
    • ① 원문 탐지 방법(원문 효과성별): 높음: 아키텍처·설계 검토 / 부분 적용: 수동 정적 분석(바이너리·바이트코드), 동적 분석(결과 자동 해석), 동적 분석(결과 수동 해석), 수동 정적 분석(소스코드) / 효과 등급 없음: 수동 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.

    이 가이드에서 다루는 곳¶

    부록 A의 이 항목 행에 있는 단계별 지침 (요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 R-01 보안 요구사항 정의
    설계 펌웨어 업데이트, 설정 변경, 키 주입, 운용 모드 전환 명령 등 중요 기능을 식별하고 각각 인증을 요구하도록 설계한다.
    구현(C·C++) 중요 명령 처리 전 인증 상태와 세션 유효성을 확인하고, 검증된 인증 라이브러리를 사용한다.
    구현(Java) 중요 기능 엔드포인트에 인증 필터를 일괄 적용하고, 우회 가능한 경로(디버그 서블릿 등)를 제거한다.
    통합 및 시험 인증 없이 중요 기능을 직접 호출하는 시험과 위협 모델링(threat modeling) 기반 공격 시나리오 시험을 수행한다.
    유지보수 신규 인터페이스 추가 시 중요 기능 목록과 인증 적용 여부를 재검토한다.
    임베디드 고려 버스 메시지 기반 명령(CAN 등)은 기본적으로 인증이 없으므로 MAC(CMAC/HMAC)·카운터 기반 메시지 인증을 적용하고 처리 지연을 실시간 예산에 반영한다.

    기준선 활동 7건

    • R-01 보안 요구사항 정의 (요구사항 분석)
    • D-02 위협 모델링·신뢰 경계 정의 (설계)
    • D-04 권한 분리·최소 권한·격리 설계 (설계)
    • D-09 설계 보안성 검토 (설계)
    • T-06 보안 기능 부정 시험 (통합 및 시험)
    • M-03 배포·설치 구성 기준선 (유지보수 · 조건: 파일시스템(S3)이 '권한 있는 FS' 또는 '단순 FS')
    • M-06 운용 보호 (유지보수)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.
