    Weak Password Requirements

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 조건부 — 사용자 계정·비밀번호 사용
    적용 플랫폼 언어 무관 · 기술 무관
    원문 MITRE CWE-521 (CWE 5.0)

    한 줄 요약

    사용자에게 강한 비밀번호를 쓰도록 요구하지 않는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 사용자에게 강한 비밀번호를 갖도록 요구하지 않는다.

    배경(Background Details)

    인증 메커니즘은 흔히 암기한 비밀(비밀번호)에 의존해 시스템 사용자의 신원을 주장한다. 따라서 이 비밀번호는 충분히 복잡하고 공격자가 추측하기 어려워야 한다. 비밀번호가 얼마나 복잡해야 하는지에 관한 구체적인 요구사항은 보호 대상 시스템의 종류에 따라 다르다. 올바른 비밀번호 요구사항을 정하고 구현으로 강제하는 것은 인증 메커니즘 전체의 성공에 매우 중요하다.

    원문(Description · Background Details)

    The product does not require that users should have strong passwords.

    Authentication mechanisms often rely on a memorized secret (also known as a password) to provide an assertion of identity for a user of a system. It is therefore important that this password be of sufficient complexity and impractical for an adversary to guess. The specific requirements around how complex a password needs to be depends on the type of system being protected. Selecting the correct password requirements and enforcing them through implementation are critical to the overall success of the authentication mechanism.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 작위(COMMISSION): 아키텍처 보안 전술과 관련된 잘못된 설계로 생기는 약점이다.
    구현(Implementation) 구현 제품 설계에 명시된 비밀번호 정책을 강제하지 않으면 사용자가 필요한 보호 수준을 제공하지 못하는 비밀번호를 만들 수 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    접근 통제 권한 획득 또는 신원 도용 공격자가 사용자 비밀번호를 쉽게 추측해 사용자 계정에 접근할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 4건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: R-01 보안 요구사항 정의

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 제품 설계는 적절한 비밀번호 정책을 따르도록 요구해야 한다. 구체적인 비밀번호 요구사항은 상황 요인에 크게 좌우되지만, 다음 속성을 갖추도록 권장한다.
    · 최소·최대 길이 강제
    · 비밀번호 재사용 제한
    · 흔한 비밀번호 사용 제한
    · 비밀번호에 상황 관련 문자열(예: 사용자 ID, 앱 이름) 사용 제한 위협 모델에 따라 비밀번호 정책에 다음 속성을 더할 수 있다.
    · 문자 종류를 섞어야 하는 복잡한 비밀번호(영문자, 숫자, 특수문자, 대소문자 혼용): 문자 범위를 넓히면 비밀번호를 크래킹하기 어려워지며, 단일 요소 인증에 의존하는 시스템에 적합할 수 있다. 다만 복잡한 비밀번호는 외우기 어려워 사용자가 짧은 비밀번호를 고르거나 비밀번호를 잘못 관리(적어 두기)하게 될 수 있다. 사람들이 여러 기호를 예측 가능하게 쓰기 때문에 전체 비밀번호 복잡도가 크게 늘지 않는 경우가 많다는 단점도 있다.
    · 큰 최소 길이(비밀번호 대신 패스프레이즈 사용 권장): 문자 수를 늘리면 비밀번호를 크래킹하기 어려워지며, 단일 요소 인증에 의존하는 시스템에 적합할 수 있다. 다만 좋은 패스프레이즈를 고르기는 쉽지 않고 약한 비밀번호가 여전히 만들어질 수 있다. 길고 예측하기 어려운 비밀번호를 쓰도록 어느 정도 안내가 필요할 수 있다.
    · 무작위로 고른 비밀 값: 사용자 대신 비밀번호를 생성하면 길이와 복잡도 요구사항을 맞추는 데 도움이 되고 안전한 비밀번호가 쓰이게 할 수 있다. 다만 결과 비밀번호나 패스프레이즈가 외우기 너무 어려워 적어 두게 될 수 있다. 그러나 복잡도 요구사항이 제각각인 많은 비밀번호를 관리할 수 있는 비밀번호 관리자의 도입이 늘고 있다. 비밀번호 요구사항에 관한 더 자세한 내용은 NIST 800-63B [REF-1053]를 참고한다.
    원문

    A product's design should require adherence to an appropriate password policy. Specific password requirements depend strongly on contextual factors, but it is recommended to contain the following attributes:

    - Enforcement of a minimum and maximum length

    - Restrictions against password reuse

    - Restrictions against using common passwords

    - Restrictions against using contextual string in the password (e.g., user id, app name)

    Depending on the threat model, the password policy may include several additional attributes.

    - Complex passwords requiring mixed character sets (alpha, numeric, special, mixed case) Increasing the range of characters makes the password harder to crack and may be appropriate for systems relying on single factor authentication. Unfortunately, a complex password may be difficult to memorize, encouraging a user to select a short password or to incorrectly manage the password (write it down). Another disadvantage of this approach is that it often does not result in a significant increase in overall password complexity due to people's predictable usage of various symbols.

    - Large Minimum Length (encouraging passphrases instead of passwords) Increasing the number of characters makes the password harder to crack and may be appropriate for systems relying on single factor authentication. A disadvantage of this approach is that selecting a good passphrase is not easy and poor passwords can still be generated. Some prompting may be needed to encourage long un-predictable passwords.

    - Randomly Chosen Secrets Generating a password for the user can help make sure that length and complexity requirements are met, and can result in secure passwords being used. A disadvantage of this approach is that the resulting password or passphrase may be too difficult to memorize, encouraging them to be written down. However, there is growing adoption of password managers that allow users to manage many passwords with varying complexity requirements.

    See NIST 800-63B [REF-1053] for further information on password requirements.

    원문

    Consider a second authentication factor beyond the password, which prevents the password from being a single point of failure. See CWE-308 for further information.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 사용자가 고른 비밀번호가 요구 속성을 충족하는지 알려 주는 비밀번호 복잡도 표시기를 구현하는 것을 고려한다.
    원문

    Consider implementing a password complexity meter to inform users when a chosen password meets the required attributes.

    		 —
    구현(Implementation) — 예전에는 약한 비밀번호의 위험을 줄이는 심층 방어로 '비밀번호 만료'(예: 90일마다 변경)가 널리 권장되어 흔한 관행이 되었다. 그러나 현재 위협 환경에서는 한계가 크고, 비밀번호 복잡도·계산 비용 같은 관련 보호 수단이 도입되고 정기 변경이 흔히 더 예측 가능한 비밀번호를 낳는다는 점이 알려지면서 효용이 줄었다. 그래서 이제는 특히 비밀번호 보호의 유일한 수단으로서는 권장하지 않는 관행(Discouraged Common Practice)이다 [REF-1488] [REF-1489]. 침해 증거가 있을 때 비밀번호 변경을 강제하는 것은 여전히 강하게 권장되며, 이는 임의 주기로 강제하는 '만료'와는 다르다.
    원문

    Previously, "password expiration" was widely advocated as a defense-in-depth approach to minimize the risk of weak passwords, and it has become a common practice. Password expiration requires a password to be changed within a fixed time window (such as every 90 days). However, this approach has significant limitations in the current threat landscape, and its utility has been reduced in light of the adoption of related protection mechanisms (such as password complexity and computational effort), along with the recognition that regular password changes often caused users to generate more predictable passwords. As a result, this is now a Discouraged Common Practice [REF-1488] [REF-1489], especially as the sole factor in protecting passwords. It is still strongly encouraged to force password changes in case of evidence of compromise, but this is not the same as a forced "expiration" on an arbitrary time frame.

    		 권장하지 않는 관행(Discouraged Common Practice)

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 정비 콘솔·운용자 계정·정비 정보 시스템·임무 계획 도구의 관리자 계정에 새 비밀번호를 설정한다. 예시의 후보 가운데 앞의 것들은 짧거나, 계정 이름을 담거나, 흔히 쓰이는 약한 값이고 마지막 하나만 정책을 만족한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <stddef.h>

/* 정비 콘솔 계정의 새 비밀번호를 설정한다: 비어 있지만 않으면 받아들인다 */
static int set_new_password(const char *account, const char *candidate)
{
    (void)account;
    if (candidate == NULL || candidate[0] == '\0') {
        return 0;
    }
    /* (저장 단계는 생략) */
    return 1;
}

int main(void)
{
    const char *account = "maint";
    const char *candidates[] = { "1234", "Maint#2026ops", "Password1234!", "EXAMPLE-Ridge-Falcon-42x" };
    for (size_t i = 0; i < sizeof candidates / sizeof candidates[0]; ++i) {
        printf("%-24s -> %s\n", candidates[i],
               set_new_password(account, candidates[i]) ? "ACCEPTED" : "REJECTED");
    }
    return 0;
}

    빈 값만 막아 '1234'나 계정 이름을 담은 비밀번호도 그대로 받는다. 이런 값은 사전 대입으로 금방 맞힐 수 있다.

    좋은 예

    #include <ctype.h>
#include <stdio.h>
#include <stddef.h>
#include <string.h>

#define MIN_LENGTH 12   /* 길이 기준은 사업 보안 요구사항에서 정한다 */

static const char *const DENYLIST[] = { "password1234", "123456789012", "qwertyuiop12" };

static int contains_nocase(const char *text, const char *word)
{
    size_t n = strlen(text), m = strlen(word);
    for (size_t i = 0; m > 0 && i + m <= n; ++i) {
        size_t k = 0;
        while (k < m && tolower((unsigned char)text[i + k]) == tolower((unsigned char)word[k])) ++k;
        if (k == m) return 1;
    }
    return 0;
}

/* 정책을 통과하지 못한 이유를 돌려주고, 통과하면 NULL */
static const char *policy_violation(const char *account, const char *pw)
{
    if (account == NULL || pw == NULL) return "missing input";
    size_t len = strlen(pw);
    int lower = 0, upper = 0, digit = 0, other = 0;
    for (size_t i = 0; i < len; ++i) {
        unsigned char ch = (unsigned char)pw[i];
        if (islower(ch)) lower = 1; else if (isupper(ch)) upper = 1;
        else if (isdigit(ch)) digit = 1; else other = 1;
    }
    if (len < MIN_LENGTH) return "too short";
    if (lower + upper + digit + other < 3) return "needs 3 character classes";
    if (contains_nocase(pw, account)) return "contains account name";
    for (size_t i = 0; i < sizeof DENYLIST / sizeof DENYLIST[0]; ++i)
        if (contains_nocase(pw, DENYLIST[i])) return "commonly used password";
    return NULL;
}

int main(void)
{
    const char *account = "maint";
    /* 예시 값이므로 실제 계정에 쓰지 않는다 */
    const char *candidates[] = { "1234", "Maint#2026ops", "Password1234!", "EXAMPLE-Ridge-Falcon-42x" };
    for (size_t i = 0; i < sizeof candidates / sizeof candidates[0]; ++i) {
        const char *why = policy_violation(account, candidates[i]);
        /* 시연용 출력: 실제 코드는 비밀번호를 화면·로그에 남기지 않는다 */
        printf("%-24s -> %s%s\n", candidates[i], why ? "REJECTED: " : "ACCEPTED", why ? why : "");
    }
    return 0;
}

std::optional<std::string_view> weak_reason(std::string_view user, std::string_view pw) {
    constexpr std::size_t kMinLen = 12;  // 사업 보안 요구사항의 값으로 바꾼다
    static constexpr std::array<std::string_view, 4> kCommon{"0000", "password", "operator", "qwerty"};
    auto has = [&](auto pred) { return std::any_of(pw.begin(), pw.end(), [&](char c) { return pred(static_cast<unsigned char>(c)); }); };
    int classes = has([](int c) { return std::islower(c); }) + has([](int c) { return std::isupper(c); }) +
                  has([](int c) { return std::isdigit(c); }) + has([](int c) { return std::ispunct(c); });
    if (pw.size() < kMinLen) return "too short";
    if (classes < 3) return "needs 3 character classes";

        std::string r(s);
        std::transform(r.begin(), r.end(), r.begin(), [](unsigned char c) { return static_cast<char>(std::tolower(c)); });
        return r;
    };
    const std::string low = lower(pw);
    if (low.find(lower(user)) != std::string::npos) return "contains account name";
    for (auto w : kCommon) if (low.find(w) != std::string::npos) return "commonly used password";
    return std::nullopt;
}

        users_.push_back(user);
        return std::nullopt;
    }
private:
    std::vector<std::string> users_;
};

{
    const int MinLength = 12;                                // 사업 보안 요구사항의 값
    string[] common = ["admin", "password", "planner", "123456"];

import java.util.Optional;
import java.util.Set;

    static final int MIN_LENGTH = 12;                        // 사업 보안 요구사항에서 정한다
    static final Set<String> COMMON = Set.of("11111111", "password", "qwerty", "letmein");

    • R-01 보안 요구사항 정의 (요구사항 분석)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 3건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
