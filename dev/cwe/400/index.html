    Uncontrolled Resource Consumption

    항목 내용
    추상화 수준 분류(Class)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    MITRE 매핑 권고 권장하지 않음(Discouraged) — 결과를 기록할 때는 더 구체적인 CWE를 쓴다(MITRE 권고 CWE: CWE-770·CWE-771·CWE-772·CWE-410·CWE-834·CWE-405)
    원문(Mapping Notes)

    Rationale: CWE-400 is intended for incorrect behaviors in which the product is expected to track and restrict how many resources it consumes, but CWE-400 is often misused because it is conflated with the "technical impact" of vulnerabilities in which resource consumption occurs. It is sometimes used for low-information vulnerability reports. It is a level-1 Class (i.e., a child of a Pillar).

    Comments: Closely analyze the specific mistake that is causing resource consumption, and perform a CWE mapping for that mistake. Consider children/descendants.
    적용 플랫폼 언어: 언어 무관, Python · 기술: 기술 무관, 인공지능·기계학습(AI/ML)
    원문 MITRE CWE-400 (CWE 5.0)

    한 줄 요약

    한정된 자원의 할당과 유지를 제대로 통제하지 않는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 한정된 자원의 할당과 유지를 제대로 통제하지 않는다.

    원문(Description · Dimensions)

    The product does not properly control the allocation and maintenance of a limited resource.

    Dimensions: Behavior-Property = Uncontrolled; Behavior-Type = Consumption; Resource-Type = Resource

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    운용(Operation) 유지보수 제품이 예상보다 자원 한도가 낮은 시스템이나 환경에서 운용될 수 있으며, 이 경우 공격자가 가용 자원을 모두 소비하기 더 쉬워질 수 있다.
    시스템 구성(System Configuration) 유지보수 제품이 예상보다 낮은 자원 한도로 설정될 수 있으며, 이 경우 공격자가 가용 자원을 모두 소비하기 더 쉬워질 수 있다.
    아키텍처·설계(Architecture and Design) 설계 설계자가 과도한 자원 요청을 처리·제한하는 방법을 고려하지 않을 수 있으며, 비정상 종료나 단순 종료 대신 정상 동작을 유지하며 처리하려면 대개 신중한 계획이 필요하다.
    구현(Implementation) 구현 자원 소진으로 흔히 이어지는 시나리오는 적어도 세 가지(할당 자원 수 제한 없음, 종료 단계 전에 자원 참조를 모두 잃음, 처리 뒤 자원을 닫거나 반환하지 않음)이며, 자원 소진 문제는 흔히 오류 상황·예외 상황을 잘못 구현하거나 프로그램의 어느 부분이 자원 해제를 책임지는지 혼동해 생긴다.

    영향(Common Consequences)¶

    영역 영향 설명
    가용성 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 자원 소모(CPU) / 서비스 거부: 자원 소모(메모리) / 서비스 거부: 자원 소모(기타) 공격자가 한정된 자원의 할당을 유발할 수 있는데 자원의 수나 크기가 통제되지 않으면 가장 흔한 결과는 서비스 거부다. 이때 정당한 사용자가 제품에 접근하지 못하게 되고 제품이 느려지거나 처리되지 않은 오류로 비정상 종료되거나 정당한 사용자를 잠그는 등 주변 환경에도 영향을 줄 수 있다(예: 애플리케이션에 대한 메모리 소진 공격은 애플리케이션과 호스트 운영체제를 함께 느리게 할 수 있다).
    접근 통제 / 기타 보호 메커니즘 우회 / 기타 일부 경우 자원 소진 시 제품을 '실패 시 개방(fail open)' 상태로 만들 수 있으며, 그러면 제품 상태와 경우에 따라 보안 기능까지 손상될 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 4건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 시스템 아키텍처에 요청 제한(throttling) 메커니즘을 설계해 넣는다. 권한 없는 사용자가 소모시킬 수 있는 자원 양을 제한하는 것이 최선의 보호이다. 강한 인증·접근 통제 모델은 이런 공격을 애초에 막는 데 도움이 된다. 로그인 애플리케이션을 DoS 공격으로부터 최대한 보호하고, 결과 집합 캐싱 등으로 데이터베이스 접근을 제한하며, 사용자별 요청 빈도를 추적해 정한 임계값을 넘는 요청을 차단하는 방안도 고려한다.
    원문

    Design throttling mechanisms into the system architecture. The best protection is to limit the amount of resources that an unauthorized user can cause to be expended. A strong authentication and access control model will help prevent such attacks from occurring in the first place. The login application should be protected against DoS attacks as much as possible. Limiting the database access, perhaps by caching result sets, can help minimize the resources expended. To further limit the potential for a DoS attack, consider tracking the rate of requests received from users and blocking requests that exceed a defined rate threshold.
    아키텍처·설계(Architecture and Design) — 자원 소진 공격을 완화하려면 대상 시스템이 공격을 인지해 해당 사용자의 접근을 일정 시간 거부하거나, 모든 요청을 균일하게 제한해 자원이 해제되는 속도보다 빨리 소비하기 어렵게 해야 한다. 단, 앞의 방법은 공격자가 정당한 사용자를 사칭해 그 사용자의 서버 접근을 막을 수 있다는 문제가 있고, 뒤의 방법은 효과적으로 구현하기 어려우며 제대로 해도 완전한 해결책이 아니라 공격자에게 더 많은 자원을 요구할 뿐이다.
    원문

    Mitigation of resource exhaustion attacks requires that the target system either:

    - recognizes the attack and denies that user further access for a given amount of time, or

    - uniformly throttles all requests in order to make it more difficult to consume resources more quickly than they can again be freed.

    The first of these solutions is an issue in itself though, since it may allow attackers to prevent the use of the system by a particular valid user. If the attacker impersonates the valid user, they may be able to prevent the user from accessing the server in question.

    The second solution is simply difficult to effectively institute -- and even when properly done, it does not provide a full solution. It simply makes the attack require more resources on the part of the attacker.
    아키텍처·설계(Architecture and Design) — 프로토콜에 구체적인 규모 제한을 둔다.
    원문

    Ensure that protocols have specific limits of scale placed on them.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 자원 할당이 실패하면 어떤 경우든 시스템이 안전한 상태로 전환되게 한다.
    원문

    Ensure that all failures in resource allocation place the system into a safe posture.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-04 퍼징, T-07 타깃 자원·장시간 시험

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 데이터링크 센서 목록 메시지·임무 계획 파일·운용자 명령처럼 바깥에서 들어오는 입력이 '몇 개를 보낼지'나 '얼마나 클지'를 스스로 정한다. 받는 쪽이 상한 없이 그 값을 믿으면, 정해진 메모리 예산이나 큐를 한 번에 써 버려 다른 기능이 자원을 얻지 못한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stddef.h>
#include <stdint.h>
#include <stdio.h>

#define HEAP_BUDGET 65536u                 /* 이 보드에 배정된 동적 메모리 예산 */
static _Alignas(max_align_t) unsigned char arena[HEAP_BUDGET];
static size_t arena_used;

static void *arena_take(size_t n)          /* 예산 안에서만 내주는 단순 할당기 */
{
    const size_t align = _Alignof(max_align_t);
    if (n > HEAP_BUDGET) {
        return NULL;
    }
    n = (n + align - 1) & ~(align - 1);    /* 다음 할당의 정렬을 맞춘다 */
    if (n > HEAP_BUDGET - arena_used) {
        return NULL;
    }
    void *p = &arena[arena_used];
    arena_used += n;
    return p;
}

typedef struct { uint16_t id; int32_t temp_mc; int32_t volt_mv; } Sensor;

/* 센서 목록 메시지: 머리말이 알려 준 개수만큼 버퍼를 잡는다 */
static void on_sensor_list(uint32_t announced)
{
    Sensor *buf = arena_take((size_t)announced * sizeof(Sensor));   /* 상한 없음 */
    printf("sensor list (%u entries): %s\n", (unsigned)announced, buf ? "buffered" : "dropped");
}

int main(void)
{
    on_sensor_list(5400);                   /* 송신측 값을 그대로 믿는다 */
    void *tlm = arena_take(1024);          /* 다음 주기의 원격측정 버퍼 */
    printf("telemetry buffer: %s\n", tlm ? "ok" : "OUT OF MEMORY");
    return 0;
}

    머리말의 센서 수를 그대로 곱해 보드의 동적 메모리 예산에서 버퍼를 잡는다. 위조되거나 깨진 값 하나로 예산을 거의 다 써서, 다음 주기의 원격측정 버퍼 할당이 실패한다.

    좋은 예

    #include <stddef.h>
#include <stdint.h>
#include <stdio.h>

#define HEAP_BUDGET 65536u                 /* 이 보드에 배정된 동적 메모리 예산 */
#define MAX_SENSORS_PER_MSG 256u            /* ICD에 정한 메시지당 최대 센서 수 */
static _Alignas(max_align_t) unsigned char arena[HEAP_BUDGET];
static size_t arena_used;

static void *arena_take(size_t n)
{
    const size_t align = _Alignof(max_align_t);
    if (n > HEAP_BUDGET) {
        return NULL;
    }
    n = (n + align - 1) & ~(align - 1);    /* 다음 할당의 정렬을 맞춘다 */
    if (n > HEAP_BUDGET - arena_used) {
        return NULL;
    }
    void *p = &arena[arena_used];
    arena_used += n;
    return p;
}

typedef struct { uint16_t id; int32_t temp_mc; int32_t volt_mv; } Sensor;

static void on_sensor_list(uint32_t announced)
{
    if (announced == 0 || announced > MAX_SENSORS_PER_MSG) {
        printf("sensor list (%u entries): rejected, limit %u\n", (unsigned)announced, MAX_SENSORS_PER_MSG);
        return;                            /* 상한을 넘는 요청은 할당 전에 거부 */
    }
    Sensor *buf = arena_take((size_t)announced * sizeof(Sensor));
    printf("sensor list (%u entries): %s\n", (unsigned)announced, buf ? "buffered" : "dropped");
}

int main(void)
{
    on_sensor_list(5400);
    void *tlm = arena_take(1024);
    printf("telemetry buffer: %s\n", tlm ? "ok" : "OUT OF MEMORY");
    return 0;
}

    ICD에 정한 메시지당 최대 센서 수를 넘으면 할당하기 전에 거부해, 한 메시지가 쓸 수 있는 메모리를 상한 안으로 묶는다.

    검증: 실행 결과 — 나쁜 예에서 telemetry buffer: OUT OF MEMORY 검출, 좋은 예에서 미검출·rejected, limit 256 출력 확인 · 참고: MITRE CWE-400 Demonstrative Example 4(메시지에 실린 길이 값을 상한 없이 믿고 처리) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 코드오류 5-9 '무한 자원 할당'(인쇄 185쪽) 참고 — 이 항목의 표 1 대응 CWE는 CWE-770이고, 참고문헌에 CWE-400이 함께 실려 있다

    C++

    나쁜 예

    #include <array>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <memory_resource>
#include <new>
#include <vector>

struct Sensor { std::uint16_t id; std::int32_t temp_mc; std::int32_t volt_mv; };

// 보드의 동적 메모리 예산(32 KB)을 넘으면 std::bad_alloc을 던지는 자원
std::array<std::byte, 32768> arena;
std::pmr::monotonic_buffer_resource pool{arena.data(), arena.size(), std::pmr::null_memory_resource()};

bool prepare(std::pmr::vector<Sensor> &out, std::uint32_t announced) {
    try {
        out.reserve(announced);                 // 메시지가 말한 개수를 그대로 쓴다
    } catch (const std::bad_alloc &) {
        return false;
    }
    return true;
}

int main() {

{
    int done = 0;
    while (done < budget && reader.TryRead(out _)) done++;
    return done;
}

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 자동화된 정적 분석은 대개 자원 소진 문제 인식에 효용이 제한적이지만, 파일·소켓·프로세스 같은 프로그램 독립 시스템 자원에서는 만료 뒤 해제되지 않는 경우를 탐지할 수 있고, 설정 파일 자동 분석으로 최댓값을 지정하지 않은 설정을 탐지할 수 있다. 단, 게시판 사용자의 하루 게시 수 제한 같은 보안 정책상 자체 정의 자원의 소진 탐지에는 적합하지 않다.
    원문

    Automated static analysis typically has limited utility in recognizing resource exhaustion problems, except for program-independent system resources such as files, sockets, and processes. For system resources, automated static analysis may be able to detect circumstances in which resources are not released after they have expired. Automated analysis of configuration files may be able to detect settings that do not specify a maximum value.

    Automated static analysis tools will not be appropriate for detecting exhaustion of custom resources, such as an intended security policy in which a bulletin board user is only allowed to make a limited number of posts per day.

    자동 동적 분석 일부 자동화된 동적 분석 기법은 특히 프로세스·메모리·연결 같은 자원의 소진 문제를 찾는 데 효과적일 수 있으며, 짧은 시간에 제품에 많은 요청을 보내는 방식이 쓰일 수 있다.
    원문

    Certain automated dynamic analysis techniques may be effective in spotting resource exhaustion problems, especially with resources such as processes, memory, and connections. The technique may involve generating a large number of requests to the product within a short time frame.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    외부 메시지의 개수·길이 필드가 할당 크기, reserve, 큐 길이, 반복 횟수로 쓰이는 곳의 상한을 확인하고, readAllBytes나 상한 없는 큐처럼 크기 제한이 없는 API 사용을 찾는다. I-09 [예시] CWE-400 예시(개수 필드로 할당, 상한 없는 읽기·큐) · [CWE] CWE-400 완화책(Architecture and Design: 프로토콜 규모 상한)
    개수 필드를 최댓값으로 바꾼 메시지, 비정상적으로 큰 파일, 고빈도 재전송을 넣고 메모리 예산 사용량과 다른 기능의 할당 실패 여부를 확인한다. T-04·T-07 [예시] CWE-400 예시 검증(다른 기능의 할당 실패 출력) · [CWE] CWE-400 탐지 방법(자동 동적 분석: 짧은 시간 대량 요청)
    타깃에서 버스 플러딩과 인터럽트 폭주를 일으키며 핵심 태스크의 주기 지연과 워치독 동작을 측정한다. T-07·T-02 [보완]
    설계 산출물에 메모리·큐·연결 수의 상한과, 상한 초과나 할당 실패 때의 동작이 정해져 있는지 확인한다. D-09·D-07 [CWE] CWE-400 완화책(Architecture and Design: 제한 메커니즘, Implementation: 할당 실패 시 안전 상태)
    • ⓪ 하위 CWE 지원 확인: 도구가 이 번호 대신 MITRE 권고 CWE(CWE-770·CWE-771·CWE-772·CWE-410·CWE-834·CWE-405)로 보고하는지 먼저 확인한다. 지원하면 '미지원'이 아니며, 지원하는 CWE 목록을 점검 결과·FA 사유서에 근거로 적는다.
    • ① 원문 탐지 방법(원문 효과성별): 보통: 자동 동적 분석 / 기회적: 퍼징(Fuzzing). 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: SER12-J, MSC05-J

    이 가이드에서 다루는 곳¶

    부록 A의 이 항목 행에 있는 단계별 지침 (요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 입력 크기, 동시 연결 수, 메시지 큐 길이, 처리 시간 상한을 설계 산출물에 정하고 최악 실행 시간(WCET)과 메모리 예산을 산정한다.
    구현(C·C++) 수신 길이·반복 횟수·재귀 깊이에 상한을 두고, 할당 실패 시 안전하게 거부한다.
    구현(Java) 입력 스트림 크기 제한, 스레드 풀·큐 크기 상한, 타임아웃을 설정한다.
    통합 및 시험 부하·스트레스 시험, 대용량/고빈도 메시지 퍼징(fuzzing), 장시간 연속 운용(soak) 시험을 수행한다.
    유지보수 운용 자원 사용률(CPU, 메모리, 큐 길이)을 모니터링하고 상한값을 조정한다.
    임베디드 고려 메시지 폭주(CAN 버스 플러딩, 인터럽트 폭주) 시에도 핵심 태스크가 기아 상태가 되지 않도록 우선순위·레이트 제한을 설계하고 스택·힙 사용량을 정적 분석(static analysis)으로 산정한다.

    도구가 보고하는 하위 CWE는 도구 미지원 시 대안 ⓪을 본다.

    기준선 활동 3건

    • D-07 자원 예산·정적 할당 설계 (설계)
    • T-04 퍼징 (통합 및 시험)
    • T-07 타깃 자원·장시간 시험 (통합 및 시험)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 15건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.

    CVE-2019-19911 연쇄: Python 라이브러리가 매우 많은 밴드 수를 지정한 이미지를 처리하는 데 쓰는 자원을 제한하지 않아(CWE-1284) 메모리가 과도하게 소비되거나(CWE-789) 정수 오버플로(CWE-190)가 일어난다.
    원문

    Chain: Python library does not limit the resources used to process images that specify a very large number of bands (CWE-1284), leading to excessive memory consumption (CWE-789) or an integer overflow (CWE-190).
    CVE-2020-7218 Go 기반 워크로드 오케스트레이터가 인증되지 않은 연결의 자원 사용을 제한하지 않아 서비스에 대량 접속을 보내 서비스 거부를 일으킬 수 있다.
    원문

    Go-based workload orchestrator does not limit resource usage with unauthenticated connections, allowing a DoS by flooding the service
    CVE-2020-3566 분산 OS에서 IGMP 큐 관리가 '불충분'해 자원 고갈이 일어난다(CISA KEV에 따르면 실제 악용됨).
    원문

    Resource exhaustion in distributed OS because of "insufficient" IGMP queue management, as exploited in the wild per CISA KEV.
    CVE-2009-2874 공격자가 많은 수의 연결로 제품을 비정상 종료시킬 수 있다.
    원문

    Product allows attackers to cause a crash via a large number of connections.
    CVE-2009-1928 잘못된 형식의 요청이 제어되지 않는 재귀를 일으켜 스택이 고갈된다.
    원문

    Malformed request triggers uncontrolled recursion, leading to stack exhaustion.
    CVE-2009-2858 연쇄: 메모리 누수(CWE-404)로 자원이 고갈된다.
    원문

    Chain: memory leak (CWE-404) leads to resource exhaustion.
    CVE-2009-2726 드라이버가 sscanf류 함수를 호출할 때 최대 폭을 지정하지 않아 스택 소비가 일어난다.
    원문

    Driver does not use a maximum width when invoking sscanf style functions, causing stack consumption.
    CVE-2009-2540 객체의 길이 속성에 큰 정수 값을 넣으면 많은 양의 메모리가 할당된다.
    원문

    Large integer value for a length property in an object causes a large amount of memory allocation.
