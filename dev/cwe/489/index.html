    원문 MITRE CWE-489 (CWE 5.0)

    한 줄 요약

    디버그 코드가 활성화되었거나 동작하는 채로 제품을 릴리스해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 디버그 코드가 여전히 활성화되었거나 동작하는 상태로 릴리스되는 약점이다.

    원문(Description)

    The product is released with debugging code still enabled or active.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 웹 기반 애플리케이션에서 디버그 코드는 애플리케이션 속성·설정 정보·기능을 시험하고 수정하는 데 쓰이며, 디버그용 애플리케이션을 운영 서버에 남겨 두는 '소프트웨어 프로세스'상의 실수는 공격자에게 디버그 기능 접근을 허용한다.
    구현(Implementation) 구현 출시·배포할 의도 없이 디버깅이나 시험 전용 '백도어(back door)' 코드를 넣는 것은 흔한 개발 관행이며, 이런 진입점은 설계·시험에서 고려되지 않고 제품의 예상 운영 조건을 벗어나므로 보안 위험이 된다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 / 무결성 / 가용성 / 접근 통제 / 기타 보호 메커니즘 우회 / 애플리케이션 데이터 읽기 / 권한 획득 또는 신원 도용 / 상황에 따라 다름 활성화된 디버그 코드는 의도하지 않은 진입점을 만들거나 민감한 정보를 노출할 수 있으며, 심각도는 사례마다 다르다. 적어도 공격자에게 서버의 웹 애플리케이션 설정·동작 방식에 관한 민감한 정보를 주고, 최악의 경우(흔히 그렇듯) 공격자가 웹 애플리케이션과 서버, 그리고 이들이 접근하는 기밀 정보까지 완전히 장악하게 한다.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 장비의 정비 명령 처리기와 운용자 콘솔에는 개발 중 벤치 시험 편의를 위해 인증이나 자체 시험(BIT)을 건너뛰는 디버그 명령·실행 옵션을 두곤 한다. 이것이 출하 빌드에 남으면 정비 단말에 접근한 누구나 인증 없이 파라미터를 바꾸거나, 자체 시험에 실패한 장비를 운용 모드로 올릴 수 있다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>

typedef struct {
    const char *name;
    void (*run)(void);
} MaintCmd;

static int authenticated;
static int servo_gain = 400;

static void cmd_param_set(void)
{
    if (!authenticated) {
        puts("param-set: denied (login required)");
        return;
    }
    servo_gain = 900;
    printf("param-set: gain=%d\n", servo_gain);
}

static void cmd_dbg_unlock(void)     /* 개발 중 벤치 시험 편의를 위해 만든 명령 */
{
    authenticated = 1;
    puts("dbg-unlock: login skipped");
}

static const MaintCmd commands[] = {
    {"param-set", cmd_param_set},
    {"dbg-unlock", cmd_dbg_unlock},  /* 출하 빌드에도 그대로 남았다 */
};

static void dispatch(const char *name)
{
    for (size_t i = 0; i < sizeof commands / sizeof commands[0]; ++i) {
        if (strcmp(commands[i].name, name) == 0) {
            commands[i].run();
            return;
        }
    }
    printf("%s: unknown command\n", name);
}

int main(void)
{
    const char *session[] = {"dbg-unlock", "param-set"};  /* 로그인 없이 접속한 정비 단말 */
    for (size_t i = 0; i < 2; ++i) dispatch(session[i]);
    return 0;
}

    벤치 시험용 dbg-unlock 명령이 출하 빌드의 명령 표에 그대로 남아, 로그인 없이 접속한 단말이 이 명령 하나로 인증을 건너뛰고 서보 이득을 바꾼다.

    좋은 예

    #include <stdio.h>
#include <string.h>

typedef struct {
    const char *name;
    void (*run)(void);
} MaintCmd;

static int authenticated;
static int servo_gain = 400;

static void cmd_param_set(void)
{
    if (!authenticated) {
        puts("param-set: denied (login required)");
        return;
    }
    servo_gain = 900;
    printf("param-set: gain=%d\n", servo_gain);
}

/* 벤치 시험 명령은 bench_cmds.c에만 두고, 그 파일은 시험 빌드의 소스 목록에만 넣는다.
   출하 빌드의 명령 표에는 운용 명령만 있다. */
static const MaintCmd commands[] = {
    {"param-set", cmd_param_set},
};

static void dispatch(const char *name)
{
    for (size_t i = 0; i < sizeof commands / sizeof commands[0]; ++i) {
        if (strcmp(commands[i].name, name) == 0) {
            commands[i].run();
            return;
        }
    }
    printf("%s: unknown command\n", name);
}

int main(void)
{
    const char *session[] = {"dbg-unlock", "param-set"};  /* 시연용 입력: 출하 코드에는 없다 */
    for (size_t i = 0; i < 2; ++i) dispatch(session[i]);
    return 0;
}

    시험 명령을 별도 소스 파일로 분리해 시험 빌드의 소스 목록에만 넣고, 출하 빌드의 명령 표에는 운용 명령만 둔다. 출하 바이너리에 디버그 명령 문자열이 없는지 통합 및 시험 단계에서 확인한다.

    검증: 실행 결과 — 나쁜 예에서 gain=900 검출, 좋은 예에서 미검출·dbg-unlock: unknown command 출력 확인 · 참고: MITRE CWE-489 Demonstrative Example 1(debug 매개변수로 인증 우회) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 캡슐화 6-1 '제거되지 않고 남은 디버그 코드'(인쇄 188쪽) 참고

    C++

    나쁜 예

    #include <iostream>
#include <string_view>

// 운용자 콘솔 실행 파일의 시작 옵션 처리
int main(int argc, char *argv[]) {
    bool login_done = false;
    for (int i = 1; i < argc; ++i) {
        std::string_view opt(argv[i]);
        if (opt == "--bench-noauth") {      // 벤치 시험 때 쓰던 옵션이 출하판에 남았다
            login_done = true;
        } else {
            std::cout << "unknown option " << opt << '\n';
        }
    }
    if (login_done) {
        std::cout << "console: maintenance mode opened without login\n";
    } else {
        std::cout << "console: login required\n";
    }
    return 0;
}

    벤치 시험 때 쓰던 --bench-noauth 시작 옵션이 출하판에 남아 있어, 이 옵션만 주면 로그인 없이 정비 모드가 열린다.

    좋은 예

    #include <array>
#include <iostream>
#include <string_view>

// 출하 빌드가 받아들이는 옵션(시험 전용 옵션은 시험 빌드 대상에만 있다)
constexpr std::array<std::string_view, 2> kReleaseOptions = {"--verbose", "--night-palette"};

int main(int argc, char *argv[]) {
    for (int i = 1; i < argc; ++i) {
        std::string_view opt(argv[i]);
        bool known = false;
        for (std::string_view k : kReleaseOptions) {
            known = known || (opt == k);
        }
        if (!known) {
            std::cout << "unknown option " << opt << ": ignored\n";
        }
    }
    std::cout << "console: login required\n";   // 인증을 건너뛰는 경로가 없다
    return 0;
}

    출하 빌드가 받아들이는 옵션을 허용목록으로 고정하고 인증 우회 경로 자체를 두지 않는다. 시험 전용 옵션은 시험 빌드 대상에만 넣는다.

    검증: 실행 결과 — 나쁜 예에서 opened without login 검출, 좋은 예에서 미검출·unknown option --bench-noauth: ignored 출력 확인 · 참고: MITRE CWE-489 Demonstrative Example 1(debug 매개변수로 인증 우회) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    bool authenticated = false;
int gain = 400;

// 정비 단말 명령 처리
void Handle(string cmd)
{
    switch (cmd)
    {
        case "param-set":
            if (!authenticated)
            {
                Console.WriteLine("param-set: denied (login required)");
                return;
            }
            gain = 900;
            Console.WriteLine($"param-set: gain={gain}");
            break;
        case "dbg-unlock":                  // 개발 중 쓰던 인증 우회 명령이 그대로 빌드된다
            authenticated = true;
            Console.WriteLine("dbg-unlock: login skipped");
            break;
        default:
            Console.WriteLine($"{cmd}: unknown command");
            break;
    }
}

foreach (string c in new[] { "dbg-unlock", "param-set" })
{
    Handle(c);
}

    인증 우회용 dbg-unlock 명령이 아무 조건 없이 빌드되어, 출하판에서도 이 명령으로 로그인 없이 파라미터를 바꿀 수 있다.

    좋은 예

    bool authenticated = false;
int gain = 400;

void Handle(string cmd)
{
    switch (cmd)
    {
        case "param-set":

            {
                Console.WriteLine("param-set: denied (login required)");
                return;
            }

            Console.WriteLine($"param-set: gain={gain}");
            break;
#if MAINT_BENCH

    시험 명령을 벤치 시험 빌드 구성에서만 정의하는 기호(MAINT_BENCH)로 감싸 출하 구성에서는 컴파일되지 않게 한다. DEBUG 기호는 일반 디버그 빌드에도 켜지므로 시험 전용 기호를 따로 둔다.

    검증: 실행 결과 — 나쁜 예에서 gain=900 검출, 좋은 예에서 미검출·dbg-unlock: unknown command 출력 확인 · 참고: MITRE CWE-489 Demonstrative Example 1(debug 매개변수로 인증 우회) 참고, 이 가이드가 새로 작성

    Java

    나쁜 예

    import java.util.LinkedHashMap;
import java.util.Map;

public class Example {
    static boolean bitPassed = false;     // 자체 시험(BIT) 결과

    static boolean runBit() {
        return false;                     // 시험용 모의: 관성 센서 BIT 실패
    }

    public static void main(String[] args) {
        Map<String, Runnable> console = new LinkedHashMap<>();
        console.put("bit.run", () -> bitPassed = runBit());
        console.put("mode.operate", () -> System.out.println(
                bitPassed ? "OPERATE mode entered" : "BIT failed: stay in MAINT"));
        // 개발 중 BIT를 건너뛰려고 넣은 명령이 배포본에 남았다
        console.put("dbg.skipbit", () -> bitPassed = true);

        for (String cmd : new String[] {"bit.run", "dbg.skipbit", "mode.operate"}) {
            console.getOrDefault(cmd, () -> System.out.println(cmd + ": unknown command")).run();
        }
    }
}

    개발 중 BIT를 건너뛰려고 넣은 dbg.skipbit 명령이 배포본에 남아, 관성 센서 BIT에 실패한 장비가 운용 모드로 올라간다.

    좋은 예

    import java.util.LinkedHashMap;
import java.util.Map;

public class Example {
    // 빌드 스크립트가 생성하는 상수: 출하 빌드에서는 false
    static final class BuildFlags {
        static final boolean BENCH = false;
    }

    static boolean bitPassed = false;     // 자체 시험(BIT) 결과

    static boolean runBit() {
        return false;                     // 시험용 모의: 관성 센서 BIT 실패
    }

    public static void main(String[] args) {
        Map<String, Runnable> console = new LinkedHashMap<>();
        console.put("bit.run", () -> bitPassed = runBit());
        console.put("mode.operate", () -> System.out.println(
                bitPassed ? "OPERATE mode entered" : "BIT failed: stay in MAINT"));
        if (BuildFlags.BENCH) {
            // 상수 false 조건이라 등록 문장은 실행 경로에서 빠진다(람다 본문은 클래스 파일에 남을 수 있다)
            console.put("dbg.skipbit", () -> bitPassed = true);
        }

        // 시연용 입력: 출하 코드에는 없다
        for (String cmd : new String[] {"bit.run", "dbg.skipbit", "mode.operate"}) {
            console.getOrDefault(cmd, () -> System.out.println(cmd + ": unknown command")).run();
        }
    }
}

    빌드가 생성하는 상수(출하 빌드는 false)로 시험 명령 등록을 감싸, 출하 빌드에서는 등록 문장이 실행 경로에서 빠진다(람다 본문은 합성 메서드로 클래스 파일에 남을 수 있다). 확실히 하려면 C 예시처럼 시험 명령을 시험 빌드 전용 소스 세트로 분리한다. 배포물 문자열 검사로 남은 명령이 없는지 확인한다.

    검증: 실행 결과 — 나쁜 예에서 OPERATE mode entered 검출, 좋은 예에서 미검출·dbg.skipbit: unknown command 출력 확인 · 참고: MITRE CWE-489 Demonstrative Example 1(debug 매개변수로 인증 우회) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「Java 시큐어코딩 가이드」(3판) 캡슐화 6-2 '제거되지 않고 남은 디버그 코드'(인쇄 272쪽) 참고

    Python

    나쁜 예

    import hashlib
import hmac
import os

# 시험 준비: 실제로는 등록 절차에서 만든 솔트와 검증값을 보호 저장소에서 읽는다
PIN_SALT = os.urandom(16)


def pin_hash(pin):
    return hashlib.scrypt(pin.encode(), salt=PIN_SALT, n=2 ** 14, r=8, p=1, dklen=32)


OPERATOR_PIN_HASH = pin_hash("EXAMPLE-ONLY")


# 장비 정비 명령 처리기
def handle(command, pin=""):
    if command == "DBG_SKIP_AUTH":                   # 벤치 시험 때 쓰던 디버그 명령이 그대로 남음
        return "OPERATE mode entered (auth skipped)"
    if command == "OPERATE":
        if hmac.compare_digest(pin_hash(pin), OPERATOR_PIN_HASH):
            return "OPERATE mode entered"
        return "auth failed"
    return "unknown command"


print(handle("OPERATE", "wrong"))
print(handle("DBG_SKIP_AUTH"))                       # 운용 배포본에서도 인증 없이 운용 모드

    벤치 시험 때 인증을 건너뛰려고 넣은 디버그 명령이 운용 배포본에 남았다. 정비 포트에 이 명령 이름만 보내면 인증 없이 운용 모드로 들어간다. Python에서는 breakpoint() 호출·import pdb, 웹 프레임워크의 debug=True(Bandit B201: Flask 디버그 모드), 디버그용 원격 셸이 같은 꼴로 남는다.

    좋은 예

    import hashlib
import hmac
import os

# 시험 준비: 실제로는 등록 절차에서 만든 솔트와 검증값을 보호 저장소에서 읽는다
PIN_SALT = os.urandom(16)


def pin_hash(pin):
    return hashlib.scrypt(pin.encode(), salt=PIN_SALT, n=2 ** 14, r=8, p=1, dklen=32)


OPERATOR_PIN_HASH = pin_hash("EXAMPLE-ONLY")


# 운용 배포본의 명령 처리기에는 인증을 건너뛰는 경로가 없다.
# 벤치 시험용 명령은 별도 시험 모듈(tests/bench_tools.py)에 두고 운용 배포 묶음에서 빼며,
# 배포 전 검사가 'DBG_' 명령·breakpoint()·pdb 가져오기가 남았는지 확인한다.
def handle(command, pin=""):
    if command == "OPERATE":
        if hmac.compare_digest(pin_hash(pin), OPERATOR_PIN_HASH):
            return "OPERATE mode entered"
        return "auth failed"
    return "unknown command"


print(handle("OPERATE", "wrong"))
print(handle("DBG_SKIP_AUTH"))

    운용 처리기에서 디버그 경로를 없애고, 벤치 시험 도구는 별도 시험 모듈로 분리해 운용 배포 묶음에서 뺀다(M-02). 배포 전 검사로 디버그 명령 이름·breakpoint()·pdb·debug=True가 남았는지 확인한다(T-08, LPY-12). assert와 __debug__는 python -O로 실행하면 사라지므로 이것에 보안 판단을 맡기지 않는다.

    검증: 실행 결과 — 나쁜 예에서 auth skipped 검출, 좋은 예에서 미검출·auth failed…unknown command 출력 확인 · 참고: MITRE CWE-489 Demonstrative Example 1(debug 매개변수로 인증 우회) 참고, 이 가이드가 새로 작성 / 과학기술정보통신부·한국인터넷진흥원 「Python 시큐어코딩 가이드」(2023. 12.) 캡슐화 6-2 '제거되지 않고 남은 디버그 코드'(인쇄 147쪽) 참고

    MITRE 원문 예시(Demonstrative Examples, 영문 1건)

    Example 1. Debug code can be used to bypass authentication. For example, suppose an application has a login script that receives a username and a password. Assume also that a third, optional, parameter, called "debug", is interpreted by the script as requesting a switch to debug mode, and that when this parameter is given the username and password are not checked. In such a case, it is very simple to bypass the authentication process if the special behavior of the application regarding the debug parameter is known. In a case where the form is:

    Bad / HTML

    <FORM ACTION="/authenticate_login.cgi">
  <INPUT TYPE=TEXT name=username>
  <INPUT TYPE=PASSWORD name=password>
  <INPUT TYPE=SUBMIT>
</FORM>

    Then a conforming link will look like:

    Informative

    http://TARGET/authenticate_login.cgi?username=...&password=...

    An attacker can change this to:

    Attack

    http://TARGET/authenticate_login.cgi?username=&password=&debug=1

    Which will grant the attacker access to the site, bypassing the authentication process.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)
