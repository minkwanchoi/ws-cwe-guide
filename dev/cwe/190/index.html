    Integer Overflow or Wraparound

    항목 내용
    추상화 수준 기본(Base)
    상태 안정(Stable)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C(CWE-658)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, C, Python · 기술 무관
    원문 MITRE CWE-190 (CWE 5.0)

    한 줄 요약

    결괏값이 항상 원래 값보다 클 것이라 가정한 계산에서 정수 오버플로나 랩어라운드가 생겨 값이 아주 작거나 음수가 될 수 있는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 수행하는 계산이 정수 오버플로(integer overflow)나 랩어라운드(wraparound)를 일으킬 수 있는데도, 로직은 결괏값이 항상 원래 값보다 클 것이라고 가정하는 약점이다. 정수 값이 해당 표현 형식에 저장할 수 있는 범위보다 큰 값으로 증가할 때 이 현상이 발생한다. 이때 값이 매우 작은 수나 음수가 될 수 있다.

    기술 해설(Technical Nuance)

    정수 오버플로는 메모리 손상 문제와 관련해 가장 흔히 언급되지만, 금융 계산, 물리적 치수, 날짜·타임스탬프처럼 개발자가 정수 연산의 특정 성질을 가정했으나 그 성질이 성립하지 않을 수 있는 다른 상황에도 해당할 수 있다.

    원문(Description · Technical Nuance)

    The product performs a calculation that can produce an integer overflow or wraparound when the logic assumes that the resulting value will always be larger than the original value. This occurs when an integer value is incremented to a value that is too large to store in the associated representation. When this occurs, the value may become a very small or negative number.

    While integer overflows are most commonly cited for memory-corruption issues, they can apply to other situations in which the developer assumes certain properties of integer arithmetic that might not hold, e.g., financial calculations, physical dimensions, date/timestamp, etc.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 이 약점은 메모리 할당, 복사, 연결 같은 동작에서 오프셋이나 크기를 정할 때 보안상 중요해질 수 있다.
    구현(Implementation) 구현 이 약점은 보안 결정이 시간에 근거하고 그 시간 필드에 정수 오버플로가 생길 수 있을 때 보안상 중요해질 수 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    가용성 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 자원 소모(메모리) / 서비스 거부: 불안정 이 약점은 일반적으로 정의되지 않은 동작과 그에 따른 비정상 종료로 이어질 수 있고, 계산 결과가 자원 할당에 쓰이면 자원을 너무 많이(또는 너무 적게) 할당하게 할 수 있으며, 제품이 제공 가능한 것보다 많은 자원을 요청하면 비정상 종료를 일으킬 수 있다. 계산 결과가 시간 값과 관련되면 제품이 이전에 계산한 시간보다 이른 시간을 만났을 때 비정상 종료될 수 있다.
    무결성 메모리 수정 그 값이 제어 흐름이 아니라 데이터에 영향을 주는 값이면 단순한 데이터 손상이 생기며, 오버플로/랩어라운드가 버퍼 오버플로 같은 다른 상황으로 이어지면 추가 메모리 손상이 생길 수 있다.
    기밀성 / 가용성 / 접근 통제 허가되지 않은 코드·명령 실행 / 보호 메커니즘 우회 이 약점은 때로 버퍼 오버플로를 일으킬 수 있고 이는 임의 코드 실행에 쓰일 수 있는데, 이는 대개 제품의 암묵적 보안 정책 범위를 벗어난다.
    가용성 / 기타 실행 논리 변경 / 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 자원 소모(CPU) 루프 인덱스 변수에서 오버플로/랩어라운드가 생기면 루프가 너무 일찍, 너무 늦게, 또는 전혀 끝나지 않는(무한 루프) 등 잘못된 시점에 끝날 수 있고, 반복이 너무 많으면 일부 루프가 메모리·파일 핸들 같은 자원을 과도하게 소비해 비정상 종료나 서비스 거부(DoS)로 이어질 수 있다.
    접근 통제 보호 메커니즘 우회 할당량이나 할당 한도 계산처럼 보안상 중요한 결정에 정수 값이 쓰이면, 정수 오버플로를 이용해 잘못된 보안 결정을 유발할 수 있다.
    접근 통제 보호 메커니즘 우회 / 서비스 거부: 비정상 종료·재시작 정수 값이 만료 시간 계산이나 이벤트가 특정 시간·날짜 범위 안에 일어나는지 판단하는 일처럼 시간 기반의 보안상 중요한 결정에 쓰이면 잘못된 보안 결정을 일으킬 수 있다. 오버플로가 보호 메커니즘 로직에서 고려하지 않은 시간 값을 만들면 '자체 서비스 거부(self-DoS)'까지 이어질 수 있다[REF-1570].

    완화책(Potential Mitigations)¶

    원문 완화책 7건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    CWE 단계(Phase) 전략 요지
    요구사항(Requirements) — 모든 프로토콜을 엄격하게 정의해 범위를 벗어난 모든 동작을 쉽게 식별할 수 있게 하고, 프로토콜을 엄격히 준수하도록 요구한다.
    원문

    Ensure that all protocols are strictly defined, such that all out-of-bounds behavior can be identified simply, and require strict conformance to the protocol.
    요구사항(Requirements) 언어 선택 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 언어를 쓴다. 가능하면 자동 경계 검사를 수행하는 언어나 컴파일러를 고른다.
    원문

    Use a language that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    If possible, choose a language or compiler that performs automatic bounds checking.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점을 허용하지 않거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리·프레임워크를 써서 [REF-1482] 예상치 못한 결과 없이 수를 다루기 쉽게 한다. 예로 SafeInt(C++)나 IntegerLib(C 또는 C++) 같은 안전한 정수 처리 패키지가 있다 [REF-106].
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid [REF-1482].

    Use libraries or frameworks that make it easier to handle numbers without unexpected consequences.

    Examples include safe integer handling packages such as SafeInt (C++) or IntegerLib (C or C++). [REF-106]
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해야 한다(CWE-602 방지). 공격자는 검사 뒤에 값을 바꾸거나 클라이언트에서 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있기 때문이다.
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) 입력값 검증 모든 숫자 입력에 입력값 검증을 수행해 기대 범위의 최솟값과 최댓값 요건을 모두 만족하는지 확인한다. 가능하면 부호 없는 정수를 써서 정수 오버플로 검증을 쉽게 하고, 부호 있는 정수가 필요하면 범위 검사에 최댓값뿐 아니라 최솟값도 포함한다.
    원문

    Perform input validation on any numeric input by ensuring that it is within the expected range. Enforce that the input meets both the minimum and maximum requirements for the expected range.

    Use unsigned integers where possible. This makes it easier to perform validation for integer overflows. When signed integers are required, ensure that the range check includes minimum values as well as maximum values.
    구현(Implementation) — 프로그래밍 언어의 내부 표현과 수치 계산의 상호작용을 이해한다(CWE-681). 바이트 크기 차이, 정밀도, 부호 있음/없음 구분, 절단, 형 변환과 캐스팅, 'not-a-number' 계산, 표현 범위보다 너무 크거나 작은 수의 처리 방식에 주의하고 [REF-7], 32비트·64비트 등 수 표현에 영향을 줄 수 있는 차이도 고려한다.
    원문

    Understand the programming language's underlying representation and how it interacts with numeric calculation (CWE-681). Pay close attention to byte size discrepancies, precision, signed/unsigned distinctions, truncation, conversion and casting between types, "not-a-number" calculations, and how the language handles numbers that are too large or too small for its underlying representation. [REF-7]

    Also be careful to account for 32-bit, 64-bit, and other potential differences that may affect the numeric representation.
    구현(Implementation) 컴파일·빌드 강화 컴파일러 경고를 꼼꼼히 살펴 메모리 연산의 부호 있음/없음 불일치나 초기화되지 않은 변수 사용처럼 보안 영향이 있을 수 있는 문제를 없앤다. 약점이 악용되는 일이 드물더라도 한 번의 실패가 시스템 전체의 침해로 이어질 수 있다.
    원문

    Examine compiler warnings closely and eliminate problems with potential security implications, such as signed / unsigned mismatch in memory operations, or use of uninitialized variables. Even if the weakness is rarely exploitable, a single failure may lead to the compromise of the entire system.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-04 퍼징, T-05 경계값·오류 주입 시험

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 임무 계획 파일에서 경로점 개수와 경로점 하나의 크기를 읽어 버퍼 크기를 계산한다. 두 값 모두 파일에서 온다. C++ 예시는 거리 센서 값과 이득의 곱, Java 예시는 누적 가동 시간, C# 예시는 수신 패킷 수 누적을 다룬다. Python 예시는 센서 목록 메시지 머리부의 16비트 길이 필드(ctypes 구조체)에 센서 수 × 레코드 크기를 넣는다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

/* 파일 헤더에서 읽었다고 가정한 값 */
static int32_t waypoint_count = 0x10000001;
static int32_t waypoint_size = 16;

int main(void)
{
    int32_t total = waypoint_count * waypoint_size;   /* 부호 있는 곱셈이 넘친다 */
    printf("alloc %ld bytes\n", (long)total);
    void *buf = malloc((size_t)total);
    free(buf);
    return 0;
}

    두 값의 곱이 int32_t 범위를 넘으면 부호 있는 정수 오버플로(정의되지 않은 동작)가 일어나고, 결과가 작은 값이나 음수가 되어 필요한 것보다 작은 버퍼를 할당하게 된다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

#define MAX_WAYPOINTS 4096u
#define MAX_WAYPOINT_SIZE 256u

static int32_t waypoint_count = 0x10000001;
static int32_t waypoint_size = 16;

int main(void)
{
    if (waypoint_count <= 0 || waypoint_size <= 0 || (uint32_t)waypoint_count > MAX_WAYPOINTS ||
        (uint32_t)waypoint_size > MAX_WAYPOINT_SIZE) {
        puts("rejected: waypoint field out of range");
        return 0;
    }
    size_t count = (size_t)waypoint_count;
    size_t size = (size_t)waypoint_size;
    if (count > SIZE_MAX / size) {
        puts("rejected: size overflow");
        return 0;
    }
    void *buf = malloc(count * size);
    if (buf == NULL) {
        puts("rejected: out of memory");
        return 0;
    }
    printf("alloc %zu bytes\n", count * size);
    free(buf);
    return 0;
}

    계산 전에 개수와 크기를 설계 상한(MAX_WAYPOINTS·MAX_WAYPOINT_SIZE)으로 제한하고, 곱셈은 넘치지 않는지(count > SIZE_MAX / size) 먼저 검사한 뒤 부호 없는 size_t로 하며, 할당 실패도 확인한다(I-05).

    나쁜 예

    #include <cstdint>
#include <cstdio>

    return raw_mm * gain;                    // 센서 원시값과 이득의 곱이 넘칠 수 있다
}

int main() {

    두 int32_t의 곱이 범위를 넘으면 정의되지 않은 동작이다. 최적화 수준에 따라 엉뚱한 거리값이 나오거나 뒤따르는 검사가 지워질 수 있다.

    좋은 예

    #include <cstdint>
#include <cstdio>
#include <limits>
#include <optional>

std::optional<std::int32_t> scale_range(std::int32_t raw_mm, std::int32_t gain) {
    std::int64_t wide = static_cast<std::int64_t>(raw_mm) * gain;   // 넓은 형으로 계산
    if (wide > std::numeric_limits<std::int32_t>::max() ||
        wide < std::numeric_limits<std::int32_t>::min()) {
        return std::nullopt;                 // 범위 밖은 상위에서 처리
    }
    return static_cast<std::int32_t>(wide);
}

int main() {
    auto r = scale_range(900000, 4000);
    if (!r) {
        std::puts("rejected: range overflow");
        return 0;
    }
    std::printf("%d\n", *r);
    return 0;
}

    더 넓은 형(int64_t)으로 계산한 뒤 목표 형의 범위를 확인하고, 넘치면 값을 쓰지 않고 실패를 알린다.

    Python

    나쁜 예

    import ctypes


class Header(ctypes.LittleEndianStructure):      # ICD 메시지 머리부(본문 길이 필드는 16비트)
    _pack_ = 1
    _fields_ = [("msg_id", ctypes.c_uint16), ("body_len", ctypes.c_uint16)]


# 센서 목록 메시지의 머리부를 만든다: 본문 길이 = 센서 수 × 센서 레코드 크기
def build_header(sensor_count, record_size):
    hdr = Header()
    hdr.msg_id = 0x2A1
    hdr.body_len = sensor_count * record_size    # 65535를 넘으면 경고 없이 하위 16비트만 남는다
    return hdr


print("body_len:", build_header(20, 48).body_len)
print("body_len:", build_header(1400, 48).body_len, "(needed 67200)")   # 수신 측은 1664바이트만 읽는다

    Python의 int는 임의 정밀도라 계산 자체는 넘치지 않는다. 그러나 ctypes 구조체·numpy 배열 같은 고정 폭 형에 값을 넣으면 C와 같이 하위 비트만 남는다. 엄밀히는 대입 때의 잘림(CWE-197)이며, Python에서 이 약점이 나타나는 대표 경로다. 예시는 67200을 16비트 길이 필드에 넣어 1664가 되고, 수신 측은 본문을 짧게 읽어 레코드를 잘못 해석한다. ctypes 필드 대입은 예외도 경고도 내지 않는다.

    좋은 예

    import ctypes

U16_MAX = 0xFFFF


class Header(ctypes.LittleEndianStructure):
    _pack_ = 1
    _fields_ = [("msg_id", ctypes.c_uint16), ("body_len", ctypes.c_uint16)]


def build_header(sensor_count, record_size):
    body_len = sensor_count * record_size        # Python int로 먼저 계산(넘침 없음)
    if not 0 <= body_len <= U16_MAX:             # 고정 폭 필드에 넣기 전에 범위를 확인
        raise ValueError(f"body too long for 16-bit length field: {body_len}")
    hdr = Header()
    hdr.msg_id = 0x2A1
    hdr.body_len = body_len
    return hdr


print("body_len:", build_header(20, 48).body_len)
try:
    build_header(1400, 48)
except ValueError as e:
    print("rejected:", e)                        # 메시지를 나눠 보내거나 센서 수를 제한한다

    길이는 Python int로 먼저 계산하고, 고정 폭 필드에 넣기 전에 그 필드가 담을 수 있는 범위(0~65535)인지 확인해 넘으면 거부한다(I-05). struct.pack과 int.to_bytes는 범위를 넘으면 예외를 내지만 ctypes 필드와 numpy 정수 배열 연산은 조용히 넘치므로, ICD 구조체를 ctypes·numpy로 다룰 때는 이 확인을 직접 넣는다.

    MITRE 원문 예시(Demonstrative Examples, 영문 5건)

    Example 1. The following image processing code allocates a table for images.

    Bad / C

    img_t table_ptr; /*struct containing img data, 10kB each*/
int num_imgs;
...
num_imgs = get_num_imgs();
table_ptr = (img_t*)malloc(sizeof(img_t)*num_imgs);
...

    This code intends to allocate a table of size num_imgs, however as num_imgs grows large, the calculation determining the size of the list will eventually overflow (CWE-190). This will result in a very small list to be allocated instead. If the subsequent code operates on the list as if it were num_imgs long, it may result in many types of out-of-bounds problems (CWE-119).

    Example 2. The following code excerpt from OpenSSH 3.3 demonstrates a classic case of integer overflow:

    Bad / C

    nresp = packet_get_int();
if (nresp > 0) {
  response = xmalloc(nresp*sizeof(char*));
  for (i = 0; i < nresp; i++) response[i] = packet_get_string(NULL);
}

    If nresp has the value 1073741824 and sizeof(char*) has its typical value of 4, then the result of the operation nresp*sizeof(char*) overflows, and the argument to xmalloc() will be 0. Most malloc() implementations will happily allocate a 0-byte buffer, causing the subsequent loop iterations to overflow the heap buffer response.

    Example 3. Integer overflows can be complicated and difficult to detect. The following example is an attempt to show how an integer overflow may lead to undefined looping behavior:

    Bad / C

    short int bytesRec = 0;
char buf[SOMEBIGNUM];

while(bytesRec < MAXGET) {
  bytesRec += getFromInput(buf+bytesRec);
}

    In the above case, it is entirely possible that bytesRec may overflow, continuously creating a lower number than MAXGET and also overwriting the first MAXGET-1 bytes of buf.

    Example 4. In this example the method determineFirstQuarterRevenue is used to determine the first quarter revenue for an accounting/business application. The method retrieves the monthly sales totals for the first three months of the year, calculates the first quarter sales totals from the monthly sales totals, calculates the first quarter revenue based on the first quarter sales, and finally saves the first quarter revenue results to the database.

    Bad / C

    #define JAN 1
#define FEB 2
#define MAR 3

short getMonthlySales(int month) {...}

float calculateRevenueForQuarter(short quarterSold) {...}

int determineFirstQuarterRevenue() {

                             // Variable for sales revenue for the quarter

  float quarterRevenue = 0.0f;

  short JanSold = getMonthlySales(JAN); /* Get sales in January */
  short FebSold = getMonthlySales(FEB); /* Get sales in February */
  short MarSold = getMonthlySales(MAR); /* Get sales in March */

                             // Calculate quarterly total

  short quarterSold = JanSold + FebSold + MarSold;

                             // Calculate the total revenue for the quarter

  quarterRevenue = calculateRevenueForQuarter(quarterSold);

  saveFirstQuarterRevenue(quarterRevenue);

  return 0;

}

    However, in this example the primitive type short int is used for both the monthly and the quarterly sales variables. In C the short int primitive type has a maximum value of 32768. This creates a potential integer overflow if the value for the three monthly sales adds up to more than the maximum value for the short int primitive type. An integer overflow can lead to data corruption, unexpected behavior, infinite loops and system crashes. To correct the situation the appropriate primitive type should be used, as in the example below, and/or provide some validation mechanism to ensure that the maximum value for the primitive type is not exceeded.

    Good / C

    ...
float calculateRevenueForQuarter(long quarterSold) {...}

int determineFirstQuarterRevenue() {

  ...

                             // Calculate quarterly total

  long quarterSold = JanSold + FebSold + MarSold;

                             // Calculate the total revenue for the quarter

  quarterRevenue = calculateRevenueForQuarter(quarterSold);

  ...

}

    Note that an integer overflow could also occur if the quarterSold variable has a primitive type long but the method calculateRevenueForQuarter has a parameter of type short.

    Example 5. The "Year 2038 Problem" [REF-1570] [REF-1571] affects systems that store Unix times in a 32-bit signed integer whose epoch begins on January 1, 1970. Once the maximum value of the 32-bit signed integer is reached - early on January 19, 2038 - the time value will overflow into the smallest negative number, producing times beginning on December 13, 1901.

    Bad / Other

         The code runs on a Unix platform and uses a 32-bit
        signed integer to store a time value that is used for
        a security-critical decision or security-critical
        metadata.

    Once the time value exceeds the epoch on January 19, 2038, then the value could "flip" to an earlier date. This could change the behavior or security decisions made by the product, possibly leading to a DoS, a failed access control routing that inadvertently blocks out otherwise-valid users, etc. The consequences could vary based on how the expected date/timestamp is used within the product.

    점검 착안점 활동 근거
    크기·개수·시간 값을 곱하거나 더한 결과가 할당 크기, 복사 길이, 배열 색인으로 쓰이는 식을 찾고, 연산 전에 상한 검사나 넓은 자료형 계산이 있는지 확인한다. I-09·I-05 [CWE] CWE-190 탐지 방법(수동 분석: 할당 크기 계산의 정확성) · [표준] SEI CERT INT30-C·INT32-C·MEM07-C
    (C·C++) 호스트 빌드를 -fsanitize=undefined로 계측하고 입력을 자료형 최댓값·최솟값, 0, -1로 바꿔 'signed integer overflow' 보고가 나오는지 확인한다. 부호 없는 정수의 랩어라운드는 정의된 동작이라 -fsanitize=undefined가 보고하지 않으므로, clang은 -fsanitize=unsigned-integer-overflow를 함께 켜 'unsigned integer overflow' 보고를 확인한다. I-10·T-05 [예시] CWE-190 C·C++ 예시 검증(UBSan 보고)
    (Java·C#) 누적 시간·카운터처럼 계속 커지는 값을 최댓값 근처에서 시작해 결과가 음수나 작은 값으로 감기는지 시험하고, checked 문맥(C#)이나 Math.addExact 계열(Java)을 썼는지 확인한다. T-05·I-09 [예시] CWE-190 Java·C# 예시 검증(값이 감긴 합계 출력 확인)
    (C·C++) int가 16비트인 타깃과 호스트에서 정수 승격 결과가 달라지는 식을 찾고, 같은 경계값 시험을 타깃에서도 수행한다. T-02·I-09 [CWE] CWE-190 완화책(Implementation: 언어의 수 표현과 크기 차이 이해) · [보완]
    • ① 원문 탐지 방법(원문 효과성별): 높음: 수동 분석, 자동 정적 분석(바이너리·바이트코드), 아키텍처·설계 검토 / 보통: 블랙박스 시험 / 부분 적용: 동적 분석(결과 수동 해석), 수동 정적 분석(소스코드). 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: INT18-C, INT30-C, INT32-C, INT35-C, MEM07-C, MEM35-C

    이 가이드에서 다루는 곳¶

    부록 A의 이 항목 행에 있는 단계별 지침 (통합 및 시험 행의 호스트 새니타이저·단위시험은 이 가이드의 활동 구분으로는 구현 단계 I-10에 해당한다. 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 R-01 보안 요구사항 정의, 원문 완화책(요구사항) 2건 → 완화책
    설계 모든 수치 데이터의 단위·범위·자료형을 ICD와 설계서에 명시하고, 고정 폭 정수형(stdint.h) 사용을 표준으로 지정한다.
    구현(C·C++) 연산 전 범위를 검사하거나 __builtin_add_overflow/mul_overflow를 사용하고, 크기 계산(malloc, memcpy 길이)은 size_t로 하여 곱셈 오버플로를 검증한다.
    구현(Java) Math.addExact()/multiplyExact()/toIntExact()를 사용하고, 바이트 데이터 처리 시 부호 확장을 막는 & 0xFF 마스킹을 명시한다.
    통합 및 시험 -Wconversion -Wsign-conversion, -fsanitize=undefined(signed-integer-overflow) 시험과 경계값(MAX, MIN, 0, -1) 단위시험(unit test)을 수행한다.
    유지보수 자료형·스케일 변경 시 관련 연산 전체를 영향분석하고 경계값 회귀시험(regression test)을 재수행한다.
    임베디드 고려 AVR/16비트 MCU는 int가 16비트이므로 정수 승격 결과가 PC와 다르다. DSP 고정소수점(Q15/Q31)은 포화 연산(_sadd 등 intrinsic)을 사용하고 시간 카운터 랩어라운드는 부호 없는 차분으로 비교한다. Unix 시간을 32비트 부호 있는 정수에 저장하면 2038년에 넘치므로 시각 자료형의 폭을 확인한다.

    기준선 활동 6건

    • R-01 보안 요구사항 정의 (요구사항 분석)
    • D-09 설계 보안성 검토 (설계)
    • I-05 정수·포인터·메모리 안전 코딩 (구현 · 조건: 언어 런타임(L1)이 '네이티브-비안전')
    • I-10 호스트(타깃 외) 동적 분석 (구현 · 조건: 타깃 외(호스트) 빌드(L3)가 '가능')
    • T-04 퍼징 (통합 및 시험)
    • T-05 경계값·오류 주입 시험 (통합 및 시험)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 25건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
