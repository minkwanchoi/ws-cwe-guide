    Incorrect Permission Assignment for Critical Resource

    항목 내용
    추상화 수준 분류(Class)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    MITRE 매핑 권고 검토 후 허용(Allowed-with-Review) — 결과를 기록할 때는 더 맞는 하위 CWE가 있는지 검토한다(하위 CWE: CWE-276·CWE-277·CWE-278·CWE-279·CWE-281·CWE-493·CWE-582·CWE-583 외 3개)
    원문(Mapping Notes)

    Rationale: While the name itself indicates an assignment of permissions for resources, this is often misused for vulnerabilities in which "permissions" are not checked, which is an "authorization" weakness (CWE-285 or descendants) within CWE's model [REF-1287].

    Comments: Closely analyze the specific mistake that is allowing the resource to be exposed, and perform a CWE mapping for that mistake.
    적용 플랫폼 언어 무관 · 기술: 기술 무관, 클라우드 컴퓨팅(Cloud Computing)
    원문 MITRE CWE-732 (CWE 5.0)

    한 줄 요약

    보안상 중요한 자원의 권한을 의도하지 않은 행위자가 읽거나 수정할 수 있게 지정해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 보안상 중요한 자원의 권한을, 의도하지 않은 행위자(actor)가 그 자원을 읽거나 수정할 수 있게 지정한다.

    원문(Description)

    The product specifies permissions for a security-critical resource in a way that allows that resource to be read or modified by unintended actors.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 —
    구현(Implementation) 구현 실현(REALIZATION): 아키텍처 보안 전술을 구현하는 과정에서 생기는 약점이다. 개발자가 소프트웨어가 단일 사용자 시스템에서 실행된다거나 신뢰할 수 있는 관리자만 접근한다는 식으로 운영 환경을 가정할 수 있으며, 다른 환경에서 실행되면 권한이 문제가 된다.
    설치(Installation) 통합 및 시험 개발자가 사용자가 처음 실행할 때의 문제를 줄이려고 권한을 느슨하게 설정하고 문서에 권한을 강화해야 한다고 적을 수 있는데, 시스템 관리자와 사용자가 항상 문서를 읽지는 않으므로 안전하지 않은 권한이 바뀌지 않고 남을 수 있다.
    운용(Operation) 유지보수 —

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 애플리케이션 데이터 읽기 / 파일·디렉터리 읽기 공격자가 관련 자원에서 파일에 저장된 자격 증명이나 설정 정보 같은 민감한 정보를 읽을 수 있다.
    접근 통제 권한 획득 또는 신원 도용 공격자가 관련 자원의 중요한 속성을 수정해 권한을 얻을 수 있다(예: 누구나 쓸 수 있는(world-writable) 실행 파일을 트로이 목마로 바꿔치기).
    무결성 / 기타 애플리케이션 데이터 수정 / 기타 공격자가 관련 자원의 중요한 데이터를 파괴하거나 손상시킬 수 있다(예: 데이터베이스 레코드 삭제). 예로 공개 사용자나 익명 사용자가 읽거나 쓸 수 있게 잘못 설정된 클라우드 저장소 계정을 들 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 9건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 소프트웨어를 익명·일반·특권·관리 영역으로 나누고, 서로 구별되는 사용자 그룹·권한·역할을 신중히 정의해 공격 표면을 줄인 뒤, 이를 데이터·기능·관련 자원에 대응시켜 권한을 설정한다. 이렇게 하면 자원을 더 세밀하게 통제할 수 있다 [REF-207].
    원문

    Divide the software into anonymous, normal, privileged, and administrative areas. Reduce the attack surface by carefully defining distinct user groups, privileges, and/or roles. Map these against data, functionality, and the related resources. Then set the permissions accordingly. This will allow you to maintain more fine-grained control over your resources. [REF-207]

    		 보통(Moderate) — 효과적인 전략이 될 수 있으나, 실제로는 자원이나 사용자 유형이 많거나 애플리케이션 기능이 빠르게 바뀌면 이런 영역을 정의하기 어렵거나 시간이 많이 들 수 있다.
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 설정 파일 같은 중요한 자원을 쓸 때 그 자원에 안전하지 않은 권한(예: 일반 사용자 누구나 수정 가능)이 있는지 확인하고 [REF-62], 인가되지 않은 당사자가 자원을 수정했을 가능성이 있으면 오류를 발생시키거나 프로그램을 종료한다.
    원문

    When using a critical resource such as a configuration file, check to see if the resource has insecure permissions (such as being modifiable by any regular user) [REF-62], and generate an error or even exit the software if there is a possibility that the resource could have been modified by an unauthorized party.

    		 —
    구현(Implementation) / 설치(Installation) — 프로그램 시작 시 기본 권한이나 umask를 가능한 한 가장 제한적으로 명시해 설정하고, 설치 시에도 적절한 권한을 설정한다. 이렇게 하면 프로그램을 설치하거나 실행하는 사용자의 안전하지 않은 권한을 물려받지 않는다. (통합 및 시험 단계에도 해당)
    원문

    During program startup, explicitly set the default permissions or umask to the most restrictive setting possible. Also set the appropriate permissions during program installation. This will prevent you from inheriting insecure permissions from any user who installs or runs the program.

    		 높음(High)
    구현(Implementation) / 시스템 구성(System Configuration) / 운용(Operation) — 클라우드(예: S3 버킷, Azure blob, Google Cloud Storage 등)에 데이터를 저장할 때 제공자의 통제 기능으로 공개 접근을 비활성화한다. (유지보수 단계에도 해당)
    원문

    When storing data in the cloud (e.g., S3 buckets, Azure blobs, Google Cloud Storage, etc.), use the provider's controls to disable public access.

    		 —

    통합 및 시험 (본문 제6장)¶

    CWE 단계(Phase) 전략 요지 효과성
    문서화(Documentation) — 문서에서 안전하지 않은 설정 변경을 권하지 않는다. 특히 그 설정이 애플리케이션 범위 밖의 자원과 다른 프로그램까지 확장될 수 있으면 더욱 그렇다.
    원문

    Do not suggest insecure configuration changes in documentation, especially if those configurations can extend to resources and other programs that are outside the scope of the application.

    		 —
    설치(Installation) — 시스템 관리자가 소프트웨어 매뉴얼에 권장된 설정으로 직접 바꿀 것이라고 가정하지 않는다.
    원문

    Do not assume that a system administrator will manually change the configuration to the settings that are recommended in the software's manual.

    		 —

    유지보수 (본문 제7장)¶

    CWE 단계(Phase) 전략 요지 효과성
    시스템 구성(System Configuration) — 모든 설정 파일·실행 파일·라이브러리는 소프트웨어 관리자만 읽고 쓸 수 있게 한다.
    원문

    For all configuration files, executables, and libraries, make sure that they are only readable and writable by the software's administrator.

    		 높음(High)
    운용(Operation) / 시스템 구성(System Configuration) 실행 환경 강화 소프트웨어가 USGCB(United States Government Configuration Baseline, REF-199) 또는 그에 준하는 하드닝 설정 가이드 아래에서 제대로 동작하게 한다. 많은 조직이 이런 가이드로 배포된 소프트웨어의 공격 표면과 잠재 위험을 줄인다.
    원문

    Ensure that the software runs properly under the United States Government Configuration Baseline (USGCB) [REF-199] or an equivalent hardening configuration guide, which many organizations use to limit the attack surface and potential risk of deployed software.

    		 —

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 세션 키·감사 로그·임무 계획·정비 기록 파일을 만드는 프로그램이다. C·C++ 예시는 탑재 컴퓨터(임베디드 Linux)에서, Python 예시는 지상 통제 소프트웨어(Linux)에서 파일 모드(umask·0600 등)로, Java·C# 예시는 지상 통제 PC(Windows)에서 ACL로 작성했다. 어느 쪽이든 만든 파일의 실제 권한을 다시 읽어 모든 계정(기타 사용자·Everyone)에게 쓰기가 열렸는지 출력한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>

#define KEY_PATH "link_session.key"

/* 데이터링크 세션 키를 탑재 컴퓨터(임베디드 Linux)의 파일로 남긴다 */
int main(void)
{
    unsigned char key[32] = {0};
    umask(0);                                    /* 정비 도구도 쓰라고 umask를 풀어 둔다 */
    unlink(KEY_PATH);                            /* 예시 재실행용 */
    int fd = open(KEY_PATH, O_WRONLY | O_CREAT, 0666);   /* 모든 계정 읽기·쓰기 */
    if (fd < 0) {
        perror("open");
        return 1;
    }
    if (write(fd, key, sizeof key) != (ssize_t)sizeof key) {
        perror("write");
    }
    close(fd);

    struct stat st;
    if (stat(KEY_PATH, &st) == 0) {
        printf("%s mode %04o\n", KEY_PATH, (unsigned)(st.st_mode & 0777));
    }
    return 0;
}

    umask를 0으로 풀고 0666으로 파일을 만들어 세션 키를 모든 계정이 읽고 바꿀 수 있다. 실행 결과의 mode 0666이 그 상태다. '다른 도구도 써야 해서' 권한을 넓히는 것이 흔한 원인이다.

    좋은 예

    #include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>

#define KEY_PATH "link_session.key"

int main(void)
{
    unsigned char key[32] = {0};
    umask(077);                                  /* 이 프로세스가 만드는 파일은 소유자만 */
    unlink(KEY_PATH);                            /* 예시 재실행용 */
    /* 처음부터 0600으로, 이미 있으면 실패(O_EXCL), 링크는 따라가지 않음 */
    int fd = open(KEY_PATH, O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW, 0600);
    if (fd < 0) {
        perror("open");
        return 1;
    }
    if (write(fd, key, sizeof key) != (ssize_t)sizeof key) {
        perror("write");
    }
    close(fd);

    struct stat st;
    if (stat(KEY_PATH, &st) == 0) {
        printf("%s mode %04o\n", KEY_PATH, (unsigned)(st.st_mode & 0777));
    }
    return 0;
}

    자동 정적 분석 자동화된 정적 분석은 파일·디렉터리·공유 메모리·장치 인터페이스 같은 시스템 자원의 권한 문제 탐지에 효과적일 수 있다. 권한을 바꾸는 라이브러리 함수 사용을 찾아, 그 호출 인자에 안전하지 않을 수 있는 값이 있는지 분석할 수 있다. 다만 의도된 보안 정책이 특정 작업(예: 웹 서버에 파일 게시)에 느슨한 권한을 허용할 수 있어, 보안 영향이 없거나 코드를 고칠 필요가 없는 경고(오탐)가 일부 생길 수 있다. 사용자 정의 권한 모델(예: 게시판에서 특정 포럼 메시지를 누가 읽을 수 있는지 정의)은 정적 분석으로 탐지하기 어려울 수 있으며, 권한 검사·할당을 구현하는 사용자 정의 함수를 식별하는 사용자 정의 시그니처를 만들 수도 있다.
    원문

    Automated static analysis may be effective in detecting permission problems for system resources such as files, directories, shared memory, device interfaces, etc. Automated techniques may be able to detect the use of library functions that modify permissions, then analyze function calls for arguments that contain potentially insecure values.

    However, since the software's intended security policy might allow loose permissions for certain operations (such as publishing a file on a web server), automated static analysis may produce some false positives - i.e., warnings that do not have any security consequences or require any code changes.

    When custom permissions models are used - such as defining who can read messages in a particular forum in a bulletin board system - these can be difficult to detect using automated static analysis. It may be possible to define custom signatures that identify any custom functions that implement the permission checks and assignments.

    Use monitoring tools that examine the software's process as it interacts with the operating system and the network. This technique is useful in cases when source code is unavailable, if the software was not developed by you, or if you want to verify that the build phase did not introduce any new weaknesses. Examples include debuggers that directly attach to the running process; system-call tracing utilities such as truss (Solaris) and strace (Linux); system activity monitors such as FileMon, RegMon, Process Monitor, and other Sysinternals utilities (Windows); and sniffers and protocol analyzers that monitor network traffic.

    Attach the monitor to the process and watch for library functions or system calls on OS resources such as files, directories, and shared memory. Examine the arguments to these calls to infer which permissions are being used.

    CVE-2022-29527 클라우드 관리용 Go 애플리케이션이 누구나 쓸 수 있는 sudoers 파일을 만들어, 로컬 공격자가 경쟁조건을 이용해 sudo 규칙을 삽입하고 root로 권한을 상승할 수 있다.

    원문

    Anti-virus product sets insecure "Everyone: Full Control" permissions for files under the "Program Files" folder, allowing attackers to replace executables with Trojan horses.
    CVE-2009-3897 제품이 설치 때 0777 권한으로 디렉터리를 만들어 사용자가 권한을 얻고 인증에 쓰이는 소켓에 접근할 수 있다.

    Product creates directories with 0777 permissions at installation, allowing users to gain privileges and access a socket used for authentication.
    CVE-2009-3489 사진 편집기가 안전하지 않은 보안 설명자로 서비스를 설치하여 사용자가 서비스를 중지·시작하거나 SYSTEM 권한으로 명령을 실행할 수 있다.
    원문

    Photo editor installs a service with an insecure security descriptor, allowing users to stop or start the service, or execute commands as SYSTEM.
    CVE-2020-15708 소켓이 안전하지 않은 권한으로 생성된다.
    원문

    socket created with insecure permissions
    CVE-2009-3289 라이브러리 함수가 파일을 새 대상으로 복사하면서 원본 파일의 권한을 대상에 쓰는데, 원본이 대개 0777 권한을 갖는 심볼릭 링크이면 잘못된 권한이 된다.

    Library function copies a file to a new target and uses the source file's permissions for the target, which is incorrect when the source file is a symbolic link, which typically has 0777 permissions.
