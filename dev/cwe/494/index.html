    Download of Code Without Integrity Check

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 조건부 — 현장·원격 업데이트 기능 사용
    적용 플랫폼 언어 무관
    원문 MITRE CWE-494 (CWE 5.0)

    한 줄 요약

    원격에서 내려받은 코드나 실행 파일의 출처와 무결성을 충분히 검증하지 않고 실행하는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 원격 위치에서 소스코드나 실행 파일을 내려받아, 그 코드의 출처와 무결성을 충분히 검증하지 않은 채 실행하는 약점이다.

    원문(Description)

    The product downloads source code or an executable from a remote location and executes the code without sufficiently verifying the origin and integrity of the code.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 누락(OMISSION): 아키텍처·설계 단계에서 보안 전술을 빠뜨려 생기는 약점이다.
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 가용성 / 기밀성 / 기타 허가되지 않은 코드·명령 실행 / 실행 논리 변경 / 기타 공격자는 호스트 서버를 장악하거나, DNS 스푸핑(DNS spoofing)을 하거나, 전송 중인 코드를 변조하여 악성 코드를 실행할 수 있다. 신뢰할 수 없는 코드를 실행하면 프로그램의 제어 흐름이 손상될 수 있으며, 그 코드가 공격자가 통제하는 명령을 실행하거나, 중요 자원을 읽거나 수정하거나, 정당한 사용자에게 소프트웨어가 제대로 동작하지 못하게 할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) / 운용(Operation) — 전송 전에 신뢰할 수 있는 암호화 방식으로 코드를 암호화한다. (유지보수 단계에도 해당)
    원문

    Encrypt the code with a reliable encryption scheme before transmitting.

    		 DNS 스푸핑을 탐지하지 못하고 호스팅 사이트에서의 코드 변조도 막지 못하므로 부분적인 해결책일 뿐이다.
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리·프레임워크를 쓴다 [REF-1482]. 특히 전송된 코드의 무결성을 검사하는 도구·프레임워크가 도움이 될 수 있다. 소프트웨어 자동 업데이트처럼 내려받을 코드를 제공할 때는 코드에 암호 서명을 하고, 다운로드 클라이언트가 서명을 검증하도록 고친다. 이 구현에 CWE-295, CWE-320, CWE-347 및 관련 약점이 없게 한다. Authenticode 같은 코드 서명 기술을 쓴다 [REF-454] [REF-455] [REF-456].
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid [REF-1482].

    Speficially, it may be helpful to use tools or frameworks to perform integrity checking on the transmitted code.

    - When providing the code that is to be downloaded, such as for automatic updates of the software, then use cryptographic signatures for the code and modify the download clients to verify the signatures. Ensure that the implementation does not contain CWE-295, CWE-320, CWE-347, and related weaknesses.

    - Use code signing technologies such as Authenticode. See references [REF-454] [REF-455] [REF-456].

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 실행 환경 강화 작업에 필요한 최소 권한으로 코드를 실행하고 [REF-76], 가능하면 한 작업에만 쓰는 제한된 권한의 격리된 계정을 만들어 공격이 성공해도 나머지 소프트웨어나 환경에 바로 접근하지 못하게 한다(예: 데이터베이스 애플리케이션은 특히 일상 운영에서 데이터베이스 관리자 권한으로 실행할 필요가 거의 없다). (유지보수 단계에도 해당)
    원문

    Run your code using the lowest privileges that are required to accomplish the necessary tasks [REF-76]. If possible, create isolated accounts with limited privileges that are only used for a single task. That way, a successful attack will not immediately give the attacker access to the rest of the software or its environment. For example, database applications rarely need to run as the database administrator, especially in day-to-day operations.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — DNS 스푸핑을 탐지하도록 정방향·역방향 DNS 조회를 제대로 수행한다.
    원문

    Perform proper forward and reverse DNS lookups to detect DNS spoofing.

    		 호스팅 사이트나 전송 중의 코드 변조는 막지 못하므로 부분적인 해결책일 뿐이다.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-06 보안 기능 부정 시험

    유지보수 (본문 제7장)¶

    이 단계를 함께 가리키는 원문 완화책은 설계 단계에 3건 실었다('유지보수 단계에도 해당' 표시). 이 단계의 기준선 활동: M-04 서명된 업데이트·배포 무결성 검증.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 비행제어·센서 신호처리·통신 단말의 펌웨어나 임무 데이터 묶음을 지상 장비나 정비 단말에서 받아 적용한다. 임무 데이터 묶음은 장비의 동작을 결정하므로 이 예시에서는 코드처럼 취급한다. 받은 바이트가 개발 측이 승인한 것인지 확인하지 않으면, 전송 경로나 정비 매체에서 바뀐 이미지가 그대로 적용된다. 예시는 실제 다운로드 대신 '받은 바이트 배열'로, 정상 이미지와 변조 이미지를 차례로 넣어 본다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <string.h>

/* 지상 장비에서 받은 비행제어 펌웨어 이미지: [본문 7바이트][합계 체크섬 1바이트] */
#define BODY_LEN 7

static uint8_t sum8(const uint8_t *p, size_t n)
{
    uint8_t s = 0;
    while (n--) s = (uint8_t)(s + *p++);
    return s;
}

static void install_update(const char *label, const uint8_t *img)
{
    if (sum8(img, BODY_LEN) != img[BODY_LEN]) {   /* 전송 오류만 확인 */
        printf("%s: REJECTED (checksum)\n", label);
        return;
    }
    printf("%s: APPLIED body=%.*s\n", label, BODY_LEN, (const char *)img);
}

int main(void)
{
    uint8_t img[BODY_LEN + 1];
    memcpy(img, "FCS-1.4", BODY_LEN);
    img[BODY_LEN] = sum8(img, BODY_LEN);
    install_update("released", img);

    /* 중간자가 본문을 바꾸고 체크섬도 다시 계산해 붙인다 */
    memcpy(img, "EVIL1.4", BODY_LEN);
    img[BODY_LEN] = sum8(img, BODY_LEN);
    install_update("tampered", img);
    return 0;
}

    본문에 붙은 합계 체크섬만 확인하고 적용한다. 체크섬은 누구나 다시 계산할 수 있으므로, 본문을 바꾸고 체크섬을 새로 붙인 변조 이미지도 적용된다(출력 APPLIED).

    좋은 예

    #include <stdbool.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>

#define BODY_LEN 7
#define SIG_LEN 4

/* 검증 모듈 인터페이스: 장비에 고정된 공개키로 서명을 검증한다.
   실제 장비에서는 보안 부트 ROM API나 검증된 암호 모듈의 ECDSA 검증을 호출한다. */
bool fw_signature_ok(const uint8_t *body, size_t n, const uint8_t *sig, size_t sig_n);

/* 시험용 대역(test double): 승인된 릴리스 본문과 서명 표식이 맞을 때만 참. 실제 검증이 아니다. */
bool fw_signature_ok(const uint8_t *body, size_t n, const uint8_t *sig, size_t sig_n)
{
    return n == BODY_LEN && memcmp(body, "FCS-1.4", n) == 0 && sig_n == SIG_LEN && memcmp(sig, "SIG1", SIG_LEN) == 0;
}

static void install_update(const char *label, const uint8_t *body, const uint8_t *sig)
{
    if (!fw_signature_ok(body, BODY_LEN, sig, SIG_LEN)) {   /* 적용 전에 서명 검증 */
        printf("%s: REJECTED, keeping current image\n", label);
        return;
    }
    printf("%s: APPLIED body=%.*s\n", label, BODY_LEN, (const char *)body);
}

int main(void)
{
    uint8_t body[BODY_LEN];
    const uint8_t sig[SIG_LEN] = {'S', 'I', 'G', '1'};
    memcpy(body, "FCS-1.4", BODY_LEN);
    install_update("released", body, sig);

    memcpy(body, "EVIL1.4", BODY_LEN);   /* 본문만 바꾼 이미지: 개인키 없이는 새 서명을 못 만든다 */
    install_update("tampered", body, sig);
    return 0;
}

    적용 전에 검증 모듈 인터페이스(fw_signature_ok)로 고정 공개키 서명을 검증하고, 실패하면 기존 이미지를 유지한다. 예시의 검증 함수는 흐름을 보이기 위한 시험용 대역이며, 실제로는 보안 부트 ROM이나 검증된 암호 모듈을 호출한다. CRC·체크섬은 전송 오류 검출용일 뿐 변조 방지가 아니다.

    검증: 실행 결과 — 나쁜 예에서 tampered: APPLIED 검출, 좋은 예에서 미검출·tampered: REJECTED 출력 확인 · 참고: MITRE CWE-494 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdint>
#include <cstdio>
#include <string>
#include <vector>

// 임무 데이터 적재 장치(MDL)가 받은 임무 데이터 묶음: "MDP" + 판 번호 1바이트 + 본문
using Bytes = std::vector<std::uint8_t>;

class MissionLoader {
    int installedRev_ = 3;
public:
    void Load(const std::string &label, const Bytes &pkg) {
        // 형식과 판 번호만 본다: 누가 만든 묶음인지는 확인하지 않는다
        if (pkg.size() < 5 || pkg[0] != 'M' || pkg[1] != 'D' || pkg[2] != 'P' || pkg[3] <= installedRev_) {
            std::printf("%s: REJECTED (format/revision)\n", label.c_str());
            return;
        }
        installedRev_ = pkg[3];
        std::string body(pkg.begin() + 4, pkg.end());
        std::printf("%s: APPLIED rev=%d body=%s\n", label.c_str(), installedRev_, body.c_str());
    }
};

int main() {
    MissionLoader mdl;
    Bytes official{'M', 'D', 'P', 4, 'W', 'P', 'T', '-', 'A'};
    mdl.Load("released", official);

    Bytes forged{'M', 'D', 'P', 5, 'W', 'P', 'T', '-', 'X'};   // 제3자가 만든 묶음
    mdl.Load("tampered", forged);
    return 0;
}

    머리말 형식과 판 번호만 보고 임무 데이터를 적재한다. 누가 만든 묶음인지 확인하지 않으므로, 형식만 맞춘 제3자 묶음이 더 높은 판 번호를 달고 적용된다.

    #include <cstdint>

// 검증 모듈 인터페이스: 실제 장비에서는 검증된 암호 모듈로 고정 공개키 서명(ECDSA 등)을 검증한다
struct SignatureVerifier {
    virtual ~SignatureVerifier() = default;
    virtual bool Verify(const Bytes &content, const Bytes &signature) const = 0;
};

// 시험용 대역(test double): 승인된 묶음과 서명 표식이 맞을 때만 참. 암호 검증이 아니다.
struct ApprovedListVerifier final : SignatureVerifier {
    bool Verify(const Bytes &content, const Bytes &signature) const override {
        const Bytes approved{'M', 'D', 'P', 4, 'W', 'P', 'T', '-', 'A'};
        return content == approved && signature == Bytes{0x5A, 0x11};
    }
};

class MissionLoader {
    const SignatureVerifier &verifier_;
    int installedRev_ = 3;
public:
    explicit MissionLoader(const SignatureVerifier &v) : verifier_(v) {}
    void Load(const std::string &label, const Bytes &pkg, const Bytes &sig) {
        if (!verifier_.Verify(pkg, sig)) {   // 서명 먼저, 형식·판 번호(롤백 방지)는 그다음
            std::printf("%s: REJECTED (signature), keeping rev=%d\n", label.c_str(), installedRev_);
            return;
        }
        if (pkg.size() < 5 || pkg[3] <= installedRev_) {
            std::printf("%s: REJECTED (revision)\n", label.c_str());
            return;
        }
        installedRev_ = pkg[3];
        std::printf("%s: APPLIED rev=%d\n", label.c_str(), installedRev_);
    }
};

int main() {

    MissionLoader mdl(verifier);
    mdl.Load("released", {'M', 'D', 'P', 4, 'W', 'P', 'T', '-', 'A'}, {0x5A, 0x11});
    mdl.Load("tampered", {'M', 'D', 'P', 5, 'W', 'P', 'T', '-', 'X'}, {0x5A, 0x11});
    return 0;
}

// 시험용 서명 키: 실제로는 개인키가 개발 측 서명 서버(HSM)에만 있고, 단말에는 공개키만 고정한다

    나쁜 예

    import java.nio.charset.StandardCharsets;
import java.util.zip.CRC32;

public class Example {
    // 업데이트 묶음: 센서 신호처리 보드 펌웨어 본문과, 함께 실려 온 CRC32 값
    record UpdatePackage(byte[] firmware, long crc) {
        static UpdatePackage of(String body) {
            byte[] fw = body.getBytes(StandardCharsets.US_ASCII);
            return new UpdatePackage(fw, crcOf(fw));   // 누구나 다시 계산할 수 있는 값
        }
    }

    static long crcOf(byte[] data) {
        CRC32 c = new CRC32();
        c.update(data);
        return c.getValue();
    }

    static void install(String label, UpdatePackage p) {
        if (crcOf(p.firmware()) != p.crc()) {          // 전송 오류만 걸러진다
            System.out.println(label + ": REJECTED (crc)");
            return;
        }
        System.out.println(label + ": APPLIED " + new String(p.firmware(), StandardCharsets.US_ASCII));
    }

    public static void main(String[] args) {
        install("released", UpdatePackage.of("SSP-FW 2.0.1"));
        install("tampered", UpdatePackage.of("SSP-FW 2.0.1+backdoor"));  // 변조 후 CRC도 새로 붙임
    }
}

    묶음에 함께 실려 온 CRC32 값과만 비교한다. CRC는 비밀 없이 누구나 계산하므로 백도어를 넣고 CRC를 다시 붙인 묶음도 통과한다.

    import java.nio.charset.StandardCharsets;

import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.PublicKey;
import java.security.Signature;
import java.security.SignatureException;

public class Example {
    record UpdatePackage(byte[] firmware, byte[] signature) {}

    // 장비에 고정해 둔 공개키로만 검증한다(서명 개인키는 개발 측 서명 서버에만 있다)
    static boolean verified(UpdatePackage p, PublicKey pinnedKey) throws GeneralSecurityException {
        Signature v = Signature.getInstance("Ed25519");
        v.initVerify(pinnedKey);
        v.update(p.firmware());
        try {
            return v.verify(p.signature());
        } catch (SignatureException e) {               // 길이가 틀린 서명 같은 형식 오류도 거부한다
            return false;
        }
    }

    static void install(String label, UpdatePackage p, PublicKey pinnedKey) throws GeneralSecurityException {
        if (!verified(p, pinnedKey)) {
            System.out.println(label + ": REJECTED (signature), keeping current firmware");
            return;
        }
        System.out.println(label + ": APPLIED " + new String(p.firmware(), StandardCharsets.US_ASCII));
    }

    public static void main(String[] args) throws GeneralSecurityException {
        KeyPair signer = KeyPairGenerator.getInstance("Ed25519").generateKeyPair();  // 시험용 키
        byte[] fw = "SSP-FW 2.0.1".getBytes(StandardCharsets.US_ASCII);
        Signature s = Signature.getInstance("Ed25519");
        s.initSign(signer.getPrivate());
        s.update(fw);
        byte[] sig = s.sign();

        install("released", new UpdatePackage(fw, sig), signer.getPublic());
        byte[] evil = "SSP-FW 2.0.1+backdoor".getBytes(StandardCharsets.US_ASCII);
        install("tampered", new UpdatePackage(evil, sig), signer.getPublic());  // 개인키 없이 서명 못 바꿈
    }
}

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    수동 분석 침투 시험, 위협 모델링, 활성 세션을 기록·수정하는 대화형 도구처럼 사람이 직접 분석하는 도구·기법으로 탐지할 수 있으며, 특히 코드 다운로드를 일으키는 동작을 찾고 무결성 검사 방법을 쓰는지 판단하려면 대개 수동 정적 분석이 필요하다.

Monitor when files are downloaded and separately executed, or if they are otherwise read back into the process. Look for evidence of cryptographic library calls that use integrity checking.

    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    업데이트·적재 경로에서 실행 전 검증이 체크섬·CRC나 같은 묶음에 실려 온 해시와 비교하는 데 그치는지, 장비에 미리 넣은 공개키로 서명을 검증하는지 확인한다. I-09·D-09 [예시] CWE-494 예시(합계 체크섬·CRC·동봉 해시만 비교) · [표준] SEI CERT SEC06-J
    본문을 바꾸고 체크섬·해시를 다시 붙인 이미지, 서명이 없는 이미지, 판 번호만 올린 제3자 묶음, 이전 판 이미지를 적재해 거부되는지 시험한다. T-06·M-04 [예시] CWE-494 예시 검증(변조 이미지가 적용되는지 실행 확인)
    업데이트 도중 전원을 끊거나 저장된 이미지의 일부 바이트를 바꾼 뒤 재부팅해, 부트로더가 부팅 때마다 서명을 다시 검증하고 검증된 이전 이미지로 돌아오는지 시험한다. T-06·T-02 [보완]
    부트로더 설정에서 공개키가 비었거나 0일 때 서명 검증을 건너뛰는 분기가 있는지 확인한다. T-08·I-09 [보완]
    • ① 원문 탐지 방법(원문 효과성별): 효과 등급 없음: 수동 분석, 블랙박스 시험. 각 방법의 시험 활동은 6.2의 대응표를 따른다.

    단계 지침
    요구사항 분석 —
    설계 펌웨어·소프트웨어 업데이트에 전자서명(digital signature) 검증과 보안 부팅(secure boot) 체인을 설계하고, 롤백 방지를 포함한다.
    구현(C·C++) 업데이트 이미지를 적용 전 ECDSA/RSA 서명으로 검증하고, 검증 실패 시 기존 이미지를 유지한다. 해시 비교만으로 대체하지 않는다.
    구현(Java) 원격 클래스·JAR 로드를 금지하고, 불가피하면 서명 JAR 검증과 해시 확인을 수행한다.
    통합 및 시험 변조·미서명·구버전 이미지 적용 시험과 업데이트 중 전원 차단 시험을 수행한다.
    유지보수 서명 키 관리와 업데이트 이력(버전) 관리를 형상관리(configuration management) 절차에 포함한다.
    임베디드 고려 부트로더에서 서명 검증 후 실행하고 이중 뱅크(A/B) 구조로 업데이트 실패를 복구한다. 하드웨어 신뢰 기점(eFuse 공개키 해시)을 사용한다.
