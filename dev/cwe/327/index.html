    원문 MITRE CWE-327 (CWE 5.0)

    한 줄 요약

    깨졌거나 위험한 암호 알고리즘 또는 프로토콜을 사용하는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 깨졌거나 위험한 암호 알고리즘 또는 프로토콜을 사용하는 약점이다. 암호 알고리즘은 권한 없는 행위자가 데이터를 관찰하거나 조작하지 못하도록 데이터를 뒤섞는 방법이며, 안전하지 않은 암호는 중요정보 노출, 예상치 못한 데이터 변조, 다른 사용자·장치의 신원 위장 등에 악용될 수 있다. 안전한 알고리즘을 만들기는 매우 어렵고 뛰어난 암호 전문가가 만든 유명 알고리즘도 깨진 적이 있으며, 여러 종류의 암호를 깨거나 약화하는 잘 알려진 기법도 있다. 따라서 대부분의 제품은 잘 이해되고 깊이 연구된 소수의 알고리즘을 써야 하며, 비표준이거나 안전하지 않다고 알려진 알고리즘을 쓰면 끈질긴 공격자가 알고리즘을 깨고 보호된 데이터를 노출하거나 변조할 수 있어 위험하다. 암호 기술은 매우 빠르게 발전하므로, 새로운 공격이 발견되거나 컴퓨팅 성능이 크게 늘어 원래 기대한 보호 수준을 제공하지 못하게 되면 한때 강하다고 여겨진 알고리즘도 흔히 '안전하지 않다'고 간주된다. 하드웨어로 배치한 암호 알고리즘은 소프트웨어 구현보다 이 약점을 관리하기가 더 어려운데, 하드웨어는 소프트웨어처럼 쉽게 교체할 수 없어 대부분의 경우 제품 리콜 없이는 결함을 고칠 수 없고, 하드웨어 제품은 수년간 쓰이는 동안 공격자의 컴퓨팅 성능이 계속 늘어나기 때문이다.

    원문(Description · Extended Description)

    The product uses a broken or risky cryptographic algorithm or protocol.

    Cryptographic algorithms are the methods by which data is scrambled to prevent observation or influence by unauthorized actors. Insecure cryptography can be exploited to expose sensitive information, modify data in unexpected ways, spoof identities of other users or devices, or other impacts.

    It is very difficult to produce a secure algorithm, and even high-profile algorithms by accomplished cryptographic experts have been broken. Well-known techniques exist to break or weaken various kinds of cryptography. Accordingly, there are a small number of well-understood and heavily studied algorithms that should be used by most products. Using a non-standard or known-insecure algorithm is dangerous because a determined adversary may be able to break the algorithm and compromise whatever data has been protected.

    Since the state of cryptography advances so rapidly, it is common for an algorithm to be considered "unsafe" even if it was once thought to be strong. This can happen when new attacks are discovered, or if computing power increases so much that the cryptographic algorithm no longer provides the amount of protection that was originally thought.

    For a number of reasons, this weakness is even more challenging to manage with hardware deployment of cryptographic algorithms as opposed to software implementation. First, if a flaw is discovered with hardware-implemented cryptography, the flaw cannot be fixed in most cases without a recall of the product, because hardware is not easily replaceable like software. Second, because the hardware product is expected to work for years, the adversary's computing power will only increase over time.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 작위(COMMISSION): 아키텍처 보안 전술과 관련된 잘못된 설계로 생기는 약점이다.
    구현(Implementation) 구현 하드웨어에서는 아키텍처·설계 단계에서 요건에 맞는 암호로 시작했더라도 구현 제약(예: 제대로 동작할 만큼의 엔트로피 부족, 구현할 실리콘 면적 부족) 때문에 이후 구현 단계에서 요건에 맞지 않는 암호로 바뀔 수 있고, 드물게(특히 수년에 걸친 장기 과제에서) 작성 당시 요건에 맞던 아키텍처 명세의 암호가 암호 공격 기술의 발전으로 시간이 지나며 요건에 맞지 않게 될 수도 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 애플리케이션 데이터 읽기 깨졌거나 위험한 암호 알고리즘을 쓰면 중요 데이터의 기밀성이 손상될 수 있다.
    무결성 애플리케이션 데이터 수정 깨졌거나 위험한 암호 알고리즘을 쓰면 중요 데이터의 무결성이 손상될 수 있다.
    책임 추적성 / 부인 방지 행위 은닉 전자서명처럼 데이터 출처의 신원을 보장하는 데 암호 알고리즘을 쓰는 경우, 깨진 알고리즘은 이 체계를 무너뜨려 데이터의 출처를 증명할 수 없게 만든다.

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 중요 데이터를 저장·전송해야 할 때는 강력한 최신 암호 알고리즘으로 암호화한다. 현재 전문가들이 강하다고 보는 충분히 검증된 알고리즘과 잘 시험된 구현을 고른다(예: 미국 정부 시스템은 FIPS 140-2 인증을 요구한다 [REF-1192]). 모든 암호 메커니즘처럼 소스코드는 분석할 수 있어야 한다. 자체·비공개 암호 알고리즘을 개발하지 않는다. 암호학자들이 잘 아는 공격에 노출될 가능성이 크고 역공학 기법도 성숙했으며, 동작 방식이 알려지면 뚫리는 알고리즘은 특히 약하다. 암호가 낡지 않았는지 주기적으로 확인한다. 한때 10억 년의 계산이 필요하다고 여겨졌던 MD4, MD5, SHA1, DES 같은 알고리즘도 이제 며칠이나 몇 시간 만에 깨질 수 있다 [REF-267].
    원문

    When there is a need to store or transmit sensitive data, use strong, up-to-date cryptographic algorithms to encrypt that data. Select a well-vetted algorithm that is currently considered to be strong by experts in the field, and use well-tested implementations. As with all cryptographic mechanisms, the source code should be available for analysis.

    For example, US government systems require FIPS 140-2 certification [REF-1192].

    Do not develop custom or private cryptographic algorithms. They will likely be exposed to attacks that are well-understood by cryptographers. Reverse engineering techniques are mature. If the algorithm can be compromised if attackers find out how it works, then it is especially weak.

    Periodically ensure that the cryptography has not become obsolete. Some older algorithms, once thought to require a billion years of computing time, can now be broken in days or hours. This includes MD4, MD5, SHA1, DES, and other algorithms that were once regarded as strong. [REF-267]

    		 —
    아키텍처·설계(Architecture and Design) — 다음 세대나 버전에서 암호 알고리즘을 다른 것으로 교체할 수 있게 설계하고, 가능하면 래퍼로 인터페이스를 통일해 더 강한 알고리즘으로 쉽게 업그레이드하게 한다. 하드웨어는 IP(Intellectual Property) 수준에서 설계해 다음 세대 하드웨어 제품에서 암호 알고리즘을 교체할 수 있게 한다.
    원문

    Ensure that the design allows one cryptographic algorithm to be replaced with another in the next generation or version. Where possible, use wrappers to make the interfaces uniform. This will make it easier to upgrade to stronger algorithms. With hardware, design the product at the Intellectual Property (IP) level so that one cryptographic algorithm can be replaced with another in the next generation of the hardware product.

    		 심층 방어(Defense in Depth)
    아키텍처·설계(Architecture and Design) — 암호 키를 신중하게 관리·보호한다(CWE-320). 키를 추측하거나 훔칠 수 있다면 암호 자체의 강도는 의미가 없다.
    원문

    Carefully manage and protect cryptographic keys (see CWE-320). If the keys can be guessed or stolen, then the strength of the cryptography itself is irrelevant.

    		 —
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리·프레임워크를 쓴다 [REF-1482]. 업계 표준 구현은 개발 시간을 줄이고 암호 알고리즘 구현 중 생길 수 있는 오류를 피할 가능성이 더 높을 수 있다. ESAPI의 Encryption 기능을 검토한다.
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid [REF-1482].

    Industry-standard implementations will save development time and may be more likely to avoid errors that can occur during implementation of cryptographic algorithms. Consider the ESAPI Encryption feature.

    		 —
    구현(Implementation) / 아키텍처·설계(Architecture and Design) — 업계에서 승인된 기법을 쓸 때는 올바르게 쓰고, 자원이 많이 드는 단계를 건너뛰지 않는다(CWE-325). 이런 단계는 흔히 일반적인 공격을 막는 데 필수적이다. (구현 단계에도 해당)
    원문

    When using industry-approved techniques, use them correctly. Don't cut corners by skipping resource-intensive steps (CWE-325). These steps are often essential for preventing common attacks.

    		 —

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 임무 계획 파일(경로점 목록)을 암호화해 이동식 매체로 옮긴다. 경로점 기록은 같은 형식이 반복되는 고정 길이 레코드여서, 알고리즘이나 운용 모드가 약하면 키 없이도 내용의 패턴이나 평문이 드러난다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <openssl/evp.h>
#include <openssl/rand.h>

/* 임무 계획의 경로점 레코드(16바이트 고정 길이)를 3DES-ECB로 암호화한다 */
static int encrypt_plan(const unsigned char *key, const unsigned char *in, int n, unsigned char *out)
{
    int len = 0, tail = 0, ok = 0;
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    if (ctx != NULL && EVP_EncryptInit_ex(ctx, EVP_des_ede3_ecb(), NULL, key, NULL) == 1
        && EVP_EncryptUpdate(ctx, out, &len, in, n) == 1
        && EVP_EncryptFinal_ex(ctx, out + len, &tail) == 1) {
        ok = 1;
    }
    EVP_CIPHER_CTX_free(ctx);
    return ok ? len + tail : -1;
}

int main(void)
{
    unsigned char key[24];   /* 시험용 키: 실제로는 키 관리 체계에서 받는다 */
    if (RAND_bytes(key, sizeof key) != 1) {
        return 1;
    }
    /* 같은 체공 지시가 두 번 연속된 경로 */
    const char plan[] = "WP3 HOLD ALT1500WP3 HOLD ALT1500WP4 RTB         ";
    unsigned char ct[64];
    int n = encrypt_plan(key, (const unsigned char *)plan, 48, ct);
    if (n < 32) {
        return 1;
    }
    /* 관측자는 키 없이도 같은 레코드가 반복됐다는 사실을 암호문에서 읽는다 */
    puts(memcmp(ct, ct + 16, 16) == 0 ? "REPEATED CIPHERTEXT BLOCKS" : "no repetition visible");
    return 0;
}

    3DES를 ECB 모드로 쓴다. 3DES는 블록 크기가 64비트인 옛 알고리즘이고, ECB는 같은 평문 블록을 같은 암호문 블록으로 만들어 반복된 경로점이 암호문에서 그대로 보인다.

    좋은 예

    #include <stdio.h>
#include <string.h>
#include <openssl/evp.h>
#include <openssl/rand.h>

/* 승인 알고리즘·인증 암호 모드(AES-256-GCM): 무작위 IV, 태그로 변조 탐지 */
static int encrypt_plan(const unsigned char *key, const unsigned char *in, int n,
                        unsigned char iv[12], unsigned char tag[16], unsigned char *out)
{
    int len = 0, tail = 0, ok = 0;
    if (RAND_bytes(iv, 12) != 1) {
        return -1;
    }
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    if (ctx != NULL && EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, key, iv) == 1
        && EVP_EncryptUpdate(ctx, out, &len, in, n) == 1
        && EVP_EncryptFinal_ex(ctx, out + len, &tail) == 1
        && EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag) == 1) {
        ok = 1;
    }
    EVP_CIPHER_CTX_free(ctx);
    return ok ? len + tail : -1;
}

int main(void)
{
    unsigned char key[32];   /* 시험용 키: 실제로는 키 관리 체계에서 받는다 */
    if (RAND_bytes(key, sizeof key) != 1) {
        return 1;
    }
    const char plan[] = "WP3 HOLD ALT1500WP3 HOLD ALT1500WP4 RTB         ";
    unsigned char iv[12], tag[16], ct[64];
    int n = encrypt_plan(key, (const unsigned char *)plan, 48, iv, tag, ct);
    if (n < 32) {
        return 1;
    }
    puts(memcmp(ct, ct + 16, 16) == 0 ? "REPEATED CIPHERTEXT BLOCKS" : "no repetition visible");
    return 0;
}

    승인 알고리즘과 인증 암호 모드(AES-256-GCM)로 바꾸고 호출마다 무작위 IV(논스)를 쓴다. 같은 레코드도 다른 암호문이 되고, 태그로 변조를 탐지한다. 알고리즘은 직접 구현하지 않고 검증된 암호 모듈에서 고른다(D-03·D-05·OSS-04).

    C++

    나쁜 예

    #include <openssl/rand.h>
#include <array>
#include <cstdio>
#include <string>

// 자체 고안 '암호': 8바이트 키를 반복해 XOR 한다
static std::string scramble(const std::string &plain, const std::array<unsigned char, 8> &key) {
    std::string out = plain;
    for (std::size_t i = 0; i < out.size(); ++i) {
        out[i] = static_cast<char>(out[i] ^ key[i % key.size()]);
    }
    return out;
}

// 공격자: 파일 머리말이 늘 "MPLAN-V2"라는 것만 안다(알려진 평문)
static std::string known_header_attack(const std::string &cipher) {
    const std::string header = "MPLAN-V2";
    std::array<unsigned char, 8> guess{};
    for (std::size_t i = 0; i < guess.size() && i < cipher.size(); ++i) {
        guess[i] = static_cast<unsigned char>(cipher[i] ^ header[i]);
    }
    return scramble(cipher, guess);   // 추정한 키로 전체를 되돌린다
}

int main() {
    std::array<unsigned char, 8> key{};   // 시험용 키
    if (RAND_bytes(key.data(), static_cast<int>(key.size())) != 1) return 1;
    const std::string plan = "MPLAN-V2;MAINT=EXAMPLE-ONLY-BAY-52;ROUTE=WP1>WP2";
    const std::string recovered = known_header_attack(scramble(plan, key));
    std::puts(recovered.find("MAINT=EXAMPLE-ONLY-BAY-52") != std::string::npos ? "PLAINTEXT RECOVERED"
                                                                               : "attack failed");
    return 0;
}

    자체 고안한 반복 키 XOR를 '암호'로 쓴다. 파일 머리말처럼 늘 같은 평문 8바이트만 알아도 키가 나오고, 그 키로 임무 계획 전체를 되돌릴 수 있다.

    #include <openssl/evp.h>
#include <openssl/rand.h>

#include <cstdio>

#include <string>

using CtxPtr = std::unique_ptr<EVP_CIPHER_CTX, decltype(&EVP_CIPHER_CTX_free)>;

// 자체 고안 대신 검증된 라이브러리의 AES-256-GCM을 쓴다(IV 12바이트는 무작위)
static std::string seal(const std::string &plain, const std::array<unsigned char, 32> &key) {
    std::array<unsigned char, 12> iv{};
    std::string body(plain.size(), '\0');
    std::array<unsigned char, 16> tag{};
    CtxPtr ctx(EVP_CIPHER_CTX_new(), &EVP_CIPHER_CTX_free);
    int n = 0;
    if (RAND_bytes(iv.data(), static_cast<int>(iv.size())) != 1 || !ctx ||
        EVP_EncryptInit_ex(ctx.get(), EVP_aes_256_gcm(), nullptr, key.data(), iv.data()) != 1 ||
        EVP_EncryptUpdate(ctx.get(), reinterpret_cast<unsigned char *>(body.data()), &n,
                          reinterpret_cast<const unsigned char *>(plain.data()), static_cast<int>(plain.size())) != 1 ||
        EVP_EncryptFinal_ex(ctx.get(), reinterpret_cast<unsigned char *>(body.data()) + n, &n) != 1 ||
        EVP_CIPHER_CTX_ctrl(ctx.get(), EVP_CTRL_GCM_GET_TAG, 16, tag.data()) != 1) {
        throw std::runtime_error("encryption failed");
    }
    return std::string(iv.begin(), iv.end()) + body + std::string(tag.begin(), tag.end());
}

// 같은 공격: 머리말 "MPLAN-V2"를 안다고 보고 반복 XOR 키를 추정해 본다
static std::string known_header_attack(const std::string &cipher) {
    const std::string header = "MPLAN-V2";
    std::string out = cipher.substr(12);   // IV 뒤의 암호문
    std::array<unsigned char, 8> guess{};
    for (std::size_t i = 0; i < guess.size() && i < out.size(); ++i) {
        guess[i] = static_cast<unsigned char>(out[i] ^ header[i]);
    }
    for (std::size_t i = 0; i < out.size(); ++i) {
        out[i] = static_cast<char>(out[i] ^ guess[i % guess.size()]);
    }
    return out;
}

int main() {
    std::array<unsigned char, 32> key{};   // 시험용 키: 실제로는 키 관리 체계에서 받는다
    if (RAND_bytes(key.data(), static_cast<int>(key.size())) != 1) return 1;
    const std::string plan = "MPLAN-V2;MAINT=EXAMPLE-ONLY-BAY-52;ROUTE=WP1>WP2";
    const std::string recovered = known_header_attack(seal(plan, key));
    std::puts(recovered.find("MAINT=EXAMPLE-ONLY-BAY-52") != std::string::npos ? "PLAINTEXT RECOVERED"
                                                                               : "attack failed");
    return 0;
}

    자체 알고리즘 대신 검증된 라이브러리의 AES-256-GCM을 쓴다. 같은 알려진 평문 공격을 해도 키나 평문이 나오지 않는다(OSS-04).

    Example 2. Suppose a chip manufacturer decides to implement a hashing scheme for verifying integrity property of certain bitstream, and it chooses to implement a SHA1 hardware accelerator for to implement the scheme.

    Bad / Other

    The manufacturer chooses a SHA1 hardware accelerator for to implement the scheme because it already has a working SHA1 Intellectual Property (IP) that the manufacturer had created and used earlier, so this reuse of IP saves design cost.

    However, SHA1 was theoretically broken in 2005 and practically broken in 2017 at a cost of $110K. This means an attacker with access to cloud-rented computing power will now be able to provide a malicious bitstream with the same hash value, thereby defeating the purpose for which the hash was used.

    This issue could have been avoided with better design.

    Good / Other

    The manufacturer could have chosen a cryptographic solution that is recommended by the wide security community (including standard-setting bodies like NIST) and is not expected to be broken (or even better, weakened) within the reasonable life expectancy of the hardware product. In this case, the architects could have used SHA-2 or SHA-3, even if it meant that such choice would cost extra.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 분석 자동화 방법은 흔히 쓰이다가 낡은 것이 된 라이브러리나 기능을 식별하는 데 유용할 수 있다.
    원문

    Automated methods may be useful for recognizing commonly-used libraries or features that have become obsolete.

    		 보통(Moderate) — 도구가 사용 중인 암호 라이브러리를 인식하지 못하거나 자체 암호를 쓰는 경우 미탐(false negative)이 생길 수 있다.
    수동 분석 침투 시험(penetration test), 위협 모델링, 활성 세션을 기록·수정하는 대화형 도구처럼 사람이 직접 분석하는 도구·기법으로 이 약점을 탐지할 수 있다.
    원문

    This weakness can be detected using tools and techniques that require manual (human) analysis, such as penetration testing, threat modeling, and interactive tools that allow the tester to record and modify an active session.

    단계 지침
    요구사항 분석 —
    설계 승인 알고리즘 목록(국가정보원 KCMVP 검증대상 암호알고리즘 기준: ARIA, SEED, LEA, AES, SHA-256 이상 등)을 지정하고, 알고리즘 교체가 가능한 구조(암호 민첩성)로 설계한다.
    구현(C·C++) DES, 3DES, RC4, MD5, SHA-1, ECB 모드를 금지한다. 검증된 라이브러리의 인증 암호(GCM/CCM)를 쓰고 같은 키에 논스를 다시 쓰지 않는다. 직접 구현을 금지한다.
    구현(Java) Cipher.getInstance("AES/GCM/NoPadding")처럼 모드·패딩을 명시하고 기본값("AES"=ECB)에 의존하지 않는다.
    통합 및 시험 정적 분석의 취약 알고리즘 API 탐지, 바이너리 내 암호 상수(S-box) 탐지, 알고리즘 설정 검사를 수행한다.
    유지보수 암호 권고 변경(키 길이, 알고리즘 폐기)을 정기 검토하고 교체 계획을 수립한다.
    임베디드 고려 연산 자원이 부족한 MCU에서도 취약 알고리즘 대신 AES 하드웨어 가속기를 쓰거나, LEA 같은 경량 승인 알고리즘을 소프트웨어로 구현한 검증된 라이브러리를 선택한다(LEA를 하드웨어로 지원하는 부품이면 그것을 쓴다).
