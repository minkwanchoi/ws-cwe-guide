    Assignment of a Fixed Address to a Pointer

    항목 내용
    추상화 수준 변형(Variant)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++, C#, Assembly
    원문 MITRE CWE-587 (CWE 5.0)

    한 줄 요약

    포인터에 NULL이나 0이 아닌 특정 고정 주소를 설정하는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 포인터를 NULL이나 0이 아닌 특정 주소로 설정한다.

    원문(Description)

    The product sets a pointer to a specific address other than NULL or 0.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 허가되지 않은 코드·명령 실행 알려진 위치의 코드를 실행하면 공격자가 미리 그곳에 코드를 삽입할 수 있다.
    가용성 서비스 거부: 비정상 종료·재시작 / 유지보수성 저하 / 신뢰성 저하 코드를 다른 플랫폼이나 환경으로 이식하면 포인터가 유효하지 않아 비정상 종료를 일으킬 가능성이 높다.
    기밀성 / 무결성 메모리 읽기 / 메모리 수정 알려진 포인터 위치의 데이터는 공격자가 쉽게 읽거나 영향을 줄 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 1건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    원문 완화책 없음

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 포인터를 고정 주소로 절대 설정하지 않는다.
    원문

    Never set a pointer to a fixed address.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 관성 센서 초기화 때 플래시의 공장 보정 영역을 읽거나(C), 보드 식별 정보(OTP 영역)의 하드웨어 개정 번호로 구동 드라이버를 고른다(C++). C#은 탑재 컴퓨터에서 unsafe 코드로 같은 보정 영역을 읽는 경우다. 이 영역의 위치는 MCU와 보드 메모리 배치에 따라 달라진다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>

typedef struct {
    uint32_t magic;            /* 0xCA1B0001이면 유효 */
    int32_t gyro_bias[3];      /* 공장 보정값 */
} CalBlock;

/* 관성 센서 초기화: 플래시의 보정 영역을 읽는다 */
static int load_gyro_bias(int32_t out[3])
{
    /* 보드 A의 링커 배치를 보고 주소를 숫자로 적어 넣었다.
       보드·메모리 배치가 바뀌어도 이 숫자는 그대로 남는다 */
    const CalBlock *cal = (const CalBlock *)0x0807F000u;
    if (cal->magic != 0xCA1B0001u) {
        return -1;
    }
    for (int i = 0; i < 3; ++i) {
        out[i] = cal->gyro_bias[i];
    }
    return 0;
}

int main(void)
{
    int32_t bias[3];
    if (load_gyro_bias(bias) != 0) {
        puts("calibration block missing");
        return 1;
    }
    printf("bias %d %d %d\n", (int)bias[0], (int)bias[1], (int)bias[2]);
    return 0;
}

    보드 한 종류의 링커 배치를 보고 보정 영역 주소를 숫자로 응용 코드에 적어 넣는다. 보드 개정·메모리 배치가 바뀌면 다른 데이터를 보정값으로 읽거나 접근 오류로 멈추며, 호스트에서 돌리면 바로 비정상 종료한다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>

typedef struct {
    uint32_t magic;            /* 0xCA1B0001이면 유효 */
    int32_t gyro_bias[3];      /* 공장 보정값 */
} CalBlock;

/* BSP가 제공하는 보정 영역 객체. 실제 타깃에서는 링커 스크립트가 보드별
   보정 섹션에 배치하고 여기서는 선언만 둔다(호스트 시험에서는 아래 정의로 대신한다) */
extern const CalBlock bsp_cal_block;

/* 관성 센서 초기화: 플래시의 보정 영역을 읽는다 */
static int load_gyro_bias(int32_t out[3])
{
    const CalBlock *cal = &bsp_cal_block;   /* 주소는 링커가 정한다: 숫자 주소 없음 */
    if (cal->magic != 0xCA1B0001u) {
        return -1;
    }
    for (int i = 0; i < 3; ++i) {
        out[i] = cal->gyro_bias[i];
    }
    return 0;
}

/* 호스트 시험용 대역(타깃 빌드에서는 BSP 소스가 정의) */
const CalBlock bsp_cal_block = {0xCA1B0001u, {12, -7, 3}};

int main(void)
{
    int32_t bias[3];
    if (load_gyro_bias(bias) != 0) {
        puts("calibration block missing");
        return 1;
    }
    printf("bias %d %d %d\n", (int)bias[0], (int)bias[1], (int)bias[2]);
    return 0;
}

    보정 영역은 BSP가 제공하는 객체로 선언만 하고 실제 위치는 보드별 링커 스크립트가 정한다. 레지스터처럼 고정 주소가 불가피하면 벤더 헤더·HAL 한 곳에만 두고 편차로 기록한다(MCU-06·LC-03).

    검증: clang-tidy — 나쁜 예에서 clang-analyzer-optin.core.FixedAddressDereference 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-587 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdint>
#include <cstdio>

// 공장에서 기록한 보드 식별 정보(OTP 영역)
struct BoardInfo {
    std::uint32_t hw_rev;
    std::uint32_t serial;
};

// 하드웨어 개정 번호에 따라 구동 드라이버를 고른다
class DriverSelector {
public:
    bool use_new_imu() const {
        // 1차 시제 보드의 메모리 맵에서 옮겨 적은 주소. MCU·보드가 바뀌어도 그대로 남는다
        const auto *info = reinterpret_cast<const BoardInfo *>(0x1FFF7800u);
        return info->hw_rev >= 3u;
    }
};

int main() {
    DriverSelector sel;
    std::printf("new IMU driver: %s\n", sel.use_new_imu() ? "yes" : "no");
    return 0;
}

    reinterpret_cast로 숫자 주소를 구조체 포인터로 바꿔 응용 클래스 안에서 바로 읽는다. 같은 주소가 여러 곳에 흩어지면 보드가 바뀔 때 고칠 곳을 놓치기 쉽다.

    좋은 예

    #include <cstdint>
#include <cstdio>

// 공장에서 기록한 보드 식별 정보(OTP 영역)
struct BoardInfo {
    std::uint32_t hw_rev;
    std::uint32_t serial;
};

namespace bsp {
// 보드별 위치는 BSP(벤더 헤더·링커 스크립트) 한 곳에서만 정하고 응용 코드는 이 함수만 쓴다
const BoardInfo &board_info();
}  // namespace bsp

// 하드웨어 개정 번호에 따라 구동 드라이버를 고른다
class DriverSelector {
public:
    bool use_new_imu() const {
        return bsp::board_info().hw_rev >= 3u;   // 숫자 주소 없이 BSP가 준 객체로 읽는다
    }
};

// 호스트 시험용 대역. 타깃 빌드에서는 BSP 소스가 보드 메모리 맵에 맞춰 정의한다
const BoardInfo &bsp::board_info() {
    static const BoardInfo host_info{3u, 1042u};
    return host_info;
}

int main() {
    DriverSelector sel;
    std::printf("new IMU driver: %s\n", sel.use_new_imu() ? "yes" : "no");
    return 0;
}

    보드 정보는 bsp::board_info() 접근 함수 하나로만 얻고, 그 정의(주소 결정)는 보드별 BSP 소스에 둔다. reinterpret_cast는 HAL의 한정된 위치에만 허용한다(LCPP-05).

    검증: clang-tidy — 나쁜 예에서 clang-analyzer-optin.core.FixedAddressDereference 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-587 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    // 관성 센서 초기화: 탑재 컴퓨터의 공장 보정 영역을 unsafe 포인터로 읽는다
unsafe
{
    // 보드 A의 메모리 배치를 보고 주소를 숫자로 적어 넣었다.
    // 보드·메모리 배치가 바뀌어도 이 숫자는 그대로 남는다
    CalBlock* cal = (CalBlock*)0x0807F000;
    if (cal->Magic != 0xCA1B0001u)
    {
        Console.WriteLine("calibration block missing");
        return;
    }
    Console.WriteLine($"bias {cal->BiasX} {cal->BiasY} {cal->BiasZ}");
}

// 보정 영역의 배치: 확인값과 세 축의 공장 보정값
internal readonly record struct CalBlock(uint Magic, int BiasX, int BiasY, int BiasZ);

    unsafe 코드에서 숫자 주소를 구조체 포인터로 바꿔 보정 영역을 바로 읽는다. 보드·메모리 배치가 바뀌면 다른 데이터를 보정값으로 읽거나 접근 오류로 멈추며, 이 예시를 호스트에서 돌리면 AccessViolationException으로 프로세스가 비정상 종료된다.

    좋은 예

    // 관성 센서 초기화: 보정 영역은 보드 지원 계층이 넘겨준 값으로만 읽는다
CalBlock cal = BoardSupport.ReadCalibration();
if (cal.Magic != 0xCA1B0001u)
{
    Console.WriteLine("calibration block missing");
    return;
}
Console.WriteLine($"bias {cal.BiasX} {cal.BiasY} {cal.BiasZ}");

// 보드 지원 계층: 보정 영역의 위치는 이 한 곳에서만 다룬다.
// 실제 장비에서는 보드별 구성(장치 트리·설치 구성 파일)에서 받은 주소로 이곳에서만 매핑하고,
// 응용 코드에는 숫자 주소도 unsafe 포인터도 내주지 않는다.
internal static class BoardSupport
{
    // 호스트 시험용 대역: 정해진 보정 블록을 돌려준다
    public static CalBlock ReadCalibration() => new(0xCA1B0001u, 12, -7, 3);
}

// 보정 영역의 배치: 확인값과 세 축의 공장 보정값
internal readonly record struct CalBlock(uint Magic, int BiasX, int BiasY, int BiasZ);

    보정 영역의 위치는 보드 지원 계층(BoardSupport) 한 곳에서만 다루고, 응용 코드는 숫자 주소나 unsafe 포인터 없이 값만 받는다. 예시의 ReadCalibration은 호스트 시험용 대체 구현이며, 실제 장비에서는 보드별 구성에서 받은 주소로 그 한 곳에서만 매핑하고 unsafe 코드는 전용 어셈블리로 격리한다(LCS-02·MCU-06).

    검증: 실행 결과 — 나쁜 예에서 AccessViolationException 또는 calibration block missing 검출, 좋은 예에서 미검출·bias 12 -7 3 출력 확인 · 참고: MITRE CWE-587 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    Java — 예시 없음(언어상 생기지 않음): Java는 정수를 참조로 바꿀 수 없어 고정 주소를 참조에 넣을 수 없다. 장치 메모리 접근이 필요하면 JNI나 FFM(java.lang.foreign) 같은 네이티브 경계 한 곳에 모으고, JNI로 부르는 네이티브 코드에는 C 예시를 적용한다(LJ-08).

    Python — 예시 없음(언어상 생기지 않음): Python 문법에는 정수를 객체 참조로 바꾸는 방법이 없어 고정 주소를 참조에 넣을 수 없다. ctypes.cast(정수, POINTER(…))·from_address나 /dev/mem의 mmap으로 장치 주소를 직접 다루는 경우에는 C와 같은 문제가 생기므로 그 코드를 한 모듈에 모으고 C 예시와 C 지침을 적용한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 1건)

    Example 1. This code assumes a particular function will always be found at a particular address. It assigns a pointer to that address and calls the function.

    Bad / C

    int (*pt2Function) (float, char, char)=0x08040000;
int result2 = (*pt2Function) (12, 'a', 'b');

                     // Here we can inject code to execute.

    The same function may not always be found at the same memory address. This could lead to a crash, or an attacker may alter the memory at the expected address, leading to arbitrary code execution.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 —
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    (C·C++·C#) 정수 상수를 포인터로 바꾸는 캐스트((T*)0x…, reinterpret_cast, unsafe 코드의 숫자 주소)를 모두 찾고, 그 위치가 HAL·BSP 계층에 모여 있는지, 응용 계층에 흩어진 것은 없는지 확인한다. I-09 [표준] SEI CERT INT36-C · [예시] CWE-587 예시(응용 코드에 보정 영역 주소를 숫자로 기록)
    (C·C++·C#) 남은 고정 주소마다 링커 스크립트·메모리 맵·데이터시트의 주소와 대조하고, 편차(deviation)로 기록됐는지 확인한다. I-01·I-09 [보완]
    (C·C++·C#) 보드 개정이나 링커 배치를 바꾼 빌드에서 고정 주소로 읽는 값(보정 영역 등)이 맞는지 시험하고, 호스트 빌드에서는 그 접근이 접근 오류로 멈추는지 본다. T-02·I-10 [예시] CWE-587 C# 예시 검증(호스트 실행 시 AccessViolationException) · [CWE] CWE-587 탐지 방법(자동 동적 분석: ASan)
    (C·C++) 사업 정적 분석 도구가 이 항목을 지원하지 않으면 clang-tidy의 clang-analyzer-optin.core.FixedAddressDereference 검사를 켜서 고정 주소 역참조를 찾는다. I-09 [예시] CWE-587 C·C++ 예시 검증(clang-analyzer-optin.core.FixedAddressDereference)
    • ① 원문 탐지 방법(원문 효과성별): 보통: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: INT36-C

    단계 지침
    요구사항 분석 —
    설계 메모리 맵 레지스터 접근은 벤더 헤더(CMSIS 등)·HAL(하드웨어 추상화 계층)으로 한정하도록 설계한다.
    구현(C·C++) 일반 코드에서 정수 상수를 포인터로 변환하지 않는다. 하드웨어 레지스터 접근은 volatile 한정 매크로를 한 곳에 정의해 사용한다.
    구현(Java) 해당 없음.
    통합 및 시험 정적 분석(MISRA C 11.4/11.6 점검)으로 정수↔포인터 변환을 탐지한다.
    유지보수 하드웨어 개정·메모리 맵 변경 시 주소 정의 헤더를 일괄 갱신한다.
    임베디드 고려 원문 완화책은 포인터에 고정 주소를 넣지 말라고 하지만, 레지스터 접근은 임베디드에서 불가피하므로 이 가이드는 '금지'가 아니라 'HAL·BSP(보드 지원 패키지) 계층에 한정하고 편차(deviation)로 문서화'하는 방식으로 관리한다([보완]).

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 5건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
