    Detection of Error Condition Without Action

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    적용 플랫폼 언어 무관
    원문 MITRE CWE-390 (CWE 5.0)

    한 줄 요약

    특정 오류를 탐지하고도 그 오류를 처리하는 조치를 하지 않는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 특정 오류를 탐지하지만 그 오류를 처리하는 조치를 취하지 않는다.

    원문(Description)

    The product detects a specific error, but takes no actions to handle the error.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 실현(REALIZATION): 이 약점은 아키텍처 보안 전술을 구현하는 과정에서 생긴다.

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기타 상황에 따라 다름 / 예상하지 못한 상태 / 실행 논리 변경 공격자는 무시된 오류 상황을 이용해 시스템을 예상하지 못한 상태로 만들 수 있고, 이는 의도하지 않은 로직 실행과 그 밖의 의도하지 않은 동작으로 이어질 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 3건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: D-08 오류 처리·안전 상태 설계

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 각 예외를 올바르게 처리하는 것이 권장 해결책이며, 언제든 시스템 상태를 확신할 수 있도록 모든 예외를 처리한다.
    원문

    Properly handle each exception. This is the recommended solution. Ensure that all exceptions are handled in such a way that you can be sure of the state of your system at any given moment.
    구현(Implementation) — 함수가 오류를 반환하면 문제를 고치고 다시 시도하거나, 사용자에게 오류를 알리고 프로그램을 계속 실행하거나, 사용자에게 알리고 프로그램을 종료·정리하는 것이 중요하다.
    원문

    If a function returns an error, it is important to either fix the problem and try again, alert the user that an error has happened and let the program continue, or alert the user and close and cleanup the program.

    통합 및 시험 (본문 제6장)¶

    CWE 단계(Phase) 전략 요지
    시험(Testing) — 오류나 반환값이 처리되지 않는 지점과 방식의 일부를 찾도록 제품을 폭넓게 시험하며, 비정형(ad hoc) 시험, 동등 분할, 강건성·결함 허용, 변이, 퍼징(fuzzing) 같은 시험 기법을 고려한다.
    원문

    Subject the product to extensive testing to discover some of the possible instances of where/how errors or return values are not handled. Consider testing techniques such as ad hoc, equivalence partitioning, robustness and fault tolerance, mutation, and fuzzing.

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 비행 제어 보조 소프트웨어와 지상 통제 소프트웨어가 센서 읽기 실패, 데이터링크 메시지 필드 변환 실패, 정비 단말 설정값 오류를 감지한다. 실패를 감지해 놓고도 아무 처리를 하지 않으면 직전 값이나 쓰레기 값으로 제어와 표시가 계속된다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

/* 시험용 모의 I2C 드라이버: 세 번째 읽기에서 장치가 응답하지 않는다(NACK) */
static int i2c_read_angle(int sample, uint16_t *raw)
{
    static const uint16_t bus[] = {33768u, 32718u};
    if (sample >= 2) {
        *raw = 0xFFFFu;          /* 응답 없음: 버스가 high로 남아 0xFFFF를 읽는다 */
        return -5;
    }
    *raw = bus[sample];
    return 0;
}

int main(void)
{
    for (int s = 0; s < 3; ++s) {
        uint16_t raw = 0;
        int rc = i2c_read_angle(s, &raw);
        if (rc != 0) {
            /* 오류를 알아차렸지만 아무것도 하지 않는다 */
        }
        int cdeg = (int)raw - 32768;           /* 0.01도 단위 각도 */
        printf("actuator cmd %s%d.%02d deg\n", cdeg < 0 ? "-" : "", abs(cdeg) / 100, abs(cdeg) % 100);
    }
    return 0;
}

    I2C 읽기가 NACK(-5)를 돌려줘 오류를 알아차렸지만 if 블록이 비어 있다. 버스에서 읽힌 0xFFFF가 그대로 각도로 바뀌어 구동기에 327.67도 명령이 나간다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

static int i2c_read_angle(int sample, uint16_t *raw)
{
    static const uint16_t bus[] = {33768u, 32718u};
    if (sample >= 2) {
        *raw = 0xFFFFu;
        return -5;
    }
    *raw = bus[sample];
    return 0;
}

int main(void)
{
    int faults = 0;
    for (int s = 0; s < 3; ++s) {
        uint16_t raw = 0;
        int rc = i2c_read_angle(s, &raw);
        if (rc != 0) {
            ++faults;                          /* 고장 기록 */
            printf("sensor fault rc=%d: actuator held at neutral (faults=%d)\n", rc, faults);
            continue;                          /* 설계에서 정한 안전 상태로 */
        }
        int cdeg = (int)raw - 32768;
        printf("actuator cmd %s%d.%02d deg\n", cdeg < 0 ? "-" : "", abs(cdeg) / 100, abs(cdeg) % 100);
    }
    return 0;
}

    오류이면 고장 횟수를 기록하고 설계에서 정한 안전 상태(중립 유지)로 처리한 뒤 그 표본은 쓰지 않는다(MCU-02).

    검증: 실행 결과 — 나쁜 예에서 actuator cmd 327.67 검출, 좋은 예에서 미검출·actuator held at neutral 출력 확인 · 참고: MITRE CWE-390 Demonstrative Example 1(실패를 감지하고도 처리하지 않음) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 에러처리 4-2 '오류상황 대응 부재'(인쇄 156쪽) 참고

    C++

    나쁜 예

    #include <cstdio>
#include <stdexcept>
#include <string>

struct SensorMsg {
    int id = -1;
    int range_m = 0;
};

// 데이터링크 센서 정보 메시지의 문자 필드를 숫자로 바꾼다
SensorMsg decode(const std::string &id_field, const std::string &range_field) {
    SensorMsg m;
    try {
        m.id = std::stoi(id_field);
        m.range_m = std::stoi(range_field);
    } catch (const std::exception &) {
    }
    return m;    // 변환에 실패해도 반쯤 채운 메시지를 그대로 돌려준다
}

int main() {
    SensorMsg m = decode("17", "x42");
    std::printf("sensor %d range %d m\n", m.id, m.range_m);
    return 0;
}

    변환 예외를 빈 catch 블록으로 삼키고 반쯤 채운 메시지를 돌려준다. 거리 필드가 잘못돼도 '거리 0 m' 센서 값으로 처리된다.

    좋은 예

    #include <cstdio>
#include <optional>
#include <stdexcept>
#include <string>

struct SensorMsg {
    int id = -1;
    int range_m = 0;
};

// std::stoi는 "42x"를 42로 받으므로 소비한 길이까지 확인한다
int to_int(const std::string &field) {
    std::size_t used = 0;
    const int value = std::stoi(field, &used);
    if (used != field.size()) throw std::invalid_argument("trailing characters");
    return value;
}

std::optional<SensorMsg> decode(const std::string &id_field, const std::string &range_field) {
    try {
        SensorMsg m;
        m.id = to_int(id_field);
        m.range_m = to_int(range_field);
        return m;
    } catch (const std::invalid_argument &) {
        std::puts("sensor msg rejected: field is not a number");
    } catch (const std::out_of_range &) {
        std::puts("sensor msg rejected: field out of range");
    }
    return std::nullopt;   // 실패를 호출자에게 알린다
}

int main() {
    if (auto m = decode("17", "x42")) {
        std::printf("sensor %d range %d m\n", m->id, m->range_m);
    } else {
        std::puts("keep previous sensor picture");
    }
    return 0;
}

    예외 형식별로 잡아 거부 사유를 남기고 std::optional로 실패를 호출자에게 알린다. 호출자는 직전 센서 화면을 유지한다.

    검증: clang-tidy — 나쁜 예에서 bugprone-empty-catch 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-390 Demonstrative Example 2(처리 없는 catch 블록) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    using System.Globalization;

// 정비 단말에서 받은 서보 이득 설정값을 읽는다
int ReadGain(string text)
{
    int gain = 0;
    try
    {
        gain = int.Parse(text, CultureInfo.InvariantCulture);
    }
    catch (Exception)
    {
        // 어떤 예외든 받아서 버린다
    }
    return gain;
}

Console.WriteLine($"servo gain set to {ReadGain("4O")}");

    catch (Exception)으로 모든 예외를 받아 버리고 이득 0을 적용한다. 일반 예외 형식을 잡는 코드는 CA1031로 경고된다.

    좋은 예

    using System.Globalization;

bool TryReadGain(string text, out int gain)
{
    // 예외 대신 성공 여부를 돌려받고, 범위도 함께 확인한다
    return int.TryParse(text, NumberStyles.Integer, CultureInfo.InvariantCulture, out gain)
           && gain is >= 1 and <= 1000;
}

void ApplyGain(string text)
{
    if (TryReadGain(text, out int g))
    {
        Console.WriteLine($"servo gain set to {g}");
    }
    else
    {
        Console.WriteLine($"servo gain '{text}' rejected: keep current value and report to operator");
    }
}

ApplyGain("4O");

    예외에 기대지 않고 TryParse로 성공 여부와 범위를 확인해, 실패하면 현재 값을 유지하고 운용자에게 알린다(LCS-08).

    검증: .NET 컴파일러·분석기 — 나쁜 예에서 CA1031 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-390 Demonstrative Example 3(처리 없는 catch 블록) 참고, 이 가이드가 새로 작성

    Java

    나쁜 예

    public class Example {
    // 임무 계획 경로점의 고도 필드(ft)를 읽는다
    static int altitudeFeet(String field) {
        int alt = 0;
        try {
            alt = Integer.parseInt(field.trim());
        } catch (NumberFormatException e) {
            // 변환 실패를 알지만 아무 처리도 하지 않는다
        }
        return alt;
    }

    public static void main(String[] args) {
        String[] fields = {"12000", "1Z000"};
        for (String f : fields) {
            System.out.println("waypoint alt=" + altitudeFeet(f) + " ft");
        }
    }
}

    NumberFormatException을 잡고 아무것도 하지 않아 초깃값 0이 고도로 돌아간다. 잘못된 필드가 '고도 0 ft' 경로점으로 바뀐다.

    좋은 예

    import java.util.OptionalInt;

public class Example {
    static OptionalInt altitudeFeet(String field) {
        try {
            return OptionalInt.of(Integer.parseInt(field.trim()));
        } catch (NumberFormatException e) {
            System.out.println("altitude field rejected: " + e.getClass().getSimpleName());
            return OptionalInt.empty();          // 실패를 호출자에게 알린다
        }
    }

    public static void main(String[] args) {
        String[] fields = {"12000", "1Z000"};
        for (String f : fields) {
            OptionalInt alt = altitudeFeet(f);
            if (alt.isPresent()) {
                System.out.println("waypoint alt=" + alt.getAsInt() + " ft");
            } else {
                System.out.println("waypoint held: plan needs operator review");
            }
        }
    }
}

    실패를 OptionalInt.empty()로 돌려주고 호출자가 경로점을 보류해 운용자 검토로 넘긴다. 빈 catch 블록을 쓰지 않는다(LJ-05).

    검증: 실행 결과 — 나쁜 예에서 alt=0 ft 검출, 좋은 예에서 미검출·altitude field rejected 출력 확인 · 참고: MITRE CWE-390 Demonstrative Example 3(처리 없는 catch 블록) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「Java 시큐어코딩 가이드」(3판) 에러처리 4-2 '오류 상황 대응 부재'(인쇄 231쪽) 참고

    Python

    나쁜 예

    altitude_ft = 0                         # 마지막으로 읽은 기압 고도


# 센서 보조 소프트웨어: 기압 고도 문자열을 읽어 고도 값을 갱신한다
def update_altitude(raw):
    global altitude_ft
    try:
        altitude_ft = int(raw)
    except Exception:
        pass                            # 실패를 알아차리고도 아무것도 하지 않는다


update_altitude("ERR:SENSOR")           # 센서 고장 문자열
print(f"alt={altitude_ft} ft (valid?)")  # 초깃값 0이 정상 고도처럼 쓰인다

    숫자 변환 실패를 except Exception: pass로 삼킨다. 오류는 감지했지만 아무 조치가 없어 초깃값 0이 정상 고도처럼 쓰인다. Bandit은 이 꼴을 B110(try/except/pass)으로 보고한다(기본 설정에서는 except Exception·맨 except만 본다).

    좋은 예

    import logging

logging.basicConfig(level=logging.WARNING, format="%(levelname)s %(message)s")
log = logging.getLogger("sensor.baro")
altitude_ft = None
altitude_valid = False


def update_altitude(raw):
    global altitude_ft, altitude_valid
    try:
        altitude_ft, altitude_valid = int(raw), True
    except ValueError:
        # 실패를 기록하고 값을 '무효'로 표시해 쓰는 쪽이 대체 수단(GPS 고도 등)으로 넘어가게 한다
        altitude_valid = False
        log.warning("baro altitude invalid: %r", raw)


update_altitude("ERR:SENSOR")
print(f"alt={altitude_ft} ft valid={altitude_valid}")

    실패하면 기록을 남기고 값을 '무효'로 표시해, 쓰는 쪽이 대체 수단으로 넘어가거나 안전 상태로 가게 한다(I-06, LPY-08). 실패를 어디서 어떻게 처리할지는 설계 단계의 오류 처리 규약에서 정한다(D-08). 예외를 잡으면 잡은 자리에서 기록·상태 표시·다시 던지기 중 하나를 한다. 잡을 예외도 ValueError처럼 구체적으로 적는다.

    검증: Bandit — 나쁜 예에서 B110 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-390 Demonstrative Example 3(예외를 잡고 아무것도 하지 않음) 참고, 이 가이드가 새로 작성 / 과학기술정보통신부·한국인터넷진흥원 「Python 시큐어코딩 가이드」(2023. 12.) 에러처리 4-2 '오류상황 대응 부재'(인쇄 130쪽) 참고

    MITRE 원문 예시(Demonstrative Examples, 영문 3건)

    Example 1. The following example attempts to allocate memory for a character. After the call to malloc, an if statement is used to check whether the malloc function failed.

    Bad / C

    foo=malloc(sizeof(char)); //the next line checks to see if malloc failed
if (foo==NULL) {
  //We do nothing so we just ignore the error.
}

    The conditional successfully detects a NULL return value from malloc indicating a failure, however it does not do anything to handle the problem. Unhandled errors may have unexpected results and may cause the program to crash or terminate.

    Instead, the if block should contain statements that either attempt to fix the problem or notify the user that an error has occurred and continue processing or perform some cleanup and gracefully terminate the program. The following example notifies the user that the malloc function did not allocate the required memory resources and returns an error code.

    Good / C

    foo=malloc(sizeof(char)); //the next line checks to see if malloc failed
if (foo==NULL) {
  printf("Malloc failed to allocate memory resources");
  return -1;
}

    Example 2. In the following C++ example the method readFile() will read the file whose name is provided in the input parameter and will return the contents of the file in char string. The method calls open() and read() may result in errors if the file does not exist or does not contain any data to read. These errors will be thrown when the is_open() method and good() method indicate errors opening or reading the file. However, these errors are not handled within the catch statement. Catch statements that do not perform any processing will have unexpected results. In this case an empty char string will be returned, and the file will not be properly closed.

    Bad / C++

    char* readfile (char *filename) {

  try {

    // open input file
    ifstream infile;
    infile.open(filename);

    if (!infile.is_open()) {
      throw "Unable to open file " + filename;
    }

    // get length of file
    infile.seekg (0, ios::end);
    int length = infile.tellg();
    infile.seekg (0, ios::beg);

    // allocate memory
    char *buffer = new char [length];

    // read data from file
    infile.read (buffer,length);

    if (!infile.good()) {
      throw "Unable to read from file " + filename;
    }

    infile.close();

    return buffer;

  }
  catch (...) {
    /* bug: insert code to handle this later */
  }

}

    The catch statement should contain statements that either attempt to fix the problem or notify the user that an error has occurred and continue processing or perform some cleanup and gracefully terminate the program. The following C++ example contains two catch statements. The first of these will catch a specific error thrown within the try block, and the second catch statement will catch all other errors from within the catch block. Both catch statements will notify the user that an error has occurred, close the file, and rethrow to the block that called the readFile() method for further handling or possible termination of the program.

    Good / C++

    char* readFile (char *filename) {

  try {

    // open input file
    ifstream infile;
    infile.open(filename);

    if (!infile.is_open()) {
      throw "Unable to open file " + filename;
    }

    // get length of file
    infile.seekg (0, ios::end);
    int length = infile.tellg();
    infile.seekg (0, ios::beg);

    // allocate memory
    char *buffer = new char [length];

    // read data from file
    infile.read (buffer,length);

    if (!infile.good()) {
      throw "Unable to read from file " + filename;
    }
    infile.close();

    return buffer;

  }
  catch (char *str) {
    printf("Error: %s \n", str);
    infile.close();
    throw str;
  }
  catch (...) {
    printf("Error occurred trying to read from file \n");
    infile.close();
    throw;
  }

}

    Example 3. In the following Java example the method readFile will read the file whose name is provided in the input parameter and will return the contents of the file in a String object. The constructor of the FileReader object and the read method call may throw exceptions and therefore must be within a try/catch block. While the catch statement in this example will catch thrown exceptions in order for the method to compile, no processing is performed to handle the thrown exceptions. Catch statements that do not perform any processing will have unexpected results. In this case, this will result in the return of a null String.

    Bad / Java

    public String readFile(String filename) {

  String retString = null;
  try {

    // initialize File and FileReader objects
    File file = new File(filename);
    FileReader fr = new FileReader(file);

    // initialize character buffer
    long fLen = file.length();
    char[] cBuf = new char[(int) fLen];

    // read data from file
    int iRead = fr.read(cBuf, 0, (int) fLen);

    // close file
    fr.close();

    retString = new String(cBuf);

  } catch (Exception ex) {
    /* do nothing, but catch so it'll compile... */
  }
  return retString;

}

    The catch statement should contain statements that either attempt to fix the problem, notify the user that an exception has been raised and continue processing, or perform some cleanup and gracefully terminate the program. The following Java example contains three catch statements. The first of these will catch the FileNotFoundException that may be thrown by the FileReader constructor called within the try/catch block. The second catch statement will catch the IOException that may be thrown by the read method called within the try/catch block. The third catch statement will catch all other exceptions thrown within the try block. For all catch statements the user is notified that the exception has been thrown and the exception is rethrown to the block that called the readFile() method for further processing or possible termination of the program. Note that with Java it is usually good practice to use the getMessage() method of the exception class to provide more information to the user about the exception raised.

    Good / Java

    public String readFile(String filename) throws FileNotFoundException, IOException, Exception {

  String retString = null;
  try {

    // initialize File and FileReader objects
    File file = new File(filename);
    FileReader fr = new FileReader(file);

    // initialize character buffer
    long fLen = file.length();
    char [] cBuf = new char[(int) fLen];

    // read data from file
    int iRead = fr.read(cBuf, 0, (int) fLen);

    // close file
    fr.close();

    retString = new String(cBuf);

  } catch (FileNotFoundException ex) {
    System.err.println ("Error: FileNotFoundException opening the input file: " + filename );
    System.err.println ("" + ex.getMessage() );
    throw new FileNotFoundException(ex.getMessage());
  } catch (IOException ex) {
    System.err.println("Error: IOException reading the input file.\n" + ex.getMessage() );
    throw new IOException(ex);
  } catch (Exception ex) {
    System.err.println("Error: Exception reading the input file.\n" + ex.getMessage() );
    throw new Exception(ex);
  }
  return retString;

}

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    오류를 검사하는 if 블록과 catch 블록 가운데 본문이 비었거나 기록만 하고 계속 진행하는 곳을 찾고, 그 뒤에 오류 값(0xFFFF, 초깃값 0)이 정상 값처럼 쓰이는지 따라간다. I-09·I-06 [예시] CWE-390 예시(빈 오류 블록 뒤 진행) · [표준] SEI CERT ERR00-J
    I2C NACK, ADC 시간 초과, 변환 예외 같은 오류를 주입해 출력(구동기 명령, 거리 측정값, 고도)이 안전 상태 값으로 바뀌는지, 오류 값이 그대로 나가는지 확인한다. T-05 [예시] CWE-390 예시 검증(오류 뒤 출력값 확인) · [CWE] CWE-390 완화책(Testing: 미처리 오류·반환값 시험)
    (C++·C#) 사업 정적 분석 도구가 이 항목을 지원하지 않으면 C++는 clang-tidy bugprone-empty-catch, C#은 CA1031 경고를 켜서 빈 catch와 일반 예외 포착을 찾는다. I-08·I-09 [예시] CWE-390 C++·C# 예시 검증(bugprone-empty-catch, CA1031)
    설계 산출물의 오류 처리 규약에 오류마다 대응(재시도, 보고, 안전 상태 전환)이 정해져 있는지 확인한다. D-09·D-08 [CWE] CWE-390 완화책(Implementation: 오류 반환 시 복구·알림·종료 중 하나)
    • ① 원문 탐지 방법은 자동 정적 분석뿐이다. 다른 정적 분석 도구·컴파일러 경고로 점검한다.
