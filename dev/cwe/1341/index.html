    Multiple Releases of Same Resource or Handle

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 언어 뷰 C·C++·Java(CWE-658·659·660)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, Java, Rust, C, C++ · 운영체제 무관 · 아키텍처 무관 · 기술 무관
    원문 MITRE CWE-1341 (CWE 5.0)

    한 줄 요약

    닫기 작업 사이에 성공한 열기 없이 자원이나 핸들을 두 번 이상 닫거나 해제하려는 약점이다.

    설명(Description)¶

    제품이 닫기 작업 사이에 성공한 열기 없이 자원이나 핸들을 두 번 이상 닫거나 해제하려는 약점이다. 자원 예약 할당 구현은 대부분(어쩌면 전부) 고유 식별자·포인터·기호 참조를 쓰는데, 이 식별자가 재사용되면 자원 닫힘 여부를 확인할 때 열린 상태로 잘못 판단해 엉뚱한 자원을 닫을 수 있으므로 식별자 재사용은 권장되지 않는다.

    배경(Background Details)

    코드는 대개 메모리, 파일, 장치, 소켓 연결, 서비스 같은 자원의 핸들이나 참조를 '열어야' 한다. 자원 사용이 끝나면 대개 그 자원을 '닫거나' '해제'해 운영체제 같은 환경에 그 자원을 관련 없는 프로세스나 행위자가(일부 경우에는 같은 프로세스 안에서) 다시 할당하거나 재사용할 수 있음을 알린다. 이 해제에는 흔히 C/C++의 free()나 delete(), 여러 언어에서 쓰는 파일 핸들 close() 같은 API 함수나 기타 추상화가 쓰인다.

    원문(Description · Extended Description · Background Details)

    The product attempts to close or release a resource or handle more than once, without any successful open between the close operations.

    Note that while the implementation for most (if not all) resource reservation allocations involve a unique identifier/pointer/symbolic reference, then if this identifier is reused, checking the identifier for resource closure may result in a false state of openness and closing of the wrong resource. For this reason, reuse of identifiers is discouraged.

    Code typically requires "opening" handles or references to resources such as memory, files, devices, socket connections, services, etc. When the code is finished with using the resource, it is typically expected to "close" or "release" the resource, which indicates to the environment (such as the OS) that the resource can be re-assigned or reused by unrelated processes or actors - or in some cases, within the same process. API functions or other abstractions are often used to perform this release, such as free() or delete() within C/C++, or file-handle close() operations that are used in many languages.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 자원 관리 API의 구현이나 설계는 자원 해제 한 번에 API를 한 번만 호출하도록 할 책임을 개발자에게 지울 수 있다. 개발자가 같은 자원·핸들을 두 번 이상 해제하려 하면 API의 기대가 충족되지 않는다.

    영향(Common Consequences)¶

    영역 영향 가능성 설명
    가용성 / 무결성 서비스 거부: 비정상 종료·재시작 중간 —
    무결성 메모리 수정 / 애플리케이션 데이터 수정 — 자원의 종류와 API의 기대 동작에 따라 메모리 손상, 데이터 손상, 실행 경로 손상으로 이어질 수 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 자원을 한 번만 닫도록 코드 논리를 바꾸며, 이를 위해 단순화나 리팩터링이 필요할 수 있다. 작은 코드 블록에서는 간단할 수 있지만 복잡한 조건문 안에 여러 닫기가 묻혀 있으면 더 어렵다.
    원문

    Change the code's logic so that the resource is only closed once. This might require simplifying or refactoring. This fix can be simple to do in small code blocks, but more difficult when multiple closes are buried within complex conditionals.

    		 —
    구현(Implementation) 리팩터링 (1) 자원을 열 때 설정하고 (2) 닫을 때 해제하며 (3) 닫기 전에 확인하는 플래그를 구현하는 것이 효과적일 수 있으며, 닫기를 수행해야 하는 경우가 서로 흩어져 있을 때 유용할 수 있다. 단, 플래그 추적은 코드 복잡도를 높일 수 있고 프로그래머의 철저한 준수가 필요하다.
    원문

    It can be effective to implement a flag that is (1) set when the resource is opened, (2) cleared when it is closed, and (3) checked before closing. This approach can be useful when there are disparate cases in which closes must be performed. However, flag-tracking can increase code complexity and requires diligent compliance by the programmer.

    		 —
    구현(Implementation) 리팩터링 자원을 닫을 때 그 자원과 연관된 변수를 NULL이나 해당 언어의 동등한 값으로 설정한다. 일부 API는 이 null 값을 오류를 일으키지 않고 무시하지만, 다른 API에서는 애플리케이션 비정상 종료나 예외가 날 수 있으며, 그래도 메모리·데이터 같은 의도하지 않은 자원을 손상시키는 것보다는 나을 수 있다.
    원문

    When closing a resource, set the resource's associated variable to NULL or equivalent value for the given language. Some APIs will ignore this null value without causing errors. For other APIs, this can lead to application crashes or exceptions, which may still be preferable to corrupting an unintended resource such as memory or data.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. This example attempts to close a file twice. In some cases, the C library fclose() function will catch the error and return an error code. In other implementations, a double-free (CWE-415) occurs, causing the program to fault. Note that the examples presented here are simplistic, and double fclose() calls will frequently be spread around a program, making them more difficult to find during code reviews.

    Bad / C

    char b[2000];

FILE *f = fopen("dbl_cls.c", "r");

if (f)

{

  b[0] = 0;

    fread(b, 1, sizeof(b) - 1, f);

    printf("%s\n'", b);

    int r1 = fclose(f);

    printf("\n-----------------\n1 close done '%d'\n", r1);

    int r2 = fclose(f); // Double close

    printf("2 close done '%d'\n", r2);

}

    There are multiple possible fixes. This fix only has one call to fclose(), which is typically the preferred handling of this problem - but this simplistic method is not always possible.

    Good / C

    char b[2000];

FILE *f = fopen("dbl_cls.c", "r");

if (f)

{

  b[0] = 0;

    fread(b, 1, sizeof(b) - 1, f);

    printf("%s\n'", b);

    int r = fclose(f);

    printf("\n-----------------\n1 close done '%d'\n", r);

}

    This fix uses a flag to call fclose() only once. Note that this flag is explicit. The variable "f" could also have been used as it will be either NULL if the file is not able to be opened or a valid pointer if the file was successfully opened. If "f" is replacing "f_flg" then "f" would need to be set to NULL after the first fclose() call so the second fclose call would never be executed.

    Good / C

    char b[2000];

int f_flg = 0;

FILE *f = fopen("dbl_cls.c", "r");

if (f)

{

  f_flg = 1;

    b[0] = 0;

    fread(b, 1, sizeof(b) - 1, f);

    printf("%s\n'", b);

    if (f_flg)

    {

    int r1 = fclose(f);

            f_flg = 0;

            printf("\n-----------------\n1 close done '%d'\n", r1);

    }

    if (f_flg)

    {

    int r2 = fclose(f); // Double close

            f_flg = 0;

            printf("2 close done '%d'\n", r2);

    }

}

    Example 2. The following code shows a simple example of a double free vulnerability.

    Bad / C

    char* ptr = (char*)malloc (SIZE);
...
if (abrt) {
  free(ptr);
}
...
free(ptr);

    Double free vulnerabilities have two common (and sometimes overlapping) causes:

    Error conditions and other exceptional circumstances Confusion over which part of the program is responsible for freeing the memory

    Although some double free vulnerabilities are not much more complicated than this example, most are spread out across hundreds of lines of code or even different files. Programmers seem particularly susceptible to freeing global variables more than once.

    탐지 방법(Detection Methods)¶

    방법 요지
    자동 정적 분석 흔히 쓰는 API와 자원 유형에 대해서는 자동화 도구가 이 문제를 찾아내는 시그니처를 갖춘 경우가 많다.
    원문

    For commonly-used APIs and resource types, automated tools often have signatures that can spot this issue.
    자동 동적 분석 AddressSanitizer(ASan) 같은 일부 컴파일러 계측 도구는 이 약점의 일부 사례를 간접적으로 탐지할 수 있다.
    원문

    Some compiler instrumentation tools such as AddressSanitizer (ASan) can indirectly detect some instances of this weakness.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법(원문 효과성별): 효과 등급 없음: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.

    언어 뷰 항목의 단계별 지침 (적용성 판정 기준은 부록 B, 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 자원 해제 책임을 한 곳으로 정하고 정리 경로를 단일 종료점(goto cleanup)으로 설계한다.
    구현 자원 해제 책임을 한 곳에 두어 한 번만 해제하고(C++은 RAII, Java는 try-with-resources), 해제 상태 플래그를 확인한 뒤에만 해제한다. 해제 후 핸들을 NULL/-1로 설정하는 것은 심층 방어로 더한다.
    통합 및 시험 정적 분석 도구(예: Coverity(DOUBLE_CLOSE, DOUBLE_FREE)), AddressSanitizer, 오류 경로 포함 단위시험으로 검출한다.
    유지보수 자원 해제 로직 변경 시 모든 종료 경로를 재점검하고 결함 패턴을 정적 분석 규칙에 반영한다.
    임베디드 고려 RTOS 객체(세마포어, 큐 핸들)와 주변장치 핸들의 이중 삭제는 커널 손상을 유발하므로 삭제 후 핸들을 무효화한다.

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.
