    Improper Resource Shutdown or Release

    적용 플랫폼 언어: 언어 무관, Python
    원문 MITRE CWE-404 (CWE 5.0)

    한 줄 요약

    자원을 재사용할 수 있게 하기 전에 해제하지 않거나 잘못 해제해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 자원을 재사용할 수 있게 하기 전에 해제하지 않거나 잘못 해제하는 약점이다. 자원을 생성하거나 할당하면 개발자는 그 자원을 올바르게 해제할 책임이 있고, 일정 시간 경과나 회수(revocation)처럼 자원이 만료되거나 무효화되는 모든 경로도 고려해야 한다.

    원문(Description · Extended Description · Dimensions)

    The product does not release or incorrectly releases a resource before it is made available for re-use.

    When a resource is created or allocated, the developer is responsible for properly releasing the resource as well as accounting for all potential paths of expiration or invalidation, such as a set period of time or revocation.

    Dimensions: Behavior-Type = Release; Behavior-Type = Shutdown; Behavior-Property = Improper; Resource-Type = Resource

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    가용성 / 기타 서비스 거부: 자원 소모(기타) / 상황에 따라 다름 해제되지 않은 자원 문제는 대부분 일반적인 소프트웨어 신뢰성 문제로 이어지지만, 공격자가 자원 누수를 일부러 일으킬 수 있으면 자원 풀을 고갈시켜 서비스 거부 공격을 할 수 있다.
    기밀성 애플리케이션 데이터 읽기 민감한 정보가 담긴 자원을 올바르게 종료하지 않으면 이후 할당에서 그 민감한 데이터가 노출될 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 4건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    CWE 단계(Phase) 전략 요지
    요구사항(Requirements) 언어 선택 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 언어를 쓴다. 예를 들어 Java, Ruby, Lisp 같은 언어는 자동 가비지 컬렉션으로 할당 해제된 객체의 메모리를 해제한다.
    원문

    Use a language that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, languages such as Java, Ruby, and Lisp perform automatic garbage collection that releases memory for objects that have been deallocated.

    설계 (본문 제4장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: D-07 자원 예산·정적 할당 설계

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 할당한 자원은 모두 스스로 해제하고, 함수 안에서 메모리를 해제하는 방식과 위치를 일관되게 하는 것이 좋다. 함수가 끝날 때 해제하려는 메모리는 오류 조건을 포함한 함수의 모든 종료 지점에서 반드시 해제해야 한다.
    원문

    It is good practice to be responsible for freeing all resources you allocate and to be consistent with how and where you free memory in a function. If you allocate memory that you intend to free upon completion of the function, you must be sure to free the memory at all exit points for that function including error conditions.
    구현(Implementation) — 메모리는 malloc/free, new/delete, new[]/delete[]처럼 짝이 맞는 함수로 할당·해제해야 한다.
    원문

    Memory should be allocated/freed using matching functions such as malloc/free, new/delete, and new[]/delete[].
    구현(Implementation) — 복잡한 객체나 구조체를 해제할 때는 객체 자체만이 아니라 모든 구성 요소를 올바르게 해제한다.
    원문

    When releasing a complex object or structure, ensure that you properly dispose of all of its member components, not just the object itself.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-07 타깃 자원·장시간 시험

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 펌웨어 업데이트 블록 검사, 정비 기록·세션 기록 파일 쓰기, 데이터 기록기 채널 사용처럼 메모리·파일 핸들·장치 핸들을 얻어 쓰고 돌려줘야 하는 작업에서, 오류나 예외로 빠져나가는 경로가 해제를 건너뛴다. 장시간 연속 운용 장비에서는 조금씩 새는 자원이 쌓여 결국 할당 실패나 핸들 고갈로 이어진다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* 펌웨어 업데이트 블록: 복사본을 만들어 검사한 뒤 플래시에 쓴다 */
static uint8_t sum8(const uint8_t *p, size_t n)
{
    uint8_t s = 0;
    while (n--) s = (uint8_t)(s + *p++);
    return s;
}

static int stage_block(const uint8_t *data, size_t len, uint8_t expected)
{
    uint8_t *copy = malloc(len);
    if (copy == NULL) return -1;
    memcpy(copy, data, len);
    if (sum8(copy, len) != expected) {
        puts("block rejected: checksum mismatch");
        return -1;                     /* 오류 경로에서 copy를 해제하지 않는다 */
    }
    puts("block staged");
    free(copy);
    return 0;
}

int main(void)
{
    uint8_t block[512];
    memset(block, 0x5A, sizeof block);
    stage_block(block, sizeof block, sum8(block, sizeof block));
    stage_block(block, sizeof block, (uint8_t)(sum8(block, sizeof block) + 1));  /* 체크섬이 어긋난 블록 */
    return 0;
}

    체크섬이 틀린 블록에서 일찍 return하면서 malloc한 복사본을 해제하지 않는다. 전송 오류가 날 때마다 메모리가 새어 장시간 운용 후 업데이트 기능이 할당 실패로 멈춘다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static uint8_t sum8(const uint8_t *p, size_t n)
{
    uint8_t s = 0;
    while (n--) s = (uint8_t)(s + *p++);
    return s;
}

/* 출구를 하나로 모아 모든 경로에서 해제한다 */
static int stage_block(const uint8_t *data, size_t len, uint8_t expected)
{
    int rc = -1;
    uint8_t *copy = malloc(len);
    if (copy == NULL) goto out;
    memcpy(copy, data, len);
    if (sum8(copy, len) != expected) {
        puts("block rejected: checksum mismatch");
        goto out;
    }
    puts("block staged");
    rc = 0;
out:
    free(copy);                        /* NULL이어도 안전하다 */
    return rc;
}

int main(void)
{
    uint8_t block[512];
    memset(block, 0x5A, sizeof block);
    stage_block(block, sizeof block, sum8(block, sizeof block));
    stage_block(block, sizeof block, (uint8_t)(sum8(block, sizeof block) + 1));
    return 0;
}

    출구를 하나(out 레이블)로 모아 정상·오류 모든 경로에서 free를 호출한다. 장기 운용 장비라면 초기화 이후 동적 할당을 하지 않고 정적 풀을 쓰는 것이 더 낫다.

    검증: AddressSanitizer(clang) · Linux(gcc)에서 빌드 — 나쁜 예에서 detected memory leaks 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-404 Demonstrative Example 4(오류 경로에서 연 파일 핸들을 닫지 않음) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 코드오류 5-2 '부적절한 자원 해제'(인쇄 165쪽) 참고

    C++

    나쁜 예

    #include <cstdio>
#include <string>

// 정비 기록 파일에 고장 코드를 덧붙인다(C 방식 FILE* 를 직접 다룸)
bool append_fault(const char *path, int code) {
    std::FILE *log = std::fopen(path, "a");
    if (log == nullptr) {
        return false;
    }
    if (code < 0) {
        return false;                      // 잘못된 코드: 파일을 닫지 않고 나간다
    }
    std::fprintf(log, "FAULT %04d\n", code);
    std::fclose(log);
    return true;
}

int main() {
    const std::string path = "maint_log.txt";   // 현재 폴더에만 쓴다
    std::printf("%d %d\n", append_fault(path.c_str(), 17), append_fault(path.c_str(), -1));
    return 0;
}

    C 방식 FILE*을 직접 다루면서, 입력 오류로 일찍 return하는 경로에서 fclose를 하지 않아 파일 핸들이 샌다.

    좋은 예

    #include <cstdio>
#include <fstream>
#include <iomanip>
#include <string>

// 파일 수명을 객체에 맡긴다(RAII): 어느 경로로 나가도 소멸자가 닫는다
bool append_fault(const std::string &path, int code) {
    if (code < 0) {
        return false;                      // 열기 전에 입력부터 검사
    }
    std::ofstream log(path, std::ios::app);
    if (!log) {
        return false;
    }
    log << "FAULT " << std::setw(4) << std::setfill('0') << code << '\n';
    log.close();                           // 버퍼를 비운 뒤의 상태로 성공을 판정한다
    return !log.fail();
}

int main() {
    const std::string path = "maint_log.txt";
    std::printf("%d %d\n", append_fault(path, 17), append_fault(path, -1));
    return 0;
}

    std::ofstream에 파일 수명을 맡겨(RAII) 어느 경로로 나가도 소멸자가 닫게 하고, 입력 검사는 파일을 열기 전에 한다. FILE*을 꼭 써야 하면 fclose를 삭제자로 둔 std::unique_ptr로 감싼다.

    검증: cppcheck — 나쁜 예에서 resourceLeak 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-404 Demonstrative Example 4(오류 경로에서 연 파일 핸들을 닫지 않음) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    // 운용자 콘솔: 교대 근무마다 근무자 로그인 기록을 현재 폴더의 파일에 남긴다
string[] shift = ["opr07", "opr11", "opr15"];
foreach (string op in shift)
{
    Console.WriteLine(AppendLogin(op));
}

static string AppendLogin(string operatorId)
{
    string path = $"shift_{operatorId}.log";
    FileStream stream = File.Open(path, FileMode.Append, FileAccess.Write, FileShare.None);
    var writer = new StreamWriter(stream);       // 만든 뒤 Dispose 하지 않는다
    writer.Write("login " + operatorId + "\n");
    writer.Flush();
    // FileShare.None으로 연 핸들이 GC 시점까지 남아 다른 기능이 이 파일을 열지 못한다
    return operatorId + ": logged, " + stream.Length + " bytes";
}

    File.Open으로 연 FileStream과 StreamWriter를 Dispose하지 않아, FileShare.None으로 잡은 파일 핸들이 가비지 수집 시점까지 남고 그동안 백업·전송 같은 다른 기능이 그 파일을 열지 못한다. 분석기가 CA2000(범위를 벗어나기 전에 개체 삭제)으로 알려 준다.

    좋은 예

    // 운용자 콘솔: 교대 근무마다 근무자 로그인 기록을 현재 폴더의 파일에 남긴다
string[] shift = ["opr07", "opr11", "opr15"];
foreach (string op in shift)
{
    Console.WriteLine(AppendLogin(op));
}

static string AppendLogin(string operatorId)
{
    string path = $"shift_{operatorId}.log";
    using FileStream stream = File.Open(path, FileMode.Append, FileAccess.Write, FileShare.None);
    using var writer = new StreamWriter(stream);  // 범위를 벗어나면 writer → stream 순으로 Dispose
    writer.Write("login " + operatorId + "\n");
    writer.Flush();
    return operatorId + ": logged, " + stream.Length + " bytes";
}

    FileStream과 StreamWriter를 using 선언으로 받아, 메서드를 벗어나는 즉시 Dispose되어 파일이 닫힌다.

    검증: .NET 컴파일러·분석기 — 나쁜 예에서 CA2000 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-404 Demonstrative Example 3(예외가 나면 닫히지 않는 데이터베이스 연결) 참고, 이 가이드가 새로 작성

    Java

    나쁜 예

    import java.util.List;

public class Example {
    static int openHandles = 0;               // 장치 드라이버가 내준 채널 핸들 수

    // 데이터 기록기(recorder) 채널: 다 쓰면 반드시 close()로 돌려줘야 한다
    static final class RecorderChannel implements AutoCloseable {
        RecorderChannel() { openHandles++; }
        void write(String frame) {
            if (frame.isEmpty()) throw new IllegalArgumentException("empty frame");
        }
        @Override public void close() { openHandles--; }
    }

    static void record(String frame) {
        try {
            RecorderChannel ch = new RecorderChannel();
            ch.write(frame);
            ch.close();                       // 예외가 나면 이 줄에 오지 않는다
        } catch (IllegalArgumentException e) {
            System.out.println("frame skipped: " + e.getMessage());
        }
    }

    public static void main(String[] args) {
        for (String f : List.of("NAV", "", "", "IMU")) record(f);
        System.out.println("open recorder handles=" + openHandles);
    }
}

    write에서 예외가 나면 close() 줄에 오지 않아 채널 핸들이 반환되지 않는다. 실행 결과 처리가 끝난 뒤에도 핸들이 열린 채 남는다.

    좋은 예
