    Exposure of Sensitive System Information to an Unauthorized Control Sphere

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, Go · 기술: 기술 무관, 웹 기반(Web Based)
    원문 MITRE CWE-497 (CWE 5.0)

    이름 표기

    「소프트웨어 개발보안 가이드」(2021. 11.)의 구현단계 기준에는 이 CWE의 항목이 따로 없고 '오류 메시지 정보노출'(인쇄 287쪽)의 참고자료로 나온다. 이 가이드는 같은 가이드 분석·설계단계 사례의 그림 제목 '시스템 데이터 정보노출'(그림 3-36, 인쇄 127쪽)을 이름으로 쓴다.

    한 줄 요약

    기반 시스템에 제품과 같은 수준의 접근 권한이 없는 비인가 행위자가 민감한 시스템 수준 정보에 접근하는 것을 적절히 막지 못하는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 기반 시스템에 대해 제품과 같은 수준의 접근 권한을 갖지 않은 비인가 행위자가 민감한 시스템 수준 정보에 접근하는 것을 적절히 막지 못한다.

    배경(Background Details)

    웹 애플리케이션 같은 네트워크 기반 제품은 흔히 운영체제나 그와 비슷한 환경 위에서 동작한다. 제품이 외부와 통신할 때 데이터 파일 경로명, 다른 OS 사용자, 설치된 패키지, 애플리케이션 환경 같은 기반 시스템의 세부 정보는 숨겨져 있을 것으로 기대된다. 이런 시스템 정보는 제품이 직접 제공하거나 진단·디버그 메시지 속에 묻혀 있을 수 있다.

    원문(Description · Background Details)

    The product does not properly prevent sensitive system-level information from being accessed by unauthorized actors who do not have the same level of access to the underlying system as the product does.

    Network-based products, such as web applications, often run on top of an operating system or similar environment. When the product communicates with outside parties, details about the underlying system are expected to remain hidden, such as path names for data files, other OS users, installed packages, the application environment, etc. This system information may be provided by the product itself, or buried within diagnostic or debugging messages.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 제품이 오류 처리 메커니즘의 일부로 스택 트레이스처럼 구현 세부를 많이 드러내는 진단 방식을 쓸 수 있다.
    시스템 구성(System Configuration) 유지보수 제품이 오류 처리 메커니즘의 일부로 스택 트레이스처럼 구현 세부를 많이 드러내는 진단 방식을 쓸 수 있다.
    운용(Operation) 유지보수 제품이 오류 처리 메커니즘의 일부로 스택 트레이스처럼 구현 세부를 많이 드러내는 진단 방식을 쓸 수 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 애플리케이션 데이터 읽기 정보 노출은 시스템 데이터나 디버그 정보가 출력 스트림이나 로깅 함수를 통해 프로그램 밖으로 나가 비인가자가 접근할 수 있게 될 때 생긴다. 디버그 정보는 공격자가 시스템을 파악하고 공격 계획을 세우는 데 도움이 된다. 공격자는 다른 약점을 이용해 오류를 일으킬 수 있고, 그 오류에 대한 응답은 다른 영향과 함께 상세한 시스템 정보를 드러낼 수 있다. 공격자는 기술·운영체제·제품 버전을 드러내는 메시지로 그 기술의 알려진 취약점에 맞춰 공격을 조정할 수 있다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) / 구현(Implementation) — 운영 환경 애플리케이션은 스택 트레이스나 오류 메시지 같은 내부 세부 정보를 만드는 메서드를, 그 정보가 최종 사용자가 볼 수 없는 로그에 바로 기록되는 경우가 아니면 절대 쓰지 않아야 한다. 또한 로그를 보는 사람에 대한 크로스사이트 스크립트 공격을 막기 위해 모든 오류 메시지 텍스트는 로그 파일에 쓰기 전에 HTML 엔티티 인코딩해야 한다. (구현 단계에도 해당)
    원문

    Production applications should never use methods that generate internal details such as stack traces and error messages unless that information is directly committed to a log that is not viewable by the end user. All error message text should be HTML entity encoded before being written to the log file to protect against potential cross-site scripting attacks against the viewer of the logs

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 정비 단말이나 지상 통제 화면이 장비에 상태 조회를 보내면 장비는 운용 상태를 돌려준다. 장비 안에는 내부 빌드 식별자·빌드 서버 이름·키 파일 위치·메모리 배치·디버그 포트 상태 같은 시스템 데이터도 있는데, 이것이 상태 응답에 함께 실리면 공격 대상을 파악하는 데 쓰인다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>

typedef struct {
    const char *fw_full;      /* 내부 빌드 식별자 */
    const char *build_host;
    const char *key_path;
    unsigned    ram_base;
    int         jtag_open;
    int         mode;
    int         battery_pct;
} SysInfo;

static const SysInfo sys = {
    "3.4.1-rc2+g9f1c", "bldsrv-07", "/opt/gcs/conf/link.key",
    0x20000000u, 1, 2, 87
};

/* 정비 단말의 STATUS 요청에 대한 응답 */
static int status_reply(char *out, size_t n)
{
    /* 내부 구조체의 모든 필드를 응답에 싣는다 */
    return snprintf(out, n, "mode=%d batt=%d fw=%s host=%s key=%s ram=0x%08X jtag=%d",
                    sys.mode, sys.battery_pct, sys.fw_full, sys.build_host,
                    sys.key_path, sys.ram_base, sys.jtag_open);
}

int main(void)
{
    char out[256];
    if (status_reply(out, sizeof out) > 0) {
        printf("STATUS -> %s\n", out);
    }
    return 0;
}

    상태 응답을 만들면서 내부 구조체의 필드를 모두 싣는다. 빌드 서버 이름, 키 파일 위치, RAM 시작 주소, JTAG 개방 여부까지 단말로 나간다.

    좋은 예

    #include <stdio.h>

typedef struct {
    const char *fw_full;      /* 내부 빌드 식별자: 정비 로그 전용 */
    const char *fw_public;    /* ICD에 정의된 외부 공개 판 번호 */
    const char *build_host;
    const char *key_path;
    unsigned    ram_base;
    int         jtag_open;
    int         mode;
    int         battery_pct;
} SysInfo;

static const SysInfo sys = {
    "3.4.1-rc2+g9f1c", "3.4", "bldsrv-07", "/opt/gcs/conf/link.key",
    0x20000000u, 1, 2, 87
};

/* 응답에는 ICD가 허용한 필드만 골라 싣는다 */
static int status_reply(char *out, size_t n)
{
    return snprintf(out, n, "mode=%d batt=%d fw=%s",
                    sys.mode, sys.battery_pct, sys.fw_public);
}

int main(void)
{
    char out[128];
    if (status_reply(out, sizeof out) > 0) {
        printf("STATUS -> %s\n", out);
    }
    return 0;
}

    ICD가 외부 공개를 허용한 필드(모드·배터리·공개 버전 번호)만 골라 응답을 만든다. 내부 빌드 식별자는 정비 로그용으로 따로 둔다.

    검증: 실행 결과 — 나쁜 예에서 host=bldsrv 또는 key=/opt/gcs 검출, 좋은 예에서 미검출·STATUS -> mode=2 batt=87 fw=3.4 출력 확인 · 참고: MITRE CWE-497 Demonstrative Example 1(PATH 환경 변수를 표준 오류로 출력) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 캡슐화 6-2 '시스템 데이터 정보노출'(인쇄 190쪽) 참고

    C++

    나쁜 예

    #include <iostream>
#include <map>
#include <string>

int main() {
    // 장비 구성 저장소(내부용 항목과 외부 공개 항목이 섞여 있다)
    const std::map<std::string, std::string> cfg = {
        {"sys.mode", "STANDBY"},
        {"sys.health", "OK"},
        {"sys.build", "bldsrv-07 2026-09-30 debug-sym"},
        {"radio.key_file", "/opt/gcs/conf/link.key"},
        {"net.peer", "192.0.2.17:7001"},
    };

    // DIAG 응답: 구성 항목 전부를 그대로 보낸다
    std::string reply;
    for (const auto &[key, value] : cfg) {
        reply += key + "=" + value + ";";
    }
    std::cout << "DIAG -> " << reply << '\n';
    return 0;
}

    진단 응답에서 구성 저장소 전체를 반복문으로 펼쳐 보낸다. 공개 항목과 내부 항목(키 파일·빌드 정보·상대 장비 주소)이 섞여 있어 모두 나간다.

    좋은 예

    #include <array>
#include <iostream>
#include <map>
#include <string>

int main() {
    const std::map<std::string, std::string> cfg = {
        {"sys.mode", "STANDBY"},
        {"sys.health", "OK"},
        {"sys.build", "bldsrv-07 2026-09-30 debug-sym"},
        {"radio.key_file", "/opt/gcs/conf/link.key"},
        {"net.peer", "192.0.2.17:7001"},
    };

    // 외부로 보내도 되는 항목을 허용목록으로 정해 두고 그것만 싣는다
    constexpr std::array<const char *, 2> kExported = {"sys.mode", "sys.health"};
    std::string reply;
    for (const char *key : kExported) {
        auto it = cfg.find(key);
        reply += std::string(key) + "=" + (it != cfg.end() ? it->second : "N/A") + ";";
    }
    std::cout << "DIAG -> " << reply << '\n';
    return 0;
}

    외부로 보낼 항목을 허용목록으로 정해 두고 그 항목만 찾아 싣는다. 구성에 항목이 늘어도 응답이 저절로 늘지 않는다.

    검증: 실행 결과 — 나쁜 예에서 radio.key_file=/opt 또는 bldsrv-07 검출, 좋은 예에서 미검출·DIAG -> sys.mode=STANDBY;sys.health=OK; 출력 확인 · 참고: MITRE CWE-497 Demonstrative Example 4(데이터베이스 연결 문자열을 콘솔에 출력) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    // 정비 단말의 상태 조회 요청에 대한 응답
static string StatusReply(DeviceState s) => "STATUS -> " + s;   // record를 통째로 문자열로

var state = new DeviceState("STANDBY", 87, "bldsrv-07", "/opt/gcs/conf/link.key");
Console.WriteLine(StatusReply(state));

// record의 자동 ToString은 모든 공개 속성을 이름과 값으로 펼친다
internal sealed record DeviceState(string Mode, int BatteryPct, string BuildHost, string KeyPath);

    record를 문자열로 바꿔 응답에 넣는다. record가 자동으로 만드는 ToString은 모든 공개 속성을 이름과 값으로 펼치므로 키 파일 위치와 빌드 서버 이름이 나간다.

    좋은 예

    using System.Globalization;

var state = new DeviceState("STANDBY", 87, "bldsrv-07", "/opt/gcs/conf/link.key");

// 응답 전용 형식으로 옮겨 ICD가 허용한 필드만 보낸다
Console.WriteLine("STATUS -> " + StatusMessage.From(state));

internal sealed record DeviceState(string Mode, int BatteryPct, string BuildHost, string KeyPath)
{
    // 실수로 문자열이 되어도 내부 값이 펼쳐지지 않게 한다
    public override string ToString() => $"DeviceState(mode={Mode})";
}

internal sealed record StatusMessage(string Mode, int BatteryPct)
{
    public static StatusMessage From(DeviceState s)
    {
        ArgumentNullException.ThrowIfNull(s);
        return new StatusMessage(s.Mode, s.BatteryPct);
    }

    public override string ToString() =>
        string.Create(CultureInfo.InvariantCulture, $"mode={Mode} batt={BatteryPct}");
}

    응답 전용 형식(StatusMessage)으로 옮겨 허용한 필드만 보내고, 내부 record의 ToString도 재정의해 실수로 문자열이 되어도 내부 값이 펼쳐지지 않게 한다.

    검증: 실행 결과 — 나쁜 예에서 KeyPath = /opt/gcs 또는 BuildHost = bldsrv 검출, 좋은 예에서 미검출·STATUS -> mode=STANDBY batt=87 출력 확인 · 참고: MITRE CWE-497 Demonstrative Example 4(데이터베이스 연결 문자열을 콘솔에 출력) 참고, 이 가이드가 새로 작성

    Java

    나쁜 예

    import java.util.Properties;

public class Example {
    static Properties loadDeviceState() {
        Properties dev = new Properties();
        dev.setProperty("mode", "STANDBY");
        dev.setProperty("health", "OK");
        dev.setProperty("build.host", "bldsrv-07");
        dev.setProperty("crypto.keyFile", "/opt/gcs/conf/link.key");
        dev.setProperty("db.url", "jdbc:h2:/opt/gcs/data/log");
        return dev;
    }

    // 지상 통제 화면의 상태 조회 응답
    static String statusReply(Properties dev) {
        return "STATUS " + dev;      // Properties.toString은 모든 항목을 펼친다
    }

    public static void main(String[] args) {
        System.out.println(statusReply(loadDeviceState()));
    }
}

    Properties 객체를 문자열 연결로 응답에 넣는다. Properties.toString()은 모든 항목을 펼치므로 키 파일 위치와 DB 주소가 함께 나간다.

    좋은 예

    import java.util.List;
import java.util.Properties;
import java.util.StringJoiner;

public class Example {
    // 외부로 보내도 되는 항목(ICD 상태 메시지 정의)
    static final List<String> EXPORTED = List.of("mode", "health");

    static Properties loadDeviceState() {
        Properties dev = new Properties();
        dev.setProperty("mode", "STANDBY");
        dev.setProperty("health", "OK");
        dev.setProperty("build.host", "bldsrv-07");
        dev.setProperty("crypto.keyFile", "/opt/gcs/conf/link.key");
        dev.setProperty("db.url", "jdbc:h2:/opt/gcs/data/log");
        return dev;
    }

    static String statusReply(Properties dev) {
        StringJoiner out = new StringJoiner(", ", "STATUS {", "}");
        for (String key : EXPORTED) {
            out.add(key + "=" + dev.getProperty(key, "N/A"));
        }
        return out.toString();
    }

    public static void main(String[] args) {
        System.out.println(statusReply(loadDeviceState()));
    }
}

    상태 조회 응답에 인터프리터 버전, 운영체제 정보, 내부 빌드 서버 이름과 소스 경로, 키 파일 위치를 담은 환경 변수를 함께 돌려준다. 정비 단말에 접근한 사람은 이 정보로 알려진 취약점이 있는 버전을 고르거나 키 파일을 노린다.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)
