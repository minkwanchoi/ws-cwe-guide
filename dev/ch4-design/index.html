    4.1 단계 목표·입력·산출물¶

    설계 단계는 요구사항 분석 단계에서 정한 보안 요구사항을 구조와 상세 설계로 옮겨, 보안약점이 생길 자리를 먼저 막는 단계다. 어느 언어 뷰에도 없는 보안기능 14개(인증·인가(authorization)·암호·키·업데이트 무결성 등)는 코딩규칙(coding rule)만으로는 막기 어렵다. 이들은 무엇을 보호하고 누가 무엇을 할 수 있는지를 설계에서 정해야 한다. [CWE] CWE 5.0 Potential Mitigations(Architecture and Design)

    입력. 요구사항 분석 단계에서 낸 SRS 보안 요구사항과 보안약점 적용성 판정(부록 G-4, 제3장), 외부 인터페이스 목록, 환경 프로파일과 지침 선택 결과(부록 G-3)를 입력으로 쓴다.

    산출물에 넣을 보안 항목. 아래 문서 이름은 매뉴얼 제2024-6호 제2장 Ⅶ·Ⅷ(구조설계·상세설계)의 산출물 이름을 따른다. SBOM 초안과 설계 보안성 검토 기록은 매뉴얼 산출물이 아니므로 과제 문서 체계에 맞춰 둔다.

    산출물 넣을 보안 항목 관련 기준선 활동
    인터페이스통제문서(ICD)·인터페이스설계기술서(IDD) 메시지별 최대 길이·필드 범위·단위(R-01의 인터페이스 요구사항을 구체화), 신뢰 경계 표시, 무결성·인증 요구 D-02
    소프트웨어설계기술서(SDD) 신뢰 경계와 검증 지점, 권한 매트릭스와 격리 구조, 키 관리, 보안 부팅·업데이트 구조, 자원 예산, 오류 처리 정책 D-02~D-08
    구성요소 목록(SBOM 초안) 언어·라이브러리·OS·툴체인의 이름·버전·출처·해시·라이선스 D-03
    설계 보안성 검토 기록 체크리스트 점검 결과와 조치 D-09

    구조설계와 상세설계. 매뉴얼은 설계를 구조설계와 상세설계로 나누고 각각 기본설계검토회의(PDR)와 상세설계검토회의(CDR)로 확정한다. 구조설계는 소프트웨어 형상항목(CSCI)의 요구사항을 상위 수준의 구조로 바꾸고 구성품(CSC)을 식별하며, CSCI 외부 인터페이스와 구성품 사이 인터페이스, 데이터베이스를 상위 수준으로 설계하는 일이다. 상세설계는 단위 소프트웨어(CSU)를 식별해 그 내부 처리와 인터페이스를 상세히 설계하고, 인터페이스는 추가 정보 없이 코딩할 수 있을 정도로 상세화하는 일이다([표준] 매뉴얼 제2024-6호 제2장 Ⅶ·Ⅷ, 인쇄 41·47~48쪽). 이 가이드는 두 단계를 설계 단계 하나로 묶고, 기준선 활동의 결정을 다음 검토 시점에 맞춘다. 이 대응은 가이드의 판단이다.

    검토 시점 이때 확정할 보안 결정
    기본설계검토회의(PDR) D-02 신뢰 경계와 검증 지점, D-03 구성요소 선정과 SBOM 초안, D-04 권한 매트릭스와 실행 단위 분리, D-05 승인 알고리즘 목록, D-06 부팅·업데이트 신뢰 체인
    상세설계검토회의(CDR) D-05 키 생성·주입·저장·교체·폐기 절차, D-07 버퍼·큐 크기와 자원 예산, D-08 오류 유형별 처리와 안전 상태, ICD 필드 범위표
    두 검토 모두 D-09 설계 보안성 검토(검토 범위는 그 시점의 설계 산출물)

    4.2 기준선 활동 D-02~D-09¶

    설계 단계의 기준선 활동은 8개다. D-06을 뺀 7개는 모든 과제가 수행한다. 요구사항 분석 단계의 R-01 보안 요구사항 정의는 3.2에 있고, 설계 단계 번호가 D-02부터인 까닭은 1.4에 있다. '강화·대체 지침' 항목의 뜻은 2.3에 있다. 근거의 SSDF 실천 번호는 SSDF 1.1 원문과 대조했다(조회 2026. 10. 15.).

    D-02 위협 모델링·신뢰 경계 정의¶

    설계 · 기준선

    • 적용 조건: 항상
    • 대상 약점: CWE-20, CWE-119, CWE-129, CWE-134, CWE-306, CWE-494
    • 지침: 데이터링크, 정비 포트, 직렬·버스 인터페이스, 저장매체, 코어 간 공유 메모리처럼 데이터가 들어오는 경로마다 신뢰 경계(trust boundary)를 긋는다. 경계마다 검증 지점을 한 곳으로 정하고, 위조·변조·재전송·폭주 위협과 대응 활동을 표로 적는다. 링크 오류 검출용 체크섬은 위조를 막지 못하므로 인증·무결성 보호로 보지 않는다.
    • 산출물: 신뢰 경계 도표, 경계별 위협·검증 지점 표
    • 근거: [CWE] CWE-306 완화책(Architecture and Design), CWE-78 완화책(Architecture and Design: Attack Surface Reduction) · [표준] SSDF PW.1 · [사례] MAVLink 개요 문서(체크섬은 링크상 전송 오류로 인한 손상만 검출, 조회 2026. 10. 15.)
    • 강화·대체 지침: (강화) PC-02, WIN-02, PSOS-02, MSVC-01, LC-02

    D-03 언어·라이브러리·외부 구성요소 선정¶

    설계 · 기준선

    • 적용 조건: 항상
    • 대상 약점: CWE-119, CWE-327, CWE-676
    • 지침: 검증된 라이브러리와 길이 인자를 받는 문자열 API를 설계 표준으로 지정한다. 암호 기능은 자체 구현하지 않고, 국내 검증필 암호모듈(KCMVP) 요구가 있는지 확인한다. 외부 구성요소는 이름·버전·출처·해시·라이선스를 SBOM(소프트웨어 구성명세서) 초안에 올리고, 이 목록을 제7장 취약점 추적(M-05)의 출발점으로 쓴다.
    • 산출물: 구성요소 선정표, SBOM 초안(SPDX 또는 CycloneDX)
    • 근거: [CWE] CWE-119 완화책(Requirements: Language Selection; Architecture and Design: Libraries or Frameworks) · [표준] SSDF PW.4(PW.4.1·PW.4.4; 언어 선정은 SSDF 과제가 아니어서 [CWE] Language Selection만 근거로 씀), KISA 암호모듈검증(KCMVP) 개요(조회 2026. 10. 15.)
    • 강화·대체 지침: (강화) LNX-01, OSS-01, OSS-04, LPY-02

    D-04 권한 분리·최소 권한·격리 설계¶

    설계 · 기준선

    • 적용 조건: 항상(수단은 실행 격리 특성에 따라 보정, 4.4)
    • 대상 약점: CWE-285, CWE-306, CWE-732
    • 지침: 운용자·정비자·관리자 역할별 권한 매트릭스를 만들고, 권한 검사는 장비 쪽에서 한곳에 모아 강제한다. 외부 통신을 처리하는 부분과 임무 핵심 기능을 서로 다른 실행 단위로 나눈다. 나누는 수단은 실행 격리 수준에 따라 프로세스·파티션, MPU(메모리 보호 장치) 기반 태스크 보호, 단일 주소공간의 모듈 경계 순으로 고른다.
    • 산출물: 권한 매트릭스, 실행 단위 구성도
    • 근거: [CWE] CWE-285 완화책(Architecture and Design: 익명·일반·특권·관리 영역 분리) · [표준] SSDF PW.1(PW.1.1·PW.1.3) · [보완] 최소 권한(SSDF 1.1의 최소 권한 문구는 코드 저장·개발 환경 대상이어서 근거로 쓰지 않음)
    • 강화·대체 지침: (강화) PC-01, SBC-02, SOC-01, WIN-01, LNX-02, VXW-01, VXW-02, FRT-01, WRW-01, MSVC-02, OSS-03

    사례 상자 4-1 — 설계 결정이 빠졌을 때 생긴 결함 이 사례는 지침이 실제 임베디드 코드에 쓰인 예다. 무기체계 적합성을 입증하지 않는다.

    • [사례·확인] (SBC-05, 관련 D-02) PX4-Autopilot v1.17.0, CVE-2026-32706 — 1.17.0-rc2 이전의 crsf_rc 파서가 지나치게 긴 가변 길이 패킷을 경계 검사 없이 고정 크기 전역 버퍼로 복사. 직렬 포트도 신뢰 경계로 다루어야 한다. (확인 2026. 10. 15.) 원문
    • [사례·확인] (FRT-01 → D-04) CVE-2021-43997 — FreeRTOS 10.2.0~10.4.5의 MPU 포트에서 비커널 코드가 xPortRaisePrivilege를 호출해 권한을 올릴 수 있었다. V10.5.0과 V10.4.3-LTS Patch 3에서 수정되었다. (확인 2026. 10. 15.) 원문
    • [사례·확인] (SOC-01, 관련 D-04) Xilinx embeddedsw xilinx_v2026.1, lib/sw_apps/zynqmp_fsbl/src/xfsbl_hw.h:958-960 — FSBL_PROT_BYPASS_EXCLUDE를 정의하지 않으면 XFSBL_PROT_BYPASS가 정의되어 XPPU·XMPU(Xilinx 주변장치·메모리 보호 장치) 보호 구성을 우회하는 것이 기본값. 하드웨어 격리도 설정으로 켜고 잠가야 한다. (확인 2026. 10. 15.) 원문

    D-05 암호·키·비밀 관리 설계¶

    설계 · 기준선

    • 적용 조건: 항상
    • 대상 약점: CWE-259, CWE-312, CWE-321, CWE-327, CWE-330, CWE-759 / 보조 항목 CWE-295, CWE-299, CWE-916
    • 지침: 사용할 암호 알고리즘과 키 길이를 목록으로 정하고, MD5·SHA-1·DES 같은 취약 알고리즘은 쓰지 않는다. 키의 생성·주입·저장·교체·폐기 주기를 키 관리 설계서에 적고, 장비마다 고유한 키를 생산 단계에서 주입한다. 비밀번호는 솔트와 반복 기반 해시로 저장하고 반복 횟수(계산 노력)를 설계값으로 정한다. 소스·설정 파일에 비밀을 두지 않으며, 키·논스는 암호학적 난수발생기로 만든다. TLS처럼 인증서를 쓰는 통신은 인증서 검증 방식과 폐기 확인 수단을 정한다. 폐쇄망이면 인증서 폐기 정보(CRL·OCSP)를 망 안으로 들여오는 방법도 함께 정한다.
    • 산출물: 키 관리 설계서, 승인 알고리즘 목록

    하드웨어 신뢰 기점(H3) 보안 부팅·보안 키 저장 eFuse 공개키 해시·암호화 부트 이미지로 보안 부팅을 설계하고, 키를 eFuse·보안 요소에 둔다. SBC-01·SOC-02(강화→D-06), SOC-04(강화→D-05)
    읽기보호·퓨즈 부트로더 서명 검증, 읽기 보호, 이중 뱅크 복구를 설계하고, 퓨즈·락비트 정책을 정한다. MCU-03(강화→D-06), AVR-02(추가), BSP-02(강화→D-06), CCS-02(추가)
    없음 서명 체인을 하드웨어에 고정할 수 없다. 업데이트가 공장 재프로그래밍뿐이면 D-06을 [보완] 해시 검증으로 대체하고, 물리 보호를 운용 절차에 넣는다. 업데이트가 원격·현장 매체이면 D-06을 그대로 적용하되, 공개키와 첫 검증 코드를 쓰기 금지 영역(부트로더 영역 락비트 등)에 두고 그 한계를 설계서에 [보완]으로 적는다. D-06 대체([보완] 해시 검증, 7.3 '공장 재프로그래밍만' 행)
    이기종 다중 실행 단위(H4) 다중 실행 단위마다 프로파일을 따로 만든다(2.5 ①). 코어·PL·DMA 마스터별 접근 권한을 하드웨어 보호 장치로 강제하고, 상대 코어가 보낸 메시지도 검증한다. SOC-01(강화→D-04), SOC-03(강화→I-03), SOC-08(강화→M-02)
    MMU 유무(H1) 없음 ASLR·프로세스 격리를 쓸 수 없고 실행 금지는 MPU 속성으로 대신하므로 MPU 영역 보호, 정적 할당, 고정 주소 접근의 HAL 국한으로 바꾼다(8.1). MCU-06(강화→I-05), BM-03(강화→D-06·M-06)

    보정할 때 남길 것. "대체됨" 기록(2.5)은 설계서에 다음처럼 남긴다. 예를 들어 단일 주소공간 RTOS(실시간 운영체제)에서 D-04의 프로세스 분리를 쓰지 못하면, 설계서에 그 사실과 대신 쓴 수단(모듈 경계, 래퍼, 정적 분석 강화)을 함께 적는다. 이렇게 해야 시험·검토 단계에서 무엇이 빠졌는지 추적할 수 있다.

    4.5 언어별 설계 고려¶

    언어별 설계 활동은 2.6 활동표의 설계 열(LC-01~03, LCPP-01~03, LJ-02·03, LCS-02·03, LPY-02·03)을 따른다. 점검 기준과 적용 범위를 정하는 LJ-01·LCS-01·LPY-01은 요구사항 분석 단계 활동이다(3.5). 여기서는 그 표에 없는 설계 결정만 덧붙인다. [근거] 언어 환경 지침(부록 C), 매뉴얼 부록 6(인쇄 6-2쪽)

    • C: 엔디언·구조체 패딩·int 크기 같은 타깃 의존 부분은 HAL에 모으고 고정폭 정수형만 쓴다(LC-03).
    • C++: 임베디드에서 -fno-exceptions·-fno-rtti와 동적 할당 금지를 쓰면 반환 코드 규약과 고정 용량 컨테이너를 설계 표준으로 둔다. 다형 기반 클래스는 복사·이동도 막는다(LCPP-02·03).
    • Java: 역직렬화(deserialization)가 불가피하면 서명·HMAC 무결성 확인과 ObjectInputFilter(JEP 290) 허용목록(allowlist)을 함께 둔다. 허용목록만으로는 충분하지 않다(LJ-02).
    • C#: BinaryFormatter는 .NET 9부터 내장 구현이 사용 시 예외를 던지므로 대체 직렬화 방식을 설계에서 정한다(LCS-03).
    • Python: 외부 데이터를 pickle뿐 아니라 marshal·yaml.load로도 읽지 않는다(LPY-03).

    다른 언어에서 네이티브 코드를 부르는 경계(C#의 P/Invoke, Java의 JNI)는 신뢰 경계로 표시하고, 네이티브 쪽에는 C/C++ 지침을 그대로 적용한다(LCS-02, LJ-08, MSVC-01).

    4.6 단계 자가점검표¶

    설계 단계 자가점검표(4-1~4-9)는 부록 G-5 설계 단계에 있다. 설계 산출물을 낼 때 그 표로 스스로 확인한다.
