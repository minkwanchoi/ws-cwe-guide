    가이드 요약¶

    이 쪽의 목차
    • 이 가이드를 쓰는 순서
    • 단계별 핵심 활동(기준선)
    • 특성별로 바꿔야 할 것
    • 계산 예

    착수·품질 담당용으로 특성 15개 전체와 매뉴얼 관계를 담아 정리했다. 이 가이드는 무기체계 임베디드 소프트웨어의 보안약점 197개와 보조 항목 4개(2.1)를 수명주기 5단계마다 예방하는 활동을 정리한다. 지침은 기준선 활동 33개와, 개발환경의 특성 15개에 따라 고르는 환경 지침 245건으로 구성한다. 매뉴얼의 정적시험·동적시험은 결과 점검이고, 이 가이드는 그 앞의 예방 활동을 중심으로 시험·유지보수 단계의 확인·유지 활동까지 다룬다(1.1).

    먼저 알아 둘 용어

    • 기준선 활동: 모든 과제에 기본으로 적용하는 단계별 공통 활동 33개(R-01~M-07, 일부는 적용 조건이 있음). 2.3
    • 특성(코드): 지침이 필요한지·가능한지를 가르는 개발환경의 속성 15개. H1(MMU 유무)~N1(개발·시험 망)처럼 하이픈 없는 코드로 쓴다. 2.4
    • 환경 지침: 특성 조건이나 고른 환경에 따라 기준선 활동에 더하는 지침 245건(예: PC-01, NET-IN-01). 2.3, 부록 C
    • 보정 유형: 환경 지침이 기준선 활동과 맺는 관계로, 추가·대체·강화·비해당이 있다. 2.3

    이 가이드를 쓰는 순서¶

    기준 절차는 2.5의 ①~⑦이다. 아래 세 묶음은 그 번호를 줄여 보인 것이다.

    묶음(2.5 번호) 할 일 쓰는 곳
    1. 내 환경 정하기(①~④) 실행 단위를 나누고 축마다 환경을 고른다. 목록에 없으면 특성 시트를 쓰고 최근접 환경을 지정한다. 후보값과 과제 결정 특성(동적 메모리 정책)을 하나로 정한다. 2.4~2.5, 부록 G-1~G-3
    2. 지침 받기·판정하기(⑤~⑥) 지침 선택 도구(또는 부록 C 역색인)로 지침 목록을 받는다. 결과는 기준선 + 특성 일치 + 선택 환경 + 상속 지침이다. 상속 지침과 '확인 필요' 지침을 판정하고, 사용 기술 체크리스트로 197개 보안약점의 적용성(해당·조건부·비해당)을 기록한다. 2.5, 8.7, 부록 G-3·G-4
    3. 단계마다 적용·점검(⑦) 단계 장(제3~7장)의 기준선 활동과 받은 지침을 함께 적용하고, 단계 검토 때 자가점검표로 확인한다. 쓸 수 없는 수단은 지우지 말고 "대체됨(→ 지침 ID)"으로 남긴다. 기능·구성이 바뀌면 판정을 다시 한다. 제3~7장, 부록 G-5

    단계별 핵심 활동(기준선)¶

    단계 대표 기준선 활동 주요 산출물 매뉴얼과의 관계·유의점
    요구사항 분석(제3장) R-01 보안 요구사항 정의, 보안약점 적용성 판정, 언어별 점검 기준(C#·Java·Python) SRS의 보안 요구사항·품질특성, 적용성 판정 기록지(G-4) 매뉴얼은 SRS 품질특성에 신뢰성·보안성 요구사항을 쓰게 한다. 점검 대상과 도구 미지원 항목의 대안은 시험계획에 반영되도록 이 단계에서 정한다.
    설계(제4장) D-02 위협 모델링·신뢰 경계 정의, D-05 암호·키·비밀 관리 설계, D-06 보안 부팅·서명된 업데이트 체계 설계, D-07 자원 예산·정적 할당 설계, D-09 설계 보안성 검토 SDD·IDD·ICD의 보안 항목, SBOM 초안, 설계 보안성 검토 기록 보안기능 14개는 어느 언어 뷰에도 없어 정적 분석 규칙만으로 막기 어렵다. 그래서 요구사항 분석·설계에서 다룬다. 구조 결정은 PDR, 상세 결정은 CDR에서 확정한다.
    구현(제5장) I-01 사업 코딩 표준 수립과 편차 관리, I-03 신뢰 경계 입력 검증, I-05 정수·포인터·메모리 안전 코딩, I-08 컴파일러 경고·빌드 하드닝, I-09 코드 리뷰·상시 정적 분석, I-10 호스트(타깃 외) 동적 분석 사업 코딩 표준, 금지 함수 목록, 빌드 설정 기준, 편차 대장, 단위시험 결과 코딩규칙은 매뉴얼 부록 6의 표준에서 고르고, 조정 사유를 제시해 사업관리회의에서 확정한다.
    통합 및 시험(제6장) T-01 정적시험(소스·바이너리)과 오탐·편차 판정, T-02 타깃 동적시험, T-04 퍼징, T-06 보안 기능 부정 시험, T-08 운용 빌드 산출물 검사 정적시험·동적시험 결과, 오탐·편차 판정 기록, 도구 미지원 항목의 대안·사유 정적시험(코딩규칙·취약점 점검·메트릭)과 실제 타깃의 코드 실행률(Coverage) 점검이 기본이다. 퍼징과 구현 단계의 호스트 시험은 보조 시험이다.
    유지보수(제7장) M-01 변경 영향분석·회귀 보안시험, M-02 운용 빌드 구성 형상관리, M-04 서명된 업데이트·배포 무결성 검증, M-05 SBOM 기반 취약점 추적과 패치, M-07 구성요소·툴체인 수명 관리 변경 영향분석서, 운용 빌드 구성 기준선, SBOM·취약점 대조 기록, 지원 종료일 대장 매뉴얼은 통합시험 단계에서 정적시험을 한 뒤 변경이 없으면 개발시험평가 때 정적시험을 생략할 수 있게 한다(부록 7, 인쇄 7-9쪽). 변경이 있으면 다시 한다.

    특성별로 바꿔야 할 것¶

    특성 코드 뒤 괄호는 특성 이름, 줄 끝 괄호는 관련 대표 지침이다. 대표 지침의 선택 조건은 다른 특성이나 환경일 수 있으므로 부록 C에서 확인한다. 자세한 표는 8.1에 있다.

    • H1(MMU 유무) = 없음 → ASLR·프로세스 격리·타깃 새니타이저(sanitizer) 대신 MPU(메모리 보호 장치) 영역 보호, 정적 할당, 호스트 단위시험으로 바꾼다(BSP-03 추가, MCU-08 강화).
    • H3(하드웨어 신뢰 기점) = 읽기보호·퓨즈 또는 없음 → 하드웨어 보안 부팅(secure boot) 대신 부트로더 서명 검증·읽기 보호·롤백 방지를 쓴다. H3 = 없음이고 공장 재프로그래밍만 하면 D-06을 해시 검증으로 대체한다(MCU-09·AVR-09, 관련 MCU-03·BM-03).
    • H4(이기종 다중 실행 단위) = 다중 → 실행 단위마다 프로파일을 만들고, 상대 코어가 보낸 메시지도 검증한다(SOC-01·03).
    • H5(자료형 모델) = 비표준 → 고정폭 정수와 명시적 바이트 처리를 쓰고, 정적 분석 도구에 타깃 자료형을 설정한다(DSP-05·08).
    • S1(OS 유형) = RTOS·베어메탈 → ISR(인터럽트 서비스 루틴) 공유변수를 보호하고 고장 안전 상태를 정의하며, 코드 실행률은 디버거·트레이스로 실보드에서 잰다(MCU-02·05, BM-08).
    • S2(실행 격리) = 태스크 보호(MPU) → 태스크별 접근 영역을 정의해 비특권으로 실행하고, 영역 위반이 안전 상태로 이어지는지 시험한다(FRT-01·08).
    • S2(실행 격리) = 단일 주소공간 → 프로세스 분리 대신 커널 모드 최소화·래퍼 계층·모듈 경계·정적 분석 강화로 바꾸고 "대체됨"을 남긴다(WRW-01, PSOS-01).
    • S3(파일시스템) = 없음 → 배포·설치 구성 기준선(M-03)과 경로 조작(path traversal, CWE-22)·링크 따라가기(CWE-59)를 비해당으로 판정한다.
    • S4(외부 통신 스택) = IP 스택 → 프로토콜 스택 입력을 검증·퍼징(fuzzing)하고 쓰지 않는 서비스를 끈다. 직렬·버스 링크만 있으면 프레임 길이·체크섬·값 범위를 검증한다(FRT-06, SBC-05).
    • S5(동적 메모리 정책) = 금지·초기화 단계 한정 → 초기화 뒤 동적 할당을 금지하고 링커 맵으로 메모리 예산을 확인한다(MCU-01, BM-01).
    • L1(언어 런타임) = 관리형·인터프리터 → 금지 함수(I-02)·메모리 안전 코딩(I-05)은 비해당이다. JNI·P/Invoke 경계에만 C/C++ 지침을 쓴다(LJ-08, LCS-02).
    • L2(컴파일러 보호 기능 지원) = 부분·없음 → L2 = 부분이면 하드닝(hardening) 플래그 대신 guard 심볼 구현 확인(없으면 직접 구현)과 컴파일러가 지원하는 trap 모드 UBSan, L2 = 없음이면 스택 페인팅(stack painting)과 정적 분석으로 대체한다(GCC-05, CCS-05, AVR-05).
    • L3(타깃 외(호스트) 빌드) = 불가 → 호스트 동적 분석(dynamic analysis, I-10)이 빠지므로 타깃 시험과 정적 분석의 범위를 넓힌다.
    • M2(디버그 인터페이스) = 있음 → 출고 전 JTAG·디버그 콘솔을 봉인하고 정비 때 다시 여는 절차를 통제한다(SBC-09, AVR-02).
    • M3(공급 수명) = 단종·레거시 → 패치 대신 접근통제·물리 보호 같은 보상통제를 문서화하고 툴체인·소스를 보존한다(PSOS-08·09).
    • N1(개발·시험 망) = 내부망·폐쇄망 → 자동 업데이트와 온라인 조회 대신 반입 번들, 사내 미러, 데이터 기준일 표기로 바꾼다(NET-CL-03·04, NET-IN-05·08).

    특성은 아니지만 수단을 바꾸는 사용 기술도 있다. 현장·원격 업데이트가 없으면(공장 재프로그래밍만) 서명된 업데이트(M-04)를 적용성 판정에 비해당으로 기록하고, 생산 단계 이미지 해시 확인과 읽기 보호로 바꾼다(부록 G-4-1).

    계산 예¶

    Cortex-M33 + Zephyr RTOS + GCC + C + 폐쇄망 조합은 기준선 32, 특성 일치 56, 선택 환경 10, 상속 8, 합계 106건의 지침을 받는다(8.7).
