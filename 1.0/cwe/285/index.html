    Improper Authorization

    항목 내용

    Rationale: CWE-285 is high-level and lower-level CWEs can frequently be used instead. It is a level-1 Class (i.e., a child of a Pillar).

    Comments: Look at CWE-285's children and descendants.
    적용 플랫폼 언어 무관 · 기술: 기술 무관, 웹 서버(Web Server), 데이터베이스 서버(Database Server)
    원문 MITRE CWE-285 (CWE 5.0)

    한 줄 요약

    자원 접근이나 동작 수행 시 인가 검사를 하지 않거나 잘못 수행해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 행위자(actor)가 자원에 접근하거나 동작을 수행하려 할 때 인가(authorization) 검사를 수행하지 않거나 잘못 수행한다.

    배경(Background Details)

    접근 통제 목록(ACL)은 주어진 객체에 대한 권한을 누가 또는 무엇이 가지는지 나타낸다. 운영체제마다 ACL을 구현하는 방식이 다르다. UNIX에는 읽기, 쓰기, 실행의 세 가지 권한이 있다. 파일 접근에서 사용자는 소유자, 소유 그룹, 그 밖의 모든 사용자의 세 부류로 나뉘며, 부류마다 권한 집합이 따로 있다. Windows NT에는 파일에 대한 기본 권한으로 "No access", "Read access", "Change access", "Full control" 네 가지가 있다. Windows NT는 UNIX의 세 가지 사용자 유형 개념을 넓혀 사용자와 그룹의 목록과 각각의 권한을 둔다. 사용자는 객체(파일)를 만들고 그 객체에 지정한 권한을 부여할 수 있다.

    원문(Description · Background Details · Dimensions)

    The product does not perform or incorrectly performs an authorization check when an actor attempts to access a resource or perform an action.

    An access control list (ACL) represents who/what has permissions to a given object. Different operating systems implement (ACLs) in different ways. In UNIX, there are three types of permissions: read, write, and execute. Users are divided into three classes for file access: owner, group owner, and all other users where each class has a separate set of rights. In Windows NT, there are four basic types of permissions for files: "No access", "Read access", "Change access", and "Full control". Windows NT extends the concept of three types of users in UNIX to include a list of users and groups along with their associated permissions. A user can create an object (file) and assign specified permissions to that object.

    Dimensions: Behavior-Property = Improper; Behavior-Type = Authorization

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 실현(REALIZATION): 아키텍처 보안 전술을 구현하는 과정에서 생기는 약점이다. 개발자가 기반 기술을 잘 이해하지 못해 인가 약점을 만들 수 있으며, 예를 들어 공격자가 헤더나 쿠키 같은 입력을 수정할 수 없다고 가정할 수 있다.
    아키텍처·설계(Architecture and Design) 설계 단일 사용자 애플리케이션을 다중 사용자 환경으로 이식할 때 인가 약점이 생길 수 있다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 애플리케이션 데이터 읽기 / 파일·디렉터리 읽기 공격자는 제대로 제한되지 않은 데이터 저장소에서 데이터를 직접 읽거나, 충분히 보호되지 않은 특권 기능에 접근해 민감한 데이터를 읽을 수 있다.
    무결성 애플리케이션 데이터 수정 / 파일·디렉터리 수정 공격자는 제대로 제한되지 않은 데이터 저장소에 데이터를 직접 쓰거나, 충분히 보호되지 않은 특권 기능에 접근해 민감한 데이터를 수정할 수 있다.
    접근 통제 권한 획득 또는 신원 도용 / 허가되지 않은 코드·명령 실행 접근 통제 검사가 일관되게 적용되지 않거나 전혀 적용되지 않으면, 공격자가 중요한 데이터를 직접 수정하거나 읽거나 충분히 보호되지 않은 특권 기능에 접근해 권한을 얻고 허가되지 않은 코드·명령을 실행할 수 있다.

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: R-01 보안 요구사항 정의

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 제품을 익명·일반·특권·관리 영역으로 나누고, 역할을 데이터·기능에 신중히 대응시켜 공격 표면을 줄이며, 역할 기반 접근 통제(RBAC)로 적절한 경계에서 역할을 강제한다. 단, 이 방법은 수평적 인가 문제(같은 역할의 다른 사용자를 공격하는 것)는 막지 못할 수 있다.
    원문

    Divide the product into anonymous, normal, privileged, and administrative areas. Reduce the attack surface by carefully mapping roles with data and functionality. Use role-based access control (RBAC) to enforce the roles at the appropriate boundaries.

    Note that this approach may not protect against horizontal authorization, i.e., it will not protect a user from attacking others with the same role.
    아키텍처·설계(Architecture and Design) — 업무 논리(business logic)와 관련된 접근 통제 검사를 수행한다. 이 검사는 파일·연결·프로세스·메모리·데이터베이스 레코드 같은 일반 자원에 적용하는 검사와 다를 수 있다(예: 데이터베이스는 의료 기록 접근을 특정 DB 사용자로 제한하지만, 각 기록은 환자와 그 담당 의사만 접근하도록 의도되었을 수 있다).
    원문

    Ensure that you perform access control checks related to your business logic. These checks may be different than the access control checks that you apply to more generic resources such as files, connections, processes, memory, and database records. For example, a database may restrict access for medical records to a specific database user, but each record might only be intended to be accessible to the patient and the patient's doctor.
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리·프레임워크를 쓴다. 예를 들어 JAAS Authorization Framework [REF-233]나 OWASP ESAPI Access Control 기능 [REF-45] 같은 인가 프레임워크 사용을 고려한다.
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, consider using authorization frameworks such as the JAAS Authorization Framework [REF-233] and the OWASP ESAPI Access Control feature [REF-45].
    아키텍처·설계(Architecture and Design) — 웹 애플리케이션은 모든 페이지에서 서버 측 접근 통제가 올바르게 강제되게 하여, 사용자가 페이지를 직접 요청하는 것만으로 인가되지 않은 기능·정보에 접근할 수 없어야 한다. 한 가지 방법은 민감한 정보가 있는 모든 페이지를 캐시하지 않고, 그 페이지에 필요한 권한을 가진 사용자의 인증된 활성 세션 토큰이 함께 온 요청만 허용하는 것이다.
    원문

    For web applications, make sure that the access control mechanism is enforced correctly at the server side on every page. Users should not be able to access any unauthorized functionality or information by simply requesting direct access to that page.

    One way to do this is to ensure that all pages containing sensitive information are not cached, and that all such pages restrict access to requests that are accompanied by an active and authenticated session token associated with a user who has the required permissions to access that page.

    통합 및 시험 (본문 제6장)¶

    CWE 단계(Phase) 전략 요지
    시스템 구성(System Configuration) / 설치(Installation) — 운영체제와 서버 환경의 접근 통제 기능을 활용해 접근 통제 목록(ACL)을 정의하고, ACL을 정의할 때 '기본 거부(default deny)' 정책을 쓴다. (유지보수 단계에도 해당)

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 운용자 콘솔이 임무 데이터 삭제·정비 기록 삭제·항법 설정 초기화 같은 중요 명령을 받는다. 요청한 사용자는 이미 로그인(인증)했지만 역할은 관찰자·운용자·정비자로 다르며, 설계상 정비자만 이 명령을 실행할 수 있다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <stddef.h>

typedef enum { ROLE_OBSERVER, ROLE_OPERATOR, ROLE_MAINTAINER } Role;

typedef struct {
    const char *user;
    Role role;
    int logged_in;             /* 인증은 이미 끝난 세션 */
} Session;

static const char *ROLE_NAME[] = { "OBSERVER", "OPERATOR", "MAINTAINER" };

/* 임무 데이터 일괄 삭제: 중요 명령 */
static const char *purge_mission_data(const Session *s)
{
    if (!s->logged_in) {
        return "DENIED (login required)";
    }
    /* 로그인 여부만 보고, 이 역할에 삭제 권한이 있는지는 확인하지 않는다 */
    return "EXECUTED";
}

int main(void)
{
    const Session users[] = {
        { "obs01", ROLE_OBSERVER, 1 },
        { "mnt07", ROLE_MAINTAINER, 1 },
    };
    for (size_t i = 0; i < sizeof users / sizeof users[0]; ++i) {
        printf("user=%s role=%s cmd=PURGE_MISSION -> %s\n", users[i].user,
               ROLE_NAME[users[i].role], purge_mission_data(&users[i]));
    }
    return 0;
}

    로그인(인증) 여부만 확인하고 요청자 역할에 삭제 권한이 있는지는 확인하지 않아, 관찰자도 임무 데이터를 지울 수 있다. 인증은 '누구인가', 인가는 '이 일을 해도 되는가'를 따로 확인해야 한다.

    좋은 예

    #include <stdio.h>
#include <stddef.h>

typedef enum { ROLE_OBSERVER, ROLE_OPERATOR, ROLE_MAINTAINER, ROLE_COUNT } Role;
typedef enum { CMD_VIEW_STATUS = 1u << 0, CMD_LOAD_PLAN = 1u << 1, CMD_PURGE_MISSION = 1u << 2 } Command;

typedef struct {
    const char *user;
    Role role;
    int logged_in;
} Session;

static const char *ROLE_NAME[ROLE_COUNT] = { "OBSERVER", "OPERATOR", "MAINTAINER" };

/* 설계 단계에서 정한 권한 매트릭스: 역할별로 허용한 명령만 1 */
static const unsigned PERMITTED[ROLE_COUNT] = {
    [ROLE_OBSERVER]   = CMD_VIEW_STATUS,
    [ROLE_OPERATOR]   = CMD_VIEW_STATUS | CMD_LOAD_PLAN,
    [ROLE_MAINTAINER] = CMD_VIEW_STATUS | CMD_LOAD_PLAN | CMD_PURGE_MISSION,
};

/* 모든 명령 진입점이 부르는 공통 인가 함수: 모르는 값은 거부(default deny) */
static int authorized(const Session *s, Command cmd)
{
    if (!s->logged_in || (unsigned)s->role >= ROLE_COUNT) {
        return 0;
    }
    return (PERMITTED[s->role] & (unsigned)cmd) != 0;
}

static const char *purge_mission_data(const Session *s)
{
    if (!authorized(s, CMD_PURGE_MISSION)) {
        return "DENIED (role not permitted)";
    }
    return "EXECUTED";
}

int main(void)
{
    const Session users[] = {
        { "obs01", ROLE_OBSERVER, 1 },
        { "mnt07", ROLE_MAINTAINER, 1 },
    };
    for (size_t i = 0; i < sizeof users / sizeof users[0]; ++i) {
        printf("user=%s role=%s cmd=PURGE_MISSION -> %s\n", users[i].user,
               ROLE_NAME[users[i].role], purge_mission_data(&users[i]));
    }
    return 0;
}

    설계 단계에서 정한 역할별 권한 매트릭스를 표로 두고, 모든 명령 진입점이 같은 인가 함수를 거치게 한다(D-04). 범위를 벗어난 역할 값이나 표에 없는 명령은 거부한다(기본 거부).

    #include <iostream>
#include <map>
#include <set>
#include <string>
#include <vector>

enum class Role { Observer, Operator, Maintainer };
enum class Command { ViewStatus, LoadPlan, PurgeMission };

// 요청 메시지에는 명령만 담는다. 신원과 역할은 메시지로 받지 않는다
struct Request {
    Command cmd;
};

// 인증 때 장비가 연결에 묶어 둔 세션(요청 메시지로 바꿀 수 없다)
struct Session {
    std::string user;
    Role role;
};

// 명령별 허용 역할도 장비 쪽 한 곳에 둔다
const std::map<Command, std::set<Role>> kPolicy{
    {Command::ViewStatus, {Role::Observer, Role::Operator, Role::Maintainer}},
    {Command::LoadPlan, {Role::Operator, Role::Maintainer}},
    {Command::PurgeMission, {Role::Maintainer}},
};

const char *role_text(Role r) {
    return r == Role::Observer ? "OBSERVER" : r == Role::Operator ? "OPERATOR" : "MAINTAINER";
}

// peer는 메시지가 들어온 연결의 세션이다. 인증하지 않은 연결이면 nullptr이다
std::string handle(const Session *peer, const Request &rq) {
    if (peer == nullptr) return "DENIED (no session)";
    auto p = kPolicy.find(rq.cmd);
    if (p == kPolicy.end() || p->second.count(peer->role) == 0) {  // 표에 없으면 거부
        return std::string("DENIED (role ") + role_text(peer->role) + " not permitted)";
    }
    return rq.cmd == Command::PurgeMission ? "EXECUTED" : "DONE";
}

int main() {
    const Session observer{"obs01", Role::Observer};
    const Session maintainer{"mnt07", Role::Maintainer};
    struct Incoming {
        const Session *peer;
        Request rq;
    };
    // 관찰자가 명령 메시지를 직접 보내거나, 인증하지 않은 연결에서 보내도 거부된다
    std::vector<Incoming> inbox{{&observer, {Command::PurgeMission}}, {nullptr, {Command::PurgeMission}},
                                {&maintainer, {Command::PurgeMission}}};
    for (const auto &in : inbox) {
        std::cout << "user=" << (in.peer != nullptr ? in.peer->user : "-") << " cmd=PURGE_MISSION -> "
                  << handle(in.peer, in.rq) << '\n';
    }
    return 0;
}

    요청 메시지에는 명령만 담고, 신원과 역할은 장비 쪽 세션(인증 때 연결에 묶어 둔 값)에서 가져온다. 메시지 안의 역할 값이나 사용자 이름은 보내는 쪽이 바꿀 수 있기 때문이다. 세션은 인증된 연결(또는 추측할 수 없는 세션 토큰)로 찾으며, 메시지에 적힌 사용자 이름으로 찾지 않는다. 명령별 허용 역할도 장비 쪽 정책 표 한 곳에 두고 처리 전에 확인하며, 세션이 없거나 표에 없는 명령·역할 조합은 거부한다.

    하위 역할 계정으로 상위 역할 전용 명령을 화면을 거치지 않고 메시지로 직접 보내 실행되는지 시험한다. T-06 [예시] CWE-285 예시 검증(관찰자·운용자 역할로 삭제·초기화 명령 실행 확인)

    유지보수 기능 추가 시 권한 매트릭스를 갱신하고 인가 누락 여부를 회귀시험(regression test)한다.
