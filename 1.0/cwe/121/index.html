    Stack-based Buffer Overflow

    항목 내용
    추상화 수준 변형(Variant)
    상태 초안(Draft)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++ · 기술 무관
    원문 MITRE CWE-121 (CWE 5.0)

    한 줄 요약

    스택에 할당된 버퍼의 끝을 지나 쓰는 약점이다.

    설명(Description)¶

    제품이 스택에 할당된 버퍼의 끝을 지나 쓰는 약점이다.

    배경(Background Details)

    실행 스택에는 일반적으로 임의 코드 실행으로 이어질 수 있는 보안상 중요한 데이터가 여럿 있다. 가장 대표적인 것은 저장된 복귀 주소로, 현재 함수의 실행이 끝난 뒤 실행을 이어 갈 메모리 주소다. 공격자는 이 값을 자신이 쓰기 권한도 가진 메모리 주소로 덮어쓰고, 그곳에 취약한 프로그램의 전체 권한으로 실행될 임의 코드를 넣을 수 있다. 또는 공격자가 POSIX system() 호출 같은 중요한 호출의 주소를 넣고 호출 인자를 스택에 남겨 둘 수 있다. 공격자가 대개 복귀 시점에 프로그램을 C 표준 라이브러리(libc)의 쓸모 있는 루틴으로 점프하게 만들기 때문에, 이 방식을 흔히 return into libc 공격(exploit)이라 부른다. 스택에 흔히 있는 다른 중요 데이터로는 메모리 주소 계산의 오프셋을 나타내는 스택 포인터와 프레임 포인터가 있다. 이 값을 수정하면 흔히 "write-what-where" 상태로 이어지게 악용할 수 있다.

    원문(Description · Background Details)

    The product writes past the end of a buffer that was allocated on the stack.

    There are generally several security-critical data on an execution stack that can lead to arbitrary code execution. The most prominent is the stored return address, the memory address at which execution should continue once the current function is finished executing. The attacker can overwrite this value with some memory address to which the attacker also has write access, into which they place arbitrary code to be run with the full privileges of the vulnerable program. Alternately, the attacker can supply the address of an important call, for instance the POSIX system() call, leaving arguments to the call on the stack. This is often called a return into libc exploit, since the attacker generally forces the program to jump at return time into an interesting routine in the C standard library (libc). Other important data commonly on the stack include the stack pointer and frame pointer, two values that indicate offsets for computing memory addresses. Modifying those values can often be leveraged into a "write-what-where" condition.

    영역 영향 설명
    가용성 메모리 수정 / 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 자원 소모(CPU) / 서비스 거부: 자원 소모(메모리) 버퍼 오버플로는 대개 비정상 종료로 이어지며, 프로그램을 무한 루프에 빠뜨리는 등 가용성을 떨어뜨리는 다른 공격도 가능하다.
    무결성 / 기밀성 / 가용성 / 접근 통제 메모리 수정 / 허가되지 않은 코드·명령 실행 / 보호 메커니즘 우회 버퍼 오버플로는 흔히 임의 코드 실행에 쓰일 수 있으며, 이는 대개 프로그램의 암묵적 보안 정책 범위를 벗어난다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 일부 컴파일러나 컴파일러 확장이 제공하는 자동 버퍼 오버플로 탐지 기능을 쓴다. 예로 Microsoft Visual Studio의 /GS 플래그, Fedora/Red Hat의 FORTIFY_SOURCE GCC 플래그, StackGuard, ProPolice가 있으며 카나리 기반 탐지와 범위·인덱스 검사 등을 제공한다(카나리 기반 탐지는 D3FEND D3-SFCV [REF-1334] 참고). (유지보수 단계에도 해당)
    원문

    Use automatic buffer overflow detection mechanisms that are offered by certain compilers or compiler extensions. Examples include: the Microsoft Visual Studio /GS flag, Fedora/Red Hat FORTIFY_SOURCE GCC flag, StackGuard, and ProPolice, which provide various mechanisms including canary-based detection and range/index checking.

    D3-SFCV (Stack Frame Canary Validation) from D3FEND [REF-1334] discusses canary-based detection in detail.

    		 심층 방어(Defense in Depth) — 이 기능들은 일부 유형의 오버플로만 탐지하므로 반드시 완전한 해결책은 아니다. 또한 대개 애플리케이션을 종료하는 방식으로 대응하므로 결과는 여전히 서비스 거부다.
    구현(Implementation) — 입력에 대한 경계 검사를 구현하고 수행한다.
    원문

    Implement and perform bounds checking on input.

    		 —
    구현(Implementation) — gets 같은 위험한 함수를 쓰지 않고, 경계 오류를 검사하는 더 안전한 대체 함수를 쓴다.
    원문

    Do not use dangerous functions such as gets. Use safer, equivalent functions which check for boundary errors.

    		 —
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 프로그램의 실행 파일과 라이브러리를 메모리에 무작위로 배치하는 기능이나 확장을 써서 실행·컴파일한다. 주소를 예측할 수 없게 되어 공격자가 악용할 코드로 안정적으로 점프하는 것을 막을 수 있다. 예로 ASLR(Address Space Layout Randomization) [REF-58] [REF-60]과 PIE(Position-Independent Executables) [REF-64]가 있다. 가져온 모듈도 기본 메모리 주소가 다른 모듈과 겹치면 무작위로 만든 주소로 재배치될 수 있다(Windows의 rebasing, Linux의 prelinking [REF-1332]). 단, 라이브러리용 ASLR은 실행 시 라이브러리를 재배치해야 해서 prelink의 목적을 없애므로 prelink와 함께 쓸 수 없다. 자세한 내용은 D3FEND의 D3-SAOR(Segment Address Offset Randomization) [REF-1335]에 있다. (유지보수 단계에도 해당)
    원문

    Run or compile the software using features or extensions that randomly arrange the positions of a program's executable and libraries in memory. Because this makes the addresses unpredictable, it can prevent an attacker from reliably jumping to exploitable code.

    Examples include Address Space Layout Randomization (ASLR) [REF-58] [REF-60] and Position-Independent Executables (PIE) [REF-64]. Imported modules may be similarly realigned if their default memory addresses conflict with other modules, in a process known as "rebasing" (for Windows) and "prelinking" (for Linux) [REF-1332] using randomly generated addresses. ASLR for libraries cannot be used in conjunction with prelink since it would require relocating the libraries at run-time, defeating the whole purpose of prelinking.

    For more information on these techniques see D3-SAOR (Segment Address Offset Randomization) from D3FEND [REF-1335].

    		 심층 방어(Defense in Depth) — 이 기법들은 완전한 해결책이 아니다. 예를 들어 익스플로잇은 코드 실행의 신뢰성을 높이려고 메모리 주소를 노출하는 버그를 흔히 이용하며 [REF-1337], 부채널 공격으로 ASLR을 우회할 수 있음도 밝혀졌다 [REF-1333].

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. While buffer overflow examples can be rather complex, it is possible to have very simple, yet still exploitable, stack-based buffer overflows:

    Bad / C

    #define BUFSIZE 256
int main(int argc, char **argv) {
  char buf[BUFSIZE];
  strcpy(buf, argv[1]);
}

    The buffer size is fixed, but there is no guarantee the string in argv[1] will not exceed this size and cause an overflow.

    Example 2. This example takes an IP address from a user, verifies that it is well formed and then looks up the hostname and copies it into a buffer.

    Bad / C

    void host_lookup(char *user_supplied_addr){

  struct hostent *hp;
  in_addr_t *addr;
  char hostname[64];
  in_addr_t inet_addr(const char *cp);

                             /*routine that ensures user_supplied_addr is in the right format for conversion */

  validate_addr_form(user_supplied_addr);
  addr = inet_addr(user_supplied_addr);
  hp = gethostbyaddr( addr, sizeof(struct in_addr), AF_INET);
  strcpy(hostname, hp->h_name);

}

    This function allocates a buffer of 64 bytes to store the hostname, however there is no guarantee that the hostname will not be larger than 64 bytes. If an attacker specifies an address which resolves to a very large hostname, then the function may overwrite sensitive data or even relinquish control flow to the attacker.

    Note that this example also contains an unchecked return value (CWE-252) that can lead to a NULL pointer dereference (CWE-476).

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법(원문 효과성별): 높음: 퍼징(Fuzzing) / 보통: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: ARR38-C, STR31-C

    이 가이드에서 다루는 곳¶

    언어 뷰 항목의 단계별 지침 (적용성 판정 기준은 부록 B, 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 스택 영역에 두는 버퍼의 최대 크기를 제한하고, 외부 입력으로 크기가 정해지는 데이터는 정적 할당 버퍼로 설계한다.
    구현 지역 배열에 gets/strcpy/sprintf 사용을 금지하고 경계 지정 함수와 입력 길이 검증을 적용하며, 가변 길이 배열(VLA)과 alloca 사용을 금지한다.
    통합 및 시험 -fstack-protector-strong -D_FORTIFY_SOURCE=2로 빌드하고 AddressSanitizer, 퍼징으로 스택 오버플로를 탐지하며 cppcheck로 지역 버퍼 접근을 점검한다.
    유지보수 스택 크기·지역 버퍼 선언 변경 시 스택 사용량을 재측정하고, 운용 중 스택 카나리 위반 로그를 분석하여 패치에 반영한다.
    임베디드 고려 MCU는 MMU가 없고 스택이 작아 오버플로가 복귀 주소 변조로 이어지기 쉬우므로 입력 경계 검사를 코드로 강제한다. 스택 워터마크 페인팅, RTOS 스택 오버플로 훅, MPU 스택 가드 영역은 스택 고갈을 잡는 수단으로 따로 적용한다.

    기준선 활동 2건

    • I-08 컴파일러 경고·빌드 하드닝 (구현)
    • T-07 타깃 자원·장시간 시험 (통합 및 시험)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 20건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
