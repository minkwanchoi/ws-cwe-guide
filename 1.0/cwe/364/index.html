    Signal Handler Race Condition

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 조건부 — 시그널(POSIX signal) 사용
    적용 플랫폼 언어: C, C++
    원문 MITRE CWE-364 (CWE 5.0)

    한 줄 요약

    경쟁조건을 일으키는 시그널 핸들러를 사용하는 약점이다.

    설명(Description)¶

    제품이 경쟁조건(race condition)을 일으키는 시그널 핸들러를 사용하는 약점이다. 이 문제는 언제든 호출될 수 있는 시그널 핸들러 안에서 재진입 불가능한(non-reentrant) 함수나 상태에 민감한 동작을 수행할 때 생기며, 중단된 '일반' 코드나 함께 호출될 수 있는 다른 시그널 핸들러의 가정을 어길 수 있다. 예를 들어 재진입 불가능한 함수가 이미 실행 중일 때 호출되면 코드 실행에 악용될 수 있는 메모리 손상이 생길 수 있고, 시그널 핸들러 안에서 free()를 호출하면 이중 해제와 임의 위치 쓰기 조건(write-what-where)이 생길 수 있으며, 해제 뒤 포인터를 NULL로 설정해도 해제 시점과 NULL 설정 시점 사이에 경쟁조건이 남는다. 같은 시그널 핸들러를 둘 이상의 시그널에 설정하면 핸들러 자체가 재진입될 수 있어 특히 문제가 된다. '시그널 핸들러 경쟁조건'으로 불리는 동작은 여럿 알려져 있다. 시그널 핸들러와 일반 코드가 함께 접근하는 공유 상태(전역 데이터·정적 변수 등)와 시그널 핸들러끼리의 공유 상태가 그 예다. 시그널 핸들러 안에서 재진입 불가능한 기능을 쓰는 것도 여기에 들며, 이는 대개 공유 상태를 쓴다는 뜻이다. 예를 들어 malloc()·free()는 메모리 관리에 전역·정적 자료구조를 쓸 수 있어 재진입 불가능하고, syslog()처럼 무해해 보이는 함수도 이를 간접적으로 쓴다. 이런 함수는 메모리 손상과, 경우에 따라 코드 실행에 악용될 수 있다. 같은 시그널 핸들러 함수를 여러 시그널에 연결하면 같은 코드와 자원에 접근하므로 공유 상태를 뜻할 수 있고, 이중 해제·해제된 자원 사용 약점의 원인이 될 수 있다. setjmp·longjmp처럼 핸들러가 원래 기능으로 제어를 돌려주지 못하게 하는 메커니즘을 쓰는 것도 여기에 든다. 엄밀히 경쟁조건은 아니지만, 최대 한 번만 호출되도록 설계된 일부 핸들러는 동시 호출이 없어도 여러 번 호출되면 보안 문제를 일으킬 수 있고 이중 해제·해제된 자원 사용 약점의 원인이 될 수 있다. 이런 취약점은 흔히 특정 보호 메커니즘의 부재로 분류되지만, 프로그래머가 여러 메커니즘 가운데 고를 수 있는 경우가 많아 CWE는 이런 분류를 권장하지 않는다. 보호 메커니즘은 공유 자원 접근의 배타성과 관련 코드의 동작상 원자성을 유지할 수 있다. 공유 상태 피하기, 시그널 핸들러에서 동기화 사용, 일반 코드에서 동기화 사용, 다른 시그널을 비활성화하거나 마스킹해 원자성(사실상 배타성)을 얻는 방법이 있다.

    원문(Description · Extended Description)

    The product uses a signal handler that introduces a race condition.

    These issues occur when non-reentrant functions, or state-sensitive actions occur in the signal handler, where they may be called at any time. These behaviors can violate assumptions being made by the "regular" code that is interrupted, or by other signal handlers that may also be invoked. If these functions are called at an inopportune moment - such as while a non-reentrant function is already running - memory corruption could occur that may be exploitable for code execution. Another signal race condition commonly found occurs when free() is called within a signal handler, resulting in a double free and therefore a write-what-where condition. Even if a given pointer is set to NULL after it has been freed, a race condition still exists between the time the memory was freed and the pointer was set to NULL. This is especially problematic if the same signal handler has been set for more than one signal -- since it means that the signal handler itself may be reentered.

    There are several known behaviors related to signal handlers that have received the label of "signal handler race condition":

    - Shared state (e.g. global data or static variables) that are accessible to both a signal handler and "regular" code

    - Shared state between a signal handler and other signal handlers

    - Use of non-reentrant functionality within a signal handler - which generally implies that shared state is being used. For example, malloc() and free() are non-reentrant because they may use global or static data structures for managing memory, and they are indirectly used by innocent-seeming functions such as syslog(); these functions could be exploited for memory corruption and, possibly, code execution.

    - Association of the same signal handler function with multiple signals - which might imply shared state, since the same code and resources are accessed. For example, this can be a source of double-free and use-after-free weaknesses.

    - Use of setjmp and longjmp, or other mechanisms that prevent a signal handler from returning control back to the original functionality

    - While not technically a race condition, some signal handlers are designed to be called at most once, and being called more than once can introduce security problems, even when there are not any concurrent calls to the signal handler. This can be a source of double-free and use-after-free weaknesses.

    Signal handler vulnerabilities are often classified based on the absence of a specific protection mechanism, although this style of classification is discouraged in CWE because programmers often have a choice of several different mechanisms for addressing the weakness. Such protection mechanisms may preserve exclusivity of access to the shared resource, and behavioral atomicity for the relevant code:

    - Avoiding shared state

    - Using synchronization in the signal handler

    - Using synchronization in the regular code

    - Disabling or masking other signals, which provides atomicity (which effectively ensures exclusivity)

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 애플리케이션 데이터 수정 / 메모리 수정 / 서비스 거부: 비정상 종료·재시작 / 허가되지 않은 코드·명령 실행 공격자가 시그널 핸들러 경쟁조건을 악용해 제품 상태를 손상시킬 수 있다. 예상하지 못한 시점에 전역 변수나 데이터 구조를 수정해 그 전역 데이터를 쓰는 코드의 가정을 어기게 하면 임의 코드를 실행할 수도 있다.
    접근 통제 권한 획득 또는 신원 도용 시그널 핸들러가 특권으로 실행 중인 코드를 중단시키면 핸들러도 높은 권한으로 실행될 수 있어, 이후 공격의 피해가 더 커질 수 있다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 시그널 핸들러는 복잡한 기능을 수행하지 말고 플래그만 설정하도록 설계하며, 그 플래그는 주 프로그램 루프에서 확인해 처리할 수 있다.
    원문

    Design signal handlers to only set flags, rather than perform complex functionality. These flags can then be checked and acted upon within the main program loop.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 시그널 핸들러 안에서는 재진입 가능한 함수만 쓰고, 실행 상태에 영향을 주는 비동기 동작을 수행하는 동안 상태가 일관된지 검증한다.
    원문

    Only use reentrant functions within signal handlers. Also, use validation to ensure that state is consistent while performing asynchronous actions that affect the state of execution.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. This code registers the same signal handler function with two different signals (CWE-831). If those signals are sent to the process, the handler creates a log message (specified in the first argument to the program) and exits.

    Bad / C

    char *logMessage;

void handler (int sigNum) {

  syslog(LOG_NOTICE, "%s\n", logMessage);
  free(logMessage);

                             /* artificially increase the size of the timing window to make demonstration of this weakness easier. */

  sleep(10);
  exit(0);

}

int main (int argc, char* argv[]) {

  logMessage = strdup(argv[1]);

                             /* Register signal handlers. */

  signal(SIGHUP, handler);
  signal(SIGTERM, handler);

                             /* artificially increase the size of the timing window to make demonstration of this weakness easier. */

  sleep(10);

}

    The handler function uses global state (globalVar and logMessage), and it can be called by both the SIGHUP and SIGTERM signals. An attack scenario might follow these lines:

    The program begins execution, initializes logMessage, and registers the signal handlers for SIGHUP and SIGTERM. The program begins its "normal" functionality, which is simplified as sleep(), but could be any functionality that consumes some time. The attacker sends SIGHUP, which invokes handler (call this "SIGHUP-handler"). SIGHUP-handler begins to execute, calling syslog(). syslog() calls malloc(), which is non-reentrant. malloc() begins to modify metadata to manage the heap. The attacker then sends SIGTERM. SIGHUP-handler is interrupted, but syslog's malloc call is still executing and has not finished modifying its metadata. The SIGTERM handler is invoked. SIGTERM-handler records the log message using syslog(), then frees the logMessage variable.

    At this point, the state of the heap is uncertain, because malloc is still modifying the metadata for the heap; the metadata might be in an inconsistent state. The SIGTERM-handler call to free() is assuming that the metadata is inconsistent, possibly causing it to write data to the wrong location while managing the heap. The result is memory corruption, which could lead to a crash or even code execution, depending on the circumstances under which the code is running.

    Note that this is an adaptation of a classic example as originally presented by Michal Zalewski [REF-360]; the original example was shown to be exploitable for code execution.

    Also note that the strdup(argv[1]) call contains a potential buffer over-read (CWE-126) if the program is called without any arguments, because argc would be 0, and argv[1] would point outside the bounds of the array.

    Example 2. The following code registers a signal handler with multiple signals in order to log when a specific event occurs and to free associated memory before exiting.

    Bad / C

    #include <signal.h>
#include <syslog.h>
#include <string.h>
#include <stdlib.h>

void *global1, *global2;
char *what;
void sh (int dummy) {

  syslog(LOG_NOTICE,"%s\n",what);
  free(global2);
  free(global1);

                             /* Sleep statements added to expand timing window for race condition */

  sleep(10);
  exit(0);

}

int main (int argc,char* argv[]) {

  what=argv[1];
  global1=strdup(argv[2]);
  global2=malloc(340);
  signal(SIGHUP,sh);
  signal(SIGTERM,sh);

                             /* Sleep statements added to expand timing window for race condition */

  sleep(10);
  exit(0);

}

    However, the following sequence of events may result in a double-free (CWE-415):

    a SIGHUP is delivered to the process sh() is invoked to process the SIGHUP This first invocation of sh() reaches the point where global1 is freed At this point, a SIGTERM is sent to the process the second invocation of sh() might do another free of global1 this results in a double-free (CWE-415)

    This is just one possible exploitation of the above code. As another example, the syslog call may use malloc calls which are not async-signal safe. This could cause corruption of the heap management structures. For more details, consult the example within "Delivering Signals for Fun and Profit" [REF-360].

    탐지 방법(Detection Methods)¶

    방법 요지
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법은 자동 정적 분석뿐이다. 다른 정적 분석 도구·컴파일러 경고로 점검한다.

    단계 지침
    요구사항 분석 원문 완화책(요구사항) 1건 → 완화책
    설계 시그널 핸들러는 플래그 설정만 수행하고 실제 처리는 메인 루프에서 수행하도록 설계한다.
    구현 핸들러에서는 volatile sig_atomic_t 변수만 갱신하고 async-signal-safe 함수만 호출하며, sigaction과 시그널 마스크로 재진입을 제어한다.
    통합 및 시험 정적 분석 도구(예: clang-tidy cert-sig30-c, Coverity)로 핸들러 내 안전하지 않은 호출을 탐지하고 시그널 연속 전송 스트레스 시험을 수행한다.
    유지보수 핸들러 변경 시 호출 함수의 async-signal-safe 여부를 재확인하고 운용 중 교착·데이터 손상 사례를 분석한다.
    임베디드 고려 베어메탈/RTOS에서는 ISR이 시그널 핸들러에 상응하므로 ISR은 최소 처리 후 플래그·큐 전달만 수행하고 공유 변수는 volatile과 원자 접근으로 보호한다.

    기준선 활동 1건

    • I-07 동시성·공유자원 보호 (구현)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    관찰 사례(원문 Observed Examples 5건, 요지는 한글 요약이고 원문은 접은 상자)

    참조 요지
    CVE-1999-0035 시그널 핸들러가 다른 시그널 핸들러를 비활성화하지 않아 실행 중에 중단될 수 있고, 그 때문에 다른 기능이 높아진 권한으로 파일 등에 접근하게 된다.
    원문

    Signal handler does not disable other signal handlers, allowing it to be interrupted, causing other functionality to access files/etc. with raised privileges
    CVE-2001-0905 다른 시그널 핸들러가 이미 실행 중일 때 공격자가 시그널을 보낼 수 있어 비정상 종료나 root 권한 실행으로 이어진다.
    원문

    Attacker can send a signal while another signal handler is already running, leading to crash or execution with root privileges
    CVE-2001-1349 시그널 핸들러에서 라이브러리 함수를 안전하지 않게 호출한다.
    원문

    unsafe calls to library functions from signal handler
    CVE-2004-0794 SIGURG로 시그널 핸들러를 원격에서 중단시킬 수 있으며, 다른 변형도 있다.
    원문

    SIGURG can be used to remotely interrupt signal handler; other variants exist.
    CVE-2004-2259 부하가 높을 때 FTP 서버가 malloc/free 같은 비재진입 함수를 실행하는 중 SIGCHLD 시그널을 받으면 비정상 종료될 수 있다.
    원문

    SIGCHLD signal to FTP server can cause crash under heavy load while executing non-reentrant functions like malloc/free.
