    Improper Validation of Array Index

    항목 내용
    추상화 수준 변형(Variant)
    상태 초안(Draft)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, C, C++
    원문 MITRE CWE-129 (CWE 5.0)

    한 줄 요약

    신뢰할 수 없는 입력으로 배열 인덱스를 계산·사용하면서 인덱스가 유효한 위치인지 검증하지 않거나 잘못 검증하는 약점이다.

    설명(Description)¶

    제품이 배열 인덱스를 계산하거나 사용할 때 신뢰할 수 없는 입력을 쓰지만, 그 인덱스가 배열 안의 유효한 위치를 가리키는지 확인하는 검증을 하지 않거나 잘못하는 약점이다.

    원문(Description)

    The product uses untrusted input when calculating or using an array index, but the product does not validate or incorrectly validates the index to ensure the index references a valid position within the array.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 가용성 서비스 거부: 비정상 종료·재시작 배열 경계를 벗어난 인덱스를 쓰면 관련 메모리와 어쩌면 명령어까지 손상될 가능성이 매우 높으며, 값이 유효한 메모리 영역 밖이면 비정상 종료로 이어진다.
    무결성 메모리 수정 손상된 메모리가 명령어가 아니라 데이터이면 시스템은 잘못된 값으로 계속 동작한다.
    기밀성 / 무결성 메모리 수정 / 메모리 읽기 배열 경계를 벗어난 인덱스 사용은 범위 밖 읽기·쓰기나 잘못된 객체에 대한 연산을 일으킬 수도 있으며(즉 결과가 늘 '버퍼 오버플로'인 것은 아니다), 그 결과 민감한 데이터가 노출되거나 변경될 수 있다.
    무결성 / 기밀성 / 가용성 허가되지 않은 코드·명령 실행 공격자가 접근할 수 있는 메모리를 효과적으로 제어할 수 있으면 일반 버퍼 오버플로처럼 임의 코드를 실행할 수 있으며, 정확한 인덱스를 제어할 수 있다면 큰 입력 없이도 가능할 수 있다.
    무결성 / 가용성 / 기밀성 서비스 거부: 비정상 종료·재시작 / 허가되지 않은 코드·명령 실행 / 메모리 읽기 / 메모리 수정 하나의 결함이 배열 인덱스의 오버플로(CWE-788)나 언더플로(CWE-786)를 일으킬 수 있으며, 그 뒤의 결과는 범위 밖에서 수행되는 연산 유형에 따라 다르지만 민감한 정보 노출, 시스템 비정상 종료, 또는 임의 코드 실행으로 이어질 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 9건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    CWE 단계(Phase) 전략 요지 효과성
    요구사항(Requirements) 언어 선택 이 약점이 생기지 않게 하거나 이 약점을 피하기 쉬운 구조를 제공하는 언어를 쓴다. 예를 들어 Ada는 변수 값의 범위를 제약할 수 있고, Java와 Ruby 같은 언어는 범위를 벗어난 인덱스에 접근할 때 예외를 처리할 수 있게 한다.
    원문

    Use a language that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, Ada allows the programmer to constrain the values of a variable and languages such as Java and Ruby will allow the programmer to handle exceptions when an out-of-bounds index is accessed.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) 입력값 검증 Struts나 OWASP ESAPI Validation API 같은 입력값 검증 프레임워크를 쓴다. 단, 프레임워크를 쓴다고 모든 입력값 검증 문제가 자동으로 해결되지는 않으므로 프레임워크 자체를 잘못 써서 생길 수 있는 약점(CWE-1173)에 유의한다.
    원문

    Use an input validation framework such as Struts or the OWASP ESAPI Validation API. Note that using a framework does not automatically address all input validation problems; be mindful of weaknesses that could arise from misusing the framework itself (CWE-1173).

    		 —
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해 CWE-602를 피한다. 공격자는 검사가 끝난 뒤 값을 바꾸거나 클라이언트를 고쳐 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있다. 클라이언트 측 검사는 서버 측 보안에는 이점이 작지만 여전히 쓸모가 있다. 침입 탐지에 쓸 수 있고(클라이언트가 거부했어야 할 입력이 서버에 오면 공격 징후일 수 있다), 사용자에게 유효한 입력의 조건을 알려 줄 수 있으며, 실수로 생긴 입력 오류의 서버 처리 시간을 줄일 수 있다(대개 절감 폭은 작다).
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.

    Even though client-side checks provide minimal benefits with respect to server-side security, they are still useful. First, they can support intrusion detection. If the server receives input that should have been rejected by the client, then it may be an indication of an attack. Second, client-side error-checking can provide helpful feedback to the user about the expectations for valid input. Third, there may be a reduction in server-side processing time for accidental input errors, although this is typically a small savings.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 실행 환경 강화 작업에 필요한 최소 권한으로 코드를 실행하고 [REF-76], 가능하면 한 작업에만 쓰는 제한된 권한의 격리된 계정을 만들어 공격이 성공해도 나머지 소프트웨어나 환경에 바로 접근하지 못하게 한다(예: 데이터베이스 애플리케이션은 특히 일상 운영에서 데이터베이스 관리자 권한으로 실행할 필요가 거의 없다). (유지보수 단계에도 해당)
    원문

    Run your code using the lowest privileges that are required to accomplish the necessary tasks [REF-76]. If possible, create isolated accounts with limited privileges that are only used for a single task. That way, a successful attack will not immediately give the attacker access to the rest of the software or its environment. For example, database applications rarely need to run as the database administrator, especially in day-to-day operations.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 프로그램의 실행 파일과 라이브러리를 메모리에 무작위로 배치하는 기능이나 확장을 써서 실행·컴파일한다. 주소를 예측할 수 없게 되어 공격자가 악용할 코드로 안정적으로 점프하는 것을 막을 수 있다. 예로 ASLR(Address Space Layout Randomization) [REF-58] [REF-60]과 PIE(Position-Independent Executables) [REF-64]가 있다. 가져온 모듈도 기본 메모리 주소가 다른 모듈과 겹치면 무작위로 만든 주소로 재배치될 수 있다(Windows의 rebasing, Linux의 prelinking [REF-1332]). 단, 라이브러리용 ASLR은 실행 시 라이브러리를 재배치해야 해서 prelink의 목적을 없애므로 prelink와 함께 쓸 수 없다. 자세한 내용은 D3FEND의 D3-SAOR(Segment Address Offset Randomization) [REF-1335]에 있다. (유지보수 단계에도 해당)
    원문

    Run or compile the software using features or extensions that randomly arrange the positions of a program's executable and libraries in memory. Because this makes the addresses unpredictable, it can prevent an attacker from reliably jumping to exploitable code.

    Examples include Address Space Layout Randomization (ASLR) [REF-58] [REF-60] and Position-Independent Executables (PIE) [REF-64]. Imported modules may be similarly realigned if their default memory addresses conflict with other modules, in a process known as "rebasing" (for Windows) and "prelinking" (for Linux) [REF-1332] using randomly generated addresses. ASLR for libraries cannot be used in conjunction with prelink since it would require relocating the libraries at run-time, defeating the whole purpose of prelinking.

    For more information on these techniques see D3-SAOR (Segment Address Offset Randomization) from D3FEND [REF-1335].

    		 심층 방어(Defense in Depth) — 이 기법들은 완전한 해결책이 아니다. 예를 들어 익스플로잇은 코드 실행의 신뢰성을 높이려고 메모리 주소를 노출하는 버그를 흔히 이용하며 [REF-1337], 부채널 공격으로 ASLR을 우회할 수 있음도 밝혀졌다 [REF-1333].
    구현(Implementation) 입력값 검증 모든 입력을 악의적이라고 가정하고, 명세에 엄격히 맞는 입력만 받는 허용목록('accept known good') 방식으로 검증해 맞지 않는 입력은 거부하거나 맞게 변환한다. 검증할 때는 길이·유형·허용 값 전체 범위·누락/추가 입력·구문·관련 필드 간 일관성·업무 규칙을 모두 고려한다(예: 'boat'는 영숫자만 있어 구문상 유효하지만 'red'·'blue' 같은 색상만 받는 필드라면 유효하지 않다). 악의적이거나 잘못된 입력을 찾는 방식(거부목록)에만 의존하지 않는다. 이 방식은 특히 코드 환경이 바뀔 때 원치 않는 입력을 하나 이상 놓치기 쉬워 검증이 우회될 수 있다. 다만 거부목록은 공격 탐지나 즉시 거부할 정도로 잘못된 입력을 가려내는 데는 쓸모가 있을 수 있다. 사용자가 제어하는 배열 인덱스에 접근할 때는 대상 배열 안에 드는 엄격한 값 범위를 쓴다. 음수를 허용하지 않도록 허용 범위의 최솟값과 최댓값을 모두 확인한다.
    원문

    Assume all input is malicious. Use an "accept known good" input validation strategy, i.e., use a list of acceptable inputs that strictly conform to specifications. Reject any input that does not strictly conform to specifications, or transform it into something that does.

    When performing input validation, consider all potentially relevant properties, including length, type of input, the full range of acceptable values, missing or extra inputs, syntax, consistency across related fields, and conformance to business rules. As an example of business rule logic, "boat" may be syntactically valid because it only contains alphanumeric characters, but it is not valid if the input is only expected to contain colors such as "red" or "blue."

    Do not rely exclusively on looking for malicious or malformed inputs. This is likely to miss at least one undesirable input, especially if the code's environment changes. This can give attackers enough room to bypass the intended validation. However, denylists can be useful for detecting potential attacks or determining which inputs are so malformed that they should be rejected outright.

    When accessing a user-controlled array index, use a stringent range of values that are within the target array. Make sure that you do not allow negative values to be used. That is, verify the minimum as well as the maximum of the range of acceptable values.

    		 —
    구현(Implementation) — 인터프리터 언어에서 네이티브 코드를 호출하는 것처럼 언어 경계를 넘는 코드를 호출할 때는 예상하지 못한 상호작용이 생길 수 있으므로 모든 입력을 특히 신중히 검증하고, 연동하는 언어의 기대를 어기지 않는지 확인한다(예: Java 자체는 버퍼 오버플로에 취약하지 않을 수 있어도 네이티브 코드 호출에 큰 인자를 넘기면 오버플로가 일어날 수 있다).
    원문

    Be especially careful to validate all input when invoking code that crosses language boundaries, such as from an interpreted language to native code. This could create an unexpected interaction between the language boundaries. Ensure that you are not violating any of the expectations of the language with which you are interfacing. For example, even though Java may not be susceptible to buffer overflows, providing a large argument in a call to native code might trigger an overflow.

    		 —

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음

    유지보수 (본문 제7장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) 실행 환경 강화 하드웨어 NX·XD 비트를 이용한 데이터 실행 방지(Data Execution Protection)를 제공하는 CPU와 운영체제, 또는 PaX [REF-60] [REF-61]처럼 이를 소프트웨어로 흉내 내는 기법을 쓴다. 이 기법들은 실행되는 모든 명령이 코드 세그먼트에 속한 메모리 주소에만 있도록 보장한다(자세한 내용은 D3FEND의 D3-PSEP(Process Segment Execution Prevention) [REF-1336]).
    원문

    Use a CPU and operating system that offers Data Execution Protection (using hardware NX or XD bits) or the equivalent techniques that simulate this feature in software, such as PaX [REF-60] [REF-61]. These techniques ensure that any instruction executed is exclusively at a memory address that is part of the code segment.

    For more information on these techniques see D3-PSEP (Process Segment Execution Prevention) from D3FEND [REF-1336].

    		 심층 방어(Defense in Depth) — 버퍼 오버플로로 인접 변수를 덮어써 소프트웨어 상태를 위험하게 바꿀 수 있으므로 완전한 해결책이 아니다. 또한 자기 수정 코드가 필요한 경우에는 쓸 수 없고, 대개 애플리케이션 종료로 대응하므로 공격은 여전히 서비스 거부를 일으킬 수 있다.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 6건)

    Example 1. In the code snippet below, an untrusted integer value is used to reference an object in an array.

    Bad / Java

    public String getValue(int index) {
  return array[index];
}

    If index is outside of the range of the array, this may result in an ArrayIndexOutOfBounds Exception being raised.

    Example 2. The following example takes a user-supplied value to allocate an array of objects and then operates on the array.

    Bad / Java

    private void buildList ( int untrustedListSize ){
  if ( 0 > untrustedListSize ){
    die("Negative value supplied for list size, die evil hacker!");
  }
  Widget[] list = new Widget [ untrustedListSize ];
  list[0] = new Widget();
}

    This example attempts to build a list from a user-specified value, and even checks to ensure a non-negative value is supplied. If, however, a 0 value is provided, the code will build an array of size 0 and then try to store a new Widget in the first location, causing an exception to be thrown.

    Example 3. In the following code, the method retrieves a value from an array at a specific array index location that is given as an input parameter to the method

    Bad / C

    int getValueFromArray(int *array, int len, int index) {

  int value;

                             // check that the array index is less than the maximum

                             // length of the array

  if (index < len) {

                                     // get the value at the specified index of the array

    value = array[index];

  }

                             // if array index is invalid then output error message

                             // and return value indicating error

  else {
    printf("Value is: %d\n", array[index]);
    value = -1;
  }

  return value;

}

    However, this method only verifies that the given array index is less than the maximum length of the array but does not check for the minimum value (CWE-839). This will allow a negative value to be accepted as the input array index, which will result in reading data before the beginning of the buffer (CWE-127) and may allow access to sensitive memory. The input array index should be checked to verify that is within the maximum and minimum range required for the array (CWE-129). In this example the if statement should be modified to include a minimum range check, as shown below.

    Good / C

    ...

                     // check that the array index is within the correct

                     // range of values for the array

if (index >= 0 && index < len) {

...

    Example 4. The following example retrieves the sizes of messages for a pop3 mail server. The message sizes are retrieved from a socket that returns in a buffer the message number and the message size, the message number (num) and size (size) are extracted from the buffer and the message size is placed into an array using the message number for the array index.

    Bad / C

                         /* capture the sizes of all messages */

int getsizes(int sock, int count, int *sizes) {

  ...
  char buf[BUFFER_SIZE];
  int ok;
  int num, size;

                             // read values from socket and added to sizes array

  while ((ok = gen_recv(sock, buf, sizeof(buf))) == 0)
  {

                                     // continue read from socket until buf only contains '.'

    if (DOTLINE(buf))
      break;

                                     else if (sscanf(buf, "%d %d", &num, &size) == 2)
      sizes[num - 1] = size;

  }
    ...

}

    In this example the message number retrieved from the buffer could be a value that is outside the allowable range of indices for the array and could possibly be a negative number. Without proper validation of the value to be used for the array index an array overflow could occur and could potentially lead to unauthorized access to memory addresses and system crashes. The value of the array index should be validated to ensure that it is within the allowable range of indices for the array as in the following code.

    Good / C

                         /* capture the sizes of all messages */

int getsizes(int sock, int count, int *sizes) {

  ...
  char buf[BUFFER_SIZE];
  int ok;
  int num, size;

                             // read values from socket and added to sizes array

  while ((ok = gen_recv(sock, buf, sizeof(buf))) == 0)
  {

                                     // continue read from socket until buf only contains '.'

    if (DOTLINE(buf))
      break;

    else if (sscanf(buf, "%d %d", &num, &size) == 2) {

      if (num > 0 && num <= (unsigned)count)
        sizes[num - 1] = size;

      else

                                                     /* warn about possible attempt to induce buffer overflow */

        report(stderr, "Warning: ignoring bogus data for message sizes returned by server.\n");

    }

  }
    ...

}

    Example 5. In the following example the method displayProductSummary is called from a Web service servlet to retrieve product summary information for display to the user. The servlet obtains the integer value of the product number from the user and passes it to the displayProductSummary method. The displayProductSummary method passes the integer value of the product number to the getProductSummary method which obtains the product summary from the array object containing the project summaries using the integer value of the product number as the array index.

    Bad / Java

                         // Method called from servlet to obtain product information

public String displayProductSummary(int index) {

  String productSummary = new String("");

  try {
    String productSummary = getProductSummary(index);

  } catch (Exception ex) {...}

  return productSummary;

}

public String getProductSummary(int index) {
  return products[index];
}

    In this example the integer value used as the array index that is provided by the user may be outside the allowable range of indices for the array which may provide unexpected results or cause the application to fail. The integer value used for the array index should be validated to ensure that it is within the allowable range of indices for the array as in the following code.

    Good / Java

                         // Method called from servlet to obtain product information

public String displayProductSummary(int index) {

  String productSummary = new String("");

  try {
    String productSummary = getProductSummary(index);

  } catch (Exception ex) {...}

  return productSummary;

}

public String getProductSummary(int index) {

  String productSummary = "";

  if ((index >= 0) && (index < MAX_PRODUCTS)) {
    productSummary = products[index];
  }
  else {
    System.err.println("index is out of bounds");
    throw new IndexOutOfBoundsException();
  }

  return productSummary;

}

    An alternative in Java would be to use one of the collection objects such as ArrayList that will automatically generate an exception if an attempt is made to access an array index that is out of bounds.

    Good / Java

    ArrayList productArray = new ArrayList(MAX_PRODUCTS);
...
try {
  productSummary = (String) productArray.get(index);
} catch (IndexOutOfBoundsException ex) {...}

    Example 6. The following example asks a user for an offset into an array to select an item.

    Bad / C

    int main (int argc, char **argv) {
  char *items[] = {"boat", "car", "truck", "train"};
  int index = GetUntrustedOffset();
  printf("You selected %s\n", items[index-1]);
}

    The programmer allows the user to specify which element in the list to select, however an attacker can provide an out-of-bounds offset, resulting in a buffer over-read (CWE-126).

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 이 약점은 흔히 자동 정적 분석 도구로 탐지할 수 있고 많은 최신 도구가 데이터 흐름 분석이나 제약 기반 기법으로 오탐을 줄이지만, 자동 정적 분석은 대개 범위 밖 메모리 연산을 보고할 때 환경적 고려를 반영하지 않아 어떤 경고를 먼저 조사할지 판단하기 어려울 수 있다(예: setuid나 다른 특수 권한으로 실행되지 않을 프로그램에서 명령행 인자로부터 생기는 배열 인덱스 오류를 보고할 수 있다).
    원문

    This weakness can often be detected using automated static analysis tools. Many modern tools use data flow analysis or constraint-based techniques to minimize the number of false positives.

    Automated static analysis generally does not account for environmental considerations when reporting out-of-bounds memory operations. This can make it difficult for users to determine which warnings should be investigated first. For example, an analysis tool might report array index errors that originate from command line arguments in a program that is not expected to run with setuid or other special privileges.

    		 높음(High) — 100% 정확도와 탐지 범위를 달성할 수 없으므로 완전한 해결책은 아니다.
    자동 동적 분석 퍼징(fuzzing)·강건성 시험·오류 주입처럼 다양한 입력의 대규모 시험 모음으로 소프트웨어와 상호작용하는 동적 도구·기법으로 이 약점을 탐지할 수 있으며, 이때 동작이 느려질 수는 있어도 불안정해지거나 비정상 종료되거나 잘못된 결과를 내서는 안 된다.
    원문

    This weakness can be detected using dynamic tools and techniques that interact with the software using large test suites with many diverse inputs, such as fuzz testing (fuzzing), robustness testing, and fault injection. The software's operation may slow down, but it should not become unstable, crash, or generate incorrect results.

    		 —
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.
    블랙박스 시험 블랙박스 방법은 제한된 시간 안에 필요한 코드 실행률(Coverage)을 얻지 못할 수 있고, 동적 분석으로 한 시험이 성공해도 눈에 띄는 부작용이 나타나지 않을 수 있다.
    원문

    Black box methods might not get the needed code coverage within limited time constraints, and a dynamic test might not produce any noticeable side effects even if it is successful.
