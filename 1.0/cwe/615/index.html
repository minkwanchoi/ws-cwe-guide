    Inclusion of Sensitive Information in Source Code Comments

    항목 내용
    추상화 수준 변형(Variant)
    상태 미완성(Incomplete)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    적용 플랫폼 언어 무관 · 기술 무관
    원문 MITRE CWE-615 (CWE 5.0)

    한 줄 요약

    소스코드 주석에 애플리케이션 관련 파일명, 옛 링크, 옛 코드 조각 같은 민감한 정보가 들어 있는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품의 소스코드에 애플리케이션 관련 파일명, 옛 링크나 사용자가 열람하도록 의도하지 않은 링크, 옛 코드 조각 같은 민감한 정보를 담은 주석이 있는 약점이다.

    원문(Description)

    The product's source code includes comments that contain sensitive information, such as filenames related to the application, old links or links that were not meant to be browsed by users, old code fragments, etc.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 애플리케이션 데이터 읽기 이런 주석을 찾은 공격자는 애플리케이션의 구조와 파일을 파악하고 사이트의 숨은 부분을 드러내며, 코드 조각을 연구해 애플리케이션을 역공학할 수 있고, 이 정보는 사이트에 대한 추가 공격을 개발하는 데 도움이 될 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 1건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    원문 완화책 없음

    구현 (본문 제5장)¶

    원문 완화책 없음

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-08 운용 빌드 산출물 검사

    유지보수 (본문 제7장)¶

    CWE 단계(Phase) 전략 요지
    배포(Distribution) — 애플리케이션 설계·구현에 관한 민감한 정보가 담긴 주석을 제거한다. 일부 주석은 사용자에게 노출되어 애플리케이션의 보안 태세에 영향을 줄 수 있다.
    원문

    Remove comments which have sensitive information about the design/implementation of the application. Some of the comments may be exposed to the user and affect the security posture of the application.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 데이터링크 단말·펌웨어 업로드·정비 기록 전송 코드에 개발자가 시험장 접속 주소, 계정과 비밀번호, 키 위치, 알려진 결함을 주석으로 남긴다. 소스코드는 협력업체·정비창 이관, 형상 반입, 문서 생성 도구(Javadoc·XML 문서 주석·Python 문서 문자열) 산출물로 퍼지므로 주석의 정보도 함께 새어 나간다. 예시의 주소는 문서용 예약 대역(192.0.2.0/24)이고 비밀번호는 가짜 값이다. 도구로 잡기 어려운 약점이라 언어마다 컴파일(Python은 실행)만 확인하고, 나쁜 예·좋은 예 판정은 생성형 AI를 쓴 별도 검토로 했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>

/*
 * 데이터링크 단말 초기화
 * 시험장 단말 접속: 192.0.2.41:7001, 계정 fieldtest / pw=EXAMPLE-ONLY
 * 링크 키 파일 /opt/gcs/conf/link.key, 키 암호 EXAMPLE-ONLY-KEYPASS
 */
static int link_init(int channel)
{
    /* 채널 9는 정비창 전용 숨은 포트(인증 없음) - 외부에 알리지 말 것 */
    if (channel < 1 || channel > 8) {
        return -1;
    }
    printf("link channel %d ready\n", channel);
    return 0;
}

int main(void)
{
    return link_init(3) == 0 ? 0 : 1;
}

    함수 머리 주석에 시험장 단말 주소·계정·비밀번호·키 파일 위치와 키 암호가, 본문 주석에 인증 없는 숨은 포트 정보가 적혀 있다.

    좋은 예

    #include <stdio.h>

/*
 * 데이터링크 단말 초기화
 * 접속 주소·계정·키 위치는 소스코드에 적지 않는다. 설치 구성 파일과 키 저장소에서
 * 읽으며, 값과 관리 책임은 형상 문서(설치 구성서)에 둔다.
 */
static int link_init(int channel)
{
    /* 허용 채널 범위는 ICD의 채널 정의를 따른다 */
    if (channel < 1 || channel > 8) {
        return -1;
    }
    printf("link channel %d ready\n", channel);
    return 0;
}

int main(void)
{
    return link_init(3) == 0 ? 0 : 1;
}

    주석에는 동작과 근거 문서만 적고, 접속 정보와 키 위치는 설치 구성 파일·키 저장소와 형상 문서로 옮긴다.

    C++

    나쁜 예

    #include <iostream>
#include <string>

// 협력업체에 함께 넘기는 공개 헤더의 일부
// 정비 서버: 192.0.2.88 (관리자 admin / pw=EXAMPLE-ONLY)
// 펌웨어 서명 개인키는 빌드 서버 /opt/gcs/sign/fw_priv.pem 에 있음
class FirmwareUploader {
public:
    // 알려진 문제: 4 MB가 넘는 이미지를 보내면 서버 업로드 데몬이 멈춤(미수정)
    bool upload(const std::string &image) const {
        if (image.empty()) {
            return false;
        }
        std::cout << "upload " << image.size() << " bytes\n";
        return true;
    }
};

int main() {
    FirmwareUploader up;
    return up.upload("FWIMG-0001") ? 0 : 1;
}

    협력업체에 넘기는 공개 헤더 주석에 정비 서버 관리자 계정·비밀번호, 서명 개인키 위치, 서버를 멈추게 하는 알려진 결함이 적혀 있다.

    좋은 예

    #include <iostream>
#include <string>

// 펌웨어 이미지를 정비 서버로 올린다.
// 서버 주소·계정은 설치 구성에서, 서명 키는 키 관리 장치에서 가져온다(형상 문서 참조).
class FirmwareUploader {
public:
    // 빈 이미지는 거부한다. 서명 검증 절차는 업데이트 설계서를 따른다.
    bool upload(const std::string &image) const {
        if (image.empty()) {
            return false;
        }
        std::cout << "upload " << image.size() << " bytes\n";
        return true;
    }
};

int main() {
    FirmwareUploader up;
    return up.upload("FWIMG-0001") ? 0 : 1;
}

    주석은 함수가 하는 일과 따르는 설계 문서만 가리킨다. 알려진 결함은 결함 관리 도구에 등록한다.

    검증: 별도 검토 판정(도구로 잡기 어려운 약점, 생성형 AI 사용) · 참고: MITRE CWE-615 Demonstrative Example 1(주석에 남은 서버 결함 정보) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    Console.WriteLine(SensorGateway.Describe(4));

/// <summary>센서 게이트웨이 설정 도우미</summary>
/// <remarks>
/// 게이트웨이 관리 웹: http://192.0.2.60:8080 (root / pw=EXAMPLE-ONLY).
/// 공장 초기화 PIN EXAMPLE-ONLY-0000 은 출하 후에도 바뀌지 않음.
/// </remarks>
internal static class SensorGateway
{
    /// <summary>채널 설명 문자열을 만든다.</summary>
    /// <param name="channel">센서 채널 번호</param>
    /// <returns>설명 문자열</returns>
    public static string Describe(int channel) =>
        string.Create(System.Globalization.CultureInfo.InvariantCulture, $"gateway channel {channel}");
}

    XML 문서 주석에 관리 웹 주소·계정·비밀번호와 바뀌지 않는 공장 초기화 PIN이 적혀 있다. 문서 파일 생성(GenerateDocumentationFile)을 켜면 이 내용이 배포 폴더의 .xml 파일로 함께 나간다.

    좋은 예

    Console.WriteLine(SensorGateway.Describe(4));

/// <summary>센서 게이트웨이 설정 도우미</summary>
/// <remarks>
/// 관리 주소와 계정은 설치 구성에서 읽는다. 초기 PIN은 설치 절차에서
/// 장비마다 바꾸도록 설치 구성서에 정한다.
/// </remarks>
internal static class SensorGateway
{
    /// <summary>채널 설명 문자열을 만든다.</summary>
    /// <param name="channel">센서 채널 번호</param>
    /// <returns>설명 문자열</returns>
    public static string Describe(int channel) =>
        string.Create(System.Globalization.CultureInfo.InvariantCulture, $"gateway channel {channel}");
}

    문서 주석에는 구성에서 읽는다는 사실과 설치 절차만 적는다. 초기 PIN은 장비마다 바꾸도록 설치 구성서에 정한다.

    Java

    나쁜 예

    public class Example {
    /**
     * 정비 기록을 중앙 서버로 보낸다.
     * <p>접속 정보: jdbc:postgresql://192.0.2.23:5432/maint,
     * 계정 maint_rw / 비밀번호 EXAMPLE-ONLY (운영 서버도 같은 값)</p>
     */
    static String upload(String recordId) {
        // 인증서 검사를 끄는 옵션 -Dmaint.insecure=true 는 정비창에서만 쓸 것
        return "uploaded " + recordId;
    }

    public static void main(String[] args) {
        System.out.println(upload("MR-2026-0412"));
    }
}

    Javadoc에 DB 접속 주소와 계정·비밀번호가, 행 주석에 인증서 검사를 끄는 숨은 옵션이 적혀 있다. Javadoc은 API 문서로 만들어져 소스보다 더 넓게 배포된다.

    좋은 예

    public class Example {
    /**
     * 정비 기록을 중앙 서버로 보낸다.
     * <p>접속 정보와 계정은 배치 구성(설치 구성서)에서 주입받으며 소스코드와
     * Javadoc에는 적지 않는다.</p>
     */
    static String upload(String recordId) {
        // 인증서 검사는 끄지 않는다(보안 설정은 구성 관리 대상)
        return "uploaded " + recordId;
    }

    public static void main(String[] args) {
        System.out.println(upload("MR-2026-0412"));
    }
}

    Javadoc에는 접속 정보를 주입받는다는 사실만 적고 값은 배치 구성으로 옮긴다. 보안 설정을 끄는 옵션은 만들지 않는다.

    나쁜 예

    """정비 기록 업로드 도구.

시험장 서버: postgresql://192.0.2.23:5432/maint  계정 maint_rw / 비밀번호 EXAMPLE-ONLY
(운용 서버도 같은 계정을 쓴다. 인증서 오류가 나면 --insecure 로 우회할 것)
"""


def upload(record_id):
    # TODO 알려진 문제: 레코드 번호에 '/'가 들어가면 서버 쪽 경로 검사를 건너뜀(수정 전 배포 금지)
    return f"uploaded {record_id}"


print(upload("MR-2026-0412"))

    모듈 문서 문자열(docstring)에 시험장 서버 주소·계정·비밀번호와 인증서 검사를 끄는 옵션이, 주석에 아직 고치지 않은 결함이 적혀 있다. Python 배포본은 소스 그대로이거나 .pyc여도 문서 문자열이 남고(python -OO로만 빠짐), pydoc·Sphinx 같은 문서 생성 도구가 문서 문자열을 API 문서로 퍼뜨린다.

    좋은 예

    """정비 기록 업로드 도구.

접속 정보(주소·계정·자격 증명)는 배치 구성에서 주입받는다(운용 설정 문서 참고).
"""


def upload(record_id):
    # 알려진 결함은 결함 관리 시스템의 번호로만 가리킨다
    return f"uploaded {record_id}"


print(upload("MR-2026-0412"))

    문서 문자열·주석에는 접속 정보를 주입받는다는 사실만 적고 값은 배치 구성으로 옮긴다. 알려진 결함은 결함 관리 번호로만 가리킨다. 도구로 잡기 어려우므로 코드 리뷰와 배포 전 산출물 검사에서 주석·문서 문자열을 password·pw·계정·IP 주소 형식·'알려진 문제' 같은 낱말로 훑는다(T-08, LPY-12). Bandit B105는 password 같은 이름의 변수에 대입·비교되는 문자열만 보므로 주석과 문서 문자열 속 비밀번호는 잡지 못한다.

    검증: 별도 검토 판정(도구로 잡기 어려운 약점, 생성형 AI 사용) · 참고: MITRE CWE-615 Demonstrative Example 1(주석에 남은 서버 결함 정보) 참고, 이 가이드가 새로 작성 / 과학기술정보통신부·한국인터넷진흥원 「Python 시큐어코딩 가이드」(2023. 12.) 보안기능 2-13 '주석문 안에 포함된 시스템 주요정보'(인쇄 110쪽) 참고

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    주석과 문서 주석(Doxygen, Javadoc, XML 문서 주석)을 password·pw·passwd·key·계정·IP 주소 형식·URL·'알려진 문제' 같은 낱말과 형식으로 검색한다. I-09 [예시] CWE-615 예시(코드 리뷰 판정: 주석 검색어)
    협력업체·정비창에 넘기는 소스·공개 헤더와 함께 배포되는 API 문서(Javadoc HTML, GenerateDocumentationFile로 만든 .xml)를 반출 전에 같은 검색어로 확인한다. M-02·T-08 [예시] CWE-615 Java·C# 예시(문서 주석이 배포 문서로 나감) · [CWE] CWE-615 완화책(Distribution: 민감 주석 제거)
    주석에서 찾은 계정·비밀번호·키 위치는 주석을 지우는 것과 함께 실제 값을 바꾸고, 형상저장소 이력에 남은 같은 주석도 확인한다. M-02 [보완]
    주석에 적힌 숨은 포트·숨은 옵션·알려진 결함이 실제 코드에 남아 있는지 확인하고, 남아 있으면 CWE-489 점검 대상에 넣는다. I-09 [예시] CWE-615 C·Java 예시(주석에 숨은 포트, 인증서 검사를 끄는 옵션 기재)
    • ① 원문 탐지 방법은 자동 정적 분석뿐이다. 다른 정적 분석 도구·컴파일러 경고로 점검한다.

    단계 지침
    요구사항 분석 —
    설계 주석 작성 표준에 비밀번호·키·내부 IP·시험 계정 기재 금지를 명시한다.
    구현(C·C++) 주석에 인증정보·내부 주소를 기록하지 않는다.
    구현(Java) 주석·Javadoc·JSP 주석(<%-- --%>)에 민감정보를 기록하지 않는다. HTML 주석(<!-- -->)은 응답에 그대로 노출되므로 특히 주의한다.
    통합 및 시험 정적 분석·키워드 스캔(password, key, IP 패턴)으로 주석을 점검한다.
    유지보수 배포 전 소스 공개·이관 시 주석 점검을 수행한다.
    임베디드 고려 소스 제공 대상(협력업체·정비창)을 고려해 이관 전 점검을 수행한다.

    • T-08 운용 빌드 산출물 검사 (통합 및 시험)
    • M-02 운용 빌드 구성 형상관리 (유지보수)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 1건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
