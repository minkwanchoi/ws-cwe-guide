    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 데이터링크·비행 기록·텔레메트리 처리 코드가 예외 상황(숫자 변환 실패, 정리 중 기록 실패, 운용자의 송신 중지 요청)을 만난다. 예외 상황을 알아차리지 못하거나 엉뚱한 방식으로 처리하면 잘못된 값으로 동작을 계속하거나, 정리 경로에서 프로그램이 비정상 종료되거나, 중지 명령이 무시된다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <errno.h>
#include <stdio.h>
#include <stdlib.h>

/* 데이터링크 설정 메시지의 "보고 주기(ms)" 필드를 정수로 바꾼다. 성공 0, 실패 -1 */
static int parse_period(const char *field, int *out)
{
    char *end = NULL;
    errno = 0;
    *out = (int)strtol(field, &end, 10);      /* 실패해도 변환 도중의 값이 이미 들어간다 */
    return (end == field || *end != '\0' || errno == ERANGE) ? -1 : 0;
}

int main(void)
{
    const char *fields[] = {"200", "2OO", ""};
    int period = 500;                         /* 현재 적용 중인 값 */
    for (int i = 0; i < 3; ++i) {
        if (parse_period(fields[i], &period) != 0) {
            printf("warning: bad period field '%s'\n", fields[i]);  /* 감지만 하고 처리하지 않는다 */
        }
        printf("report period applied: %d ms\n", period);
    }
    return 0;
}

    C에는 예외가 없어 예외 상황은 반환값·errno로 알린다. 이 코드는 strtol의 실패를 반환값으로 감지하고도 경고만 찍고, 변환 도중에 이미 들어간 값("2OO"는 2 ms, 빈 문자열은 0 ms)을 그대로 적용한다.

    좋은 예

    #include <errno.h>
#include <stdio.h>
#include <stdlib.h>

/* 성공하면 0, 숫자가 아니면 -1, 허용 범위 밖이면 -2. 실패하면 *out을 건드리지 않는다 */
static int parse_period(const char *field, int *out)
{
    char *end = NULL;
    errno = 0;
    long v = strtol(field, &end, 10);         /* 결과는 임시 변수에 받는다 */
    if (end == field || *end != '\0') {
        return -1;
    }
    if (errno == ERANGE || v < 10 || v > 10000) {
        return -2;
    }
    *out = (int)v;
    return 0;
}

int main(void)
{
    const char *fields[] = {"200", "2OO", ""};
    int period = 500;                         /* 현재 적용 중인 값 */
    for (int i = 0; i < 3; ++i) {
        int rc = parse_period(fields[i], &period);
        if (rc != 0) {
            /* 설계에서 정한 처리: 현재 값을 유지하고 거부 사유를 알린다 */
            printf("field '%s' rejected (rc=%d): keep %d ms\n", fields[i], rc, period);
            continue;
        }
        printf("report period applied: %d ms\n", period);
    }
    return 0;
}

    변환 결과는 임시 변수에 받고 끝 포인터·ERANGE·허용 범위를 확인해, 실패하면 출력값을 건드리지 않는다. 호출자는 현재 값을 유지하고 거부 사유를 알린다. 실패했을 때 무엇을 할지(이전 값 유지, 안전 상태 전환)는 설계에서 정한다(D-08).

    검증: 실행 결과 — 나쁜 예에서 report period applied: [02] ms 검출, 좋은 예에서 미검출·field '2OO' rejected 출력 확인 · 참고: MITRE CWE-755 Demonstrative Example 2(실패를 감지하고도 처리하지 않음) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdio>
#include <stdexcept>

// 비행 기록 장치에 남은 데이터를 세션이 끝날 때 기록한다
class RecorderSession {
public:
    void add_frame() { ++pending_; }
    void media_fault() { media_ok_ = false; }

    void flush() {
        if (pending_ > 0 && !media_ok_) {
            throw std::runtime_error("recorder media write failed");
        }
        pending_ = 0;
    }

    ~RecorderSession() {
        flush();    // 실패하면 소멸자 밖으로 예외가 나가 std::terminate로 이어진다
    }

private:
    int pending_ = 0;
    bool media_ok_ = true;
};

int main() {
    RecorderSession s;
    s.add_frame();
    s.media_fault();
    std::puts("leaving scope");
    return 0;
}

    소멸자는 암묵적으로 noexcept인데, 소멸자에서 부른 flush()의 예외가 밖으로 나가 std::terminate로 프로그램이 비정상 종료된다. 기록 매체 고장 한 번이 전체 정지로 번진다.

    좋은 예

    #include <cstdio>
#include <stdexcept>

class RecorderSession {
public:
    void add_frame() { ++pending_; }
    void media_fault() { media_ok_ = false; }

    // 정상 경로에서는 호출자가 직접 부르고 실패를 처리한다
    void flush() {
        if (pending_ > 0 && !media_ok_) {
            throw std::runtime_error("recorder media write failed");
        }
        pending_ = 0;
    }

    // 남은 프레임 수를 돌려주고 비운다: 호출자가 예비 장치로 넘길 때 쓴다
    int take_pending() {
        const int n = pending_;
        pending_ = 0;
        return n;
    }

    ~RecorderSession() {
        try {
            flush();
        } catch (const std::exception &e) {
            // 소멸자에서는 예외를 밖으로 내보내지 않고 고장 기록만 남긴다
            std::printf("recorder fault logged: %s (%d frames lost)\n", e.what(), pending_);
        } catch (...) {
            std::printf("recorder fault logged: unknown error (%d frames lost)\n", pending_);
        }
    }

private:
    int pending_ = 0;
    bool media_ok_ = true;
};

int main() {
    RecorderSession s;
    s.add_frame();
    s.media_fault();
    try {
        s.flush();
    } catch (const std::exception &e) {
        std::printf("switch to backup recorder: %s\n", e.what());
        std::printf("%d frames moved to backup\n", s.take_pending());
    }
    std::puts("leaving scope");
    return 0;
}

    정상 경로에서는 호출자가 flush()를 직접 불러 실패를 처리(예비 기록 장치로 전환)하고, 소멸자는 어떤 예외든 잡아 고장 기록만 남긴다(LCPP-02). 예비 장치로 넘긴 프레임은 take_pending()으로 비워 소멸자가 다시 처리하지 않게 한다.

    검증: clang-tidy — 나쁜 예에서 bugprone-exception-escape 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-755 설명 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    using (var port = new TelemetryPort())
{
    port.Queue(3);
    port.MarkLinkDown();
    Console.WriteLine("closing telemetry port");
}   // Dispose에서 예외가 나가면 정리 경로에서 원래 오류를 덮어쓰거나 프로그램이 멈춘다

internal sealed class TelemetryPort : IDisposable
{
    private int pending;
    private bool linkUp = true;

    public void Queue(int frames) => pending += frames;
    public void MarkLinkDown() => linkUp = false;

    public void Dispose()
    {
        if (pending > 0 && !linkUp)
        {
            throw new InvalidOperationException("pending frames lost");
        }
        pending = 0;
    }
}

    Dispose에서 예외를 던진다. Dispose는 using·finally 같은 정리 경로에서 불리므로 원래 오류를 덮어쓰거나, 이 예시처럼 처리되지 않은 예외로 프로그램을 비정상 종료시킨다. 검증한 분석기 구성(AnalysisMode=All)에서도 CA1065가 이 예시를 경고하지 않아 실행으로 확인한다.

    좋은 예

    using (var port = new TelemetryPort())
{
    port.Queue(3);
    port.MarkLinkDown();
    if (!port.TryFlush())
    {
        int frames = port.TakePending();          // 보내지 못한 프레임을 꺼내 예비 링크로 넘긴다
        Console.WriteLine($"flush failed: {frames} frames handed to backup link");
    }
    Console.WriteLine("closing telemetry port");
}

internal sealed class TelemetryPort : IDisposable
{
    private int pending;
    private bool linkUp = true;

    public int LostOnClose { get; private set; }

    public void Queue(int frames) => pending += frames;
    public void MarkLinkDown() => linkUp = false;

    // 실패할 수 있는 작업은 정상 경로에서 결과를 돌려준다
    public bool TryFlush()
    {
        if (pending > 0 && !linkUp)
        {
            return false;
        }
        pending = 0;
        return true;
    }

    // 보내지 못한 프레임을 호출자에게 넘기고 큐를 비운다
    public int TakePending()
    {
        int frames = pending;
        pending = 0;
        return frames;
    }

    public void Dispose()
    {
        // Dispose에서는 예외를 던지지 않고 잃은 양만 기록한다
        LostOnClose = pending;
        pending = 0;
    }
}

    실패할 수 있는 송신은 TryFlush로 정상 경로에서 결과를 돌려받아, 실패하면 보내지 못한 프레임을 꺼내 예비 링크로 넘긴다. Dispose는 예외 없이 잃은 양만 기록한다.

    검증: 실행 결과 — 나쁜 예에서 Unhandled exception. System.InvalidOperationException 검출, 좋은 예에서 미검출·flush failed: 3 frames handed to backup link 출력 확인 · 참고: MITRE CWE-755 설명 참고, 이 가이드가 새로 작성

    Java

    나쁜 예

    public class Example {
    static int sent = 0;

    static void sendFrame(int frame) {
        sent++;                                        // 텔레메트리 프레임 송신(모의)
        if (frame == 1) {
            Thread.currentThread().interrupt();        // 시험용 모의: 운용자가 '송신 중지'를 요청
        }
    }

    // 프레임 사이 송신 간격을 맞춘다
    static void pace() {
        try {
            Thread.sleep(5);
        } catch (InterruptedException e) {
            // 중지 요청을 삼킨다: 인터럽트 상태도 지워진 채로 돌아간다
        }
    }

    public static void main(String[] args) {
        for (int frame = 0; frame < 5 && !Thread.currentThread().isInterrupted(); frame++) {
            sendFrame(frame);
            pace();
        }
        System.out.println("frames sent: " + sent + " of 5 (stop requested after frame 2)");
    }
}

    InterruptedException을 잡고 아무것도 하지 않는다. 예외가 던져질 때 인터럽트 상태가 지워지므로 루프가 중지 요청을 보지 못하고 남은 프레임을 모두 보낸다.

    좋은 예

    public class Example {
    static int sent = 0;

    static void sendFrame(int frame) {
        sent++;                                        // 텔레메트리 프레임 송신(모의)
        if (frame == 1) {
            Thread.currentThread().interrupt();        // 시험용 모의: 운용자가 '송신 중지'를 요청
        }
    }

    // 프레임 사이 송신 간격을 맞춘다
    static void pace() {
        try {
            Thread.sleep(5);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();        // 중지 요청을 호출자에게 되돌려 준다
        }
    }

    public static void main(String[] args) {
        for (int frame = 0; frame < 5 && !Thread.currentThread().isInterrupted(); frame++) {
            sendFrame(frame);
            pace();
        }
        if (Thread.currentThread().isInterrupted()) {
            System.out.println("stop request honored: link set to idle");
        }
        System.out.println("frames sent: " + sent + " of 5 (stop requested after frame 2)");
    }
}

    잡은 뒤 Thread.currentThread().interrupt()로 인터럽트 상태를 되살려, 루프가 중지 요청을 보고 링크를 대기 상태로 둔다.

    검증: 실행 결과 — 나쁜 예에서 frames sent: 5 of 5 검출, 좋은 예에서 미검출·stop request honored 출력 확인 · 참고: MITRE CWE-755 설명 참고, 이 가이드가 새로 작성

    Python

    나쁜 예

    import time


class Transmitter:
    def __init__(self, stop_at):
        self.stop_at = stop_at

    def send(self, n):
        if n == self.stop_at:
            raise KeyboardInterrupt           # 운용자가 송신 중지(Ctrl+C)를 누른 순간
        if n == 2:
            raise ValueError("bad frame")     # 형식 오류 프레임
        time.sleep(0.01)


# 텔레메트리 송신 반복문
tx, sent = Transmitter(stop_at=3), []
for n in range(1, 6):
    try:
        tx.send(n)
        sent.append(n)
    except:                                   # 맨 except: 송신 중지 요청까지 삼킨다
        continue
print("frames sent:", sent)
if any(n > tx.stop_at for n in sent):
    print("SENT AFTER STOP REQUEST")

    맨 except:는 KeyboardInterrupt·SystemExit·GeneratorExit까지 잡는다. 운용자가 송신 중지를 눌러도 예외가 삼켜져 반복문이 끝까지 송신을 이어 간다. 형식 오류 같은 예상한 예외와 중지 요청을 구분하지 않고 같은 방식으로 처리한다. Bandit은 except 블록이 continue만 하는 꼴을 B112로 보고한다.

    좋은 예

    import logging
import time

log = logging.getLogger("telemetry.tx")


class Transmitter:
    def __init__(self, stop_at):
        self.stop_at = stop_at

    def send(self, n):
        if n == self.stop_at:
            raise KeyboardInterrupt
        if n == 2:
            raise ValueError("bad frame")
        time.sleep(0.01)


tx, sent = Transmitter(stop_at=3), []
try:
    for n in range(1, 6):
        try:
            tx.send(n)
            sent.append(n)
        except ValueError as e:              # 예상한 예외만 잡고 기록한다
            log.warning("frame %d dropped: %s", n, e)
except KeyboardInterrupt:                    # 중지 요청은 반복문 밖에서 받아 안전하게 멈춘다
    print(f"transmission stopped by operator at frame {n}")
print("frames sent:", sent)
if any(n > tx.stop_at for n in sent):
    print("SENT AFTER STOP REQUEST")

    잡을 예외를 구체적으로 적어(ValueError) 예상한 오류만 기록하고 넘긴다. KeyboardInterrupt는 반복문 밖에서 받아 송신을 멈추고 안전 상태로 간다(I-06, LPY-08). 넓게 잡아야 할 때도 except Exception으로 하고(KeyboardInterrupt·SystemExit은 Exception이 아니라 BaseException을 직접 상속하므로 빠진다) 기록 후 다시 던진다. 어떤 예외를 어디서 처리할지는 오류 처리 설계에서 정한다(D-08).

    Example 1. The following example attempts to resolve a hostname.

    Bad / Java

    A DNS lookup failure will cause the Servlet to throw an exception.

    Example 2. The following example attempts to allocate memory for a character. After the call to malloc, an if statement is used to check whether the malloc function failed.

    Bad / C

    foo=malloc(sizeof(char)); //the next line checks to see if malloc failed
if (foo==NULL) {
  //We do nothing so we just ignore the error.
}

    The conditional successfully detects a NULL return value from malloc indicating a failure, however it does not do anything to handle the problem. Unhandled errors may have unexpected results and may cause the program to crash or terminate.

    Instead, the if block should contain statements that either attempt to fix the problem or notify the user that an error has occurred and continue processing or perform some cleanup and gracefully terminate the program. The following example notifies the user that the malloc function did not allocate the required memory resources and returns an error code.

    Good / C

    foo=malloc(sizeof(char)); //the next line checks to see if malloc failed
if (foo==NULL) {
  printf("Malloc failed to allocate memory resources");
  return -1;
}

    탐지 방법(Detection Methods)¶

    방법 요지
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)
