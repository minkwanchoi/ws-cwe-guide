    Function Call with Incorrectly Specified Arguments

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 해당
    적용 플랫폼 언어 무관
    원문 MITRE CWE-628 (CWE 5.0)

    한 줄 요약

    함수·프로시저·루틴을 올바르게 지정되지 않은 인자로 호출하는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 함수, 프로시저, 루틴을 올바르게 지정되지 않은 인자로 호출하는 약점이다.

    기술 해설(Technical Nuance)

    이 약점은 다음을 포함해 여러 방식으로 생길 수 있다.

    • 잘못된 변수나 참조

    • 잘못된 인자 개수

    • 잘못된 인자 순서

    • 잘못된 인자 형식

    • 잘못된 값

    원문(Description · Technical Nuance)

    The product calls a function, procedure, or routine with arguments that are not correctly specified.

    There are multiple ways in which this weakness can be introduced, including:

    - the wrong variable or reference;

    - an incorrect number of arguments;

    - incorrect order of arguments;

    - wrong type of arguments; or

    - wrong value.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    기타 / 접근 통제 품질 저하 / 권한 획득 또는 신원 도용 / 예상하지 못한 상태 / 상황에 따라 다름 이 약점은 의도하지 않은, 늘 잘못된 동작을 일으킬 수 있다. 공격자가 시스템 자원에 의도하지 않은 접근을 얻는 등 추가 약점으로 이어질 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 2건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 수신 프레임 버퍼 비우기, 고도 경계 설정, 냉각 펌프 구동 명령, 펌웨어 이미지 백업처럼 같은 형의 인자를 여러 개 받는 함수를 부르면서 인자의 순서를 함수 원형과 다르게 넘긴다. 형이 같아 컴파일은 되지만(Python은 실행 전 형 검사가 없다) 값이 엉뚱한 매개변수로 들어가 기능이 조용히 잘못 동작한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>

/* 수신 프레임 버퍼를 다음 프레임 전에 비운다 */
static unsigned char rx_frame[32];

static void receive(const char *payload)
{
    memset(rx_frame, sizeof rx_frame, 0);      /* 인자 순서가 뒤바뀌어 0바이트만 지운다 */
    memcpy(rx_frame, payload, strlen(payload));
}

int main(void)
{
    receive("WAYPOINT,00.00,000.00,450");
    receive("HOLD");                           /* 짧은 프레임 */
    /* 지워지지 않은 이전 프레임 꼬리가 남아 다음 처리 단계로 넘어간다 */
    printf("frame tail after HOLD: '%.20s'\n", (const char *)rx_frame + 4);
    return 0;
}

    memset(대상, 값, 크기)의 값과 크기 순서를 바꿔 0바이트만 지운다. 짧은 프레임을 받으면 이전 프레임의 꼬리가 버퍼에 남아 다음 처리 단계로 넘어간다.

    좋은 예

    #include <stdio.h>
#include <string.h>

static unsigned char rx_frame[32];

static void receive(const char *payload)
{
    size_t n = strlen(payload);
    memset(rx_frame, 0, sizeof rx_frame);      /* 원형 memset(dst, 값, 크기) 순서대로 */
    if (n >= sizeof rx_frame) {
        n = sizeof rx_frame - 1;               /* 버퍼 크기를 넘지 않게 자른다 */
    }
    memcpy(rx_frame, payload, n);
}

int main(void)
{
    receive("WAYPOINT,00.00,000.00,450");
    receive("HOLD");
    printf("frame tail after HOLD: '%.20s'\n", (const char *)rx_frame + 4);
    return 0;
}

    원형 순서대로 memset(대상, 0, 크기)로 호출하고, 복사 길이도 버퍼 크기를 넘지 않게 한다. 컴파일러 경고를 오류로 다루면(-Werror) 이런 호출은 빌드 단계에서 막힌다.

    검증: 컴파일러 경고 — 나쁜 예에서 -Wmemset-transposed-args 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-628 Demonstrative Example 1(매개변수 순서를 거꾸로 넘긴 호출) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdio>

// 비행 금지 고도 경계(geofence) 설정: (하한, 상한) 순서
struct AltitudeFence {
    int floor_m = 0;
    int ceiling_m = 0;
    bool allows(int alt_m) const { return alt_m >= floor_m && alt_m <= ceiling_m; }
};

AltitudeFence make_fence(int floor_m, int ceiling_m) {
    return AltitudeFence{floor_m, ceiling_m};
}

int main() {
    const int ceiling_m = 3000;
    const int floor_m = 150;
    // 같은 int 두 개라 순서를 바꿔 넘겨도 컴파일된다
    AltitudeFence fence = make_fence(ceiling_m, floor_m);
    std::printf("cruise at 1200 m allowed: %s\n", fence.allows(1200) ? "yes" : "no");
    return 0;
}

    make_fence(하한, 상한)에 상한·하한 순서로 넘겨 모든 고도를 금지하는 경계가 만들어진다. 같은 int라 컴파일러는 막지 못하고 clang-tidy가 인자 이름과 매개변수 이름이 엇갈린 것을 알려 준다.

    좋은 예

    #include <cstdio>

// 매개변수마다 다른 형을 써서 순서가 바뀌면 컴파일 오류가 나게 한다
struct Floor { int m; };
struct Ceiling { int m; };

struct AltitudeFence {
    int floor_m = 0;
    int ceiling_m = 0;
    bool allows(int alt_m) const { return alt_m >= floor_m && alt_m <= ceiling_m; }
};

AltitudeFence make_fence(Floor lower, Ceiling upper) {
    return AltitudeFence{lower.m, upper.m};
}

int main() {
    const Ceiling top{3000};
    const Floor bottom{150};
    // make_fence(top, bottom) 는 형이 맞지 않아 빌드되지 않는다
    AltitudeFence fence = make_fence(bottom, top);
    std::printf("cruise at 1200 m allowed: %s\n", fence.allows(1200) ? "yes" : "no");
    return 0;
}

    하한·상한마다 다른 형(Floor, Ceiling)을 두어 순서를 바꾸면 컴파일 오류가 나게 한다.

    검증: clang-tidy — 나쁜 예에서 readability-suspicious-call-argument 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-628 Demonstrative Example 1(매개변수 순서를 거꾸로 넘긴 호출) 참고, 이 가이드가 새로 작성

    C#

    나쁜 예

    // 펌웨어 업데이트 전에 현재 이미지를 백업 영역으로 복사한다
byte[] current = new byte[64];
for (int i = 0; i < current.Length; i++) current[i] = (byte)(i + 1);
int expected = Checksum(current);
byte[] backup = new byte[current.Length];

// Array.Copy(원본, 대상, 길이)인데 순서를 거꾸로 넘겨 빈 백업이 현재 이미지를 덮는다
Array.Copy(backup, current, current.Length);

Console.WriteLine(Checksum(current) == expected ? "current image intact" : "current image CORRUPTED");
Console.WriteLine(Checksum(backup) == expected ? "backup valid" : "backup EMPTY");

static int Checksum(byte[] image)
{
    int s = 0;
    foreach (byte b in image) s += b;
    return s;
}

    Array.Copy(원본, 대상, 길이)에 대상과 원본을 거꾸로 넘겨, 빈 백업 영역이 현재 펌웨어 이미지를 덮어쓴다. 형이 같아 컴파일러는 막지 못한다.

    좋은 예

    // 펌웨어 업데이트 전에 현재 이미지를 백업 영역으로 복사한다
byte[] current = new byte[64];
for (int i = 0; i < current.Length; i++) current[i] = (byte)(i + 1);
int expected = Checksum(current);
byte[] backup = new byte[current.Length];

// 명명 인자로 원본·대상을 드러내 순서 실수를 코드 리뷰에서 보이게 한다(또는 current.AsSpan().CopyTo(backup))
Array.Copy(sourceArray: current, destinationArray: backup, length: current.Length);

Console.WriteLine(Checksum(current) == expected ? "current image intact" : "current image CORRUPTED");
Console.WriteLine(Checksum(backup) == expected ? "backup valid" : "backup EMPTY");

static int Checksum(byte[] image)
{
    int s = 0;
    foreach (byte b in image) s += b;
    return s;
}

    명명 인자(sourceArray:, destinationArray:)로 원본·대상을 드러내 순서 실수를 코드 리뷰에서 바로 보이게 한다. 방향이 메서드 이름에 드러나는 Span.CopyTo를 써도 된다.

    검증: 실행 결과 — 나쁜 예에서 current image CORRUPTED 검출, 좋은 예에서 미검출·current image intact 출력 확인 · 참고: MITRE CWE-628 Demonstrative Example 1(매개변수 순서를 거꾸로 넘긴 호출) 참고, 이 가이드가 새로 작성

    Java

    나쁜 예

    public class Example {
    // 냉각 펌프 구동 명령: (펄스 폭 ms, 반복 주기 ms)
    static void drivePulses(String pump, int pulseMs, int periodMs) {
        int duty = pulseMs * 100 / periodMs;
        System.out.println(pump + " pulse=" + pulseMs + "ms period=" + periodMs
                + "ms duty=" + duty + "%");
    }

    public static void main(String[] args) {
        int periodMs = 200;
        int pulseMs = 50;
        // 두 인자가 모두 int라 순서를 바꿔도 컴파일·실행된다
        drivePulses("PUMP-3", periodMs, pulseMs);
    }
}

    펄스 폭과 반복 주기가 모두 int라 순서를 바꿔 넘겨도 컴파일된다. 실행하면 듀티(구동 비율)가 400%로 계산되어 펌프가 의도보다 훨씬 오래 구동된다.

    좋은 예

    public class Example {
    // 의미마다 다른 값 형(record)을 두어 순서가 바뀌면 컴파일 오류가 나게 한다
    record PulseWidth(int ms) {}
    record Period(int ms) {}

    static void drivePulses(String pump, PulseWidth pulse, Period period) {
        if (pulse.ms() <= 0 || pulse.ms() > period.ms()) {
            throw new IllegalArgumentException("pulse must be within period");
        }
        int duty = pulse.ms() * 100 / period.ms();
        System.out.println(pump + " pulse=" + pulse.ms() + "ms period=" + period.ms()
                + "ms duty=" + duty + "%");
    }

    public static void main(String[] args) {
        Period period = new Period(200);
        PulseWidth pulse = new PulseWidth(50);
        // drivePulses("PUMP-3", period, pulse) 는 형이 달라 컴파일되지 않는다
        drivePulses("PUMP-3", pulse, period);
    }
}

    펄스 폭·주기를 서로 다른 record 형으로 만들어 순서가 바뀌면 컴파일 오류가 나게 하고, 펄스가 주기 안에 있는지도 검사한다.

    검증: 실행 결과 — 나쁜 예에서 duty=…% 검출, 좋은 예에서 미검출·duty=25% 출력 확인 · 참고: MITRE CWE-628 Demonstrative Example 1(매개변수 순서를 거꾸로 넘긴 호출) 참고, 이 가이드가 새로 작성

    Python

    나쁜 예

    # 냉각 펌프를 구동한다(구동 시간 ms, 듀티 %)
def run_pump(pump_id, duration_ms, duty_pct):
    return f"pump {pump_id}: {duration_ms} ms at duty={duty_pct}%"


# 냉각 명령 처리: 인자 순서를 잘못 넘김
print(run_pump(2, 40, 200))       # 의도: 200 ms, 40 %

    구동 시간과 듀티(구동 비율)가 둘 다 정수라 순서를 바꿔 넘겨도 오류가 나지 않는다. 동적 타입 언어라 컴파일러가 막아 주지 않고, 듀티 200%라는 불가능한 값으로 명령이 만들어진다.

    좋은 예

    # 같은 형의 인자가 여러 개이면 키워드 전용 인자(*)로 받아 이름을 적어야만 부를 수 있게 한다
def run_pump(pump_id, *, duration_ms, duty_pct):
    if not 0 < duty_pct <= 100 or not 0 < duration_ms <= 500:    # 범위도 확인
        raise ValueError(f"out of range: duration_ms={duration_ms}, duty_pct={duty_pct}")
    return f"pump {pump_id}: {duration_ms} ms at duty={duty_pct}%"


print(run_pump(2, duration_ms=200, duty_pct=40))
try:
    print(run_pump(2, 40, 200))   # 위치 인자로 부르면 TypeError
except TypeError as e:
    print("call rejected:", e)

    같은 형의 인자가 여러 개인 함수는 키워드 전용 인자(*)로 정의해 호출할 때 이름을 적게 하고, 함수 안에서 값의 범위도 확인한다. 단위가 다른 값은 별도 형(NewType·dataclass)으로 나누면 mypy가 뒤바뀐 호출을 찾는다. 컴파일러 경고에 기대는 언어(C·C++)의 대책(I-08)을 Python에서는 키워드 인자와 타입 검사가 대신한다.

    검증: 실행 결과 — 나쁜 예에서 duty=…% 검출, 좋은 예에서 미검출·call rejected 출력 확인 · 참고: MITRE CWE-628 Demonstrative Example 1(매개변수 순서를 거꾸로 넘긴 호출) 참고, 이 가이드가 새로 작성

    MITRE 원문 예시(Demonstrative Examples, 영문 3건)

    Example 1. The following PHP method authenticates a user given a username/password combination but is called with the parameters in reverse order.

    Bad / PHP

    function authenticate($username, $password) {

                             // authenticate user

  ...

}

authenticate($_POST['password'], $_POST['username']);

    Example 2. This Perl code intends to record whether a user authenticated successfully or not, and to exit if the user fails to authenticate. However, when it calls ReportAuth(), the third argument is specified as 0 instead of 1, so it does not exit.

    Bad / Perl

    sub ReportAuth {

sub PrivilegedFunc
{
  my $result = CheckAuth($username);

  DoReallyImportantStuff();

    탐지 방법(Detection Methods)¶

    방법 요지
    기타 이런 버그는 대개 사용자에게 드러나는 잘못된 동작을 일으키므로, 드물게 시험되는 코드 경로에 있지 않은 한 빨리 발견된다. 포맷 스트링을 쓰거나 가변 개수 인자를 지원하는 경우에는 올바른 인자 개수를 관리하기가 더 어려워질 수 있다.
    원문

    Since these bugs typically introduce incorrect behavior that is obvious to users, they are found quickly, unless they occur in rarely-tested code paths. Managing the correct number of arguments can be made more difficult in cases where format strings are used, or when variable numbers of arguments are supported.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    같은 자료형의 인자가 둘 이상 이어지는 함수(memset, memcpy, Array.Copy, 하한·상한, 펄스 폭·주기)의 호출에서 인자 순서가 원형의 매개변수 이름과 맞는지 확인한다. I-09 [예시] CWE-628 예시(memset 값·크기, 하한·상한, 원본·대상 순서 뒤바뀜) · [표준] SEI CERT EXP37-C
    (C·C++) 사업 정적 분석 도구가 이 항목을 지원하지 않으면 -Wmemset-transposed-args 같은 컴파일러 경고와 clang-tidy readability-suspicious-call-argument로 인자 이름과 매개변수 이름이 엇갈린 호출을 찾는다. I-08·I-09 [예시] CWE-628 C·C++ 예시 검증(-Wmemset-transposed-args, readability-suspicious-call-argument)
    벤더 HAL·BSP 판을 바꿀 때 함수 원형과 인자 의미(단위, 순서)의 변경 목록을 받아 호출부와 대조한다. M-01 [CWE] CWE-628 완화책(Architecture and Design: 안정된 API 사용) · [보완]
    컴파일러가 막지 못하는 인자 순서 오류는 결과 값의 범위(비율 100% 초과, 원본·대상 내용)를 확인하는 단위시험으로 찾는다. I-10·T-05 [예시] CWE-628 Java·C# 예시 검증(구동 비율 400%, 현재 이미지 손상 출력)
    • ① 원문 탐지 방법(원문 효과성별): 효과 등급 없음: 기타. 각 방법의 시험 활동은 6.2의 대응표를 따른다.
    • ③ SEI CERT 대응 규칙: DCL10-C, EXP37-C
