    Improper Neutralization of Special Elements used in an OS Command

    항목 내용
    추상화 수준 기본(Base)
    상태 안정(Stable)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 조건부 — OS 명령 실행 사용
    적용 플랫폼 언어: 언어 무관, Python · 기술: 기술 무관, 인공지능·기계학습(AI/ML), 웹 서버(Web Server)
    원문 MITRE CWE-78 (CWE 5.0)

    한 줄 요약

    외부 입력으로 운영체제 명령을 만들면서 명령을 바꿀 수 있는 특수 요소를 무력화하지 않거나 잘못 무력화해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 상위 구성요소에서 온 외부 영향을 받은 입력으로 운영체제 명령의 전부 또는 일부를 만들면서, 그 명령을 하위 구성요소로 보내기 전에 의도한 명령을 바꿀 수 있는 특수 요소를 무력화(neutralize)하지 않거나 잘못 무력화하는 약점이다.

    기술 해설(Technical Nuance)

    운영체제 명령어 삽입에는 적어도 두 하위 유형이 있다.

    • 애플리케이션이 자신이 제어하는 고정 프로그램 하나를 실행하고 외부에서 받은 입력을 그 프로그램의 인자로 쓰려는 경우다. 예를 들어 프로그램이 system("nslookup [HOSTNAME]")으로 nslookup을 실행하고 사용자가 인자로 쓰이는 HOSTNAME을 지정하게 할 수 있다. 공격자는 nslookup 실행 자체는 막지 못한다. 그러나 프로그램이 HOSTNAME 인자에서 명령 구분자를 제거하지 않으면, 공격자가 인자에 구분자를 넣어 nslookup 실행이 끝난 뒤 자신의 프로그램을 실행할 수 있다.

    • 애플리케이션이 입력으로 실행할 프로그램과 사용할 명령을 전부 고르고, 그 명령 전체를 운영체제로 그대로 넘기는 경우다. 예를 들어 프로그램이 "exec([COMMAND])"로 사용자가 준 [COMMAND]를 실행할 수 있다. 공격자가 COMMAND를 제어하면 임의의 명령이나 프로그램을 실행할 수 있다. exec()와 CreateProcess() 같은 함수로 명령을 실행하면 공격자가 한 줄에 여러 명령을 결합하지 못할 수 있다.

    약점 관점에서 두 변형은 서로 다른 프로그래머 오류다. 첫째 변형에서 프로그래머는 신뢰할 수 없는 주체의 입력을 실행할 명령의 인자로 쓰려는 의도가 분명하다. 둘째 변형에서 프로그래머는 명령을 신뢰할 수 없는 주체에게 열어 둘 의도가 없지만, 악의적인 공격자가 입력을 넣을 다른 경로를 고려하지 않았을 가능성이 크다.

    원문(Description · Technical Nuance · Dimensions)

    The product constructs all or part of an OS command using externally-influenced input from an upstream component, but it does not neutralize or incorrectly neutralizes special elements that could modify the intended OS command before it is sent to a downstream component.

    There are at least two subtypes of OS command injection:

    - The application intends to execute a single, fixed program that is under its own control. It intends to use externally-supplied inputs as arguments to that program. For example, the program might use system("nslookup [HOSTNAME]") to run nslookup and allow the user to supply a HOSTNAME, which is used as an argument. Attackers cannot prevent nslookup from executing. However, if the program does not remove command separators from the HOSTNAME argument, attackers could place the separators into the arguments, which allows them to execute their own program after nslookup has finished executing.

    - The application accepts an input that it uses to fully select which program to run, as well as which commands to use. The application simply redirects this entire command to the operating system. For example, the program might use "exec([COMMAND])" to execute the [COMMAND] that was supplied by the user. If the COMMAND is under attacker control, then the attacker can execute arbitrary commands or programs. If the command is being executed using functions like exec() and CreateProcess(), the attacker might not be able to combine multiple commands together in the same line.

    From a weakness standpoint, these variants represent distinct programmer errors. In the first variant, the programmer clearly intends that input from untrusted parties will be part of the arguments in the command to be executed. In the second variant, the programmer does not intend for the command to be accessible to any untrusted party, but the programmer probably has not accounted for alternate ways in which malicious attackers can provide input.

    Dimensions: Behavior-Property = Improper; Behavior-Type = Neutralization; Input-Type = Special Elements; Other = OS Command; Common-Name = OS Command Injection

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 / 무결성 / 가용성 / 부인 방지 허가되지 않은 코드·명령 실행 / 서비스 거부: 비정상 종료·재시작 / 파일·디렉터리 읽기 / 파일·디렉터리 수정 / 애플리케이션 데이터 읽기 / 애플리케이션 데이터 수정 / 행위 은닉 공격자가 허가되지 않은 운영체제 명령을 실행해 제품을 무력화하거나 직접 접근 권한이 없는 데이터를 읽고 수정할 수 있으며, 명령은 공격자가 아니라 애플리케이션이 실행하므로 악성 행위가 애플리케이션이나 그 소유자에게서 나온 것처럼 보일 수 있다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 가능하면 외부 프로세스 대신 라이브러리 호출로 원하는 기능을 구현한다.
    원문

    If at all possible, use library calls rather than external processes to recreate the desired functionality.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.
    아키텍처·설계(Architecture and Design) 공격 표면 축소 실행할 명령을 만드는 데 쓰이는 데이터는 가능한 한 외부 제어 밖에 둔다. 예를 들어 웹 애플리케이션에서는 데이터를 숨은 폼 필드로 클라이언트에 보내지 않고 세션 상태에 로컬로 저장해야 할 수 있다.
    원문

    For any data that will be used to generate a command to be executed, keep as much of that data out of external control as possible. For example, in web applications, this may require storing the data locally in the session's state instead of sending it out to the client in a hidden form field.

    		 —
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해야 한다(CWE-602 방지). 공격자는 검사 뒤에 값을 바꾸거나 클라이언트에서 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있기 때문이다.
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.

    		 —
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않게 하거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리나 프레임워크를 쓴다. 예를 들어 ESAPI Encoding 컨트롤 [REF-45]이나 그와 비슷한 도구·라이브러리·프레임워크의 사용을 고려한다. 이들은 프로그래머가 출력을 오류가 덜 나게 인코딩하도록 돕는다.
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, consider using the ESAPI Encoding control [REF-45] or a similar tool, library, or framework. These will help the programmer encode outputs in a manner less prone to error.

    		 —
    아키텍처·설계(Architecture and Design) 매개변수화 데이터와 코드의 분리를 자동으로 강제하는 구조적 메커니즘이 있으면 쓴다. 출력을 만드는 곳마다 개발자가 인용·인코딩·검증을 직접 하지 않아도 이 메커니즘이 자동으로 처리할 수 있다. 명령 전체를 문자열 하나로 받아 셸을 호출하는 함수는 가능하면 인자를 하나씩 따로 받는 함수로 바꾼다. 이런 함수는 대개 인자를 알맞게 인용·필터링한다. 예: C의 system()은 실행할 명령 전체를 문자열로 받지만 execl()·execve() 등은 인자별 문자열 배열을 받는다. Windows의 CreateProcess()는 한 번에 명령 하나만 받고, Perl의 system()은 인자 배열을 주면 각 인자를 인용한다.
    원문

    If available, use structured mechanisms that automatically enforce the separation between data and code. These mechanisms may be able to provide the relevant quoting, encoding, and validation automatically, instead of relying on the developer to provide this capability at every point where output is generated.

    Some languages offer multiple functions that can be used to invoke commands. Where possible, identify any function that invokes a command shell using a single string, and replace it with a function that requires individual arguments. These functions typically perform appropriate quoting and filtering of arguments. For example, in C, the system() function accepts a string that contains the entire command to be executed, whereas execl(), execve(), and others require an array of strings, one for each argument. In Windows, CreateProcess() only accepts one command at a time. In Perl, if system() is provided with an array of arguments, then it will quote each of the arguments.

    		 —
    아키텍처·설계(Architecture and Design) 변환을 통한 강제 파일 이름이나 URL처럼 허용할 대상이 제한되거나 알려져 있으면 숫자 ID 같은 고정 입력값을 실제 파일 이름·URL에 대응시키고 그 밖의 입력은 모두 거부한다.
    원문

    When the set of acceptable objects, such as filenames or URLs, is limited or known, create a mapping from a set of fixed input values (such as numeric IDs) to the actual filenames or URLs, and reject all other inputs.

    Assume all input is malicious. Use an "accept known good" input validation strategy, i.e., use a list of acceptable inputs that strictly conform to specifications. Reject any input that does not strictly conform to specifications, or transform it into something that does.

    When performing input validation, consider all potentially relevant properties, including length, type of input, the full range of acceptable values, missing or extra inputs, syntax, consistency across related fields, and conformance to business rules. As an example of business rule logic, "boat" may be syntactically valid because it only contains alphanumeric characters, but it is not valid if the input is only expected to contain colors such as "red" or "blue."

    Do not rely exclusively on looking for malicious or malformed inputs. This is likely to miss at least one undesirable input, especially if the code's environment changes. This can give attackers enough room to bypass the intended validation. However, denylists can be useful for detecting potential attacks or determining which inputs are so malformed that they should be rejected outright.

    When constructing OS command strings, use stringent allowlists that limit the character set based on the expected value of the parameter in the request. This will indirectly limit the scope of an attack, but this technique is less important than proper output encoding and escaping.

    Note that proper output encoding, escaping, and quoting is the most effective solution for preventing OS command injection, although input validation may provide some defense-in-depth. This is because it effectively limits what will appear in output. Input validation will not always prevent OS command injection, especially if you are required to support free-form text fields that could contain arbitrary characters. For example, when invoking a mail program, you might need to allow the subject field to contain otherwise-dangerous inputs like ";" and ">" characters, which would need to be escaped or otherwise handled. In this case, stripping the character might reduce the risk of OS command injection, but it would produce incorrect behavior because the subject field would not be recorded as the user intended. This might seem to be a minor inconvenience, but it could be more important when the program relies on well-structured subject lines in order to pass messages to other components.

    Even if you make a mistake in your validation (such as forgetting one out of 100 input fields), appropriate encoding is still likely to protect you from injection-based attacks. As long as it is not done in isolation, input validation is still a useful technique, since it may significantly reduce your attack surface, allow you to detect some attacks, and provide other security benefits that proper encoding does not address.

    #include <stdio.h>

/* 운용자 콘솔에서 받은 장비 이름으로 진단 스크립트를 실행(여기서는 echo로 대신) */

{
    char cmd[128];
    snprintf(cmd, sizeof cmd, "echo diag start %s", device);  /* 입력을 셸 명령에 이어 붙임 */
    fflush(stdout);

}

static int valid_device(const char *s)
{
    size_t n = strlen(s);
    if (n == 0 || n > 16) return 0;
    for (size_t i = 0; i < n; ++i) {
        if (!islower((unsigned char)s[i]) && !isdigit((unsigned char)s[i])) return 0;
    }
    return 1;
}

static void run_diag(const char *device)
{
    if (!valid_device(device)) { puts("rejected: invalid device name"); return; }
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) {
        /* 셸 없이 고정 경로 프로그램에 인자 배열로 넘긴다 */

        execve("/bin/echo", argv, envp);
        _exit(127);
    }
    if (pid > 0) { waitpid(pid, NULL, 0); }
