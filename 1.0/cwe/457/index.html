    Use of Uninitialized Variable

    항목 내용
    추상화 수준 변형(Variant)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, C, C++, Perl, PHP
    원문 MITRE CWE-457 (CWE 5.0)

    한 줄 요약

    초기화되지 않은 변수를 사용해 예측할 수 없거나 의도하지 않은 결과가 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    코드가 초기화되지 않은 변수를 사용해 예측할 수 없거나 의도하지 않은 결과가 생기는 약점이다.

    배경(Background Details)

    C와 C++ 같은 일부 언어에서는 스택 변수가 기본적으로 초기화되지 않으며, 대개 함수가 호출되기 전의 스택 메모리 내용인 쓰레기 데이터가 들어 있다. 다른 언어나 조건에서는 명시적으로 초기화하지 않은 변수에 기본값이 주어질 수 있는데, 프로그램 논리에 따라 이 기본값이 보안에 영향을 줄 수 있다.

    원문(Description · Background Details)

    The code uses a variable that has not been initialized, leading to unpredictable or unintended results.

    In some languages such as C and C++, stack variables are not initialized by default. They generally contain junk data with the contents of stack memory before the function was invoked. In other languages or conditions, a variable that is not explicitly initialized can be given a default value that has security implications, depending on the logic of the program.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 초기화되지 않은 변수가 있다는 것은 때로 코드의 오타를 나타내기도 한다.
    구현(Implementation) 구현 C에서 일부 문자열 라이브러리에 초기화되지 않은 char *를 쓰면, 라이브러리가 문자열이 비어 있더라도 널 종료 문자가 항상 문자열 끝에 있다고 기대하므로 잘못된 결과를 반환한다.

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 / 무결성 / 가용성 / 기타 상황에 따라 다름 / 애플리케이션 데이터 읽기 초기화되지 않은 변수에는 대개 쓰레기 값이 들어 있어 일관성을 믿을 수 없다. 상황에 따라 서비스 거부로 이어지거나 제어 흐름을 예상하지 못한 방식으로 바꿀 수 있다. 민감한 정보가 들어 있을 수도 있어 그 변수를 출력에 쓰면 유출될 수 있다. 일부 경우 공격자가 이전 동작으로 변수를 '사전 초기화'(곧 변수 내용을 제어)할 수 있고, 이것이 코드 실행으로 이어질 수 있다.
    가용성 실행 논리 변경 / 예상하지 못한 상태 잠금 변수 검사가 통과하지 말아야 할 때 통과하면 경쟁조건(race condition)이 생길 수 있다.
    인가 / 기타 상황에 따라 다름 초기화되지 않은 문자열은 특히 위험한데, 많은 함수가 문자열 끝에, 그리고 끝에만 널 문자가 있다고 가정하기 때문이다.

    완화책(Potential Mitigations)¶

    원문 완화책 5건(수명주기 단계로 묶은 규칙은 색인에 있다).

    원문

    원문

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) 공격 표면 축소 중요 변수는 처음 사용하기 전에 초기화되게 한다 [REF-1485].
    원문

    빌드·컴파일(Build and Compilation) 컴파일·빌드 강화 대부분의 컴파일러는 경고를 켜면 초기화되지 않은 변수 사용을 지적한다.
    원문

    구현(Implementation) / 운용(Operation) — 변수를 명시적으로 선언할 필요가 없는 언어에서는 선언되지 않았거나 알 수 없는 변수를 보고하는 모드로 실행하거나 컴파일한다. 이런 보고는 변수 이름의 오타를 나타낼 수 있다. (유지보수 단계에도 해당)
    원문

    When using a language that does not require explicit declaration of variables, run or compile the software in a mode that reports undeclared or unknown variables. This may indicate the presence of a typographic error in the variable's name.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 거리 센서 운용 모드별 구동 펄스 폭이나 관성측정장치(IMU) 채널의 보정값처럼, 일부 분기나 생성자 경로에서만 값을 넣는 변수를 다른 경로에서 그대로 읽는다. 스택·레지스터에 남아 있던 이전 값이 쓰여 실행할 때마다 결과가 달라질 수 있다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>

/* 거리 센서 운용 모드별 구동 펄스 폭(us) */
enum RangeSensorMode { MODE_COARSE = 0, MODE_DETAIL = 1, MODE_STANDBY = 2 };

static int pulse_width_us(int mode)
{
    int width;
    if (mode == MODE_COARSE) {
        width = 40;
    } else if (mode == MODE_DETAIL) {
        width = 12;
    }
    /* 대기 모드와 알 수 없는 모드에서는 width가 정해지지 않는다 */
    return width;
}

int main(void)
{
    for (int m = MODE_COARSE; m <= MODE_STANDBY; ++m) {
        printf("mode %d pulse %d us\n", m, pulse_width_us(m));
    }
    return 0;
}

    대기 모드와 알 수 없는 모드에서는 width에 값을 넣지 않고 돌려준다. 스택에 남은 이전 값이 펄스 폭으로 쓰일 수 있어, 구동하면 안 되는 모드에서 구동이 일어날 수 있다.

    좋은 예

    #include <stdio.h>

/* 거리 센서 운용 모드별 구동 펄스 폭(us) */
enum RangeSensorMode { MODE_COARSE = 0, MODE_DETAIL = 1, MODE_STANDBY = 2 };

static int pulse_width_us(int mode)
{
    int width = 0;                     /* 선언과 동시에 안전값(구동 안 함)으로 초기화 */
    if (mode == MODE_COARSE) {
        width = 40;
    } else if (mode == MODE_DETAIL) {
        width = 12;
    } else {
        width = 0;                     /* 대기·알 수 없는 모드: 명시적으로 구동 금지 */
    }
    return width;
}

int main(void)
{
    for (int m = MODE_COARSE; m <= MODE_STANDBY; ++m) {
        printf("mode %d pulse %d us\n", m, pulse_width_us(m));
    }
    return 0;
}

    선언할 때 안전값(0: 구동 안 함)으로 초기화하고 마지막 else로 남은 모드를 명시적으로 처리한다.

    검증: 컴파일러 경고 — 나쁜 예에서 -Wsometimes-uninitialized 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-457 Demonstrative Example 2·3(일부 분기에서만 변수에 값을 넣음) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdio>

// 관성측정장치(IMU) 채널 설정
class ImuChannel {
public:
    explicit ImuChannel(int rate_hz) : rate_hz_(rate_hz) {}   // bias_ 를 초기화하지 않는다

    int corrected(int raw) const { return raw - bias_; }
    void calibrate(int bias) { bias_ = bias; }

private:
    int rate_hz_;
    int bias_;
};

int main() {
    ImuChannel gyro_x(400);
    // 보정 절차를 건너뛴 채 바로 값을 읽으면 bias_ 는 쓰레기 값이다
    std::printf("gyro x corrected %d\n", gyro_x.corrected(1000));
    return 0;
}

    생성자가 bias_를 초기화하지 않아, calibrate()를 부르기 전에 corrected()를 쓰면 쓰레기 값으로 보정한다.

    좋은 예

    #include <cstdio>

// 관성측정장치(IMU) 채널 설정
class ImuChannel {
public:
    explicit ImuChannel(int rate_hz) : rate_hz_(rate_hz) {}

    int corrected(int raw) const { return raw - bias_; }
    void calibrate(int bias) { bias_ = bias; calibrated_ = true; }
    bool calibrated() const { return calibrated_; }

private:
    int rate_hz_ = 0;
    int bias_ = 0;              // 멤버 기본 초기화: 어떤 생성자로 만들어도 값이 정해진다
    bool calibrated_ = false;
};

int main() {
    ImuChannel gyro_x(400);
    if (!gyro_x.calibrated()) {
        std::puts("gyro x not calibrated: using raw value");
    }
    std::printf("gyro x corrected %d\n", gyro_x.corrected(1000));
    return 0;
}

    모든 멤버에 기본 초기화 값을 주어 어느 생성자를 쓰든 값이 정해지고, 보정 여부는 calibrated()로 따로 확인한다.

    검증: cppcheck — 나쁜 예에서 uninitMemberVar 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-457 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(언어상 생기지 않음): C#도 명확한 할당 규칙으로 할당 전 지역 변수 읽기를 컴파일 오류(CS0165)로 막고, 필드·배열 요소는 기본값으로 초기화된다. 다만 SkipLocalsInit을 건 unsafe 코드의 stackalloc처럼 초기화를 건너뛰는 경계는 C 지침을 따른다. 필드 기본값(0·null)을 정상값처럼 믿는 논리 오류는 해당 약점(예: CWE-476)에서 다룬다.

    Java — 예시 없음(언어상 생기지 않음): Java는 명확한 할당(definite assignment) 규칙 때문에 값을 넣지 않은 지역 변수를 읽으면 컴파일 오류가 나고, 필드는 0·false·null로 자동 초기화되므로 쓰레기 값을 읽는 일은 생기지 않는다. 다만 필드 기본값(0·null)을 정상값처럼 믿고 쓰는 논리 오류는 남는다. 이 오류는 널 포인터 역참조(CWE-476) 같은 다른 약점에서 다룬다.

    Python — 예시 없음(언어상 생기지 않음): Python 변수는 값을 넣어야 생기므로 초기화하지 않은 메모리의 쓰레기 값을 읽는 일이 없다. 일부 분기에서만 값을 넣은 변수를 읽으면 실행 중 UnboundLocalError·NameError 예외가 나고 처리하지 않으면 비정상 종료하므로, 모든 분기에서 값을 정하거나 정적 분석(pylint, possibly-undefined 오류 코드를 켠 mypy 등)으로 할당 전 사용을 찾는다. ctypes 구조체는 0으로 초기화된다.

    MITRE 원문 예시(Demonstrative Examples, 영문 3건)

    Example 1. This code prints a greeting using information stored in a POST request:

    Bad / PHP

    if (isset($_POST['names'])) {
  $nameArray = $_POST['names'];
}
echo "Hello " . $nameArray['first'];

    This code checks if the POST array 'names' is set before assigning it to the $nameArray variable. However, if the array is not in the POST request, $nameArray will remain uninitialized. This will cause an error when the array is accessed to print the greeting message, which could lead to further exploit.

    Example 2. The following switch statement is intended to set the values of the variables aN and bN before they are used:

    Bad / C

    int aN, Bn;
switch (ctl) {

  case -1:
    aN = 0;
    bN = 0;
    break;

  case 0:
    aN = i;
    bN = -i;
    break;

  case 1:
    aN = i + NEXT_SZ;
    bN = i - NEXT_SZ;
    break;

  default:
    aN = -1;
    aN = -1;
    break;

}
repaint(aN, bN);

    In the default case of the switch statement, the programmer has accidentally set the value of aN twice. As a result, bN will have an undefined value. Most uninitialized variable issues result in general software reliability problems, but if attackers can intentionally trigger the use of an uninitialized variable, they might be able to launch a denial of service attack by crashing the program. Under the right circumstances, an attacker may be able to control the value of an uninitialized variable by affecting the values on the stack prior to the invocation of the function.

    Example 3. This example will leave test_string in an unknown condition when i is the same value as err_val, because test_string is not initialized (CWE-456). Depending on where this code segment appears (e.g. within a function body), test_string might be random if it is stored on the heap or stack. If the variable is declared in static memory, it might be zero or NULL. Compiler optimization might contribute to the unpredictability of this address.

    Bad / C

                    char *test_string;

                if (i != err_val)

                {

  test_string = "Hello World!";

                }

                printf("%s", test_string);

    When the printf() is reached, test_string might be an unexpected address, so the printf might print junk strings (CWE-457). To fix this code, there are a couple approaches to making sure that test_string has been properly set once it reaches the printf(). One solution would be to set test_string to an acceptable default before the conditional:

    Good / C

                  char *test_string = "Done at the beginning";

                if (i != err_val)

                {

  test_string = "Hello World!";

                }

                printf("%s", test_string);

    Another solution is to ensure that each branch of the conditional - including the default/else branch - could ensure that test_string is set:

    Good / C

                  char *test_string;

                if (i != err_val)

                {

  test_string = "Hello World!";

                }

                else {

  test_string = "Done on the other side!";

                }

                printf("%s", test_string);

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)
