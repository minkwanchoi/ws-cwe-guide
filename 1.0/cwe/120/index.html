    Buffer Copy without Checking Size of Input

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    MITRE 매핑 권고 검토 후 허용(Allowed-with-Review)
    원문(Mapping Notes)

    Rationale: There are some indications that this CWE ID might be misused and selected simply because it mentions "buffer overflow" - an increasingly vague term. This CWE entry is only appropriate for "Buffer Copy" operations (not buffer reads), in which where there is no "Checking [the] Size of Input", and (by implication of the copy) writing past the end of the buffer.

    Comments: If the vulnerability being analyzed involves out-of-bounds reads, then consider CWE-125 or descendants. For root cause analysis: if there is any input validation, consider children of CWE-20 such as CWE-1284. If there is a calculation error for buffer sizes, consider CWE-131 or similar.
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++, Assembly
    원문 MITRE CWE-120 (CWE 5.0)

    한 줄 요약

    입력 버퍼가 출력 버퍼보다 작은지 확인하지 않고 입력 버퍼를 출력 버퍼로 복사하는 약점이다.

    설명(Description)¶

    제품이 입력 버퍼의 크기가 출력 버퍼의 크기보다 작은지 확인하지 않고 입력 버퍼를 출력 버퍼로 복사하는 약점이다.

    원문(Description)

    The product copies an input buffer to an output buffer without verifying that the size of the input buffer is less than the size of the output buffer.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 메모리 수정 / 허가되지 않은 코드·명령 실행 버퍼 오버플로는 흔히 임의 코드 실행에 이용될 수 있고, 이는 대개 제품의 암묵적 보안 정책 범위를 벗어나며 흔히 다른 보안 서비스를 무력화하는 데 쓰일 수 있다.
    가용성 메모리 수정 / 서비스 거부: 비정상 종료·재시작 / 서비스 거부: 자원 소모(CPU) 버퍼 오버플로는 일반적으로 비정상 종료로 이어지며, 제품을 무한 루프에 빠뜨리는 등 가용성을 떨어뜨리는 다른 공격도 가능하다.

    완화책(Potential Mitigations)¶

    원문 완화책 13건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    CWE 단계(Phase) 전략 요지 효과성
    요구사항(Requirements) 언어 선택 이 약점이 생기지 않거나 피하기 쉬운 구조를 제공하는 언어를 쓴다. 예를 들어 Java, Perl처럼 자체 메모리 관리를 하는 많은 언어는 버퍼 오버플로가 생기지 않고 Ada, C#은 대개 오버플로 보호를 제공하지만 프로그래머가 끌 수 있으며, 언어 자체가 이론상 안전해도 네이티브 코드와의 인터페이스에서는 여전히 오버플로가 생길 수 있음에 유의한다.
    원문

    Use a language that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    For example, many languages that perform their own memory management, such as Java and Perl, are not subject to buffer overflows. Other languages, such as Ada and C#, typically provide overflow protection, but the protection can be disabled by the programmer.

    Be wary that a language's interface to native code may still be subject to overflows, even if the language itself is theoretically safe.

    		 —

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) 라이브러리·프레임워크 활용 이 약점이 생기지 않거나 피하기 쉬운 구조를 제공하는 검증된 라이브러리나 프레임워크를 쓴다. 예로 Messier와 Viega의 Safe C String Library(SafeStr) [REF-57], Microsoft의 Strsafe.h [REF-56]가 있으며, 오버플로가 생기기 쉬운 문자열 처리 함수의 더 안전한 버전을 제공한다.
    원문

    Use a vetted library or framework that does not allow this weakness to occur or provides constructs that make this weakness easier to avoid.

    Examples include the Safe C String Library (SafeStr) by Messier and Viega [REF-57], and the Strsafe.h library from Microsoft [REF-56]. These libraries provide safer versions of overflow-prone string-handling functions.

    		 많은 버퍼 오버플로는 문자열과 관련이 없으므로 완전한 해결책이 아니다.
    아키텍처·설계(Architecture and Design) — 클라이언트 측에서 하는 보안 검사는 서버 측에서도 똑같이 수행해야 한다(CWE-602 방지). 공격자는 검사 뒤에 값을 바꾸거나 클라이언트에서 검사를 아예 없앤 뒤 수정된 값을 서버에 보낼 수 있기 때문이다.
    원문

    For any security checks that are performed on the client side, ensure that these checks are duplicated on the server side, in order to avoid CWE-602. Attackers can bypass the client-side checks by modifying values after the checks have been performed, or by changing the client to remove the client-side checks entirely. Then, these modified values would be submitted to the server.

    		 —
    아키텍처·설계(Architecture and Design) 변환을 통한 강제 파일 이름이나 URL처럼 허용할 대상이 제한되거나 알려져 있으면 숫자 ID 같은 고정 입력값을 실제 파일 이름·URL에 대응시키고 그 밖의 입력은 모두 거부한다.
    원문

    When the set of acceptable objects, such as filenames or URLs, is limited or known, create a mapping from a set of fixed input values (such as numeric IDs) to the actual filenames or URLs, and reject all other inputs.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 실행 환경 강화 작업에 필요한 최소 권한으로 코드를 실행하고 [REF-76], 가능하면 한 작업에만 쓰는 제한된 권한의 격리된 계정을 만들어 공격이 성공해도 나머지 소프트웨어나 환경에 바로 접근하지 못하게 한다(예: 데이터베이스 애플리케이션은 특히 일상 운영에서 데이터베이스 관리자 권한으로 실행할 필요가 거의 없다). (유지보수 단계에도 해당)
    원문

    Run your code using the lowest privileges that are required to accomplish the necessary tasks [REF-76]. If possible, create isolated accounts with limited privileges that are only used for a single task. That way, a successful attack will not immediately give the attacker access to the rest of the software or its environment. For example, database applications rarely need to run as the database administrator, especially in day-to-day operations.

    		 —
    아키텍처·설계(Architecture and Design) / 운용(Operation) 샌드박스·격리 프로세스와 운영체제 사이에 엄격한 경계를 두는 'jail'이나 비슷한 샌드박스(sandbox) 환경에서 코드를 실행하면, 특정 디렉터리에서 접근할 수 있는 파일이나 소프트웨어가 실행할 수 있는 명령을 제한할 수 있다. 운영체제 수준의 예로 Unix chroot jail, AppArmor, SELinux가 있고, 관리형 코드도 일부 보호를 줄 수 있다(예: Java SecurityManager의 java.io.FilePermission으로 파일 작업 제한을 지정). 단, 적용하기 어려울 수 있고, 운영체제에 미치는 영향만 제한할 뿐이어서 애플리케이션의 나머지 부분은 여전히 침해될 수 있다. CWE-243 등 jail 관련 약점을 피하도록 주의한다. (유지보수 단계에도 해당)
    원문

    Run the code in a "jail" or similar sandbox environment that enforces strict boundaries between the process and the operating system. This may effectively restrict which files can be accessed in a particular directory or which commands can be executed by the software.

    OS-level examples include the Unix chroot jail, AppArmor, and SELinux. In general, managed code may provide some protection. For example, java.io.FilePermission in the Java SecurityManager allows the software to specify restrictions on file operations.

    This may not be a feasible solution, and it only limits the impact to the operating system; the rest of the application may still be subject to compromise.

    Be careful to avoid CWE-243 and other weaknesses related to jails.

    		 제한적(Limited) — 이 완화책의 효과는 사용하는 샌드박스나 jail의 예방 능력에 달려 있으며, 공격자를 특정 시스템 호출로 제한하거나 접근 가능한 파일 시스템 범위를 줄이는 등 공격 범위를 줄이는 데만 도움이 될 수도 있다.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 일부 컴파일러나 컴파일러 확장이 제공하는 자동 버퍼 오버플로 탐지 기능을 쓴다. 예로 Microsoft Visual Studio의 /GS 플래그, Fedora/Red Hat의 FORTIFY_SOURCE GCC 플래그, StackGuard, ProPolice가 있으며 카나리 기반 탐지와 범위·인덱스 검사 등을 제공한다(카나리 기반 탐지는 D3FEND D3-SFCV [REF-1334] 참고). (유지보수 단계에도 해당)
    원문

    Use automatic buffer overflow detection mechanisms that are offered by certain compilers or compiler extensions. Examples include: the Microsoft Visual Studio /GS flag, Fedora/Red Hat FORTIFY_SOURCE GCC flag, StackGuard, and ProPolice, which provide various mechanisms including canary-based detection and range/index checking.

    D3-SFCV (Stack Frame Canary Validation) from D3FEND [REF-1334] discusses canary-based detection in detail.

    		 심층 방어(Defense in Depth) — 이 기능들은 일부 유형의 오버플로만 탐지하므로 반드시 완전한 해결책은 아니다. 또한 대개 애플리케이션을 종료하는 방식으로 대응하므로 결과는 여전히 서비스 거부다.
    구현(Implementation) — 메모리를 할당·관리할 때 다음 규칙을 따르는 것을 고려한다: 버퍼가 지정한 만큼 큰지 다시 확인하고, strncpy()처럼 복사할 바이트 수를 받는 함수는 대상 버퍼 크기가 소스 버퍼 크기와 같으면 문자열을 NUL로 종단하지 않을 수 있음에 유의하며, 루프에서 버퍼에 접근하면 경계를 검사해 할당 공간 너머에 쓸 위험이 없게 하고, 필요하면 복사·연결 함수에 넘기기 전에 모든 입력 문자열을 적당한 길이로 자른다.
    원문

    Consider adhering to the following rules when allocating and managing an application's memory:

    - Double check that your buffer is as large as you specify.

    - When using functions that accept a number of bytes to copy, such as strncpy(), be aware that if the destination buffer size is equal to the source buffer size, it may not NULL-terminate the string.

    - Check buffer boundaries if accessing the buffer in a loop and make sure there is no danger of writing past the allocated space.

    - If necessary, truncate all input strings to a reasonable length before passing them to the copy and concatenation functions.

    		 —
    구현(Implementation) 입력값 검증 모든 입력을 악의적이라고 가정하고, 명세에 엄격히 맞는 입력만 받는 허용목록('accept known good') 방식으로 검증해 맞지 않는 입력은 거부하거나 맞게 변환한다. 검증할 때는 길이·유형·허용 값 전체 범위·누락/추가 입력·구문·관련 필드 간 일관성·업무 규칙을 모두 고려한다(예: 'boat'는 영숫자만 있어 구문상 유효하지만 'red'·'blue' 같은 색상만 받는 필드라면 유효하지 않다). 악의적이거나 잘못된 입력을 찾는 방식(거부목록)에만 의존하지 않는다. 이 방식은 특히 코드 환경이 바뀔 때 원치 않는 입력을 하나 이상 놓치기 쉬워 검증이 우회될 수 있다. 다만 거부목록은 공격 탐지나 즉시 거부할 정도로 잘못된 입력을 가려내는 데는 쓸모가 있을 수 있다.
    원문

    Assume all input is malicious. Use an "accept known good" input validation strategy, i.e., use a list of acceptable inputs that strictly conform to specifications. Reject any input that does not strictly conform to specifications, or transform it into something that does.

    When performing input validation, consider all potentially relevant properties, including length, type of input, the full range of acceptable values, missing or extra inputs, syntax, consistency across related fields, and conformance to business rules. As an example of business rule logic, "boat" may be syntactically valid because it only contains alphanumeric characters, but it is not valid if the input is only expected to contain colors such as "red" or "blue."

    Do not rely exclusively on looking for malicious or malformed inputs. This is likely to miss at least one undesirable input, especially if the code's environment changes. This can give attackers enough room to bypass the intended validation. However, denylists can be useful for detecting potential attacks or determining which inputs are so malformed that they should be rejected outright.

    		 —
    운용(Operation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 프로그램의 실행 파일과 라이브러리를 메모리에 무작위로 배치하는 기능이나 확장을 써서 실행·컴파일한다. 주소를 예측할 수 없게 되어 공격자가 악용할 코드로 안정적으로 점프하는 것을 막을 수 있다. 예로 ASLR(Address Space Layout Randomization) [REF-58] [REF-60]과 PIE(Position-Independent Executables) [REF-64]가 있다. 가져온 모듈도 기본 메모리 주소가 다른 모듈과 겹치면 무작위로 만든 주소로 재배치될 수 있다(Windows의 rebasing, Linux의 prelinking [REF-1332]). 단, 라이브러리용 ASLR은 실행 시 라이브러리를 재배치해야 해서 prelink의 목적을 없애므로 prelink와 함께 쓸 수 없다. 자세한 내용은 D3FEND의 D3-SAOR(Segment Address Offset Randomization) [REF-1335]에 있다. (유지보수 단계에도 해당)
    원문

    Run or compile the software using features or extensions that randomly arrange the positions of a program's executable and libraries in memory. Because this makes the addresses unpredictable, it can prevent an attacker from reliably jumping to exploitable code.

    Examples include Address Space Layout Randomization (ASLR) [REF-58] [REF-60] and Position-Independent Executables (PIE) [REF-64]. Imported modules may be similarly realigned if their default memory addresses conflict with other modules, in a process known as "rebasing" (for Windows) and "prelinking" (for Linux) [REF-1332] using randomly generated addresses. ASLR for libraries cannot be used in conjunction with prelink since it would require relocating the libraries at run-time, defeating the whole purpose of prelinking.

    For more information on these techniques see D3-SAOR (Segment Address Offset Randomization) from D3FEND [REF-1335].

    		 심층 방어(Defense in Depth) — 이 기법들은 완전한 해결책이 아니다. 예를 들어 익스플로잇은 코드 실행의 신뢰성을 높이려고 메모리 주소를 노출하는 버그를 흔히 이용하며 [REF-1337], 부채널 공격으로 ASLR을 우회할 수 있음도 밝혀졌다 [REF-1333].
    빌드·컴파일(Build and Compilation) / 운용(Operation) — 지금까지 컴파일러나 OS 수준의 완화 기술 대부분은 버퍼 오버플로 문제의 일부만 다루며 그 일부에 대해서도 완전한 보호를 제공하는 일은 드물다. 실행할 때마다 바뀌는 알 수 없는 값을 공격자가 추측하게 하는 것처럼 공격자의 작업량을 늘리는 전략을 구현하는 것이 좋은 관행이다. (유지보수 단계에도 해당)
    원문

    Most mitigating technologies at the compiler or OS level to date address only a subset of buffer overflow problems and rarely provide complete protection against even that subset. It is good practice to implement strategies to increase the workload of an attacker, such as leaving the attacker to guess an unknown value that changes every program execution.

    		 —
    구현(Implementation) — strcpy를 strncpy로 바꾸는 것처럼, 길이 제한 없는 복사 함수를 길이 인자를 받는 대응 함수로 바꾼다. 그런 함수가 없으면 만든다.
    원문

    Replace unbounded copy functions with analogous functions that support length arguments, such as strcpy with strncpy. Create these if they are not available.

    		 보통(Moderate) — 이 방법도 경계값 오류(off-by-one, CWE-193), 버퍼 길이 계산 오류(CWE-131) 같은 계산 실수에는 여전히 취약하다.

    운용(Operation) 실행 환경 강화 하드웨어 NX·XD 비트를 이용한 데이터 실행 방지(Data Execution Protection)를 제공하는 CPU와 운영체제, 또는 PaX [REF-60] [REF-61]처럼 이를 소프트웨어로 흉내 내는 기법을 쓴다. 이 기법들은 실행되는 모든 명령이 코드 세그먼트에 속한 메모리 주소에만 있도록 보장한다(자세한 내용은 D3FEND의 D3-PSEP(Process Segment Execution Prevention) [REF-1336]).
    원문

    Use a CPU and operating system that offers Data Execution Protection (using hardware NX or XD bits) or the equivalent techniques that simulate this feature in software, such as PaX [REF-60] [REF-61]. These techniques ensure that any instruction executed is exclusively at a memory address that is part of the code segment.

    For more information on these techniques see D3-PSEP (Process Segment Execution Prevention) from D3FEND [REF-1336].

    		 심층 방어(Defense in Depth) — 버퍼 오버플로로 인접 변수를 덮어써 소프트웨어 상태를 위험하게 바꿀 수 있으므로 완전한 해결책이 아니다. 또한 자기 수정 코드가 필요한 경우에는 쓸 수 없고, 대개 애플리케이션 종료로 대응하므로 공격은 여전히 서비스 거부를 일으킬 수 있다.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 4건)

    Example 1. The following code asks the user to enter their last name and then attempts to store the value entered in the last_name array.

    Bad / C

    char last_name[20];
printf ("Enter your last name: ");
scanf ("%s", last_name);

    The problem with the code above is that it does not restrict or limit the size of the name entered by the user. If the user enters "Very_very_long_last_name" which is 24 characters long, then a buffer overflow will occur since the array can only hold 20 characters total.

    Example 2. The following code attempts to create a local copy of a buffer to perform some manipulations to the data.

    Bad / C

    void manipulate_string(char * string){
  char buf[24];
  strcpy(buf, string);
  ...
}

    However, the programmer does not ensure that the size of the data pointed to by string will fit in the local buffer and copies the data with the potentially dangerous strcpy() function. This may result in a buffer overflow condition if an attacker can influence the contents of the string parameter.

    Example 3. The code below calls the gets() function to read in data from the command line.

    Bad / C

      char buf[24];
  printf("Please enter your name and press <Enter>\n");
  gets(buf);
  ...
}

    However, gets() is inherently unsafe, because it copies all input from STDIN to the buffer without checking size. This allows the user to provide a string that is larger than the buffer size, resulting in an overflow condition.

    Example 4. In the following example, a server accepts connections from a client and processes the client request. After accepting a client connection, the program will obtain client information using the gethostbyaddr method, copy the hostname of the client that connected to a local variable and output the hostname of the client to a log file.

    Bad / C

    ...

  struct hostent *clienthp;
  char hostname[MAX_LEN];

  // create server socket, bind to server address and listen on socket
  ...

  // accept client connections and process requests
  int count = 0;
  for (count = 0; count < MAX_CONNECTIONS; count++) {

    int clientlen = sizeof(struct sockaddr_in);
    int clientsocket = accept(serversocket, (struct sockaddr *)&clientaddr, &clientlen);

    if (clientsocket >= 0) {

      clienthp = gethostbyaddr((char*) &clientaddr.sin_addr.s_addr, sizeof(clientaddr.sin_addr.s_addr), AF_INET);
      strcpy(hostname, clienthp->h_name);
      logOutput("Accepted client connection from host ", hostname);

      // process client request
      ...
      close(clientsocket);

    }

  }
  close(serversocket);

...

    However, the hostname of the client that connected may be longer than the allocated size for the local hostname variable. This will result in a buffer overflow when copying the client hostname to the local variable using the strcpy method.

    환경 지침 6건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.

    축 지침
    운영체제/런타임 (2건) WIN-04 MSVC 보안 빌드 옵션, PSOS-06 레거시 툴체인 정적 분석
    IDE/컴파일러 (3건) WRW-05 하드닝 옵션 지원 확인, MSVC-04 안전하지 않은 CRT 함수 금지, GCC-03 hosted 타깃 하드닝
    개발 언어 (1건) LC-04 금지 문자열 함수 대체
