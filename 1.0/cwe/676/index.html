    Use of Potentially Dangerous Function

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: C, C++
    원문 MITRE CWE-676 (CWE 5.0)

    한 줄 요약

    잘못 쓰면 취약점이 생길 수 있는 잠재적으로 위험한 함수를 호출해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 잘못 쓰면 취약점을 만들 수 있는 잠재적으로 위험한 함수를 호출하는 약점이다. 단, 그 함수는 안전하게 쓸 수도 있다.

    원문(Description)

    The product invokes a potentially dangerous function that could introduce a vulnerability if it is used incorrectly, but the function can also be used safely.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    기타 상황에 따라 다름 / 품질 저하 / 예상하지 못한 상태 함수를 잘못 쓰면 보안 문제가 생길 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 1건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: D-03 언어·라이브러리·외부 구성요소 선정, D-09 설계 보안성 검토

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    빌드·컴파일(Build and Compilation) / 구현(Implementation) — 금지 API 함수 목록을 정해 개발자가 쓰지 못하게 하고 더 안전한 대안을 제공한다. 일부 경우 Microsoft SDL의 "banned.h" 포함 파일처럼 자동 코드 분석 도구나 컴파일러가 금지 함수 사용을 찾아내도록 설정할 수 있다. [REF-554] [REF-1009] [REF-7]
    원문

    Identify a list of prohibited API functions and prohibit developers from using these functions, providing safer alternatives. In some cases, automatic code analysis tools or the compiler can be instructed to spot use of prohibited functions, such as the "banned.h" include file from Microsoft's SDL. [REF-554] [REF-1009] [REF-7]

    원문 완화책 없음

    유지보수 (본문 제7장)¶

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 운용자 콘솔의 장비 제어 명령을 감사 로그 한 줄로 만들거나(C), 정비 단말 명령 'GAIN <값>'의 값 글자를 수신기 이득으로 바꾼다(C++). 쓰는 함수가 대상 크기나 변환 오류를 알 수 없는 '위험한 함수'인지가 문제다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>

#define LOG_LINE 32

/* 운용자 콘솔의 장비 제어 명령을 감사 로그 한 줄로 만든다 */
static void audit_line(char *out, const char *operator_id, const char *command)
{
    strcpy(out, "OP=");           /* 대상 크기를 모르는 함수: 길이 검사를 호출자에게 떠넘긴다 */
    strcat(out, operator_id);
    strcat(out, " CMD=");
    strcat(out, command);
}

int main(void)
{
    char line[LOG_LINE];
    audit_line(line, "OPR-KIM-0417", "HOLD HEATER 3");
    puts(line);
    return 0;
}

    strcpy·strcat은 대상 버퍼 크기를 받지 않아 모든 길이 검사를 호출자에게 떠넘긴다. 운용자 ID와 명령이 조금만 길어도(이 예에서 종단 문자 포함 34바이트) 32바이트 버퍼를 넘어 스택을 덮어쓴다.

    좋은 예

    #include <stdio.h>

#define LOG_LINE 64   /* 운용자 ID·명령의 최대 길이(ICD)에 맞춰 잡는다 */

/* 운용자 콘솔의 장비 제어 명령을 감사 로그 한 줄로 만든다. 성공 0, 잘림 1, 실패 -1(out은 빈 문자열) */
static int audit_line(char *out, size_t out_size, const char *operator_id, const char *command)
{
    /* 대상 크기를 인자로 받는 함수를 쓰고 반환값으로 잘림을 확인한다 */
    int n = snprintf(out, out_size, "OP=%s CMD=%s", operator_id, command);
    if (n < 0) {
        out[0] = '\0';      /* 실패하면 버퍼 내용이 보장되지 않는다 */
        return -1;
    }
    return (size_t)n >= out_size ? 1 : 0;
}

int main(void)
{
    char line[LOG_LINE];
    int rc = audit_line(line, sizeof line, "OPR-KIM-0417", "HOLD HEATER 3");
    if (rc < 0) {
        puts("audit line failed: operator notified");
    } else if (rc > 0) {
        /* 잘림은 기록 쪽에서 처리한다: 표시를 남기고 알리되 명령 처리는 막지 않는다 */
        line[LOG_LINE - 2] = '~';
        puts("audit line truncated: operator notified");
    }
    puts(line);
    return 0;
}

    대상 크기를 인자로 받는 snprintf를 쓰고 반환값으로 잘림을 확인한다. 버퍼 크기는 운용자 ID·명령의 최대 길이(ICD)에 맞춰 잡고, 사업 차원에서 금지 함수 목록과 대체 API를 정해 빌드에서 막는다(I-02·LC-04). 잘리면 잘림 표시를 남기고 운용자에게 알린다. 감사 기록 실패가 운용 통제 명령 자체를 막지 않도록 처리 방침은 설계 단계의 오류 처리·안전 상태 설계에서 정한다.

    검증: clang-tidy — 나쁜 예에서 clang-analyzer-security.insecureAPI.strcpy 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-676 Demonstrative Example 1(크기 확인 없이 strcpy로 지역 버퍼에 복사) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) API 오용 7-2 '위험하다고 알려진 함수 사용'(인쇄 196쪽) 참고 — 이 항목의 표 1 대응 CWE는 CWE-242이고, 참고문헌에 CWE-676이 함께 실려 있다

    C++

    나쁜 예

    #include <cstdio>
#include <cstdlib>
#include <string>

// 정비 단말 명령 "GAIN <값>"의 값 부분으로 수신기 이득을 설정한다
class ReceiverConfig {
public:
    void set_gain_from_text(const std::string &arg) {
        gain_db_ = std::atoi(arg.c_str());   // 숫자가 아니거나 범위를 넘어도 오류를 알리지 않는다
    }
    int gain_db() const { return gain_db_; }

private:
    int gain_db_ = 20;
};

int main() {
    ReceiverConfig rx;
    rx.set_gain_from_text("2O");             // 숫자 0 대신 영문자 O를 입력한 실수
    std::printf("gain set to %d dB\n", rx.gain_db());
    return 0;
}

    std::atoi는 숫자가 아닌 글자나 범위 초과를 오류로 알리지 않는다. '2O'(숫자 0 대신 영문자 O)를 2로 바꿔 이득이 20 dB가 아니라 2 dB로 조용히 설정된다.

    좋은 예

    #include <charconv>
#include <cstdio>
#include <string>
#include <system_error>

// 정비 단말 명령 "GAIN <값>"의 값 부분으로 수신기 이득을 설정한다
class ReceiverConfig {
public:
    bool set_gain_from_text(const std::string &arg) {
        int value = 0;
        const char *end = arg.data() + arg.size();
        auto [ptr, ec] = std::from_chars(arg.data(), end, value);
        if (ec != std::errc{} || ptr != end || value < 0 || value > 60) {
            return false;                    // 변환 오류·남는 글자·범위 밖이면 거부
        }
        gain_db_ = value;
        return true;
    }
    int gain_db() const { return gain_db_; }

private:
    int gain_db_ = 20;
};

int main() {
    ReceiverConfig rx;
    if (!rx.set_gain_from_text("2O")) {      // 숫자 0 대신 영문자 O를 입력한 실수
        std::puts("rejected: GAIN value is not a number in 0..60");
    }
    std::printf("gain set to %d dB\n", rx.gain_db());
    return 0;
}

    std::from_chars로 변환 오류와 남는 글자를 확인하고 허용 범위(0~60)를 검사해, 어긋나면 기존 설정을 유지하고 명령을 거부한다.

    검증: clang-tidy — 나쁜 예에서 cert-err34-c 또는 bugprone-unchecked-string-to-number-conversion 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-676 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(MITRE 적용 언어 밖): MITRE는 CWE-676의 적용 언어를 C·C++로 둔다. C#의 위험한 API(BinaryFormatter, 보안 용도의 System.Random 등)는 CWE-502·CWE-338 같은 해당 약점의 해설·지침을 따르고, unsafe·P/Invoke 경계의 네이티브 함수 사용에는 C 예시를 적용한다(LCS-02).

    Java — 예시 없음(MITRE 적용 언어 밖): MITRE는 CWE-676의 적용 언어를 C·C++로 두며, 대상은 strcpy처럼 C 라이브러리의 위험한 함수다. Java의 위험한 API(신뢰할 수 없는 데이터의 역직렬화, 폐기 예정 API 등)는 CWE-502·CWE-477 같은 해당 약점의 해설·지침을 따르고, JNI로 부르는 네이티브 코드에는 C 예시를 적용한다(LJ-08).

    Python — 예시 없음(MITRE 적용 언어 밖): MITRE는 CWE-676의 적용 언어를 C·C++로 두며, 대상은 strcpy처럼 C 라이브러리의 위험한 함수다. Python의 위험한 함수(eval·exec·pickle.loads·안전하지 않은 Loader의 yaml.load 등)는 CWE-95·CWE-502 같은 해당 약점의 해설·지침을 따르고, ctypes·C 확장 모듈로 부르는 C 함수에는 C 예시를 적용한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 1건)

    Example 1. The following code attempts to create a local copy of a buffer to perform some manipulations to the data.

    Bad / C

    void manipulate_string(char * string){
  char buf[24];
  strcpy(buf, string);
  ...
}

    However, the programmer does not ensure that the size of the data pointed to by string will fit in the local buffer and copies the data with the potentially dangerous strcpy() function. This may result in a buffer overflow condition if an attacker can influence the contents of the string parameter.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석(바이너리·바이트코드) SOAR [REF-1479]에 따르면 다음 탐지 기법이 유용할 수 있다 — 비용 효과 매우 높음: 바이트코드 약점 분석(디스어셈블러와 소스코드 약점 분석 포함), 바이너리 약점 분석(디스어셈블러와 소스코드 약점 분석 포함). 부분 적용에 비용 효과적: 바이너리/바이트코드 품질 분석, 바이너리/바이트코드 단순 추출기(strings, ELF 판독기 등).

    Highly cost effective:

    Debugger

    Cost effective for partial coverage:

    단계 지침
    요구사항 분석 —
    설계 금지 함수 목록과 대체 함수를 코딩규칙(coding rule)에 정의한다.
    구현(C·C++) gets, strcpy, strcat, sprintf, vsprintf, scanf(%s), strtok, atoi 등을 금지하고 fgets, snprintf, strtol 등으로 대체한다.
    구현(Java) Thread.stop(), Runtime.runFinalizersOnExit() 등 폐기 API를 사용하지 않는다.
    통합 및 시험 금지 함수 목록 기반 정적 분석·grep 점검을 빌드 파이프라인에 포함한다.
    유지보수 금지 함수 목록을 주기적으로 갱신하고 레거시 코드 정비 계획을 수립한다.
    임베디드 고려 벤더 라이브러리·레거시 코드에서도 사용 여부를 점검하고, 금지 함수에 #pragma GCC poison을 적용한다.
