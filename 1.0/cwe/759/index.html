    Use of a One-Way Hash without a Salt

    항목 내용
    추상화 수준 변형(Variant)
    상태 미완성(Incomplete)
    소속 「보안약점 점검 목록」(44개)
    가이드 적용성 조건부 — 사용자 계정·비밀번호 사용
    적용 플랫폼 언어 무관
    원문 MITRE CWE-759 (CWE 5.0)

    이름 표기

    「소프트웨어 개발보안 가이드」(2021. 11.)의 항목명은 '솔트 없이 일방향 해쉬함수 사용'(부록 인쇄 349쪽은 '해쉬 함수')이다. 이 가이드는 외래어 표기 '해시'를 쓴 과학기술정보통신부·한국인터넷진흥원 「Python 시큐어코딩 가이드」(2023. 12.)의 항목명을 따른다.

    한 줄 요약

    비밀번호처럼 되돌릴 수 없어야 하는 입력을 해시할 때 솔트를 쓰지 않아 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 비밀번호처럼 되돌릴 수 없어야 하는 입력에 일방향 암호 해시를 적용하면서 입력의 일부로 솔트(salt)를 쓰지 않는다.

    배경(Background Details)

    암호학에서 솔트(salt)는 사전 공격을 더 어렵게 하려고 해싱 전에 입력에 무작위 데이터를 덧붙이는 것을 가리킨다.

    원문(Description · Background Details)

    The product uses a one-way cryptographic hash against an input that should not be reversible, such as a password, but the product does not also use a salt as part of the input.

    In cryptography, salt refers to some random addition of data to an input before hashing to make dictionary attacks more difficult.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 실현(REALIZATION): 이 약점은 아키텍처 보안 전술을 구현하는 과정에서 생긴다.

    영향(Common Consequences)¶

    영역 영향 설명
    접근 통제 보호 메커니즘 우회 / 권한 획득 또는 신원 도용 공격자가 해시에 접근할 수 있으면 솔트가 없어 무차별 대입 공격을 하기 쉬워진다. 예를 들어 레인보 테이블(rainbow table) 같은 사전 공격 기법으로 해시 값을 미리 계산할 수 있다. 해시 함수의 계산 비용이 크지 않으면 오프라인 비밀번호 크래킹은 여전히 효과적일 수 있으며, 많은 암호 함수가 효율적으로 설계되어 해시가 암호학적으로 강하더라도 대규모 컴퓨팅 자원을 쓰는 공격에 취약할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 3건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 해시 계산에 드는 노력(반복 횟수 '스트레칭'이나 필요한 메모리 양)을 설정으로 바꿀 수 있는 적응형 해시 함수를 쓴다. 일부 해시 함수는 솔트를 자동으로 적용한다. 이런 함수는 MD5처럼 일부러 빠르게 만든 함수보다 무차별 대입 공격의 부담을 크게 늘릴 수 있어, 계산 부담 때문에 레인보 테이블 공격이 비현실적이 될 수 있다. 계산 능력이 빨라지고 싸지면 사용 중인 알고리즘을 통째로 바꾸지 않고 작업량을 늘리도록 다시 설정할 수 있다. 이런 성질 중 하나 이상을 가진 해시 함수로 bcrypt [REF-291], scrypt [REF-292], PBKDF2 [REF-293]가 있다. 어느 것이 가장 효과적인지는 논쟁 중이지만, 모두 계산 부담이 매우 작은 해시 함수에 솔트를 쓰는 것보다 강하다.
    원문

    Use an adaptive hash function that can be configured to change the amount of computational effort needed to compute the hash, such as the number of iterations ("stretching") or the amount of memory required. Some hash functions perform salting automatically. These functions can significantly increase the overhead for a brute force attack compared to intentionally-fast functions such as MD5. For example, rainbow table attacks can become infeasible due to the high computing overhead. Finally, since computing power gets faster and cheaper over time, the technique can be reconfigured to increase the workload without forcing an entire replacement of the algorithm in use.

    Some hash functions that have one or more of these desired properties include bcrypt [REF-291], scrypt [REF-292], and PBKDF2 [REF-293]. While there is active debate about which of these is the most effective, they are all stronger than using salts with hash functions with very little computing overhead.

    		 높음(High) — 이런 함수를 쓰면 성능에 영향을 줄 수 있어 서비스 거부 공격을 피하도록 특별히 고려해야 한다. 다만 설정으로 CPU·메모리 사용량을 세밀하게 조정할 수 있어 환경에 맞출 수 있다.
    아키텍처·설계(Architecture and Design) — 추가 계산 노력을 요구하는 기법을 구현할 수 없다면, 비밀번호마다 예측할 수 없는 시드를 쓰는 강한 난수 생성기로 새 무작위 솔트를 만들어 평문 비밀번호에 더한 뒤 해시하고, 해시를 저장할 때 솔트도 함께 저장한다. 모든 비밀번호에 같은 솔트를 쓰지 않는다.
    원문

    If a technique that requires extra computational effort can not be implemented, then for each password that is processed, generate a new random salt using a strong random number generator with unpredictable seeds. Add the salt to the plaintext password before hashing it. When storing the hash, also store the salt. Do not use the same salt for every password.

    		 제한적(Limited) — 흔한 인식과 달리, 좋은 솔트를 해시에 써도 개별 해시(예: 중요 인물의 비밀번호)를 노리는 표적 공격의 작업량은 충분히 늘지 않는다. 일반적으로 솔트는 적응형 해시 함수로 계산 시간이나 메모리 부담을 늘리는 등의 다른 해싱 기법보다 효과가 작다. 작업량이 내장되어 있지 않으면, 현대의 공격은 대규모 병렬 컴퓨팅(클라우드 서비스 등)이나 저렴할 수 있는 GPU, ASIC, FPGA 같은 특수 하드웨어를 써서 아주 짧은 시간 안에 많은 해시를 계산하거나 가능한 모든 비밀번호 공간을 소진할 수도 있다. 자세한 내용은 CWE-916을 참고한다.
    구현(Implementation) / 아키텍처·설계(Architecture and Design) — 업계에서 승인된 기법을 쓸 때는 올바르게 쓰고, 자원이 많이 드는 단계를 건너뛰지 않는다(CWE-325). 이런 단계는 흔히 일반적인 공격을 막는 데 필수적이다. (구현 단계에도 해당)
    원문

    When using industry-approved techniques, use them correctly. Don't cut corners by skipping resource-intensive steps (CWE-325). These steps are often essential for preventing common attacks.

    		 —

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 정비 단말·운용자 콘솔이 운용자 비밀번호를 그대로 두지 않고 일방향 해시값(검증값)으로 바꿔 계정 파일에 저장한다. 계정 파일이 유출되면 공격자는 같은 검증값끼리 묶고 미리 계산한 해시 표와 대조해 비밀번호를 알아낼 수 있다. 예시는 같은 비밀번호를 쓰는 두 계정의 검증값이 같은지 비교한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <openssl/sha.h>

/* 정비 단말 계정 파일에 저장할 검증값: SHA-256(비밀번호) */
typedef struct {
    char operator_id[16];
    unsigned char verifier[SHA256_DIGEST_LENGTH];
} AccountRecord;

static void enroll(AccountRecord *rec, const char *id, const char *password)
{
    snprintf(rec->operator_id, sizeof rec->operator_id, "%s", id);
    SHA256((const unsigned char *)password, strlen(password), rec->verifier);   /* 솔트 없음 */
}

int main(void)
{
    AccountRecord a, b;
    enroll(&a, "maint-01", "EXAMPLE-ONLY-pw1");
    enroll(&b, "maint-02", "EXAMPLE-ONLY-pw1");   /* 우연히 같은 비밀번호 */

    /* 계정 파일을 빼낸 공격자는 같은 값끼리 묶고, 미리 계산한 해시 표와 바로 대조한다 */
    puts(memcmp(a.verifier, b.verifier, sizeof a.verifier) == 0 ? "IDENTICAL VERIFIERS" : "verifiers differ");
    return 0;
}

    비밀번호를 솔트 없이 SHA-256 한 번으로 바꿔 저장한다. 같은 비밀번호는 같은 검증값이 되어 한 계정만 풀면 나머지도 풀리고, 미리 계산한 표(레인보 테이블)가 그대로 통한다.

    좋은 예

    #include <stdio.h>
#include <string.h>
#include <openssl/crypto.h>
#include <openssl/evp.h>
#include <openssl/rand.h>

#define PBKDF2_ROUNDS 600000   /* 장비 성능·인증 지연 요구에 맞춰 정하고 주기적으로 올린다 */

/* 계정마다 무작위 솔트 16바이트 + PBKDF2-HMAC-SHA256 검증값 */
typedef struct {
    char operator_id[16];
    unsigned char salt[16];
    unsigned char verifier[32];
} AccountRecord;

static int derive(const char *pw, const unsigned char *salt, unsigned char *out)
{
    return PKCS5_PBKDF2_HMAC(pw, (int)strlen(pw), salt, 16, PBKDF2_ROUNDS, EVP_sha256(), 32, out) == 1 ? 0 : -1;
}

static int enroll(AccountRecord *rec, const char *id, const char *pw)
{
    snprintf(rec->operator_id, sizeof rec->operator_id, "%s", id);
    if (RAND_bytes(rec->salt, sizeof rec->salt) != 1) return -1;
    return derive(pw, rec->salt, rec->verifier);
}

static int verify(const AccountRecord *rec, const char *pw)
{
    unsigned char probe[32];
    return derive(pw, rec->salt, probe) == 0 && CRYPTO_memcmp(probe, rec->verifier, 32) == 0;
}

int main(void)
{
    AccountRecord a, b;
    if (enroll(&a, "maint-01", "EXAMPLE-ONLY-pw1") != 0 || enroll(&b, "maint-02", "EXAMPLE-ONLY-pw1") != 0) {
        return 1;
    }
    printf("login maint-01: %s\n", verify(&a, "EXAMPLE-ONLY-pw1") ? "ok" : "denied");
    puts(memcmp(a.verifier, b.verifier, sizeof a.verifier) == 0 ? "IDENTICAL VERIFIERS" : "verifiers differ");
    return 0;
}

    계정마다 RAND_bytes로 16바이트 솔트를 만들고 PBKDF2-HMAC-SHA256(반복 600,000회는 예시 값)으로 검증값을 만든다. 같은 비밀번호도 검증값이 달라지고, 비교는 CRYPTO_memcmp로 상수 시간에 한다. 반복 횟수는 장비 성능·인증 지연 요구에 맞춰 정한다(D-05).

    검증: 실행 결과 · Linux(gcc)에서 빌드 — 나쁜 예에서 IDENTICAL VERIFIERS 검출, 좋은 예에서 미검출·verifiers differ 출력 확인 · 참고: MITRE CWE-759 Demonstrative Example 1·2(솔트 없는 해시로 비밀번호 검사·저장) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 보안기능 2-11 '솔트 없이 일방향 해쉬 함수 사용'(인쇄 114쪽) 참고

    C++

    나쁜 예

    #include <openssl/evp.h>
#include <array>
#include <cstdio>
#include <map>
#include <string>

using Digest = std::array<unsigned char, 32>;

// 운용자 콘솔 계정 저장소: 비밀번호를 SHA-256 한 번으로 바꿔 둔다
static Digest hash_password(const std::string &pw) {
    Digest d{};
    unsigned int len = 0;
    EVP_Digest(pw.data(), pw.size(), d.data(), &len, EVP_sha256(), nullptr);   // 솔트 없음
    return d;
}

int main() {
    std::map<std::string, Digest> accounts;
    accounts["op-alpha"] = hash_password("EXAMPLE-ONLY-pw1");

    좋은 예

    import java.security.GeneralSecurityException;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Arrays;
import java.util.HashMap;
import java.util.Map;
import javax.crypto.SecretKeyFactory;
import javax.crypto.spec.PBEKeySpec;

public class Example {
    static final SecureRandom RNG = new SecureRandom();
    static final int ROUNDS = 600_000;   // 장비 성능·인증 지연 요구에 맞춰 정하고 주기적으로 올린다

    record Verifier(byte[] salt, byte[] dk) {}

    static byte[] derive(char[] password, byte[] salt) throws GeneralSecurityException {
        PBEKeySpec spec = new PBEKeySpec(password, salt, ROUNDS, 256);
        try {
            return SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).getEncoded();
        } finally {
            spec.clearPassword();
        }
    }

    // 계정마다 무작위 솔트 16바이트 + PBKDF2-HMAC-SHA256
    static Verifier enroll(char[] password) throws GeneralSecurityException {
        byte[] salt = new byte[16];
        RNG.nextBytes(salt);
        return new Verifier(salt, derive(password, salt));
    }

    static boolean verify(Verifier v, char[] attempt) throws GeneralSecurityException {
        return MessageDigest.isEqual(derive(attempt, v.salt()), v.dk());   // 상수 시간 비교
    }

    public static void main(String[] args) throws GeneralSecurityException {
        Map<String, Verifier> accounts = new HashMap<>();
        accounts.put("maint-01", enroll("EXAMPLE-ONLY-pw1".toCharArray()));
        accounts.put("maint-02", enroll("EXAMPLE-ONLY-pw1".toCharArray()));
        System.out.println("login maint-01: " + (verify(accounts.get("maint-01"), "EXAMPLE-ONLY-pw1".toCharArray()) ? "ok" : "denied"));
        boolean same = Arrays.equals(accounts.get("maint-01").dk(), accounts.get("maint-02").dk());
        System.out.println(same ? "IDENTICAL VERIFIERS" : "verifiers differ");
    }
}

    SecretKeyFactory("PBKDF2WithHmacSHA256")에 SecureRandom 솔트 16바이트와 반복 횟수를 지정하고, 비교는 MessageDigest.isEqual로 한다. PBEKeySpec의 비밀번호는 사용 뒤 지운다.

    params = dict(SCRYPT)                        # 비용 인자를 계정 기록에 함께 남겨 나중에 올려도 기존 계정을 확인한다

    trial = hashlib.scrypt(password.encode(), salt=salt, dklen=32, **params)
    return hmac.compare_digest(trial, digest)

    비밀번호를 해시하는 곳에서 SHA-256·MD5를 한 번만 적용하는지, 계정마다 강한 난수로 만든 솔트와 반복 횟수를 쓰는 적응형 함수(PBKDF2, bcrypt, scrypt, Argon2)를 쓰는지 확인한다. I-09 [CWE] CWE-759 완화책(Architecture and Design: 적응형 해시 함수, 비밀번호마다 새 솔트)
    저장 형식 문서에 솔트 길이, 반복 횟수, 알고리즘 식별자가 정해져 있고 반복 횟수를 타깃 연산 성능과 인증 지연 요구로 정했는지 확인한다. D-09·D-05 [보완]
    • ① 원문 탐지 방법(원문 효과성별): 높음: 수동 정적 분석(소스코드), 아키텍처·설계 검토 / 부분 적용: 자동 정적 분석(바이너리·바이트코드), 수동 정적 분석(바이너리·바이트코드). 각 방법의 시험 활동은 6.2의 대응표를 따른다.

    요구사항 분석 —
    설계 비밀번호 저장에 솔트와 반복(키 유도) 기반 해시를 쓰도록 설계에 정한다.
    구현(C·C++) 사용자별 랜덤 솔트와 PBKDF2(충분한 반복 횟수) 등 검증된 키 유도 함수를 사용한다.
    구현(Java) SecretKeyFactory("PBKDF2WithHmacSHA256")에 SecureRandom 솔트와 반복 횟수를 지정한다.

    유지보수 반복 횟수를 하드웨어 성능 향상에 맞춰 주기적으로 상향한다.
    임베디드 고려 MCU 연산 성능을 고려해 반복 횟수를 결정하되 인증 지연 요구와 균형을 맞춘다.
