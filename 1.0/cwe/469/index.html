    Use of Pointer Subtraction to Determine Size

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: C, C++
    원문 MITRE CWE-469 (CWE 5.0)

    한 줄 요약

    크기를 구하려고 포인터끼리 빼지만 두 포인터가 같은 메모리 덩어리에 없으면 결과가 틀릴 수 있는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 크기를 구하려고 한 포인터에서 다른 포인터를 빼지만, 두 포인터가 같은 메모리 덩어리(chunk)에 있지 않으면 이 계산은 틀릴 수 있다.

    원문(Description)

    The product subtracts one pointer from another in order to determine size, but this calculation can be incorrect if the pointers do not exist in the same memory chunk.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    접근 통제 / 무결성 / 기밀성 / 가용성 메모리 수정 / 메모리 읽기 / 허가되지 않은 코드·명령 실행 / 권한 획득 또는 신원 도용 취약한 프로그램의 권한으로 임의 코드가 실행될 가능성이 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 1건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    원문 완화책 없음

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 권장 해법은 인덱스 변수를 두는 것이다. 포인터끼리 빼지 말고 해당 포인터와 같은 크기의 인덱스 변수로 한 포인터에서 다른 포인터까지 '이동'하며 차이를 계산하고, 이 값은 항상 검증한다.
    원문

    Save an index variable. This is the recommended solution. Rather than subtract pointers from one another, use an index variable of the same size as the pointers in question. Use this variable to "walk" from one pointer to the other and calculate the difference. Always validate this number.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 데이터링크 송신 프레임의 길이(헤더+본문)를 구하거나(C), ADC 표본을 두 버퍼에 번갈아 받는 이중 버퍼(핑퐁 버퍼)에서 지금까지 받은 표본 수를 구한다(C++). 두 경우 모두 포인터 두 개의 차로 개수를 계산한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <string.h>

#define HDR_LEN 4
#define BODY_LEN 16

/* 송신 프레임의 헤더와 본문을 서로 다른 전역 배열에 따로 둔다 */
static uint8_t link_hdr[HDR_LEN] = {0xEB, 0x90, 0x01, BODY_LEN};
static uint8_t link_body[BODY_LEN];

int main(void)
{
    memset(link_body, 0x5A, sizeof link_body);

    const uint8_t *first = link_hdr;
    const uint8_t *past_end = link_body + BODY_LEN;
    /* 별개 객체를 가리키는 두 포인터의 차로 프레임 길이를 구한다(미정의 동작) */
    long frame_len = (long)(past_end - first);

    printf("frame length %ld (expected %d)\n", frame_len, HDR_LEN + BODY_LEN);
    return 0;
}

    헤더와 본문은 서로 다른 전역 배열인데, 본문 끝 포인터에서 헤더 시작 포인터를 빼 프레임 길이를 구한다. 서로 다른 객체 사이의 포인터 뺄셈은 미정의 동작이고 결과는 링커 배치에 따라 달라지며, 기대값 20이 나온다는 보장이 없다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <string.h>

#define HDR_LEN 4
#define BODY_LEN 16

/* 헤더와 본문을 한 배열 안에 두고 본문 위치는 오프셋으로 정한다 */
static uint8_t link_frame[HDR_LEN + BODY_LEN] = {0xEB, 0x90, 0x01, BODY_LEN};

int main(void)
{
    uint8_t *body = link_frame + HDR_LEN;
    memset(body, 0x5A, BODY_LEN);

    const uint8_t *first = link_frame;
    const uint8_t *past_end = body + BODY_LEN;
    /* 같은 배열 안의 두 포인터끼리만 뺀다 */
    long frame_len = (long)(past_end - first);

    printf("frame length %ld (expected %d)\n", frame_len, HDR_LEN + BODY_LEN);
    return 0;
}

    헤더와 본문을 한 배열 안에 두고 본문 위치는 오프셋으로 정해, 같은 배열 안의 포인터끼리만 뺀다. 별개 버퍼라면 포인터 차 대신 각 버퍼의 길이를 더한다.

    검증: cppcheck — 나쁜 예에서 subtractPointers 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-469 Demonstrative Example 1(연결 리스트의 두 노드 포인터를 빼서 노드 수를 계산) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <array>
#include <cstdint>
#include <cstdio>

// ADC 표본을 두 버퍼에 번갈아 받는 이중 버퍼(핑퐁 버퍼)
struct AdcBuffers {
    std::array<std::int16_t, 32> ping{};
    std::array<std::int16_t, 32> pong{};
};

int main() {
    AdcBuffers adc;
    // DMA가 ping 32개를 다 채운 뒤 pong으로 넘어가 8개를 더 썼다
    const std::int16_t *dma_pos = adc.pong.data() + 8;

    // 서로 다른 배열을 가리키는 포인터의 차로 받은 표본 수를 구한다(미정의 동작)
    auto received = dma_pos - adc.ping.data();
    std::printf("samples received %td (expected 40)\n", received);
    return 0;
}

    ping과 pong은 서로 다른 배열인데, pong 안의 DMA 위치에서 ping 시작 포인터를 빼 표본 수를 구한다. 이 호스트 빌드에서는 두 배열이 붙어 있어 우연히 40이 나오므로 시험으로는 드러나지 않고, 구조체 배치·컴파일러가 바뀌면 틀린 값이 될 수 있다.

    좋은 예

    #include <array>
#include <cstddef>
#include <cstdint>
#include <cstdio>

// ADC 표본을 받는 이중 버퍼: 저장 공간 하나를 앞뒤 절반(ping·pong)으로 나눠 쓴다
class AdcBuffers {
public:
    static constexpr std::size_t kHalf = 32;
    std::int16_t *half(std::size_t which) { return storage_.data() + which * kHalf; }
    // 같은 배열 안의 포인터끼리만 빼서 받은 표본 수를 구한다
    std::ptrdiff_t received(const std::int16_t *pos) const { return pos - storage_.data(); }

private:
    std::array<std::int16_t, 2 * kHalf> storage_{};
};

int main() {
    AdcBuffers adc;
    // DMA가 ping 32개를 다 채운 뒤 pong으로 넘어가 8개를 더 썼다
    const std::int16_t *dma_pos = adc.half(1) + 8;
    std::printf("samples received %td (expected 40)\n", adc.received(dma_pos));
    return 0;
}

    저장 공간 하나를 앞뒤 절반으로 나눠 쓰고, 표본 수는 같은 배열 안의 포인터 차로만 구하도록 클래스 안에 감춘다. 인덱싱 외의 포인터 산술은 이런 한 곳으로 제한한다(LCPP-04).

    검증: cppcheck — 나쁜 예에서 mismatchingContainers 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-469 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(언어상 생기지 않음): C# 관리 코드에는 포인터 산술이 없다. unsafe 코드의 포인터 뺄셈은 같은 버퍼(fixed로 고정한 같은 배열) 안에서만 써야 하므로 그 범위에는 C 예시와 C 지침을 적용한다(LCS-02).

    Java — 예시 없음(언어상 생기지 않음): Java에는 포인터 산술이 없어 포인터 뺄셈으로 크기를 구할 수 없고 크기는 배열 length나 컬렉션 size()로 얻는다. JNI로 부르는 네이티브 코드에는 C 예시를 적용한다(LJ-08).

    Python — 예시 없음(언어상 생기지 않음): Python에는 포인터 산술이 없어 포인터 뺄셈으로 크기를 구할 수 없고 크기는 len()으로 얻는다. ctypes.addressof로 얻은 주소끼리 빼서 크기를 구하는 코드는 같은 버퍼 안에서만 성립하므로 그 범위에는 C 예시와 C 지침을 적용한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 1건)

    Example 1. The following example contains the method size that is used to determine the number of nodes in a linked list. The method is passed a pointer to the head of the linked list.

    Bad / C

    struct node {
  int data;
  struct node* next;
};

                     // Returns the number of nodes in a linked list from

                     // the given pointer to the head of the list.

int size(struct node* head) {
  struct node* current = head;
  struct node* tail;
  while (current != NULL) {
    tail = current;
    current = current->next;
  }
  return tail - head;
}

                     // other methods for manipulating the list

...

    However, the method creates a pointer that points to the end of the list and uses pointer subtraction to determine the number of nodes in the list by subtracting the tail pointer from the head pointer. There no guarantee that the pointers exist in the same memory area, therefore using pointer subtraction in this way could return incorrect results and allow other unintended behavior. In this example a counter should be used to determine the number of nodes in the list, as shown in the following code.

    Good / C

    ...

int size(struct node* head) {
  struct node* current = head;
  int count = 0;
  while (current != NULL) {
    count++;
    current = current->next;
  }
  return count;
}

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    (C·C++) 두 포인터를 빼는 식을 모두 찾아 두 포인터가 같은 배열을 가리키는지 확인하고, 서로 다른 배열·버퍼 사이의 뺄셈은 인덱스 변수로 바꿔야 하는지 본다. I-09·I-05 [표준] SEI CERT ARR36-C · [CWE] CWE-469 완화책(Implementation: 인덱스 변수 저장)
    (C·C++) 이중 버퍼(ping·pong)나 헤더·본문처럼 따로 선언된 배열의 선언 순서나 구조체 배치를 바꾼 빌드에서 같은 시험을 돌려 계산된 길이가 달라지는지 확인한다. I-10·T-05 [예시] CWE-469 C++ 예시(두 배열이 붙어 있어 시험에서 드러나지 않음) · [보완]
    (C·C++) 사업 정적 분석 도구가 이 항목을 지원하지 않으면 cppcheck의 subtractPointers(C)·mismatchingContainers(C++) 검사로 서로 다른 객체 사이의 포인터 뺄셈을 찾는다. I-09 [예시] CWE-469 예시 검증(cppcheck subtractPointers, mismatchingContainers)

    구현(C·C++) 동일 배열에 속하지 않은 포인터 간 뺄셈을 금지하고, 인덱스 또는 시작 포인터 기준 오프셋을 사용한다.

    임베디드 고려 DSP·하버드 구조(AVR 플래시/RAM 분리 주소공간)에서는 서로 다른 메모리 영역 포인터 간 연산이 의미가 없으므로 금지한다.
