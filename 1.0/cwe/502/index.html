    Deserialization of Untrusted Data

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 언어 뷰 Java(CWE-660)
    가이드 적용성 조건부 — 직렬화 사용
    적용 플랫폼 언어: Java, Ruby, PHP, Python, JavaScript · 기술: 기술 무관, 산업제어시스템·운영기술(ICS/OT), 인공지능·기계학습(AI/ML)
    원문 MITRE CWE-502 (CWE 5.0)

    한 줄 요약

    신뢰할 수 없는 데이터를 역직렬화하면서 결과 데이터가 유효한지 충분히 확인하지 않는 약점이다.

    설명(Description)¶

    제품이 신뢰할 수 없는 데이터를 역직렬화(deserialization)하면서 그 결과 데이터가 유효한지 충분히 확인하지 않는 약점이다.

    배경(Background Details)

    직렬화와 역직렬화는 프로그램 내부의 객체 관련 데이터를 외부에 저장하거나 전송할 수 있는 형태로 묶고("직렬화"), 그렇게 직렬화된 데이터를 꺼내 원래 객체를 다시 구성하는("역직렬화") 과정을 가리킨다.

    원문(Description · Background Details)

    The product deserializes untrusted data without sufficiently ensuring that the resulting data will be valid.

    Serialization and deserialization refer to the process of taking program-internal object-related data, packaging it in a way that allows the data to be externally stored or transferred ("serialization"), then extracting the serialized data to reconstruct the original object ("deserialization").

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 누락(OMISSION): 아키텍처·설계 단계에서 보안 전술을 빠뜨려 생기는 약점이다.
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 애플리케이션 데이터 수정 / 예상하지 못한 상태 공격자는 수정되지 않는다고 가정한 예상 밖의 객체나 데이터를 바꿀 수 있다. 역직렬화된 데이터나 코드가 제공된 접근자 함수를 거치지 않고 수정되거나, 예상하지 못한 함수가 호출될 수 있다.
    가용성 서비스 거부: 자원 소모(CPU) 함수가 문자열 안의 센티널(sentry, 끝을 표시하는 값)을 기준으로 언제 끝낼지 가정하면 쉽게 끝나지 않게 될 수 있다.
    기타 상황에 따라 다름 결과는 어떤 객체나 메서드를 역직렬화하고 어떻게 쓰는지에 따라 크게 달라진다. 역직렬화된 객체의 코드가 유효하다고 가정하는 것은 위험하며 악용을 가능하게 할 수 있다. 예를 들어 공격자가 가젯 체인으로 셸 생성 같은 허가되지 않은 동작을 수행할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 7건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) / 구현(Implementation) — 가능하면 프로그래밍 언어의 서명·봉인(signing/sealing) 기능을 사용해 역직렬화된 데이터가 오염되지 않았음을 확인한다. 예를 들어 해시 기반 메시지 인증 코드(HMAC)로 데이터가 수정되지 않았음을 확인할 수 있다. (구현 단계에도 해당)
    원문

    If available, use the signing/sealing features of the programming language to assure that deserialized data has not been tainted. For example, a hash-based message authentication code (HMAC) could be used to ensure that data has not been modified.

    		 —
    아키텍처·설계(Architecture and Design) / 구현(Implementation) — 필드를 transient로 지정해 역직렬화로부터 보호한다. transient 필드가 있는 클래스를 직렬화했다가 역직렬화하면 그 데이터 자리에 NULL이 들어가므로, 시간·환경 기반 변수나 민감한 변수가 넘어가 부적절하게 쓰이는 것을 막는 좋은 방법이다. (구현 단계에도 해당)
    원문

    Make fields transient to protect them from deserialization.

    An attempt to serialize and then deserialize a class containing transient fields will result in NULLs where the transient data should be. This is an excellent way to prevent time, environment-based, or sensitive variables from being carried over and used improperly.

    		 —
    아키텍처·설계(Architecture and Design) / 구현(Implementation) — 데이터나 코드를 암호화해 보호한다. 다만 이는 여전히 클라이언트 측 보안이어서, 클라이언트가 침해되면 클라이언트에 구현된 보안(암호화)이 우회될 수 있으므로 위험하다. (구현 단계에도 해당)
    원문

    Employ cryptography of the data or code for protection. However, it's important to note that it would still be client-side security. This is risky because if the client is compromised then the security implemented on the client (the cryptography) can be bypassed.

    		 —

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 데이터를 역직렬화할 때 단순히 역직렬화만 하지 말고 새 객체를 채운다. 그러면 데이터가 안전한 입력값 검증을 거치고 함수도 안전해진다.
    원문

    When deserializing data, populate a new object rather than just deserializing. The result is that the data flows through safe input validation and that the functions are safe.

    		 —
    구현(Implementation) — 역직렬화를 막기 위해 final object()를 명시적으로 정의한다.
    원문

    Explicitly define a final object() to prevent deserialization.

    		 —
    구현(Implementation) — 악의적으로 활용될 수 있는 불필요한 타입이나 가젯(gadget: 역직렬화 중 스스로 실행될 수 있는 인스턴스·메서드 호출의 연쇄로, 흔히 라이브러리에 있다)을 두지 않아 공격자가 의도하지 않은·허가되지 않은 타입과 가젯을 활용할 가능성을 줄이고, 허용되는 클래스만 허용목록에 추가한다. 단, 새로운 가젯이 계속 발견되므로 이것만으로는 충분한 완화책이 아니다.
    원문

    Avoid having unnecessary types or gadgets (a sequence of instances and method invocations that can self-execute during the deserialization process, often found in libraries) available that can be leveraged for malicious ends. This limits the potential for unintended or unauthorized types and gadgets to be leveraged by the attacker. Add only acceptable classes to an allowlist. Note: new gadgets are constantly being discovered, so this alone is not a sufficient mitigation.

    		 —

    유지보수 (본문 제7장)¶

    CWE 단계(Phase) 전략 요지 효과성
    운용(Operation) 방화벽 이 약점에 대한 공격을 탐지할 수 있는 애플리케이션 방화벽을 쓴다. 코드를 고칠 수 없을 때(제3자가 관리하는 경우), 더 포괄적인 소프트웨어 보증 조치를 적용하는 동안의 긴급 예방책으로, 또는 심층 방어로 유용할 수 있다 [REF-1481].
    원문

    Use an application firewall that can detect attacks against this weakness. It can be beneficial in cases in which the code cannot be fixed (because it is controlled by a third party), as an emergency prevention measure while more comprehensive software assurance measures are applied, or to provide defense in depth [REF-1481].

    		 보통(Moderate) — 애플리케이션 방화벽은 모든 입력 경로를 다루지 못할 수 있고, 수신 구성요소가 여전히 처리하는 잘못된 형식의 입력 등으로 우회될 수 있으며, 기능에 따라 정상 요청을 의도치 않게 거부·변경할 수 있고, 맞춤 설정에 일부 수작업이 필요할 수 있다.

    예시(나쁜 예·좋은 예)¶

    이 가이드가 새로 쓰는 예시는 언어별로 컴파일과 분석기 검증을 거치므로, 이 판은 「보안약점 점검 목록(44개)」과 보조 항목에만 싣는다. 아래 MITRE 원문 예시를 참고한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. This code snippet deserializes an object from a file and uses it as a UI button:

    Bad / Java

    try {
  File file = new File("object.obj");
  ObjectInputStream in = new ObjectInputStream(new FileInputStream(file));
  javax.swing.JButton button = (javax.swing.JButton) in.readObject();
  in.close();
}

    This code does not attempt to verify the source or contents of the file before deserializing it. An attacker may be able to replace the intended file with a file that contains arbitrary malicious code which will be executed when the button is pressed.

    To mitigate this, explicitly define final readObject() to prevent deserialization. An example of this is:

    Good / Java

    private final void readObject(ObjectInputStream in) throws java.io.IOException {
throw new java.io.IOException("Cannot be deserialized"); }

    Example 2. In Python, the Pickle library handles the serialization and deserialization processes. In this example derived from [REF-467], the code receives and parses data, and afterwards tries to authenticate a user based on validating a token.

    Bad / Python

    try {

  class ExampleProtocol(protocol.Protocol):
  def dataReceived(self, data):

  # Code that would be here would parse the incoming data
  # After receiving headers, call confirmAuth() to authenticate

  def confirmAuth(self, headers):
  try:
  token = cPickle.loads(base64.b64decode(headers['AuthToken']))
  if not check_hmac(token['signature'], token['data'], getSecretKey()):
  raise AuthFail
  self.secure_data = token['data']
  except:
  raise AuthFail

}

    Unfortunately, the code does not verify that the incoming data is legitimate. An attacker can construct a illegitimate, serialized object "AuthToken" that instantiates one of Python's subprocesses to execute arbitrary commands. For instance,the attacker could construct a pickle that leverages Python's subprocess module, which spawns new processes and includes a number of arguments for various uses. Since Pickle allows objects to define the process for how they should be unpickled, the attacker can direct the unpickle process to call Popen in the subprocess module and execute /bin/sh.

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    • ① 원문 탐지 방법은 자동 정적 분석뿐이다. 다른 정적 분석 도구·컴파일러 경고로 점검한다.
    • ③ SEI CERT 대응 규칙: SER01-J, SER03-J, SER06-J, SER08-J

    이 가이드에서 다루는 곳¶

    언어 뷰 항목의 단계별 지침 (적용성 판정 기준은 부록 B, 요구사항 분석 행은 기준선 활동·환경 지침과 원문 완화책에서 모았다)

    단계 지침
    요구사항 분석 —
    설계 신뢰할 수 없는 출처의 객체 역직렬화를 지양하고 JSON 등 데이터 전용 포맷과 무결성 서명을 사용하도록 설계한다.
    구현 ObjectInputStream에 외부 입력을 전달하지 않고, 불가피하면 서명·HMAC으로 변조 여부를 확인하고 ObjectInputFilter로 허용 클래스를 제한하며 readObject에서 불변식을 검증한다. 새 가젯이 계속 발견되므로 허용 클래스 제한만으로는 충분하지 않다.
    통합 및 시험 find-sec-bugs/SpotBugs로 readObject 사용을 탐지하고 ysoserial 페이로드로 시험한다.
    유지보수 역직렬화 대상 클래스와 라이브러리 취약점(가젯 체인)을 주기적으로 점검하고 패치한다.
    임베디드 고려 SBC에서 도는 Java 서비스가 외부 장치·네트워크로 객체 스트림을 받는 구조를 피하고 직렬화 대신 고정 필드 프로토콜을 사용한다.

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 8건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.
