    Double Free

    항목 내용
    추상화 수준 변형(Variant)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 C·C++(CWE-658·659)
    가이드 적용성 해당
    적용 플랫폼 언어: 메모리 비안전 언어(Memory-Unsafe), C, C++
    원문 MITRE CWE-415 (CWE 5.0)

    한 줄 요약

    같은 메모리 주소에 대해 free()를 두 번 호출하는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 같은 메모리 주소에 대해 free()를 두 번 호출하는 약점이다.

    원문(Description)

    The product calls free() twice on the same memory address.

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    구현(Implementation) 구현 —

    영향(Common Consequences)¶

    영역 영향 설명
    무결성 / 기밀성 / 가용성 메모리 수정 / 허가되지 않은 코드·명령 실행 같은 인자로 free()를 두 번 호출하면 프로그램의 메모리 관리 자료구조가 손상되어 예상하지 못한 메모리 주소를 읽거나 바꾸게 될 수 있다. 이 손상으로 프로그램이 비정상 종료되거나, 경우에 따라 이후 두 번의 malloc() 호출이 같은 포인터를 돌려줄 수 있다. malloc()이 같은 값을 두 번 돌려주고 이 이중 할당된 메모리에 쓰는 데이터를 나중에 공격자가 제어하게 되면 버퍼 오버플로 공격에 취약해진다. 이중 해제는 임의 위치 쓰기 조건(write-what-where)으로 이어질 수 있으며, 그러면 공격자가 임의 코드를 실행할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 3건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지
    아키텍처·설계(Architecture and Design) — 자동 메모리 관리를 제공하는 언어를 선택한다.
    원문

    Choose a language that provides automatic memory management.

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지
    구현(Implementation) — 각 할당은 한 번만 해제되게 하고, 해제한 뒤에는 포인터를 NULL로 설정해 다시 해제되지 않게 한다. 복잡한 오류 상황에서는 정리 루틴이 할당 상태를 올바르게 따르게 하고, 객체 지향 언어라면 소멸자가 각 메모리 덩어리를 한 번만 삭제하게 한다.
    원문

    Ensure that each allocation is freed only once. After freeing a chunk, set the pointer to NULL to ensure the pointer cannot be freed again. In complicated error conditions, be sure that clean-up routines respect the state of allocation properly. If the language is object oriented, ensure that object destructors delete each chunk of memory only once.
    구현(Implementation) — 정적 분석 도구로 이중 해제 사례를 찾는다.
    원문

    Use a static analysis tool to find double free instances.

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: T-04 퍼징

    유지보수 (본문 제7장)¶

    원문 완화책 없음

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 지상 정비 장비가 받은 펌웨어 업데이트 블록을 작업 버퍼에 옮겨 검사한 뒤 플래시 쓰기 대기열에 올린다. 검사에 실패하면 블록을 버리고 오류를 돌려준다(C++는 이미지 조각을 업로드 대기열에 넣는 버퍼 클래스). 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define BLOCK_SIZE 256

static uint8_t block_sum(const uint8_t *p, size_t n)
{
    uint8_t s = 0;
    for (size_t i = 0; i < n; ++i) {
        s = (uint8_t)(s + p[i]);
    }
    return s;
}

/* 받은 펌웨어 업데이트 블록을 검사해 플래시 쓰기 대기열에 올린다. 성공 0, 실패 -1 */
static int stage_block(const uint8_t *rx, uint8_t expected_sum)
{
    int rc = 0;
    uint8_t *work = malloc(BLOCK_SIZE);
    if (work == NULL) {
        return -1;
    }
    memcpy(work, rx, BLOCK_SIZE);
    if (block_sum(work, BLOCK_SIZE) != expected_sum) {
        puts("block rejected: checksum");
        free(work);                    /* 오류 경로에서 먼저 해제한다 */
        rc = -1;
    }
    /* (정상 경로: 대기열 등록 생략) */
    free(work);                        /* 공통 정리에서 같은 버퍼를 또 해제한다 */
    return rc;
}

int main(void)
{
    uint8_t rx[BLOCK_SIZE] = {0x12, 0x34, 0x56};
    return stage_block(rx, 0x00) == 0 ? 0 : 1;
}

    검사 실패 경로에서 버퍼를 해제한 뒤 함수 끝의 공통 정리에서 같은 버퍼를 또 해제한다. 이중 해제는 할당기 내부 구조를 망가뜨려 이후 할당이 엉뚱한 주소를 돌려주거나 비정상 종료로 이어진다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define BLOCK_SIZE 256

static uint8_t block_sum(const uint8_t *p, size_t n)
{
    uint8_t s = 0;
    for (size_t i = 0; i < n; ++i) {
        s = (uint8_t)(s + p[i]);
    }
    return s;
}

/* 받은 펌웨어 업데이트 블록을 검사해 플래시 쓰기 대기열에 올린다. 성공 0, 실패 -1 */
static int stage_block(const uint8_t *rx, uint8_t expected_sum)
{
    int rc = -1;
    uint8_t *work = malloc(BLOCK_SIZE);
    if (work == NULL) {
        return -1;
    }
    memcpy(work, rx, BLOCK_SIZE);
    if (block_sum(work, BLOCK_SIZE) != expected_sum) {
        puts("block rejected: checksum");
        goto cleanup;                  /* 오류 경로는 해제하지 않고 정리 지점으로 간다 */
    }
    /* (정상 경로: 대기열 등록 생략) */
    rc = 0;
cleanup:
    free(work);                        /* 해제는 이 한 곳에서만 한다 */
    return rc;
}

int main(void)
{
    uint8_t rx[BLOCK_SIZE] = {0x12, 0x34, 0x56};
    return stage_block(rx, 0x00) == 0 ? 0 : 1;
}

    오류 경로는 해제하지 않고 정리 지점으로 이동해 해제를 한 곳에서만 한다. 해제 뒤에도 쓰는 변수라면 NULL로 바꿔 같은 변수의 실수를 줄이되, 같은 메모리를 가리키는 다른 포인터까지 막지는 못한다(LC-07). 동적 할당 자체를 초기화 단계로 제한하는 설계(LC-01)가 더 근본적인 대책이다.

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: attempting double-free 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-415 Demonstrative Example 1(오류 조건 분기와 함수 끝에서 같은 메모리를 두 번 해제) 참고, 이 가이드가 새로 작성

    C++

    나쁜 예

    #include <cstdint>
#include <cstdio>
#include <cstring>
#include <vector>

// 펌웨어 이미지 조각을 담는 버퍼. 소멸자만 있고 복사 규칙은 정하지 않았다
class ImageChunk {
public:
    explicit ImageChunk(std::size_t n) : size_(n), bytes_(new std::uint8_t[n]) {
        std::memset(bytes_, 0xFF, n);
    }
    ~ImageChunk() { delete[] bytes_; }
    std::size_t size() const { return size_; }

private:
    std::size_t size_;
    std::uint8_t *bytes_;   // 기본 복사 생성자는 이 포인터 값만 복사한다
};

int main() {
    std::vector<ImageChunk> upload_queue;
    ImageChunk first(512);
    upload_queue.push_back(first);   // 얕은 복사: 두 객체가 같은 버퍼를 가리킨다
    std::printf("queued %zu bytes\n", upload_queue.front().size());
    return 0;                        // 두 소멸자가 같은 버퍼를 각각 delete[] 한다
}

    소멸자에서 delete[]를 하는 클래스에 복사 생성자를 정의하지 않아, 대기열에 넣을 때 포인터 값만 복사된다. 원본과 복사본의 소멸자가 같은 버퍼를 각각 해제한다(3의 규칙 위반).

    좋은 예

    #include <cstdint>
#include <cstdio>
#include <vector>

// 펌웨어 이미지 조각을 담는 버퍼. 메모리 소유는 표준 컨테이너에 맡긴다
class ImageChunk {
public:
    explicit ImageChunk(std::size_t n) : bytes_(n, 0xFF) {}
    std::size_t size() const { return bytes_.size(); }

private:
    std::vector<std::uint8_t> bytes_;   // 복사하면 내용까지 복사되고 해제는 각자 한 번
};

int main() {
    std::vector<ImageChunk> upload_queue;
    ImageChunk first(512);
    upload_queue.push_back(first);
    std::printf("queued %zu bytes\n", upload_queue.front().size());
    return 0;
}

    버퍼 소유를 std::vector에 맡겨 복사하면 내용까지 복사되고 해제는 각 객체가 한 번씩만 한다. raw new/delete 대신 RAII 래퍼로 수명을 관리한다(LCPP-01).

    검증: AddressSanitizer(clang) — 나쁜 예에서 AddressSanitizer: attempting double-free 검출, 좋은 예에서 미검출 · 참고: MITRE CWE-415 설명·완화책(Potential Mitigations) 참고, 이 가이드가 새로 작성

    C# — 예시 없음(언어상 생기지 않음): C#의 관리 힙은 가비지 수집기가 해제하므로 이중 해제가 없다. Marshal.AllocHGlobal·FreeHGlobal처럼 비관리 메모리를 직접 해제하는 unsafe·P/Invoke 경계에서는 같은 문제가 생기므로 SafeHandle로 감싸고(LCS-04) 그 범위에는 C 예시와 C 지침을 적용한다(LCS-02).

    Java — 예시 없음(언어상 생기지 않음): Java는 가비지 수집기가 메모리를 해제하고 개발자가 해제를 직접 호출하지 않으므로 이중 해제가 생기지 않는다. JNI로 부르는 네이티브 코드에는 C 예시를 적용한다(LJ-08).

    Python — 예시 없음(언어상 생기지 않음): Python은 참조 계수와 가비지 수집기가 메모리를 해제하고 개발자가 해제를 직접 호출하지 않으므로 이중 해제가 생기지 않는다. ctypes로 C 라이브러리의 free를 직접 부르거나 C 확장 모듈을 작성하는 경우에는 같은 문제가 생기므로 그 범위에는 C 예시와 C 지침을 적용한다.

    MITRE 원문 예시(Demonstrative Examples, 영문 2건)

    Example 1. The following code shows a simple example of a double free vulnerability.

    Bad / C

                       char* ptr = (char*)malloc (SIZE);

                   ...

                   if (abrt) {

                     free(ptr);

                   }

                   ...

                   free(ptr);

    Double free vulnerabilities have two common (and sometimes overlapping) causes:

    Error conditions and other exceptional circumstances Confusion over which part of the program is responsible for freeing the memory

    Although some double free vulnerabilities are not much more complicated than this example, most are spread out across hundreds of lines of code or even different files. Programmers seem particularly susceptible to freeing global variables more than once.

    Example 2. While contrived, this code should be exploitable on Linux distributions that do not ship with heap-chunk check summing turned on.

    Bad / C

    #include <stdio.h>
#include <unistd.h>
#define BUFSIZE1 512
#define BUFSIZE2 ((BUFSIZE1/2) - 8)

int main(int argc, char **argv) {
  char *buf1R1;
  char *buf2R1;
  char *buf1R2;
  buf1R1 = (char *) malloc(BUFSIZE2);
  buf2R1 = (char *) malloc(BUFSIZE2);
  free(buf1R1);
  free(buf2R1);
  buf1R2 = (char *) malloc(BUFSIZE1);
  strncpy(buf1R2, argv[1], BUFSIZE1-1);
  free(buf2R1);
  free(buf1R2);
}

    탐지 방법(Detection Methods)¶

    방법 요지 효과성
    퍼징(Fuzzing) 퍼징(fuzzing)은 무작위 또는 알고리즘으로 다양한 입력을 대량 생성해 코드를 동적으로 호출하는 강력한 기법으로, 무작위 입력으로도 흔히 비정상 종료·메모리 손상·자원 소모 같은 예상치 못한 결과를 일으키며, 버그를 분명히 보여 주는 재현 가능한 시험 케이스를 만들어 진단을 돕는다.
    원문

    Fuzz testing (fuzzing) is a powerful technique for generating large numbers of diverse inputs - either randomly or algorithmically - and dynamically invoking the code with those inputs. Even with random inputs, it is often capable of generating unexpected results such as crashes, memory corruption, or resource consumption. Fuzzing effectively produces repeatable test cases that clearly indicate bugs, which helps developers to diagnose the issues.

    		 높음(High)
    자동 정적 분석 흔히 SAST(Static Application Security Testing)라 부르는 자동 정적 분석(static analysis)은 소스코드(또는 바이너리·컴파일된 코드)를 실행하지 않고 분석해 이 약점의 일부 사례를 찾을 수 있으며, 대개 데이터 흐름·제어 흐름 모델을 만든 뒤 입력 출처('source')와 외부 구성요소나 운영체제 같은 하위 계층과 상호작용하는 목적지('sink')를 잇는 잠재적 취약 패턴을 찾는다.
    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    		 높음(High)
    자동 동적 분석 C/C++용 AddressSanitizer(ASan) [REF-1518]처럼 컴파일 시 통합되어 메모리 안전성 오류에 대한 실행 시 오류 검사 장치를 넣는 도구를 쓴다.
    원문

    Use tools that are integrated during compilation to insert runtime error-checking mechanisms related to memory safety errors, such as AddressSanitizer (ASan) for C/C++ [REF-1518].

    		 보통(Moderate) — 오류가 있는 코드에 도달하려면 퍼징 도구가 생성하는 것과 같은 조작된 입력이 필요하고, 이런 도구는 성능을 떨어뜨릴 수 있으며 오류 상태만 보고할 뿐 오류를 낳은 원래 실수는 알려 주지 않는다.

    탐지 방법별 시험 활동은 제6장에 있다.

    도구 미지원 시 대안. 공통안은 6.2에 있고, 이 절에는 이 항목의 고유안만 적는다.

    점검 착안점 활동 근거
    (C·C++) 같은 포인터를 해제하는 호출이 둘 이상인 함수에서 오류 경로의 해제와 함수 끝 공통 정리의 해제가 겹치는지, 해제 직후 포인터에 NULL을 넣는지 확인한다. I-09·I-05 [예시] CWE-415 C 예시(오류 경로와 공통 정리에서 두 번 해제) · [표준] SEI CERT MEM30-C·MEM01-C
    (C++) 소멸자에서 메모리를 해제하는 클래스가 복사 생성자·복사 대입 연산자를 정의하거나 막았는지 확인한다. I-09 [예시] CWE-415 C++ 예시(3의 규칙 위반으로 같은 버퍼를 두 번 해제)
    (C·C++) AddressSanitizer로 계측한 호스트 빌드에서 오류 경로를 하나씩 일으켜 'attempting double-free' 보고가 나오는지 확인한다. I-10·T-05 [예시] CWE-415 예시 검증(AddressSanitizer 보고) · [CWE] CWE-415 탐지 방법(자동 동적 분석: ASan)
    (C·C++) RTOS 힙은 이중 해제를 잡지 못하거나 일부만 잡으므로(FreeRTOS heap_4는 할당 표시 비트로 반환을 건너뛰고 configASSERT를 켜면 멈추지만, 재할당된 블록의 이중 해제는 잡지 못한다), 타깃 시험 빌드에서 힙 검사 assert를 켠 채 오류 경로를 하나씩 일으키고, 운용 빌드의 링커 맵·심볼에서 해제 함수(free, vPortFree)가 링크됐는지 보아 초기화 이후의 해제 호출 위치를 확인한다. T-02·T-08·I-09 [보완]
    • ① 원문 탐지 방법(원문 효과성별): 높음: 퍼징(Fuzzing) / 보통: 자동 동적 분석. 각 방법의 시험 활동은 6.2의 대응표를 따른다.

    단계 지침
    요구사항 분석 —
    설계 동적 할당 메모리 소유권 규칙(단일 소유자)을 정의하고 가능하면 정적 할당을 우선한다.
    구현(C·C++) free 후 포인터 NULL 설정은 심층 방어로 더하고, C++은 std::unique_ptr/std::shared_ptr로 소유권을 표현해 수동 delete를 피한다.
    구현(Java) 해당 없음(GC). 단, JNI 네이티브 코드는 C 규칙을 적용한다.
    통합 및 시험 AddressSanitizer, Valgrind, 오류 경로 퍼징(fuzzing)으로 이중 해제(double free)를 탐지한다.
    유지보수 메모리 관리 코드 변경 시 소유권 규칙 준수 여부를 코드 리뷰로 확인한다.
    임베디드 고려 RTOS(실시간 운영체제) 힙의 이중 해제 검사는 제한적이다(FreeRTOS heap_4는 할당 표시 비트만 보므로 재할당된 블록의 이중 해제는 잡지 못한다). 운용 중 동적 할당 금지 원칙을 적용한다.
