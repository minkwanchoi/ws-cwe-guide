    Use of Password Hash With Insufficient Computational Effort

    항목 내용
    추상화 수준 기본(Base)
    상태 미완성(Incomplete)
    소속 보조 항목(「보안약점 점검 목록」·언어 뷰 밖, 매뉴얼 7-10쪽 '추가 식별' 근거)
    가이드 적용성 조건부 — 비밀번호 저장(해시) 사용
    적용 플랫폼 언어 무관
    원문 MITRE CWE-916 (CWE 5.0)

    한 줄 요약

    비밀번호 해시를 만들 때, 비밀번호 크래킹 공격을 불가능하게 하거나 비용이 많이 들게 할 만큼의 계산 노력을 요구하지 않는 방식을 쓰는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 비밀번호의 해시를 만들지만, 비밀번호 크래킹 공격을 불가능하게 하거나 비용이 많이 들게 할 만큼의 계산 노력을 요구하지 않는 방식을 쓰는 약점이다. 많은 비밀번호 저장 방식은 원래 비밀번호를 평문으로 저장하는 대신 해시를 계산해 저장하며, 인증 때는 들어온 비밀번호의 해시를 계산해 저장된 해시와 비교한다. 많은 해시 알고리즘은 암호 해시라도 최소한의 부담으로 빠르게 실행되도록 설계된다. 이 효율성은 무차별 대입 비밀번호 크래킹에 드는 공격자의 작업량을 줄일 수 있어 비밀번호 저장에는 문제가 된다. 공격자가 다른 방법(예: 해시를 저장한 데이터베이스에 대한 SQL 삽입)으로 해시를 얻을 수 있다면, 해시를 오프라인에 두고 해시를 효율적으로 계산하는 여러 기법으로 비밀번호를 크래킹할 수 있다. 내장된 작업량이 없으면 최신 공격은 대규모 병렬 컴퓨팅(클라우드 컴퓨팅 등)과 GPU·ASIC·FPGA 하드웨어로 매우 짧은 시간에 많은 해시를 계산하거나 가능한 비밀번호 공간 전체를 소진할 수도 있으며, 이 경우 효율적인 해시 알고리즘은 공격자에게 유리하다. 오프라인 대규모 병렬 공격에 대한 해시 방식의 강도와 관련된 속성에는 해시 계산에 필요한 CPU 시간('스트레칭'), 해시 계산에 필요한 메모리 양('메모리 하드' 연산), 해시 계산 입력에 비밀번호와 함께 무작위 값을 넣는 것('솔트'), 해시가 주어졌을 때 가능한 입력을 추측하는 것 말고는 그 해시를 만드는 입력(예: 비밀번호)을 알아낼 방법이 알려져 있지 않은 것('일방향' 해시), 그 방식이 만들 수 있는 모든 해시 수에 비해 서로 다른 입력이 같은 해시를 낼 가능성이 낮은 것('충돌 저항성')이 있다. 제품의 보안 요구사항은 환경과 비밀번호의 가치에 따라 다를 수 있다. 어떤 방식은 이 속성을 모두 제공하지 않아도 그 환경에 충분한 보안을 제공할 수 있다. 반대로 어떤 방식은 한 속성은 매우 강하게 지키면서 다른 속성을 노리는 공격에는 매우 약하거나, 대규모 병렬 공격의 효율을 크게 낮추지 못할 수 있다.

    원문(Description · Extended Description)

    The product generates a hash for a password, but it uses a scheme that does not provide a sufficient level of computational effort that would make password cracking attacks infeasible or expensive.

    Many password storage mechanisms compute a hash and store the hash, instead of storing the original password in plaintext. In this design, authentication involves accepting an incoming password, computing its hash, and comparing it to the stored hash.

    Many hash algorithms are designed to execute quickly with minimal overhead, even cryptographic hashes. However, this efficiency is a problem for password storage, because it can reduce an attacker's workload for brute-force password cracking. If an attacker can obtain the hashes through some other method (such as SQL injection on a database that stores hashes), then the attacker can store the hashes offline and use various techniques to crack the passwords by computing hashes efficiently. Without a built-in workload, modern attacks can compute large numbers of hashes, or even exhaust the entire space of all possible passwords, within a very short amount of time, using massively-parallel computing (such as cloud computing) and GPU, ASIC, or FPGA hardware. In such a scenario, an efficient hash algorithm helps the attacker.

    There are several properties of a hash scheme that are relevant to its strength against an offline, massively-parallel attack:

    - The amount of CPU time required to compute the hash ("stretching")

    - The amount of memory required to compute the hash ("memory-hard" operations)

    - Including a random value, along with the password, as input to the hash computation ("salting")

    - Given a hash, there is no known way of determining an input (e.g., a password) that produces this hash value, other than by guessing possible inputs ("one-way" hashing)

    - Relative to the number of all possible hashes that can be generated by the scheme, there is a low likelihood of producing the same hash for multiple different inputs ("collision resistance")

    Note that the security requirements for the product may vary depending on the environment and the value of the passwords. Different schemes might not provide all of these properties, yet may still provide sufficient security for the environment. Conversely, a solution might be very strong in preserving one property, which still being very weak for an attack against another property, or it might not be able to significantly reduce the efficiency of a massively-parallel attack.

    영향(Common Consequences)¶

    영역 영향 설명
    접근 통제 보호 메커니즘 우회 / 권한 획득 또는 신원 도용 공격자가 해시에 접근할 수 있다면, 계산 노력이 부족해 레인보 테이블 같은 기법이나, 해시 계산에서 범용 CPU보다 훨씬 빠를 수 있는 GPU 같은 특수 하드웨어를 이용한 무차별 대입 공격이 쉬워진다.

    설계 (본문 제4장)¶

    CWE 단계(Phase) 전략 요지 효과성
    아키텍처·설계(Architecture and Design) — 해시 계산에 드는 노력(반복 횟수 '스트레칭'이나 필요한 메모리 양)을 설정으로 바꿀 수 있는 적응형 해시 함수를 쓴다. 일부 해시 함수는 솔트를 자동으로 적용한다. 이런 함수는 MD5처럼 일부러 빠르게 만든 함수보다 무차별 대입 공격의 부담을 크게 늘릴 수 있어, 계산 부담 때문에 레인보 테이블 공격이 비현실적이 될 수 있다. 계산 능력이 빨라지고 싸지면 사용 중인 알고리즘을 통째로 바꾸지 않고 작업량을 늘리도록 다시 설정할 수 있다. 이런 성질 중 하나 이상을 가진 해시 함수로 bcrypt [REF-291], scrypt [REF-292], PBKDF2 [REF-293]가 있다. 어느 것이 가장 효과적인지는 논쟁 중이지만, 모두 계산 부담이 매우 작은 해시 함수에 솔트를 쓰는 것보다 강하다. 단, 성능에 영향을 줄 수 있어 서비스 거부 공격을 피하도록 특별히 고려해야 하며, 설정으로 CPU·메모리 사용량을 세밀하게 조정해 환경에 맞출 수 있다.
    원문

    Use an adaptive hash function that can be configured to change the amount of computational effort needed to compute the hash, such as the number of iterations ("stretching") or the amount of memory required. Some hash functions perform salting automatically. These functions can significantly increase the overhead for a brute force attack compared to intentionally-fast functions such as MD5. For example, rainbow table attacks can become infeasible due to the high computing overhead. Finally, since computing power gets faster and cheaper over time, the technique can be reconfigured to increase the workload without forcing an entire replacement of the algorithm in use.

    Some hash functions that have one or more of these desired properties include bcrypt [REF-291], scrypt [REF-292], and PBKDF2 [REF-293]. While there is active debate about which of these is the most effective, they are all stronger than using salts with hash functions with very little computing overhead.

    Note that using these functions can have an impact on performance, so they require special consideration to avoid denial-of-service attacks. However, their configurability provides finer control over how much CPU and memory is used, so it could be adjusted to suit the environment's needs.

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 정비 콘솔·정비 기록 서버가 운용자 비밀번호를 검증값으로 바꿔 계정 파일에 저장한다. 솔트를 넣더라도 해시 한 번이나 적은 반복으로 만든 검증값은 계정 파일이 유출되면 공격자가 GPU 등으로 빠르게 대입해 비밀번호를 찾는다. 예시는 유출된 검증값 하나를 두고 코어 하나로 1초에 몇 번 추측할 수 있는지 재어 예시 기준(초당 100회)을 넘는지 본다. C# 예시는 .NET 분석기 규칙으로 반복 횟수를 점검한다. Bandit은 SHA-256 한 번을 잡지 못하므로 Python 예시도 추측 속도로 판정한다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <string.h>
#include <time.h>
#include <openssl/evp.h>
#include <openssl/rand.h>
#include <openssl/sha.h>

/* 정비 콘솔 계정 파일의 한 줄: 솔트 16바이트 + SHA-256(솔트 || 비밀번호) */
typedef struct {
    unsigned char salt[16];
    unsigned char verifier[SHA256_DIGEST_LENGTH];
} ConsoleAccount;

static void make_verifier(const unsigned char salt[16], const char *pw, unsigned char out[SHA256_DIGEST_LENGTH])
{
    EVP_MD_CTX *h = EVP_MD_CTX_new();
    if (h == NULL) return;
    EVP_DigestInit_ex(h, EVP_sha256(), NULL);
    EVP_DigestUpdate(h, salt, 16);
    EVP_DigestUpdate(h, pw, strlen(pw));
    EVP_DigestFinal_ex(h, out, NULL);   /* 해시 한 번으로 끝난다 */
    EVP_MD_CTX_free(h);
}

/* 계정 파일을 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다 */
static double guesses_per_second(const ConsoleAccount *acct)
{
    unsigned char probe[SHA256_DIGEST_LENGTH];
    struct timespec t0, t1;
    long tries = 0;
    double spent = 0.0;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    do {
        make_verifier(acct->salt, "guess-0000", probe);
        tries++;
        clock_gettime(CLOCK_MONOTONIC, &t1);
        spent = (double)(t1.tv_sec - t0.tv_sec) + (double)(t1.tv_nsec - t0.tv_nsec) / 1e9;
    } while (spent < 0.5);
    return (double)tries / spent;
}

int main(void)
{
    ConsoleAccount acct;
    if (RAND_bytes(acct.salt, sizeof acct.salt) != 1) return 1;
    make_verifier(acct.salt, "EXAMPLE-ONLY-pw1", acct.verifier);

    /* 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다 */
    double rate = guesses_per_second(&acct);
    printf("offline guesses per second per core: %.0f\n", rate);
    puts(rate > 100.0 ? "CHEAP TO GUESS" : "costly to guess");
    return 0;
}

    솔트는 넣었지만 SHA-256 한 번으로 검증값을 만든다. 범용 해시는 빠르게 계산하도록 설계되어 예시 환경의 코어 하나로도 초당 수백만 번 추측할 수 있고, GPU를 쓰면 더 빠르다. 솔트는 같은 비밀번호를 서로 다른 검증값으로 만들 뿐 추측 속도를 늦추지 못한다.

    좋은 예

    #include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <openssl/crypto.h>
#include <openssl/evp.h>
#include <openssl/rand.h>

/* 정비 콘솔 계정 파일의 한 줄: scrypt 매개변수 + 솔트 + 검증값. 매개변수를 함께 저장해 기준을 올린 뒤에도 기존 계정을 검증한다 */
typedef struct {
    uint64_t n;            /* 반복·메모리 비용(2의 거듭제곱) */
    uint64_t r, p;
    unsigned char salt[16];
    unsigned char verifier[32];
} ConsoleAccount;

static int make_verifier(const ConsoleAccount *a, const char *pw, unsigned char out[32])
{
    /* 메모리를 많이 쓰는 키 유도 함수(scrypt): N=2^15, r=8이면 한 번에 약 32 MiB를 쓴다.
       메모리 상한은 레코드의 매개변수로 계산해 기준을 올려도 실패하지 않게 한다 */
    const uint64_t maxmem = 128u * a->r * (a->n + a->p + 2);
    return EVP_PBE_scrypt(pw, strlen(pw), a->salt, sizeof a->salt, a->n, a->r, a->p,
                          maxmem, out, 32) == 1 ? 0 : -1;
}

static int enroll(ConsoleAccount *a, const char *pw)
{
    a->n = 1u << 15;       /* 예시 값, 대상 장비에서 재어 정한다. 인증 지연 요구에 맞춰 주기적으로 올린다 */
    a->r = 8;
    a->p = 1;
    if (RAND_bytes(a->salt, sizeof a->salt) != 1) return -1;
    return make_verifier(a, pw, a->verifier);
}

static int login(const ConsoleAccount *a, const char *pw)
{
    unsigned char probe[32];
    return make_verifier(a, pw, probe) == 0 && CRYPTO_memcmp(probe, a->verifier, 32) == 0;
}

/* 계정 파일을 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다 */
static double guesses_per_second(const ConsoleAccount *acct)
{
    unsigned char probe[32];
    struct timespec t0, t1;
    long tries = 0;
    double spent = 0.0;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    do {
        if (make_verifier(acct, "guess-0000", probe) != 0) return -1.0;
        tries++;
        clock_gettime(CLOCK_MONOTONIC, &t1);
        spent = (double)(t1.tv_sec - t0.tv_sec) + (double)(t1.tv_nsec - t0.tv_nsec) / 1e9;
    } while (spent < 0.5);
    return (double)tries / spent;
}

int main(void)
{
    ConsoleAccount acct;
    if (enroll(&acct, "EXAMPLE-ONLY-pw1") != 0) return 1;
    printf("login: %s\n", login(&acct, "EXAMPLE-ONLY-pw1") ? "ok" : "denied");

    /* 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다 */
    double rate = guesses_per_second(&acct);
    printf("offline guesses per second per core: %.0f\n", rate);
    puts(rate < 0 ? "derivation failed" : rate > 100.0 ? "CHEAP TO GUESS" : "costly to guess");
    return 0;
}

    메모리를 많이 쓰는 키 유도 함수 scrypt(N=2^15, r=8, p=1은 예시 값)로 검증값을 만든다. 한 번 계산에 약 32 MiB의 메모리와 수십 밀리초가 들어 예시 환경에서 코어당 초당 수십 번 이하로 줄고, 메모리 요구 때문에 GPU 병렬 대입도 비싸진다. 매개변수는 레코드에 함께 저장해 기준을 올린 뒤에도 기존 계정을 검증하고, 비교는 CRYPTO_memcmp로 상수 시간에 한다(D-05). OpenSSL 3.2 이상이나 다른 검증된 라이브러리를 쓸 수 있으면 Argon2id도 검토한다.

    검증: 실행 결과 · Linux(gcc)에서 빌드 — 나쁜 예에서 CHEAP TO GUESS 검출, 좋은 예에서 미검출·costly to guess 출력 확인 · 참고: MITRE CWE-916 Demonstrative Example 1(빠른 해시로 비밀번호 저장) 참고, 이 가이드가 새로 작성

    #include <openssl/evp.h>
#include <openssl/rand.h>

#include <chrono>
#include <cstdio>
#include <string>

// 정비 콘솔 계정 저장소: 옛 판에서 물려받은 PBKDF2 설정(HMAC-SHA1, 반복 1,000회)
struct OperatorRecord {
    std::array<unsigned char, 16> salt{};
    std::array<unsigned char, 20> dk{};
};

static bool derive(const std::string &pw, const OperatorRecord &rec, unsigned char *out) {
    return PKCS5_PBKDF2_HMAC(pw.data(), static_cast<int>(pw.size()), rec.salt.data(), static_cast<int>(rec.salt.size()),
                             1000, EVP_sha1(), static_cast<int>(rec.dk.size()), out) == 1;
}

// 계정 파일을 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다
static double guesses_per_second(const OperatorRecord &rec) {
    using clock = std::chrono::steady_clock;
    std::array<unsigned char, 20> probe{};
    long tries = 0;
    const auto start = clock::now();
    std::chrono::duration<double> spent{};
    do {
        if (!derive("guess-0000", rec, probe.data())) return -1.0;
        ++tries;
        spent = clock::now() - start;
    } while (spent.count() < 0.5);
    return static_cast<double>(tries) / spent.count();
}

int main() {
    OperatorRecord rec;
    if (RAND_bytes(rec.salt.data(), static_cast<int>(rec.salt.size())) != 1 || !derive("EXAMPLE-ONLY-pw1", rec, rec.dk.data())) {
        return 1;
    }
    // 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다

    std::printf("offline guesses per second per core: %.0f\n", rate);
    std::puts(rate > 100.0 ? "CHEAP TO GUESS" : "costly to guess");
    return 0;
}

    PBKDF2를 쓰지만 HMAC-SHA1에 반복 1,000회라는 옛 설정을 그대로 둔다. 예시 환경의 코어 하나로 초당 수천 번 추측할 수 있어 계정 파일이 유출되면 흔한 비밀번호는 금방 찾는다. 반복 횟수가 코드 상수로 박혀 있고 레코드에 저장되지 않아, 기준을 올리려면 모든 계정을 한꺼번에 다시 등록해야 한다.

    좋은 예

    #include <openssl/crypto.h>
#include <openssl/evp.h>
#include <openssl/rand.h>
#include <array>
#include <chrono>
#include <cstdio>
#include <string>

constexpr int kCurrentRounds = 600000;   // 장비 성능·인증 지연 요구에 맞춰 정하고 주기적으로 올린다

// 정비 콘솔 계정 저장소: 반복 횟수를 레코드에 함께 저장하고, 기준을 올리면 로그인 때 계정별로 옮긴다
struct OperatorRecord {
    int rounds = kCurrentRounds;
    std::array<unsigned char, 16> salt{};
    std::array<unsigned char, 32> dk{};
};

static bool derive(const std::string &pw, const OperatorRecord &rec, unsigned char *out) {
    return PKCS5_PBKDF2_HMAC(pw.data(), static_cast<int>(pw.size()), rec.salt.data(), static_cast<int>(rec.salt.size()),
                             rec.rounds, EVP_sha256(), static_cast<int>(rec.dk.size()), out) == 1;
}

static bool enroll(OperatorRecord &rec, const std::string &pw) {
    rec.rounds = kCurrentRounds;
    return RAND_bytes(rec.salt.data(), static_cast<int>(rec.salt.size())) == 1 && derive(pw, rec, rec.dk.data());
}

// 로그인에 성공했는데 저장된 반복 횟수가 현재 기준보다 낮으면 새 솔트·새 기준으로 다시 만든다
static bool login(OperatorRecord &rec, const std::string &pw) {
    std::array<unsigned char, 32> probe{};
    if (!derive(pw, rec, probe.data()) || CRYPTO_memcmp(probe.data(), rec.dk.data(), probe.size()) != 0) return false;
    if (rec.rounds < kCurrentRounds) {
        OperatorRecord fresh;                // 임시 레코드에 만들고 성공할 때만 바꾼다. 실패하면 옛 검증값이 그대로 남는다
        if (enroll(fresh, pw)) rec = fresh;
    }
    return true;
}

// 계정 파일을 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다
static double guesses_per_second(const OperatorRecord &rec) {
    using clock = std::chrono::steady_clock;
    std::array<unsigned char, 32> probe{};
    long tries = 0;
    const auto start = clock::now();
    std::chrono::duration<double> spent{};
    do {
        if (!derive("guess-0000", rec, probe.data())) return -1.0;
        ++tries;
        spent = clock::now() - start;
    } while (spent.count() < 0.5);
    return static_cast<double>(tries) / spent.count();
}

int main() {
    OperatorRecord rec;
    if (!enroll(rec, "EXAMPLE-ONLY-pw1")) return 1;
    std::printf("login: %s\n", login(rec, "EXAMPLE-ONLY-pw1") ? "ok" : "denied");
    // 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다
    const double rate = guesses_per_second(rec);
    std::printf("offline guesses per second per core: %.0f\n", rate);
    std::puts(rate > 100.0 ? "CHEAP TO GUESS" : "costly to guess");
    return 0;
}

    PBKDF2-HMAC-SHA256에 반복 600,000회(예시 값)를 쓰고 반복 횟수를 레코드에 함께 저장한다. 로그인에 성공했는데 저장된 반복 횟수가 현재 기준보다 낮으면 새 솔트·새 기준으로 임시 레코드에 검증값을 다시 만들어, 성공할 때만 계정을 옮긴다. 비교는 CRYPTO_memcmp로 한다(D-05).

// 정비 콘솔 계정 파일에 저장할 비밀번호 검증값을 만든다(옛 판에서 옮겨 온 코드)

    using System.Security.Cryptography;

// 계정 파일 한 줄: 알고리즘·반복 횟수·솔트·검증값을 함께 저장해 반복 횟수를 올린 뒤에도 기존 계정을 검증한다
const int Iterations = 600_000;   // 장비 성능·인증 지연 요구에 맞춰 정하고 주기적으로 올린다
byte[] salt = RandomNumberGenerator.GetBytes(16);
byte[] verifier = MakeVerifier("EXAMPLE-ONLY-pw1", salt, Iterations);
string record = $"pbkdf2-sha256${Iterations}${Convert.ToBase64String(salt)}${Convert.ToBase64String(verifier)}";
Console.WriteLine($"stored {record[..22]}...");
Console.WriteLine($"login: {(Verify("EXAMPLE-ONLY-pw1", record) ? "ok" : "denied")}");

static byte[] MakeVerifier(string password, byte[] salt, int iterations) =>
    Rfc2898DeriveBytes.Pbkdf2(password, salt, iterations, HashAlgorithmName.SHA256, 32);

static bool Verify(string password, string record)
{
    string[] f = record.Split('$');
    if (f.Length != 4 || f[0] != "pbkdf2-sha256" || !int.TryParse(f[1], out int n) || n < 1) return false;
    // n이 현재 기준(Iterations)보다 작으면 로그인에 성공한 뒤 새 기준으로 검증값을 다시 만든다(이 예시에서는 생략)
    byte[] probe = MakeVerifier(password, Convert.FromBase64String(f[2]), n);
    return CryptographicOperations.FixedTimeEquals(probe, Convert.FromBase64String(f[3]));   // 상수 시간 비교
}

    정적 메서드 Rfc2898DeriveBytes.Pbkdf2에 SHA-256과 반복 600,000회(예시 값)를 주고, 알고리즘·반복 횟수·솔트·검증값을 한 줄에 저장한다. 비교는 CryptographicOperations.FixedTimeEquals로 한다(D-05). net10.0 실험에서 CA5387은 생성자만 검사하고 정적 메서드 Pbkdf2의 반복 횟수는 경고하지 않았으므로, 반복 횟수는 코드 리뷰로도 확인한다.

    나쁜 예

    import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.SecureRandom;

public class Example {
    // 정비 기록 서버 계정 테이블에 저장할 검증값: SHA-512(솔트 || 비밀번호) 한 번
    static byte[] verifier(byte[] salt, String password) throws Exception {
        MessageDigest sha = MessageDigest.getInstance("SHA-512");
        sha.update(salt);
        return sha.digest(password.getBytes(StandardCharsets.UTF_8));
    }

    // 계정 테이블을 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다
    static double guessesPerSecond(byte[] salt) throws Exception {
        long start = System.nanoTime(), tries = 0;
        double spent;
        do {
            verifier(salt, "guess-0000");
            tries++;
            spent = (System.nanoTime() - start) / 1e9;
        } while (spent < 0.5);
        return tries / spent;
    }

    public static void main(String[] args) throws Exception {
        byte[] salt = new byte[16];
        new SecureRandom().nextBytes(salt);
        verifier(salt, "EXAMPLE-ONLY-pw1");
        // 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다
        double rate = guessesPerSecond(salt);
        System.out.printf("offline guesses per second per core: %.0f%n", rate);
        System.out.println(rate > 100.0 ? "CHEAP TO GUESS" : "costly to guess");
    }
}

    솔트를 붙여 SHA-512 한 번으로 검증값을 만든다. 해시 길이가 길어도 계산량은 늘지 않아 예시 환경의 코어 하나로 초당 수백만 번 추측할 수 있다.

    좋은 예

    import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Arrays;
import javax.crypto.SecretKeyFactory;
import javax.crypto.spec.PBEKeySpec;

public class Example {
    static final int CURRENT_ROUNDS = 600_000;   // 장비 성능·인증 지연 요구에 맞춰 정하고 주기적으로 올린다

    // 정비 기록 서버 계정 테이블의 한 행: 반복 횟수·솔트·검증값을 함께 저장한다
    record Account(int rounds, byte[] salt, byte[] verifier) { }

    static byte[] derive(char[] password, byte[] salt, int rounds) throws Exception {
        PBEKeySpec spec = new PBEKeySpec(password, salt, rounds, 256);
        try {
            return SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).getEncoded();
        } finally {
            spec.clearPassword();
        }
    }

    static Account enroll(char[] password) throws Exception {
        byte[] salt = new byte[16];
        new SecureRandom().nextBytes(salt);
        return new Account(CURRENT_ROUNDS, salt, derive(password, salt, CURRENT_ROUNDS));
    }

    static boolean login(Account a, char[] password) throws Exception {
        return MessageDigest.isEqual(derive(password, a.salt(), a.rounds()), a.verifier());   // 상수 시간 비교
    }

    // 계정 테이블을 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다
    static double guessesPerSecond(Account a) throws Exception {
        long start = System.nanoTime(), tries = 0;
        double spent;
        do {
            derive("guess-0000".toCharArray(), a.salt(), a.rounds());
            tries++;
            spent = (System.nanoTime() - start) / 1e9;
        } while (spent < 0.5);
        return tries / spent;
    }

    public static void main(String[] args) throws Exception {
        char[] typed = "EXAMPLE-ONLY-pw1".toCharArray();
        Account acct = enroll(typed);
        System.out.println("login: " + (login(acct, typed) ? "ok" : "denied"));
        Arrays.fill(typed, '\0');
        // 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다
        double rate = guessesPerSecond(acct);
        System.out.printf("offline guesses per second per core: %.0f%n", rate);
        System.out.println(rate > 100.0 ? "CHEAP TO GUESS" : "costly to guess");
    }
}

    PBKDF2WithHmacSHA256에 반복 600,000회(예시 값)로 256비트 검증값을 만들고 반복 횟수·솔트와 함께 저장한다. 비교는 MessageDigest.isEqual로 상수 시간에 하고, 비밀번호는 char[]로 받아 쓴 뒤 지운다(D-05). JDK에는 scrypt·Argon2가 없으므로 이 함수가 필요하면 검증된 외부 라이브러리를 공급망 점검을 거쳐 들인다.

    Python

    나쁜 예

    import hashlib
import hmac
import os
import time

accounts = {}


# 정비 기록 서버의 계정 DB: 솔트는 붙였지만 빠른 해시 한 번으로 검증값을 만든다
def enroll(user, password):
    salt = os.urandom(16)
    accounts[user] = (salt, hashlib.sha256(salt + password.encode()).digest())


def verify(user, password):
    salt, digest = accounts[user]
    return hmac.compare_digest(hashlib.sha256(salt + password.encode()).digest(), digest)


# 계정 DB를 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다
def guesses_per_second(check_one):
    start, tries = time.perf_counter(), 0
    while True:
        check_one("guess-0000")
        tries += 1
        spent = time.perf_counter() - start
        if spent >= 0.5:
            return tries / spent


enroll("op-12", "EXAMPLE-ONLY-pw1")
print("login:", verify("op-12", "EXAMPLE-ONLY-pw1"))
# 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다
rate = guesses_per_second(lambda pw: verify("op-12", pw))
print(f"offline guesses per second per core: {rate:.0f}")
print("CHEAP TO GUESS" if rate > 100.0 else "costly to guess")

    솔트는 붙였지만 SHA-256 한 번으로 검증값을 만든다. 범용 해시는 빠르게 계산하도록 설계되어 GPU 같은 병렬 장비로 짧은 시간에 매우 많은 후보를 시도할 수 있으므로, 계정 DB가 유출되면 흔한 비밀번호는 금방 되찾는다. 예시 환경의 코어 하나로도 초당 백만 번 넘게 추측할 수 있다. Bandit은 보안 용도의 hashlib MD5·SHA-1만 B324로 보고하므로 SHA-256 한 번은 잡지 못한다. 그래서 이 예시는 C·C++·Java 예시와 같이 실행해 초당 추측 횟수로 판정하고, 실제 코드에서는 코드 리뷰로 본다.

    좋은 예

    import hashlib
import hmac
import os
import time

ITERATIONS = 600_000                 # 대상 장비에서 한 번 확인에 걸리는 시간을 재어 정하고 저장 형식에 남긴다
accounts = {}


def enroll(user, password):
    salt = os.urandom(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, ITERATIONS)
    accounts[user] = ("pbkdf2_sha256", ITERATIONS, salt, digest)


def verify(user, password):
    scheme, rounds, salt, digest = accounts[user]
    trial = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, rounds)
    ok = hmac.compare_digest(trial, digest)
    if ok and rounds < ITERATIONS:   # 예전 기준으로 만든 검증값은 로그인에 성공할 때 새 기준으로 바꾼다
        enroll(user, password)
    return ok


# 계정 DB를 빼낸 공격자가 코어 하나로 1초에 몇 번 추측해 볼 수 있는지 잰다
def guesses_per_second(check_one):
    start, tries = time.perf_counter(), 0
    while True:
        check_one("guess-0000")
        tries += 1
        spent = time.perf_counter() - start
        if spent >= 0.5:
            return tries / spent


enroll("op-12", "EXAMPLE-ONLY-pw1")
print("login:", verify("op-12", "EXAMPLE-ONLY-pw1"))
# 예시 기준: 코어 하나에서 초당 100회보다 많이 추측할 수 있으면 계산량이 부족하다고 본다
rate = guesses_per_second(lambda pw: verify("op-12", pw))
print(f"offline guesses per second per core: {rate:.0f}")
print("CHEAP TO GUESS" if rate > 100.0 else "costly to guess")

    비밀번호용으로 설계해 계산 비용을 조절할 수 있는 함수(hashlib.pbkdf2_hmac·hashlib.scrypt, 또는 argon2-cffi 패키지의 Argon2)를 쓰고, 반복 횟수는 대상 장비에서 한 번 확인에 걸리는 시간을 재어 정한다(D-05, LPY-07). 방식·반복 횟수·솔트를 검증값과 함께 저장해 두고, 예전 기준의 검증값은 로그인에 성공할 때 새 기준으로 바꾼다.

    검증: 실행 결과 — 나쁜 예에서 CHEAP TO GUESS 검출, 좋은 예에서 미검출·costly to guess 출력 확인 · 참고: MITRE CWE-916 Demonstrative Example 1(빠른 해시로 비밀번호 저장) 참고, 이 가이드가 새로 작성

    MITRE 원문 예시(Demonstrative Examples, 영문 1건)

    Example 1. In this example, a new user provides a new username and password to create an account. The program hashes the new user's password then stores it in a database.

    Bad / Python

    def storePassword(userName,Password):
  hasher = hashlib.new('md5')
  hasher.update(Password)
  hashedPassword = hasher.digest()

                          # UpdateUserLogin returns True on success, False otherwise

  return updateUserLogin(userName,hashedPassword)

    While it is good to avoid storing a cleartext password, the program does not provide a salt to the hashing function, thus increasing the chances of an attacker being able to reverse the hash and discover the original password if the database is compromised.

    Fixing this is as simple as providing a salt to the hashing function on initialization:

    Good / Python

    def storePassword(userName,Password):
  hasher = hashlib.new('md5',b'SaltGoesHere')
  hasher.update(Password)
  hashedPassword = hasher.digest()

                          # UpdateUserLogin returns True on success, False otherwise

  return updateUserLogin(userName,hashedPassword)

    Note that regardless of the usage of a salt, the md5 hash is no longer considered secure, so this example still exhibits CWE-327.
