    Generation of Error Message Containing Sensitive Information

    항목 내용
    추상화 수준 기본(Base)
    상태 초안(Draft)
    소속 「보안약점 점검 목록」(44개) · 언어 뷰 Java(CWE-660)
    가이드 적용성 해당
    적용 플랫폼 언어: 언어 무관, Go, PHP, Java, Python · 기술 무관
    원문 MITRE CWE-209 (CWE 5.0)

    한 줄 요약

    실행 환경·사용자·관련 데이터의 민감한 정보를 담은 오류 메시지를 생성해 생기는 약점이다.

    → 나쁜 예·좋은 예

    설명(Description)¶

    제품이 실행 환경, 사용자 또는 관련 데이터에 관한 민감한 정보를 포함한 오류 메시지를 생성하는 약점이다.

    원문(Description · Dimensions)

    The product generates an error message that includes sensitive information about its environment, users, or associated data.

    Dimensions: Behavior-Type = Generation; Resource-Type = Error Message; Info-Type = Information; Info-Property = Sensitive

    발생 단계(Modes Of Introduction)¶

    CWE 단계(Phase) 수명주기 단계(가이드 대응) 설명
    아키텍처·설계(Architecture and Design) 설계 —
    구현(Implementation) 구현 실현(REALIZATION): 이 약점은 아키텍처 보안 전술을 구현하는 과정에서 생긴다.
    시스템 구성(System Configuration) 유지보수 —
    운용(Operation) 유지보수 —

    영향(Common Consequences)¶

    영역 영향 설명
    기밀성 애플리케이션 데이터 읽기 흔히 더 정밀한 후속 공격에 쓰일 민감한 정보나 서버에 저장된 개인 정보가 드러난다. 예를 들어 경로 조작(CWE-22) 시도에서 설치된 애플리케이션의 전체 경로가 드러나면 대상 파일까지 필요한 ".." 개수를 고를 수 있고, 처음에는 실패한 SQL 삽입(CWE-89)도 오류 메시지가 잘못된 쿼리를 드러내 쿼리 논리와 경우에 따라 쿼리 안의 비밀번호 같은 민감한 정보까지 노출할 수 있다.

    완화책(Potential Mitigations)¶

    원문 완화책 7건(수명주기 단계로 묶은 규칙은 색인에 있다).

    요구사항 분석 (본문 제3장)¶

    원문 완화책 없음

    설계 (본문 제4장)¶

    원문 완화책 없음. 이 단계의 기준선 활동: D-08 오류 처리·안전 상태 설계

    구현 (본문 제5장)¶

    CWE 단계(Phase) 전략 요지 효과성
    구현(Implementation) — 오류 메시지에는 의도한 대상에게만 쓸모 있는 최소 정보를 담는다. 메시지는 너무 모호해 사용자를 혼란스럽게 하지도, 너무 자세해 의도보다 많이 드러내지도 않게 균형을 맞추고, 오류를 판별한 방법을 드러내지 않는다(공격자는 상세 정보로 원래 공격을 다듬어 성공 가능성을 높일 수 있다). 자세한 오류를 남겨야 하면 로그에 기록하되 공격자가 로그를 볼 수 있는 경우를 고려하고, 비밀번호 같은 매우 민감한 정보는 로그 파일에 절대 저장하지 않는다. 사용자 계정 존재 여부처럼 내부 상태를 공격자에게 뜻하지 않게 알려 줄 수 있는 일관되지 않은 메시지를 피한다.
    원문

    Ensure that error messages only contain minimal details that are useful to the intended audience and no one else. The messages need to strike the balance between being too cryptic (which can confuse users) or being too detailed (which may reveal more than intended). The messages should not reveal the methods that were used to determine the error. Attackers can use detailed information to refine or optimize their original attack, thereby increasing their chances of success.

    If errors must be captured in some detail, record them in log messages, but consider what could occur if the log messages can be viewed by attackers. Highly sensitive information such as passwords should never be saved to log files.

    Avoid inconsistent messaging that might accidentally tip off an attacker about internal state, such as whether a user account exists or not.

    		 —
    구현(Implementation) — 예외는 내부에서 처리하고, 민감할 수 있는 정보가 담긴 오류를 사용자에게 보여 주지 않는다.
    원문

    Handle exceptions internally and do not display errors containing potentially sensitive information to a user.

    		 —
    구현(Implementation) 공격 표면 축소 명명 규칙과 강한 타입을 써서 민감한 데이터가 쓰이는 곳을 쉽게 알아보게 하고, 구조체·객체 같은 복합 개체를 만들 때 민감한 데이터와 그렇지 않은 데이터를 가능한 한 분리한다.
    원문

    Use naming conventions and strong types to make it easier to spot when sensitive data is being used. When creating structures, objects, or other complex entities, separate the sensitive and non-sensitive data as much as possible.

    		 심층 방어(Defense in Depth) — 코드에서 암호화되지 않은 데이터가 쓰이는 곳을 쉽게 찾게 해 준다.
    구현(Implementation) / 빌드·컴파일(Build and Compilation) 컴파일·빌드 강화 디버그 정보가 제품 릴리스에 들어가서는 안 된다.
    원문

    Debugging information should not make its way into a production release.

    		 —
    구현(Implementation) / 빌드·컴파일(Build and Compilation) 실행 환경 강화 디버그 정보가 제품 릴리스에 들어가서는 안 된다.
    원문

    Debugging information should not make its way into a production release.

    		 —

    통합 및 시험 (본문 제6장)¶

    원문 완화책 없음

    유지보수 (본문 제7장)¶

    CWE 단계(Phase) 전략 요지 효과성
    시스템 구성(System Configuration) — 가능하면 덜 상세한 오류 메시지를 쓰도록 환경을 설정한다. 예를 들어 PHP에서는 설정 단계에서 display_errors 설정을 끄거나 실행 중 error_reporting() 함수로 끈다.
    원문

    Where available, configure the environment to use less verbose error messages. For example, in PHP, disable the display_errors setting during configuration, or at runtime using the error_reporting() function.

    		 —
    시스템 구성(System Configuration) — 어떤 정보도 흘리지 않는 기본 오류 페이지나 메시지를 만든다.
    원문

    Create default error pages or messages that do not leak any information.

    		 —

    예시(나쁜 예·좋은 예)¶

    아래 코드는 이 가이드가 다음 상황을 가정해 새로 작성한 것이다. 지상 통제 소프트웨어가 원격 운용자 콘솔에서 받은 임무 계획 레코드나 설정 요청을 해석하다 실패하면 오류 응답을 돌려보낸다. 응답은 망 너머 단말로 나가므로, 여기에 내부 파일 위치·키 파일 경로·스택 추적이 담기면 공격자가 다음 공격 대상을 고르는 단서가 된다. 언어마다 분석기·새니타이저·실행 결과로 나쁜 예는 잡히고 좋은 예는 잡히지 않음을 확인했다. 좋은 예는 그 약점 하나를 막는 최소 예이며 그대로 운용 코드가 되는 것은 아니다. 언어 상자를 눌러 펼친다.

    C

    나쁜 예

    #include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define MISSION_DB "/opt/gcs/data/mission.db"
#define LINK_KEY   "/opt/gcs/conf/link.key"

/* 임무 계획 레코드 "ALT=<m>"에서 고도를 꺼낸다 */
static int parse_alt(const char *rec, long *alt)
{
    char *end = NULL;
    if (strncmp(rec, "ALT=", 4) != 0) {
        return 11;                          /* 형식 오류 */
    }
    *alt = strtol(rec + 4, &end, 10);
    if (end == rec + 4 || *end != '\0') {
        return 12;                          /* 숫자 아님 */
    }
    return 0;
}

static void reply(const char *rec, char *resp, size_t n)
{
    long alt = 0;
    int rc = parse_alt(rec, &alt);
    if (rc != 0) {
        /* 내부 파일 위치·키 파일·메모리 주소를 응답에 그대로 싣는다 */
        snprintf(resp, n, "ERR %d: bad record '%s' (db=%s, key=%s, ctx=%p)",
                 rc, rec, MISSION_DB, LINK_KEY, (void *)resp);
        return;
    }
    snprintf(resp, n, "OK alt=%ld", alt);
}

int main(void)
{
    char resp[256];
    reply("ALT=1200", resp, sizeof resp);
    printf("to console: %s\n", resp);
    reply("ALT=12O0", resp, sizeof resp);   /* 숫자 0 대신 영문자 O */
    printf("to console: %s\n", resp);
    return 0;
}

    해석 실패 응답에 임무 DB 위치, 키 파일 경로, 메모리 주소(%p)를 그대로 넣어 단말로 보낸다. 실행하면 응답 문자열에 키 파일 경로가 실제로 실린다.

    좋은 예

    #include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define MISSION_DB "/opt/gcs/data/mission.db"

/* 보호된 내부 진단 로그(정비 권한으로만 열람한다고 가정) */
static char diag_log[8][128];
static size_t diag_count;

static void diag(const char *rec, int rc)
{
    if (diag_count < 8) {
        snprintf(diag_log[diag_count++], sizeof diag_log[0],
                 "parse rc=%d rec=%.40s db=%s", rc, rec, MISSION_DB);
    }
}

static int parse_alt(const char *rec, long *alt)
{
    char *end = NULL;
    if (strncmp(rec, "ALT=", 4) != 0) {
        return 11;
    }
    *alt = strtol(rec + 4, &end, 10);
    if (end == rec + 4 || *end != '\0') {
        return 12;
    }
    return 0;
}

static void reply(const char *rec, char *resp, size_t n)
{
    long alt = 0;
    int rc = parse_alt(rec, &alt);
    if (rc != 0) {
        diag(rec, rc);                      /* 상세 원인은 내부 로그로 */
        snprintf(resp, n, "ERR %d: record rejected", rc);  /* 단말에는 오류 코드만 */
        return;
    }
    snprintf(resp, n, "OK alt=%ld", alt);
}

int main(void)
{
    char resp[256];
    reply("ALT=1200", resp, sizeof resp);
    printf("to console: %s\n", resp);
    reply("ALT=12O0", resp, sizeof resp);
    printf("to console: %s\n", resp);
    printf("internal log entries: %zu\n", diag_count);
    return 0;
}

    상세 원인은 보호된 내부 진단 로그에만 남기고, 단말에는 미리 정한 오류 코드와 짧은 문구만 보낸다.

    검증: 실행 결과 — 나쁜 예에서 /opt/gcs/conf/link.key 검출, 좋은 예에서 미검출·ERR 12: record rejected 출력 확인 · 참고: MITRE CWE-209 Demonstrative Example 2·3(오류 메시지로 구성 파일·디렉터리 위치 노출) 참고, 이 가이드가 새로 작성 / KISA·행정안전부 「C 시큐어코딩 가이드」(3판) 에러처리 4-1 '오류 메시지 통한 정보 노출'(인쇄 152쪽) 참고

    C++

    나쁜 예

    #include <iostream>
#include <stdexcept>
#include <string>

const std::string kIcdTable = "/opt/gcs/conf/icd_v3.xml";

// ICD 필드 "갱신 주기(Hz)"를 정수로 바꾼다
int decode_rate(const std::string &field) {
    std::size_t used = 0;
    int hz = std::stoi(field, &used);
    if (used != field.size()) {
        throw std::runtime_error("trailing chars in rate field, see " + kIcdTable + " row 42");
    }
    return hz;
}

std::string handle(const std::string &field) {
    try {
        return "OK rate=" + std::to_string(decode_rate(field));
    } catch (const std::exception &e) {
        return std::string("ERR ") + e.what();   // 내부 메시지를 그대로 원격 단말로
    }
}

int main() {
    for (const char *f : {"50", "50Hz"}) {
        std::cout << "to console: " << handle(f) << '\n';
    }
    return 0;
}

    내부 진단용으로 만든 예외 메시지(ICD 표 파일 위치·행 번호 포함)를 e.what() 그대로 원격 단말 응답에 붙인다.

    좋은 예

    #include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

const std::string kIcdTable = "/opt/gcs/conf/icd_v3.xml";
std::vector<std::string> g_diag;   // 보호된 내부 진단 로그

int decode_rate(const std::string &field) {
    std::size_t used = 0;
    int hz = std::stoi(field, &used);
    if (used != field.size()) {
        throw std::runtime_error("trailing chars in rate field, see " + kIcdTable + " row 42");
    }
    return hz;
}

std::string handle(const std::string &field) {
    try {
        return "OK rate=" + std::to_string(decode_rate(field));
    } catch (const std::invalid_argument &e) {
        g_diag.push_back(e.what());
        return "ERR 0x21 rate field rejected";      // 단말에는 미리 정한 오류 코드만
    } catch (const std::out_of_range &e) {
        g_diag.push_back(e.what());
        return "ERR 0x22 rate out of range";
    } catch (const std::runtime_error &e) {
        g_diag.push_back(e.what());                 // 상세 원인은 내부 로그에만
        return "ERR 0x23 rate field rejected";
    }
}

int main() {
    for (const char *f : {"50", "50Hz"}) {
        std::cout << "to console: " << handle(f) << '\n';
    }
    std::cout << "internal log entries: " << g_diag.size() << '\n';
    return 0;
}

    Example 1. In the following example, sensitive information might be printed depending on the exception that occurs.

    Bad / Java

    try {
  /.../
}

  System.out.println(e);
}

    If an exception related to SQL is handled by the catch, then the output might contain sensitive information such as SQL query structure or private information. If this output is redirected to a web user, this may represent a security problem.

    Example 2. This code tries to open a database connection, and prints any exceptions that occur.

    Bad / PHP

    try {
  openDbConnection();
}

                     //print exception message that includes exception message and configuration file location

catch (Exception $e) {
  echo 'Caught exception: ', $e->getMessage(), '\n';
  echo 'Check credentials in config file at: ', $Mysql_config_location, '\n';
}

    If an exception occurs, the printed message exposes the location of the configuration file the script is using. An attacker can use this information to target the configuration file (perhaps exploiting a Path Traversal weakness). If the file can be read, the attacker could gain credentials for accessing the database. The attacker may also be able to replace the file with a malicious one, causing the application to use an arbitrary database.

    Example 3. The following code generates an error message that leaks the full pathname of the configuration file.

    Bad / Perl

    $ConfigDir = "/home/myprog/config";
$uname = GetUserInput("username");

                     # avoid CWE-22, CWE-78, others.

if (! (-e $file)) {
  ExitError("Error: $file does not exist");
}
...

    If this code is running on a server, such as a web application, then the person making the request should not know what the full pathname of the configuration directory is. By submitting a username that does not produce a $file that exists, an attacker could get this pathname. It could then be used to exploit path traversal or symbolic link following problems that may exist elsewhere in the application.

    Example 4. In the example below, the method getUserBankAccount retrieves a bank account object from a database using the supplied username and account number to query the database. If an SQLException is raised when querying the database, an error message is created and output to a log file.

    Bad / Java

    public BankAccount getUserBankAccount(String username, String accountNumber) {

  BankAccount userAccount = null;
  String query = null;
  try {
    if (isAuthorizedUser(username)) {
      query = "SELECT * FROM accounts WHERE owner = "
      + username + " AND accountID = " + accountNumber;
      DatabaseManager dbManager = new DatabaseManager();
      Connection conn = dbManager.getConnection();
      Statement stmt = conn.createStatement();
      ResultSet queryResult = stmt.executeQuery(query);
      userAccount = (BankAccount)queryResult.getObject(accountNumber);
    }
  } catch (SQLException ex) {
    String logMessage = "Unable to retrieve account information from database,\nquery: " + query;

    The error message that is created includes information about the database query that may contain sensitive information about the database or query logic.     탐지 방법(Detection Methods)¶

    방법 요지 효과성
    수동 분석 이 약점은 대개 수동 분석으로 도메인에 맞는 해석이 필요하지만, 발생 가능한 오류 조건이 너무 많아 제한된 시간 안에 모두 다루지 못할 수 있다.
    원문

    This weakness generally requires domain-specific interpretation using manual analysis. However, the number of potential error conditions may be too large to cover completely within limited time constraints.

    		 높음(High)
    자동 분석 자동화 방법은 노출된 스택 추적이나 경로 이름 같은 일부 관용 패턴을 탐지할 수 있지만, 업무 규칙이나 개인정보 요구사항 위반은 대개 탐지하지 못한다.
    원문

    Automated methods may be able to detect certain idioms automatically, such as exposed stack traces or pathnames, but violation of business rules or privacy requirements is not typically feasible.

    		 보통(Moderate)
    자동 동적 분석 퍼징(fuzzing)·강건성 시험·오류 주입(fault injection)처럼 다양한 대량 입력을 쓰는 동적 도구·기법으로 탐지할 수 있고(소프트웨어는 느려질 수 있어도 불안정해지거나 비정상 종료되거나 잘못된 결과를 내서는 안 된다), 많은 스레드나 프로세스에서 동시에 호출하는 스트레스 시험으로 오류 조건을 일으켜 예상치 못한 동작의 흔적을 살필 수 있다.
    원문

    This weakness can be detected using dynamic tools and techniques that interact with the software using large test suites with many diverse inputs, such as fuzz testing (fuzzing), robustness testing, and fault injection. The software's operation may slow down, but it should not become unstable, crash, or generate incorrect results.

    Error conditions may be triggered with a stress-test by calling the software simultaneously from a large number of threads or processes, and look for evidence of any unexpected behavior.

    		 보통(Moderate)
    수동 동적 분석 메모리 부족, 권한 부족, 트랜잭션 완료 전 중단, DNS 같은 기본 네트워크 서비스 차단처럼 정상 사용에서 잘 일어나지 않는 오류 조건을 일부러 일으켜 예상치 못한 동작을 감시하며, 애플리케이션이 처리하지 않아 실행 환경이 대신 잡은 예외도 애플리케이션 자체가 처리하지 못한 예상 밖 조건을 뜻할 수 있다.
    원문

    Identify error conditions that are not likely to occur during normal usage and trigger them. For example, run the program under low memory conditions, run with insufficient privileges or permissions, interrupt a transaction before it is completed, or disable connectivity to basic network services such as DNS. Monitor the software for any unexpected behavior. If you trigger an unhandled exception or similar error that was discovered and handled by the application's environment, it may still indicate unexpected conditions that were not handled by the application itself.

    		 —

    원문

    Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

    설계 외부 사용자용 오류 메시지와 내부 진단 로그를 분리하는 오류 처리 정책을 정의한다.
    구현(C·C++) 사용자에게는 일반화된 오류 코드만 반환하고 상세 원인은 보호된 내부 로그에 기록한다.
    구현(Java) 예외 스택 추적을 응답에 출력하지 않고, web.xml/프레임워크 공통 오류 페이지를 설정한다.
    통합 및 시험 비정상 입력으로 오류를 유발하여 응답 메시지의 민감정보 포함 여부를 확인한다.
    유지보수 로그 접근 통제와 로그 내 민감정보 마스킹을 정기 점검한다.
    임베디드 고려 정비 단말·원격 진단 응답에 메모리 주소, 레지스터 덤프를 운용 모드에서 출력하지 않는다.

    기준선 활동 2건

    • D-08 오류 처리·안전 상태 설계 (설계)
    • I-06 오류·반환값·예외 처리 (구현)

    모든 항목에 공통인 시험 활동. T-01 정적시험과 T-02 타깃 동적시험은 대상 약점을 가리지 않고 모든 과제가 수행한다.

    환경 지침 2건. 과제 환경에 맞는 지침은 지침 선택 도구로 고른다. 축별로 최대 8건을 보이고 나머지는 부록 C에서 찾는다.

    축 지침
    개발 언어 (2건) LCS-08 예외와 null 안전, LJ-05 예외 처리 규약

    참조 요지
    CVE-2008-2049 POP3 서버가 APOP 명령을 여러 번 받은 뒤 오류 메시지에 비밀번호를 드러내며, 다른 약점의 결과로 생긴 것일 수 있다.
    원문

    POP3 server reveals a password in an error message after multiple APOP commands are sent. Might be resultant from another weakness.
    CVE-2007-5172 공격자가 특정 데이터베이스 오류를 일으킬 수 있으면 프로그램이 오류 메시지에 비밀번호를 드러낸다.
    원문

    Program reveals password in error message if attacker can trigger certain database errors.
    CVE-2008-4638 복합: 높은 권한으로 실행되는 애플리케이션(CWE-250)이 사용자가 처리할 제한된 파일을 지정하도록 허용해, 구문 분석 오류가 나면서 파일 내용이 유출된다(CWE-209).
    원문

    Composite: application running with high privileges (CWE-250) allows user to specify a restricted file to process, which generates a parsing error that leaks the contents of the file (CWE-209).
    CVE-2008-1579 존재하지 않는 블로그를 요청하고 오류 메시지를 읽으면 사용자 이름이 존재하는지 알아낼 수 있다.
    원문

    Existence of user names can be determined by requesting a nonexistent blog and reading the error message.
    CVE-2007-1409 웹 애플리케이션의 라이브러리 파일을 직접 요청하면 오류 메시지에 경로 이름이 유출된다.
    원문

    Direct request to library file in web application triggers pathname leak in error message.
    CVE-2008-3060 로그인 페이지에 잘못된 형식의 입력을 넣으면 IMAP 호출이 실패할 때 전체 경로가 유출된다.
    원문

    Malformed input to login page causes leak of full path when IMAP call fails.
    CVE-2005-0603 잘못된 형식의 정규식 구문으로 오류 메시지에 정보가 노출된다.
    원문

    Malformed regexp syntax leads to information exposure in error message.
    CVE-2017-9615 상세 로깅이 관리자 자격 증명을 모든 사용자가 읽을 수 있는 로그 파일에 저장한다.
    원문

    verbose logging stores admin credentials in a world-readable log file
